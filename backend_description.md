# backend_description — описание Backend

Backend — Python-сервис на FastAPI. Он принимает вопрос абонента, выбирает путь ответа, ищет контекст в базе
знаний, обращается к модели через встроенный шлюз (LLM Gateway) и отдаёт ответ потоком SSE. Код лежит в папке
`app/` (по схеме сдачи — «/backend»). Точка входа — `app/main.py`, запуск — по `infra_instruction.md`.

## 2. HTTP-контракт

Сервис отдаёт ровно два рабочих адреса; спецификация OpenAPI 3.0.3 — `AI_docs/API_Spec.yaml`
(собирается из кода скриптом `scripts/build_openapi.py`).

- `POST /v1/generate` — вопрос абонента. Тело: `system`, `query` (до 2000 знаков), `parameters.stream`,
  `metadata` (`subscriber_id`, `session_id`). Ответ — поток SSE с событиями `token`, `metadata`, `done`,
  `error` либо один JSON при `stream: false`.
  - `metadata`: источники (`sources`), `confidence_score`, кнопки следующих действий (`suggested_actions`);
  - `done`: причина завершения, использованные токены, отчёт об обезличивании (`pii_report`), маршрут
    (`routing`), идентификатор трассировки (`trace_id`).
- `GET /v1/healthz` — проверка живости, ответ `{"status":"ok"}`.
- Ошибки — `application/problem+json` (RFC 7807): `400` (схема), `429` (лимит, с `Retry-After`), `502`
  (провайдер ответил ошибкой), `503` (хранилище счётчиков недоступно, с `Retry-After`), `504` (провайдер не
  ответил вовремя). Ошибка внутри начатого потока приходит событием `error` с тем же телом.

## 3. Путь запроса

1. `app/api.py` проверяет тело запроса по схеме `GenerateRequest`.
2. `Orchestrator` (`app/backend/orchestrator.py`) загружает состояние диалога из Redis (`SessionStore`,
   срок жизни 30 минут).
3. Классификация (`Triage`): тема определяется правилами по ключевым словам; если правила молчат, работает
   запасной классификатор на эмбеддингах (k-NN по размеченным примерам, модель `multilingual-e5-small`, та же,
   что в поиске). Тип обращения для регистрации определяется ключевыми словами, запасной классификатор
   работает на 7 из 16 типов.
4. Детектор намерений делит реплику на отдельные задачи; по каждой части даётся ответ по порядку.
5. Прямые ответчики без модели опрашиваются в фиксированном порядке (таблица ниже). Первый, узнавший тему,
   отвечает.
6. Если ответчик не сработал, выполняется поиск по базе знаний. Пустая выдача даёт ответ без модели с
   телефоном контакт-центра. Найденный контекст вместе с вопросом уходит в LLM Gateway.
7. Если абонент просит оформить обращение, включается путь регистрации (раздел 7).
8. Ответ отдаётся потоком; в конце пишутся события использования и метрики.

Лимиты запросов проверяются один раз на запрос: для запроса к модели — в шлюзе, для запроса, который
отвечается без модели, — в Backend.

## 4. Ответчики без модели

| Тема | Модуль | Источник |
|---|---|---|
| Качество воды | `app/regulated.py` | Утверждённая формулировка дословно (реестр регламентных текстов) |
| Тарифы | `app/tariffs/` | `reference/tariffs_voronezh.json`, ответ по дате |
| Отключения | `app/outages/` | `data_example/график_отключений_демо.txt`, точный поиск по адресу абонента |
| Лицевой счёт | `app/billing/answer.py` | Данные Биллинга (`data_example/*.csv`): задолженность, начисления, сроки поверки, показания |
| Бланки заявлений | `app/documents/` | Семь образцов по ПП РФ 644/776; готовый бланк отдаётся ссылкой на лист для печати (TTL ссылки 24 часа) |

## 5. Поиск по базе знаний и модель

- **Источники:** `kb/faq_voronezh.json` (FAQ), Word-документы из `kb/regulations/` и `kb/contracts/`
  (разбираются по заголовкам). Индекс сейчас — 51 фрагмент.
- **Эмбеддинги:** `intfloat/multilingual-e5-small` на CPU, встроены в процесс Backend.
- **Хранилище векторов:** Qdrant (`VECTOR_STORE=qdrant`, gRPC), коллекция `kb_faq`; при запуске без Qdrant —
  индекс в памяти процесса. Переиндексация — `scripts/reindex_kb.py`, коллекция переключается алиасом без
  остановки поиска.
- **Параметры:** `vector_top_k=20` кандидатов, `rerank_top_n=3` фрагмента в промпт, порог косинусной близости
  `score_threshold=0.872`, фильтр по типу обращения применяется внутри поиска.
- **Реранкер:** кросс-энкодер `BAAI/bge-reranker-v2-m3` реализован (`app/kb/reranker.py`) и выключен по
  умолчанию (`RERANKER_ENABLED=false`).

## 6. LLM Gateway

Порядок обработки в шлюзе фиксирован: **Backend → Quota Manager → PII Sanitizer → LiteLLM → Guardrails →
Backend**.

| Шаг | Реализация |
|---|---|
| Лимиты | `quota.py`, счётчики в Redis; по умолчанию 20 запросов в минуту на абонента, 10 на сессию, 300 на сервис; превышение — `429` |
| Обезличивание | `pii_filter.py`: Presidio, spaCy `ru_core_news_md` и собственные распознаватели (ФИО, СНИЛС, ИНН, лицевой счёт, телефон, email); провайдер получает метки вместо значений |
| Провайдеры | LiteLLM Router (`litellm_config.yaml`): `local-test` (Ollama, Qwen2.5-7B), `yandexgpt`, `gigachat`; запасные цепочки `yandexgpt → local-test` и `gigachat → yandexgpt`, до двух повторов |
| Охранители на потоке | `guardrails.py`: персональные данные в ответе, тон, разглашение промпта, фраза о невыполненном действии; накопленный текст проверяется на каждом куске, нарушение обрывает поток и заменяет ответ безопасной заглушкой; обоснованность ответа считается асинхронно после потока |
| Учёт | `usage.py`: строка на вызов модели в базе `telemetry` (токены, модель, задержка, исход) |

Выбор провайдера — переменная `LLM_PROVIDER`; переключение не требует изменения кода.

## 7. Регистрация обращений и агент записи

- **Этап 1 (работает):** `app/backend/registration.py` ведёт сценарий из трёх реплик. Абонент просит
  оформить обращение, получает черновик и кнопки; после подтверждения запись выполняет
  `InquiryServiceAdapter` в таблицу Postgres (`app/inquiries/store.py`, база `inquiries_stub`) с
  идемпотентностью; отказ пишется в аудит. Регистрация предлагается для 7 типов: «Заказать поверку», «Заказать опломбировку»,
  «Заказать установку прибора учета», «Снятие пломбы», «Справка», «Обследование», «Направить документы». Слоты (ФИО, лицевой счёт,
  основание) берутся из данных Биллинга и текста вопроса.
- **Автомат обращения:** `app/fsm.py`, состояния `INIT → CLASSIFIED → FILLING → DRAFT_READY →
  AWAITING_CONFIRMATION → SUBMITTED → COMPLETED`; недопустимый переход отклоняется.
- **Этап 2 (адаптеры):** `app/adapters/` содержит адаптеры Биллинга, формирования документов и сервиса
  обращений с общими гейтами (запись только после подтверждения, проверка привязки `subscriber_id` к
  сессии, ключ идемпотентности). Адаптеры Биллинга и документов реализованы как заглушки этапа 2 и в пути
  ответа не вызываются. Оркестрация записи на MVP планируется на LangGraph (ADR-200).

## 8. Качество ответов

- `app/quality/judge.py` — судья (LLM-judge) оценивает faithfulness и answer relevancy; судья не совпадает с
  отвечающей моделью.
- `app/quality/live.py` — оценка каждого ответа после потока (`QUALITY_SAMPLE_RATE`), запись в
  `quality_assessments`.
- `scripts/run_quality_eval.py` — ночной прогон по эталонному набору из 30 вопросов, результат в
  `quality_reports` и `golden_set/quality.json`.

## 9. Метрики и телеметрия

- Метрики Prometheus на отдельном порту 9100 (`app/metrics/prometheus.py`): `assistant_ttft_seconds`,
  `assistant_response_seconds`, `assistant_responses_total`, `assistant_multi_intent_total`,
  `guardrails_checked_total`, `guardrails_blocked_total`, `guardrails_check_seconds`,
  `llm_gateway_tokens_total`, `llm_provider_used_total`, `pii_sanitizer_requests_total`,
  `pii_sanitizer_entities_detected_total`, `pii_sanitize_seconds`, `quota_rejections_total`,
  `http_requests_total`, `vector_db_pending_queries`.
- Телеметрия использования — база `telemetry` в Postgres (`usage_events`, `quality_reports`,
  `quality_assessments`). Сырых персональных данных в ней нет: только идентификаторы и типы найденных
  сущностей.

## 10. Настройки

Все настройки читаются из переменных окружения (`app/config.py`, справочник — `env.example.sh`). Файл `.env`
не используется. Секреты провайдеров задаются переменными хоста; опционально секреты загружаются из
HashiCorp Vault (`app/secrets_vault.py`).

## 11. Тесты и скрипты

- Тесты: `python -m pytest -q` — 916 тестов проходят, 3 пропускаются по условию среды, 10 живых тестов выключены маркером `live` (прогон занимает около 95 секунд). Каталог `tests/`: `unit/` (модули по отдельности), `contract/` (HTTP-контракт,
  шлюз, оркестратор, провайдеры), `data/` (тестовые данные). Живые тесты на реальной модели помечены
  `live` и в обычный прогон не входят. Список тестов с описаниями — `AI_docs/Test_List.xlsx`.
- Скрипты (`scripts/`): сборка данных (`fetch_faq.py`, `generate_charges.py`, `sanitize_inquiries.py`,
  `build_golden_set.py`), переиндексация (`reindex_kb.py`), замеры (`measure_retrieval.py`,
  `measure_reranking.py`, `measure_reranker_latency.py`, `measure_search_models.py`,
  `measure_classifier.py`, `measure_local_model.py`), качество (`run_quality_eval.py`), нагрузка
  (`load_server.py`, `load_test.py`, отчёт — `AI_docs/Load_Report.md`), спецификация API
  (`build_openapi.py`).
