# 1. Краткая суть проекта

Разрабатывается AI-помощник для абонентов водоканала.

Помощник встроен в существующий Личный кабинет абонента и помогает:
- искать ответы по базе знаний;
- выбирать тип обращения;
- понимать, как заполнить обращение;
- получать рекомендации по следующим шагам;
- на этапе 2 — формировать документы, отправлять заявки и выполнять операции в биллинге с подтверждением абонента.

Конечный пользователь — только абонент водоканала.

Операторы колл-центра, внутренние сотрудники и подрядчики не являются конечными пользователями чат-интерфейса.

---

# 2. Главная бизнес-цель

Абонент часто не знает:
- какое обращение выбрать;
- как его заполнить;
- какие документы нужны;
- что делать после отправки.

AI-помощник должен вести абонента по процессу:

выбор типа обращения
→ уточнение деталей
→ сбор обязательных данных
→ формирование документа / рекомендации
→ подтверждение
→ отправка / запись в биллинг / заявка
→ следующие шаги

Цели:
- сократить время поиска ответа;
- снизить долю неверно оформленных обращений;
- снизить повторные обращения;
- улучшить пользовательский опыт в ЛК.

---

# 3. Этапы развития

## Этап 1: RAG-ассистент

Текущий базовый этап.

Система:
1. Принимает вопрос абонента.
2. Определяет тип обращения.
3. Ищет контекст в Vector DB.
4. Генерирует ответ на основе найденных фрагментов.
5. Возвращает:
   - ответ;
   - источники;
   - confidence_score;
   - suggested_actions;
   - disclaimer.

На этапе 1 нет write-операций в биллинг и автоотправки заявок.

---

## Этап 1.5: улучшение качества RAG

Нужно до внедрения полноценного агента.

Включает:
- Golden Set;
- A/B тестирование LLM;
- score_threshold;
- fallback без LLM;
- улучшение чанкинга;
- улучшение метаданных;
- rerank при необходимости.

---

## Этап 2: агент

Этап 2 добавляет выполнение действий.

По некоторым типам обращений агент должен уметь:
- выдавать заполненные документы;
- добавлять данные в биллинг;
- отправлять заявки в подразделения или подрядчикам;
- давать рекомендации по следующим шагам.

Обязательные требования:
- Human-in-the-loop;
- подтверждение абонента перед любой write-операцией;
- идемпотентность;
- аудит-лог;
- ограничение списка типов обращений для первого rollout;
- возможность отмены или исправления до отправки.

# 4. Жёсткие архитектурные правила

Эти правила нельзя нарушать без явного обновления архитектуры.

## 4.1. L2 — источник истины

Контейнера `AI Service` нет.

RAG-логика живёт внутри:

```text
API Gateway / Backend
```

PII-фильтрация — ответственность:

```text
LLM Gateway
```

Нельзя вводить новые контейнеры без обновления L2.

---

## 4.2. PII-фильтрация только в LLM Gateway

PII должна фильтроваться до отправки запроса в LLM Provider.

> **[УТОЧНЕНО 7 сентября 2026 — ADR-015.]** Правило распространяется на текст, **происхождение которого неизвестно**: на вопрос абонента и на ответ модели. Текст, попавший в систему через наш собственный приём, проверяется **при приёме** — один раз, с возможностью отказать, — а не на каждом ответе.
>
> Прежняя редакция чистила и найденный контекст. На практике это портило собственный корпус проекта: на вопрос про перерасчёт модель получала «3. ⟨ФИО⟩ выполняется по заявлению абонента», где ⟨ФИО⟩ — слово «Перерасчёт», а ⟨АДРЕС⟩ — заголовок колонки «Документы». Обезличиватель сделан для чужого текста; корпус базы знаний собрали мы.
>
> Тот же приём, что в ADR-012: проверки не отменены, а сдвинуты ко входу. Проверка живёт в `app/kb/build.py`, **роняет** сборку корпуса и опирается только на сильные свидетельства — контрольные суммы и слова-подсказки, не на догадку по заглавной букве.

Правильно:

```text
Backend → LLM Gateway → PII filter → LLM Provider
```

Неправильно:
- фильтровать PII только после ответа LLM;
- отправлять сырые ПДн напрямую в LLM Provider;
- логировать сырые ПДн.

Допустимо логировать только `pii_report`, например:

```json
{
  "pii_detected": true,
  "entities": ["SNILS", "PHONE", "ACCOUNT_NUMBER"]
}
```

---

## 4.3. Streaming Loop обязателен

Ответ должен доходить до пользователя как поток.

Путь streaming:

```text
LLM Provider
→ LLM Gateway
→ Backend
→ AI-виджет
→ Абонент
```

Пользователь должен видеть, что ответ печатается.

В прототипе допустим async generator, но для продакшена нужен SSE / WebSocket-совместимый поток.

---

## 4.4. Минимальный API-контракт

Разрешены:

```text
POST /v1/generate
GET /v1/healthz
```

Endpoint `/models` удалён.

---

## 4.5. Ошибки — RFC 7807

Все ошибки API должны соответствовать RFC 7807.

Пример:

```json
{
  "type": "https://vodokanal.example/errors/upstream-llm-unavailable",
  "title": "LLM provider unavailable",
  "status": 502,
  "detail": "Upstream LLM provider did not respond in time",
  "instance": "/v1/generate",
  "trace_id": "..."
}
```

---

## 4.6. Версионирование API

Только URI-версионирование:

```text
/v1/
```

---

## 4.7. Human-in-the-loop для write-операций

Любые write-операции:
- биллинг;
- отправка заявок;
- сохранение документов;
- изменение данных абонента;

выполняются только после подтверждения абонента.

Обязательны:
- состояние ожидания подтверждения;
- идемпотентность;
- аудит-лог;
- возможность отказа.

---

## 4.8. Таксономия — единый справочник

Типы обращений хранятся как справочник и используются для:
- классификации запросов;
- фильтрации RAG;
- маршрутизации агента;
- выбора шаблона документа;
- выбора подразделения;
- аналитики.

Ключевое поле:

```text
inquiry_type
```

Значения должны быть:
- стабильными;
- машиночитаемыми;
- без пробелов в начале и конце;
- одинаковыми во всех компонентах;
- подходящими для metadata filter;
- отображаемыми пользователю через отдельные display names.

Источники:

- публичный FAQ и сайт/соцсети.

#### LLM Provider

Внешний провайдер LLM.

Варианты:
- GigaChat Pro;
- GPT-4;
- self-hosted Qwen / Llama при триггерах.

> **[ПРИМЕЧАНИЕ v4.0]** Зарубежные провайдеры общего назначения (в т.ч. GPT-класс) для рабочего контура

> Провайдер по умолчанию — управляемый API на территории РФ (например, GigaChat Pro / YandexGPT).

#### Микросервис обращений

> **[ПОПРАВКА v4.5]** В версиях 3.0–4.4 этот узел назывался «Системы подразделений / подрядчики» и
> описывался расплывчато как получатель заявок. Уточнено при построении диаграммы C1 (файл
> `C4_L1_Context.html`): это **единая точка регистрации обращений абонентов** (источник 3 раздела 29,
> «БД / CRM обращений»), а не набор систем на стороне подрядчиков.

Единый микросервис, где регистрируются обращения абонентов (поверка, подключение, приём документов и
т.д.). Три независимых потребителя одной и той же базы обращений:
- AI-помощник — регистрирует обращение (этап 2, только после подтверждения абонента, HITL);
- подрядчики и подразделения — читают зарегистрированные обращения, чтобы выполнять работы;
- пайплайн дообучения модели — берёт корпус обращений (источник 3, раздел 30, «Корпус для дообучения»).

Подрядчики **не интегрированы с AI-помощником напрямую** — они потребители микросервиса обращений.

#### Диспетчерская система

> **[ПОПРАВКА v4.5]** Ранняя формулировка этой поправки («только этап 2», «AI-помощник передаёт
> аварийную заявку») была неполной. Уточнено при ревью C4 L2: у Диспетчерской системы **два потока**.

Отдельная система аварийных заявок, near real-time (источник 7 раздела 29). Взаимодействие с
AI-помощником:
- **Этап 1 (чтение)** — AI-помощник читает данные по авариям (статус, зона, ETA), чтобы включить их в
  ответ абоненту; это один из онлайн-источников инференса (раздел 30, раздел 33.1);
- **Этап 2 (запись)** — AI-помощник передаёт аварийную заявку после подтверждения абонента (HITL).

> **[ОТМЕНЕНО v4.17 решением ADR-009]** Утверждение ниже больше не действует: аварийная заявка
> пишется **только в Диспетчерскую систему** и в микросервисе обращений не регистрируется. Причина
> — устранение расхождения Р6: при двух записях в разные системы понадобилось бы согласование,
> которое на прототипе непроверяемо. Следствия (аварии не попадают в корпус дообучения, в
> аналитику по типам и в эталонный набор) разобраны в ADR-009, раздел «Последствия».

## 5.2. L2 Containers — этап 1

| Контейнер | Технология | Ответственность |
|---|---|---|
| AI-виджет в ЛК | React / TypeScript / Node.js Upper | Чат-UI, SSE-рендер, кнопки действий, suggested_actions |
| API Gateway / Backend | Go Middle или Python FastAPI | Оркестрация, сессии, Retrieval, сборка промпта, интеграция с ЛК; чтение Биллинга (XML-RPC API) и Диспетчерской системы (REST API) |
| LLM Gateway | Python Service / LiteLLM | Абстракция над моделями, ретраи, токены, квоты; Security Layer (PII Sanitizer + Guardrails, раздел 35) |
| Vector Database | Qdrant / Milvus / Pgvector MVP | Эмбеддинги, семантический поиск, фильтры по inquiry_type |
| ETL Worker | Python Worker [GPU] | Парсинг, чанкинг, эмбеддинг, upsert в Vector DB |

## 5.3. Связи L2

Все связи должны быть подписаны.

| Откуда | Куда | Действие | Технология |
|---|---|---|---|
| AI-виджет | Backend | Отправка запроса | HTTPS / JSON |

### ETL Worker

Компоненты (как описано в версии 3.0):

```text

→ Text Splitter

```

> **[ПРИМЕЧАНИЕ v4.0 — расхождение с диаграммой]** Фактическая диаграмма L3 (файл
> `C4_L3_ETL_RAG_1.html`, названа в самой диаграмме «финальная, целевая модель») описывает более богатый
> пайплайн, чем текст выше:
>
> ```text
> Ingest Pipeline (ридер + 3-уровневый классификатор метаданных: regex → эмбеддинг → LLM-fallback)
> → Text Splitter (RecursiveCharacterTextSplitter, heading-aware границы)
> → Quality & Dedup Filter (MinHash/SimHash, quality_score, near-duplicate кластеры Jaccard ≥ 0.9)
> → Reranker Client offline (BGE-reranker-v2-m3 — отбор представительного чанка из кластера дублей)
> → Embedding Client (BGE-M3 основная модель, GigaChat Embeddings — fallback, батчи 32–64)
> → Vector DB Client (upsert + tombstones по source_id + blue-green переключение alias при реиндексе,
>   без простоя поиска)
> ```
>
> Плюс отдельный компонент **Sync State** (PostgreSQL/Redis) — курсоры источников, история запусков,
> контрольные суммы документов для инкрементальной (delta) индексации.
>
> Текст версии 3.0 (раздел 5.5, оригинал ниже) не обновлён под эту версию диаграммы — это считается
> задокументированным известным расхождением (см. раздел 25.2), а не ошибкой: диаграмма считается более
> новым источником истины для ETL-пайплайна.

> (BGE-reranker-v2-m3, обученного на паре запрос↔документ) для задачи отбора представительного чанка из

# 6. Динамика / Sequence

## 6.1. Этап 1: RAG-запрос

Участники:

```text
Абонент
AI-виджет
Backend
Vector DB
LLM Gateway
LLM Provider
```

### Шаги

1. Абонент вводит вопрос в ЛК.
2. AI-виджет отправляет запрос:

```text
POST /v1/generate
```

с параметром:

```json
{
  "stream": true
}
```

3. Backend классифицирует обращение (Triage через LLM Gateway) и получает `inquiry_type` +
   `confidence`. При недоступности LLM — keyword-режим (fallback).

4. Backend выполняет ретривал: эмбеддинг запроса → поиск → реранжинг.

```text
Embedding(query)
Search(вектор, top_k=20, filter=inquiry_type)
Rerank(top_k=20 → top_n=3)
```

Vector DB возвращает 20 кандидатов, Reranker Inference отбирает три:

```text
Chunk_1
Chunk_2
Chunk_3
```

5. Backend вызывает LLM Gateway:

```text
POST /v1/generate
```

Передаёт:
- system;
- query;
- context;
- metadata.

6. LLM Gateway проверяет квоту (Quota Manager: абонент / сессия / сервис; превышение — 429 +
   Retry-After), затем выполняет PII-анонимизацию (PII Sanitizer). Порядок quota-first —
   отклонить по лимиту дешевле, чем обезличивать; ПДн всё равно скрыты до Provider (правило 4.2).

7. LLM Gateway вызывает LLM Provider.

8. LLM Provider возвращает поток:

```text
text/event-stream
```

9. Поток проходит (в Gateway — sync-проверка Guardrails, менее 50 мс, до отдачи наружу):

```text
Provider → Gateway (Guardrails sync) → Backend → Widget → Абонент
```

10. После завершения:

```text
[DONE]
```

возвращаются метаданные:

```json
{
  "sources": [],
  "confidence_score": 0.0,
  "suggested_actions": [],
  "disclaimer": "..."
}
```

> **[ПОПРАВКА v4.5 — заменяет примечание v4.0]** Sequence-артефакт теперь существует:
> `C4_Sequence_Diagrams.html` (draw.io, две диаграммы — Этап 1 и Этап 2). Открытый P1-пункт раздела 27
> закрыт. **Источником истины по сценарию считается диаграмма**, текст выше — её краткий пересказ; при
> расхождении правится текст (та же логика, что для ETL в разделе 5.5, находка F8).
>
> Диаграмма показывает то, чего в тексте нет и не должно быть ради краткости: участников Embedding
> Inference и Reranker Inference отдельными lifeline; блок `ref Retrieval`; ветку fallback при
> `score_threshold < 0.7`; keyword-режим Triage при недоступности LLM; повтор виджета по 429 +
> Retry-After; async-выход `quality_report` и Billing Callback в ClickHouse; заголовки `X-Internal-Token`
> и `X-Trace-Id` (раздел 7).
>
> Прежнее примечание v4.0 гласило, что sequence-артефакта не существует — оно устарело.

## 6.3. Этап 2: агентный write-сценарий

Участники:

```text
Абонент
AI-виджет
Backend / Agent Orchestrator
LLM Gateway
Vector DB
Document Generator
Billing Adapter
Сервис работы с обращениями
```

### Шаги

1. Абонент задаёт запрос.
2. Triage определяет `inquiry_type`.
3. Advisor даёт консультацию по RAG.
4. Form Agent запрашивает недостающие слоты.
5. Система формирует черновик.

   - Сервис работы с обращениями отправляет заявку;

   - ID заявки;
   - подразделение;
   - статус;
   - следующие шаги.

# 11. Известные дефекты прототипа

## 11.1. Таксономический mismatch

В последней версии прототипа наблюдаются несоответствия:

### INQUIRY_TYPES

Содержит русские значения, возможно с хвостовыми пробелами:

```text
"перерасчёт "
"поверка_счётчика "
"задолженность "
```

### RAG metadata

Содержит значения с хвостовыми пробелами и иногда пробелы в ключах:

```text
"inquiry_type ": "перерасчёт "
"source ": "Регламент_перерасчёт_v3 "
"department ": "Абонентский отдел "
```

### Triage keywords

Могут использовать ключи без пробелов:

```text
"перерасчёт"
"поверка_счётчика"
"задолженность"
```

### Последствие

RAG-фильтр не находит документы из-за:
- разных языков представления;
- лишних пробелов;
- несогласованных ключей.

---

## 11.2. Требуемая нормализация

Ввести единый canonical enum.

Рекомендуется:

```python
INQUIRY_TYPES = [
    "recalculation",
    "meter_verification",
    "reconciliation",
    "contract_signing",
    "contract_termination",
    "debt",
    "water_quality",
    "emergency",
    "tariff_change",
    "other",
]
```

Metadata:

```python
metadata={
    "source": "Регламент_перерасчёт_v3",
    "inquiry_type": "recalculation",
    "department": "Абонентский отдел",
}
```

Keywords:

```python
KEYWORDS = {
    "recalculation": ["перерасчёт", "перерасчет", "recalculat", "overcharge", "refund"],
    "meter_verification": ["поверка", "счётчика", "счетчика", "meter", "verification"],
    "debt": ["задолженность", "долг", "debt", "owe", "overdue", "penalty"],
}
```

Перед сравнением всегда использовать:

```python
inquiry_type = inquiry_type.strip().lower()
```

---

## 11.3. Синтаксические артефакты

В тексте файла встречаются артефакты:

```python
from future import annotations
```

Должно быть:

```python
from __future__ import annotations
```

---

```python
def init(self, ...):
```

Должно быть:

```python
def __init__(self, ...):
```

---

```python
if name == "main":
```

Должно быть:

```python
if __name__ == "__main__":
```

---

## 11.4. Ошибка regex телефона

Текущий паттерн может быть невалиден:

```python
r'(?:+7|8)\s*(?\d{3})?[\s-]?\d{3}[\s-]?\d{2}[\s-]?\d{2}'
```

Нужно исправить:

```python
r'(?:\+7|8)\s*(?:\d{3})?[\s-]?\d{3}[\s-]?\d{2}[\s-]?\d{2}'
```

---

## 11.5. PII regex для лицевого счёта

Текущий паттерн:

```python
r'\b\d{9,10}\b'
```

Может быть слишком широким.

Рекомендация:
- использовать только для контекста лицевого счёта;
- или применять рядом с keywords:

```text
лицевой счёт
л/с
ЛС
account
```

---

## 11.6. Embedding search не всегда учитывает фильтр

В части версий прототипа embedding-ветка использует:

```python
similarity_search(query, k=3)
```

без фильтра `inquiry_type`.

Нужно:

```python
similarity_search(
    query,
    k=3,
    filter={"inquiry_type": inquiry_type}
)
```

И учитывать, что metadata значения должны быть нормализованы.

---

## 11.7. Нет полноценного SSE

Сейчас streaming имитируется через:

```python
async generator
print(chunk)
```

Для продакшена нужен:
- SSE endpoint;
- event types;
- metadata event;
- done event;
- error event;
- client-side rendering.

---

## 11.8. Fallback type mismatch

В fallback-логике встречается значение:

```text
prochee
```

Но в таксономии может быть:

```text
прочее
```

или рекомендуемый код:

```text
other
```

Нужно привести к единому canonical code.

---

## 11.9. Пробелы в dict-ключах

В предоставленном тексте встречаются артефакты вида:

```python
{ "trigger ": "classify " }
```

Должно быть:

```python
{ "trigger": "classify" }
```

Если такие пробелы есть в реальном файле, библиотека `transitions` не найдёт ожидаемые ключи.

# 13. Риски и митигации

| Риск | Митигация |
|---|---|
| Галлюцинации | RAG + score_threshold + Guardrails + sources + Annotator |
| ИБ / ПДн 152-ФЗ | PII-фильтр в LLM Gateway до провайдера + pii_report |
| Неверный тип обращения | Таксономия + фильтр inquiry_type + confidence + fallback «выберите вручную» |
| Абонент не понимает следующие шаги | suggested_actions + пошаговые сценарии + кнопки в ЛК |
| Бюджет | Token Counter + квоты + ClickHouse-аналитика |
| Сбои провайдеров | Retry / Circuit Breaker / fallback |
| Этап 2: write в биллинг | HITL, идемпотентность, аудит, лимит типов, постепенный rollout |
| Scope creep | Stage-gating: агент только после метрик этапа 1 |
| Плохая таксономия | Единый canonical enum + display mapping + тесты |
| Низкое качество RAG | Golden Set + Recall@3 + score_threshold + rerank |

> **[ДОПОЛНЕНО v4.0 — риски, найденные при верификации, но не входившие в исходную таблицу]**

| Риск | Митигация |
|---|---|
| Spoofing subscriber_id: Backend/Orchestrator доверяет полю subscriber_id без повторной проверки на write-шаге | Явная проверка subscriber_id на каждом write-вызове Billing Adapter / Сервис работы с обращениями (открытый P1-пункт, раздел 27) |
| IDOR: Billing Adapter / Сервис работы с обращениями выполняет операцию не над тем абонентом при подмене subscriber_id | То же — проверка привязки subscriber_id к аутентифицированной сессии на каждом write-шаге |
| Конкуренция за GPU между офлайн ETL-реиндексом и онлайн-обслуживанием запросов (общие Embedding/Reranker Inference сервисы) | Изоляция GPU / приоритетные очереди / окно обслуживания для полного реиндекса (открытый P0-пункт, раздел 27) |

# 24. Верификация архитектуры (CTO Challenge) — результаты

## 24.1. Методология (кратко, самодостаточно)

Верификация проводилась по методике «CTO Challenge» — аудит архитектурного решения перед тратой бюджета,
концептуально аналогичный quality gate между проектированием и разработкой. Использованные инструменты:

- **Definition of Ready (DoR)** — обязательный минимум перед началом траты бюджета: понятная проблема,
  визуализированное решение (диаграммы C4), посчитанная цена (CAPEX + прогноз OPEX), названные риски с
  планом митигации. Отсутствие любого из четырёх пунктов — «стоп-фактор».
- **Матрица Verification vs Validation** — инженерный вопрос «соблюдены ли нефункциональные требования?»
  (проверяется расчётами и диаграммами) отдельно от бизнесового «решает ли это задачу?» (проверяется
  ROI/бизнес-эффектом).
- **ATAM Utility Tree** — формализация нефункциональных требований («надёжно» → измеримые метрики с
  приоритетом по важности и сложности реализации).
- **STRIDE** — упрощённая модель угроз безопасности: Spoofing, Tampering, Repudiation, Information
  disclosure, Denial of service, Elevation of privilege — для каждой угрозы должен быть явный ответ в
  архитектуре.
- **Sizing по закону Литтла** — `L = λ × W` (среднее число одновременных запросов = RPS × средняя
  задержка обработки одного запроса) как минимальная математическая проверка, выдержит ли выбранная
  архитектура целевую нагрузку.

## 24.2. Итоговый вердикт: CONDITIONAL

«Да, но»: архитектурная дисциплина проекта (жёсткие правила раздела 4, HITL/идемпотентность/аудит,
явное разделение этапов, PII-барьер на границе LLM Gateway) — сильная и последовательная. Но целевая
архитектура Этапа 2 и любые траты на GPU-инфраструктуру не готовы к защите бюджета: нет сметы CAPEX/OPEX,
нет расчёта производительности под заявленные NFR, в диаграммах есть конкретные технические дефекты
(раздел 25).

## 24.3. Definition of Ready — по пунктам

| Пункт DoR | Статус | Комментарий |
|---|---|---|
| Проблема понятна (бизнес-цели) | Есть | Разделы 1–2 этого документа: цели и боли абонента сформулированы, роль AI-помощника внятная. |
| Решение визуализировано (C4 Context + Container) | Частично | Container (L2) и один Component (L3, ETL) есть как файлы. Файла L1 Context среди переданных артефактов нет — нужно подтвердить, что он существует отдельно. |
| Цена посчитана (CAPEX + прогноз OPEX) | Отсутствует | Ни одной цифры бюджета во всём проекте — при том, что инфраструктура включает Kubernetes, GPU-инференс, self-hosted LLM, Vault/Prometheus/Grafana/Loki. Это стоп-фактор в терминах методики DoR. |
| Риски названы (таблица + план митигации) | Есть | Раздел 13 этого документа: 10+ рисков с митигацией. Не хватало risk-владельцев/сроков и явных пунктов Spoofing/IDOR — последнее дополнено в разделе 13 версии 4.0. |

## 24.4. Verification vs Validation — конкретные пробелы

- **Нет Sizing Calculator под заявленные NFR.** Цели TTFT < 500 мс, P99 поиска < 100 мс, Recall@3 > 90%
  (раздел 18) заявлены, но не подкреплены расчётом по закону Литтла под целевой RPS и не подкреплены
  разбивкой латентности LLM-генерации (`T_total = T_prefill + N_tokens × T_per_token`) для конкретной
  GPU и модели. Без расчёта эти цифры — декларация, а не архитектурное решение.
- **Валидация бизнес-эффекта не квантифицирована.** Цели («сократить время поиска ответа», «снизить
  повторные обращения», раздел 2) сформулированы качественно, но не привязаны к числам — нет базовой
  линии и целевого процента снижения, на которые можно сослаться при защите бюджета.

## 24.5. STRIDE — что закрыто, а что нет

| Угроза | Вопрос челленджера | Текущее покрытие |
|---|---|---|

| Tampering (PII) | Уходят ли сырые ПДн в LLM Provider? | Закрыто — правило раздела 4.2, LLM Gateway фильтрует до отправки |
| DoS | Что произойдёт при резком всплеске запросов от одного абонента? | Закрыто — Quota Manager (slowapi + Redis), 429 + Retry-After (раздел 5.5) |

## 26.1. ADR-002: Стратегия хостинга LLM — SaaS vs Self-hosted

**Файл-первоисточник:** `ADR-002-llm-hosting-strategy.md`. **Статус:** Proposed (направление решено,
финальный Accepted — после утверждения сметы CAPEX/OPEX и sizing-расчёта под конкретную GPU-конфигурацию
self-hosted-сценария).

> Ниже — полный текст ADR-002 дословно, без сокращений (по состоянию файла на момент написания этой
> версии контекста). Раздел самодостаточен: другой LLM не обязана открывать отдельный файл ADR, чтобы
> понимать решение и его аргументацию целиком. Сам файл `ADR-002-llm-hosting-strategy.md` остаётся
> официальным источником истины и должен обновляться в первую очередь — этот раздел нужно синхронизировать
> с ним при любой последующей правке решения.

### Контекст и постановка проблемы

Проект «AI-помощник абонента водоканала» использует языковую модель (LLM) для двух задач: генерация
ответов в режиме вопрос-ответ по базе знаний (консультационный сценарий, без записи данных) и, на более
позднем этапе — классификация обращений и вызов инструментов в агентном сценарии, который включает
операции записи (заявки, изменения в биллинге) с обязательным подтверждением абонента перед выполнением.

Нужно решить, где физически исполняется модель: на управляемом облачном API стороннего провайдера (SaaS)
или как модель с открытыми весами, развёрнутая на собственных серверах компании (self-hosted, он же
on-premise).

Абонент — физическое лицо, и в переписке с помощником неизбежно фигурируют его персональные данные (ФИО,
номер лицевого счёта, адрес). Это делает выбор хостинга LLM не только техническим, но и регуляторным
решением: по 152-ФЗ «О персональных данных» передача таких данных за пределы РФ требует отдельного
правового основания, которого у проекта нет.

На момент принятия решения: инфраструктурная смета (CAPEX на оборудование, ежемесячный OPEX) ещё не
утверждена; фактический объём обращений неизвестен, так как продукт не запущен; вспомогательная
GPU-инфраструктура для поиска по базе знаний (сервисы эмбеддинга и реранжинга) уже спроектирована как
собственная (self-hosted) независимо от того, какая модель используется для генерации ответов. То есть
вопрос стоит не «self-hosted или нет вообще», а «self-hosted для генерации LLM-ответов — начиная с какого
момента».

### Драйверы решения (силы, действующие на решение)

| Сила | Требование | В чём конфликт |
|---|---|---|
| Регуляторный (152-ФЗ) | Персональные данные абонента не должны покидать периметр РФ без правового основания | Обращение к зарубежному управляемому API технически означает передачу запроса (и части данных) за периметр |
| Бюджетный | Смета CAPEX/OPEX на инфраструктуру LLM пока не утверждена | Self-hosted требует капитальных вложений в GPU до того, как ценность продукта подтверждена реальным использованием |
| Продуктовый | Реальный объём обращений неизвестен — продукт ещё не запущен | Инвестиция в собственную инфраструктуру сейчас — ставка без данных о фактической нагрузке |
| Качество ответа | Целевая полнота ответа (доля релевантных источников в топ-3) — не ниже 90% на тестовой выборке | Модели с открытыми весами среднего размера на сложных рассуждениях уступают топовым управляемым моделям без дополнительной донастройки |
| Задержка ответа | Время до первого токена ответа — не более 500 мс; задержка поиска по базе знаний — не более 100 мс | Сетевой вызов к внешнему API добавляет задержку, которую команда не контролирует напрямую |
| Ресурс поддержки | В команде нет выделенного инженера по эксплуатации ML-инфраструктуры на полной занятости | Self-hosted инференс требует постоянного сопровождения: мониторинг модели, обновление весов, GPU-инфраструктура |

### Рассмотренные варианты

#### Вариант A — Только SaaS весь жизненный цикл проекта

Управляемый API стороннего провайдера на всех этапах, без собственного инференса LLM.

**Pros**
- Нулевой CAPEX на GPU под генерацию ответов; оплата по факту использования, предсказуема на малых объёмах.
- Минимальное время до первого релиза — не нужно поднимать и валидировать собственный инференс-стек.
- Обновления и качество модели — ответственность провайдера, не команды проекта.

**Cons**
- Не закрывает ситуации, когда объём запросов становится очень большим, требуется задержка ответа ниже
  той, что может дать внешний API, или требуется запрет на передачу данных за периметр — при их
  наступлении понадобится незапланированная миграция под давлением, а не по заранее согласованному плану.
- Стоимость использования растёт линейно с объёмом запросов без потолка — при значительном росте
  нагрузки может обогнать по цене владение собственным оборудованием.
- Зависимость от доступности и политики стороннего провайдера — единая точка отказа вне периметра
  компании.

#### Вариант B — Только Self-hosted с самого начала

Развёртывание модели с открытыми весами на собственных GPU-серверах уже на первом релизе.

**Pros**
- Данные не покидают периметр с первого дня — регуляторный вопрос снимается полностью и сразу.
- Предсказуемая стоимость эксплуатации после ввода в строй, нет оплаты за каждый запрос.
- Задержка ответа полностью в руках команды — единственный реалистичный путь к очень низкой задержке
  генерации, если она понадобится.

**Cons**
- Капитальные вложения в GPU-сервер требуются до подтверждения того, что продукт вообще востребован —
  риск потратить бюджет впустую, если пилот не подтвердит эффект.
- Постоянная эксплуатационная нагрузка (настройка сети и доступа, мониторинг модели, резервное
  копирование, обновление весов) ложится на команду без выделенного инженера по эксплуатации ML-систем.
- Модели среднего размера с открытыми весами на сложных рассуждениях уступают топовым управляемым
  моделям «из коробки» — для сопоставимого качества потребуется дополнительная настройка поиска и,
  возможно, дообучение, что съедает выигрыш во времени.

#### Вариант C — Гибрид через единый шлюз доступа к модели, с поэтапной миграцией по триггерам (ВЫБРАНО)

Все обращения к языковой модели проходят через единый внутренний компонент-шлюз, который абстрагирует
конкретного провайдера от остального кода приложения. По умолчанию шлюз обращается к управляемому API
российского провайдера. Переход на self-hosted-модель выполняется поэтапно, по факту наступления заранее
определённых условий (см. таблицу триггеров ниже), и не требует изменения кода остальной системы —
только конфигурации самого шлюза.

**Pros**
- Нулевой CAPEX на LLM-инференс на старте — не блокирует запуск первой версии продукта.
- Единая точка абстракции делает смену способа хостинга операцией конфигурации, а не переписыванием
  бизнес-логики.
- Переход управляется заранее согласованными, измеримыми условиями, а не календарём или интуицией —
  решение о стратегии принимается один раз, дальше оно просто исполняется по факту данных.
- Сравнение управляемой и собственной модели на реальных вопросах можно проводить как штатную процедуру
  ещё до того, как переход станет обязательным.

**Cons**
- Требует спроектировать и построить шлюз доступа к модели уже на первом этапе — дополнительная
  инженерная работа, которую вариант A не потребовал бы.
- «Нулевой эксплуатационной нагрузки» всё равно не будет: вспомогательные GPU-сервисы для поиска по базе
  знаний (эмбеддинг и реранжинг) уже спроектированы как собственные независимо от выбора провайдера
  генеративной модели — часть сложности self-hosted присутствует в проекте в любом случае.
- Если условие перехода наступает резко (например, внезапный запрет на использование внешних API), а не
  постепенно, нужен заранее подготовленный, пусть и минимальный, резервный self-hosted контур — иначе
  сама миграция в моменте нарушит непрерывность сервиса. Это означает необходимость держать небольшую
  резервную мощность ещё до формального перехода.

### Решение (Decision Outcome)

Выбран **Вариант C**. Единый шлюз доступа к модели становится обязательным компонентом архитектуры уже
на первом этапе. Провайдер по умолчанию — управляемый API **на территории РФ** (а не зарубежный
провайдер общего назначения): обращение к зарубежному управляемому API означало бы передачу персональных
данных абонента за периметр без правового основания по 152-ФЗ, поэтому зарубежный провайдер в принципе
исключён из рассмотрения для рабочего контура — это не вопрос «дешевле/дороже» или «лучше/хуже» наравне
с отечественным провайдером, а вопрос допустимости варианта как такового.

Переход на self-hosted-модель выполняется по мере фактического наступления хотя бы одного из условий,
перечисленных ниже.

### Триггеры перехода на self-hosted (on-premise)

| № | Триггер | Пороговое значение | Что происходит при срабатывании |
|---|---|---|---|
| 1 | Запрет на использование внешних API | Служба информационной безопасности налагает полный запрет на передачу запросов абонентов во внешние управляемые API, в том числе после обезличивания | Немедленный перевод трафика на резервный self-hosted контур, подготовленный заранее в тестовом режиме |
| 2 | Объём запросов | Устойчиво более 50 млн токенов в месяц на протяжении двух и более месяцев подряд | **[ИЗМЕНЕНО v4.5]** Не перевод трафика, а обязательный **пересчёт стоимости владения**; перевод — только если self-hosted оказался дешевле при измеренной конкурентности. Причина — раздел 42.2 |
| 3 | Требование по задержке ответа | Целевая задержка генерации ответа менее 200 мс для конкретного сценария — недостижима через внешний сетевой вызов | Перевод соответствующих сценариев (не обязательно всей системы) на self-hosted-модель |
| 4 | Потребность в дообучении модели | Необходимость дообучить модель (например, методом LoRA) на закрытых данных обращений абонентов, которые нельзя передавать третьей стороне | Развёртывание дообученной self-hosted-модели для соответствующих сценариев |

Наступление любого одного из этих четырёх условий — достаточное основание для запуска перехода на
соответствующий сценарий или на систему целиком; условия не обязаны наступить одновременно.

### Последствия (Consequences)

**Хорошо, потому что:**
- Решение не требует капитальных вложений в GPU до того, как продукт подтвердит свою ценность.
- Соответствие требованиям к персональным данным обеспечено выбором провайдера с самого начала, а не
  доработкой постфактум.
- Смена способа хостинга — операция конфигурации шлюза, а не архитектурный рефакторинг остальной
  системы.
- Условия перехода объективны, измеримы и согласованы заранее — это снижает риск споров «пора переходить
  или ещё рано» в будущем.

**Плохо, потому что:**
- Шлюз доступа к модели нужно спроектировать и протестировать (обработка сбоев провайдера, фильтрация
  персональных данных до отправки запроса) уже на первом этапе — это требует времени, которого не
  потребовал бы прямой вызов API без промежуточного слоя.
- Резкое (не постепенное) наступление триггера запрета на внешние API потребует заранее готового
  резервного self-hosted контура — это добавляет небольшую, но постоянную эксплуатационную нагрузку и
  стоимость ещё до формального перехода.
- Решение фиксирует стратегию перехода, но не заменяет собой расчёт стоимости владения — конкретная
  экономика self-hosted-сценария (сколько единиц GPU-оборудования, какой ежемесячный расход) должна быть
  посчитана отдельно и обновляться по мере приближения к пороговым значениям.

### Подтверждение (Confirmation)

Решение считается реализованным, когда выполнены все условия:
1. Шлюз доступа к модели развёрнут с поддержкой минимум двух провайдеров (управляемый API как основной и
   минимум один self-hosted-кандидат в тестовом контуре) и работающим автоматическим переключением при
   сбое основного провайдера.
2. Объём запросов, задержка ответа и стоимость использования измеряются ежемесячно и сверяются с
   пороговыми значениями из таблицы триггеров выше.
3. Результат сравнения качества ответов управляемой модели и self-hosted-кандидата на контрольной
   выборке вопросов зафиксирован документально до конца первого этапа.
4. Расчёт стоимости владения (CAPEX оборудования + ежемесячный OPEX) для self-hosted-сценария выполнен
   заранее, до фактического наступления триггера, а не после него — иначе переход всё равно окажется
   незапланированным.

# 28. Рабочие инструменты для P0-расчётов (формулы и шаблоны)

Этот раздел — не описание методики, а готовые к применению инструменты для закрытия P0-пунктов 1 и 2 из
раздела 27 (смета CAPEX/OPEX и расчёт производительности). Их нужно не пересказывать, а подставлять в них
реальные числа проекта.

## 28.1. Sizing производительности — закон Литтла

```text
L = λ × W
```

- `λ` (лямбда) — целевая пиковая нагрузка, запросов в секунду (RPS).
- `W` — средняя задержка обработки одного запроса целиком, в секундах (не путать с TTFT — это полное
  время от запроса до последнего токена ответа).
- `L` — среднее число одновременно обрабатываемых запросов (concurrency), которое обязана выдерживать
  система, не теряя запросы и не превышая целевую задержку.

**Как применить к этому проекту:** `λ` пока не определён — его нужно оценить (например, из ожидаемого
числа активных абонентов в ЛК и доли, которая обратится к AI-помощнику в пиковый час). `W` оценивается
по формуле из раздела 28.2 ниже. Дальше:

```text
требуемая RAM (при синхронной модели обработки) = L × RAM_на_один_воркер
```

Если `L` получается больше разумного числа процессов на одной машине — нужна асинхронная модель
обработки запросов (не блокирующая поток на время ожидания ответа LLM) и/или горизонтальное
масштабирование, а не просто больше RAM.

## 28.2. Латентность генерации LLM

```text
T_total = T_prefill + (N_tokens × T_per_token)
```

- `T_prefill` — время обработки входного промпта (системный промпт + найденный контекст + история
  диалога) до начала генерации первого токена. Определяет фактический TTFT.
- `N_tokens` — ожидаемая длина ответа модели в токенах.
- `T_per_token` — время генерации одного токена на конкретном железе и конкретной модели. Для
  управляемого API — предоставляется/измеряется провайдером; для self-hosted-кандидата (Qwen2.5-32B/72B)
  — нужно измерить эмпирически на целевой GPU или получить из документации поставщика GPU для этой
  конкретной модели и её квантования, а не брать «по аналогии» с другой моделью.

**Как применить:** сравнить получившийся `T_total` (и отдельно `T_prefill` как оценку TTFT) с целевыми
NFR (раздел 18: TTFT < 500 мс, полный ответ < 3 сек). Если self-hosted-кандидат не укладывается —
варианты: более мощная GPU, квантование модели, сокращение `N_tokens` (короче целевая длина ответа) или
сохранение этого сценария на управляемом API даже после общего перехода на self-hosted.

## 28.3. Sizing хранилища

**Векторная база знаний:**

```text
число_векторов = число_страниц_базы_знаний × чанков_на_страницу
размер_одного_вектора_КБ = размерность_вектора × 4_байта / 1024   (для float32; меньше при квантовании)
итоговый_объём = число_векторов × размер_одного_вектора_КБ
```

**Логи и observability:**

```text
событий_в_сутки = средний_RPS × 86400
объём_в_месяц = событий_в_сутки × 30 × размер_одной_записи_лога_КБ
```

Без политики ротации (например, хранить 30 дней) или выгрузки старых логов в холодное хранилище (S3 /
MinIO, раздел 8.5) диск обычного размера заполняется логами за считанные месяцы — это нужно учитывать
в OPEX-строке «хранилище логов», а не считать бесплатным побочным эффектом.

## 28.4. Шаблон CAPEX/OPEX (структура для заполнения, НЕ готовые цифры)

> Это категории для расчёта, а не суммы. Заполнять нужно реальными коммерческими предложениями/
> оценками команды этого проекта. Ни одна цифра ниже не должна заполняться «по аналогии» с числами из
> файлов, описанных в разделе 26.4 (`7.3 млн ₽`, `53 дня`, `$50–100/мес`, `$800–1500/мес` и т.п.) — это
> сфабрикованные цифры постороннего примера, не факты этого проекта.

**CAPEX (разовые затраты) — категории:**
- разработка (человеко-часы команды по ролям, раздел 14 RACI);
- управление проектом / архитектура;
- резерв на риски;
- (только при self-hosted-сценарии) закупка или аренда GPU-сервера под инференс.

**OPEX (ежемесячные затраты) — категории:**
- оплата управляемого API по токенам — считается по ожидаемому объёму запросов × средняя длина
  (промпт + ответ) в токенах × цена провайдера за 1000 токенов;
- хостинг Vector DB / managed DB;
- балансировщики и трафик;
- инфраструктура мониторинга/логирования (Prometheus/Grafana/Loki, раздел 8.5) и хранилище логов
  (раздел 28.3);
- (только при self-hosted-сценарии) аренда/амортизация GPU-сервера, электричество, обслуживание.

**Как использовать для проверки триггера №2 (раздел 26.3, «> 50 млн токенов/мес»):** посчитать OPEX
управляемого API при целевом объёме токенов по формуле выше и сравнить с суммой амортизации CAPEX
self-hosted-сценария в пересчёте на месяц плюс OPEX self-hosted-сценария по тем же категориям. Объём
запросов, при котором вторая сумма становится меньше первой — и есть фактический экономический порог
перехода для этого конкретного проекта; сверить его с порогом 50 млн токенов/мес и при расхождении
обновить сам триггер в ADR-002, а не игнорировать расхождение.

## 29.5. Доступ к Биллингу — через его собственный XML-RPC API

> **[ПОПРАВКА v4.5 — отменяет предыдущую редакцию этого раздела]** Раздел раньше утверждал, что
> протокол Биллинга — «прямой SQL через сервис на Go (приоритет) либо внешний XML-RPC API (резерв)», и
> вводил из-за этого отдельный наш контейнер «Контейнер доступа к Биллингу» как anti-corruption layer.
> Уточнено: **у Биллинга есть собственный внешний XML-RPC API, и это единственный способ доступа.**
> Прямого SQL в БД Биллинга нет ни у одного нашего компонента. Отдельный слой доступа нашей разработки
> **не нужен и не вводится** — API самой системы уже выполняет эту роль.

Доступ к Биллингу (источники 1 и 9) — только через внешний XML-RPC API системы:
- **Backend** читает данные абонента через этот API уже на Этапе 1 (online, низкая задержка);
- **Billing Adapter** (Этап 2) выполняет write через тот же API, добавляя HITL-подтверждение и
  Idempotency-Key. Собственного SQL-клиента к БД Биллинга не имеет.

### Общее правило доступа к внешним системам

Оно же объясняет симметричное решение по обращениям:

> **Наш адаптер обращается к чужой системе только через её API, никогда — напрямую в её БД.**

| Внешняя система | Кто ходит | Через что | Почему не в БД |
|---|---|---|---|
| Биллинг | Backend (read, Этап 1), Billing Adapter (write, Этап 2) | внешний XML-RPC API Биллинга | БД принадлежит Биллингу; схема — не контракт, изменится без предупреждения |
| Микросервис обращений | Сервис работы с обращениями (Этап 2) | API микросервиса | прямая запись в таблицу обошла бы бизнес-логику микросервиса (номер обращения, валидация, переходы статусов, уведомление подрядчиков), а подрядчики читают именно через микросервис — увидели бы необработанную запись |
| Диспетчерская система | Backend (read, Этап 1), Сервис работы с обращениями (write, Этап 2) | REST API | то же правило |

**Исключение, которое нужно решить явно:** офлайн-пайплайн дообучения (раздел 30, «Корпус для
дообучения», источник 3) по текущему плану читает **БД обращений** батчем, а не API микросервиса —
для bulk-выгрузки это оправданно, но формально нарушает правило выше. Нужно зафиксировать решение
(чтение с реплики read-only со схемой как контрактом vs. постраничная выгрузка через API) — открытый
пункт, раздел 33.3.

Само правило доступа к внешним системам формально не принято отдельным ADR — открытый пункт, раздел 33.3.

# 30. ETL/ELT и Stream/Batch — где что и почему

| Участок пайплайна | Режим | Паттерн | Технология | Почему |
|---|---|---|---|---|
| Индексация базы знаний (источники 2, 5, 8, 11) | BATCH | ELT | Celery Beat | Документы сначала грузятся «как есть» в Data Lake, трансформация — потом: неизвестно, какая стратегия чанкинга или версия эмбеддинг-модели понадобится через полгода, а сырые копии избавляют от повторного похода к источнику. В Vector DB в итоге попадает только очищенный результат (после Dedup и Rerank), не сырьё из Data Lake напрямую. Delta-индексация — через Sync State (курсоры, checksum, источник 14): переиндексируются только изменённые документы, полный прогон по всей базе — редкое исключение, а не норма (снижает частоту нагрузки на GPU-инференс эмбеддингов; конкретный способ изоляции этой нагрузки от онлайн-инференса не решён — открытый вопрос, находка F7, раздел 25). Celery Beat — потому что сам конвейер линейный, без ветвлений (Ingest→Split→Dedup→Rerank→Embed→Load одной цепочкой), но требует task-уровневого retry и fan-out (если эмбеддинг упал на одном чанке из тысячи, повторить нужно только его) — это даёт именно task-очередь, а не голый планировщик. |
| Корпус для дообучения (источники 3, 6, 10) | BATCH | ETL | K8s CronJob + PII Filter | Обезличивание обязано отработать до того, как данные лягут в любое хранилище — иначе сырые ПДн (включая голос-биометрию) хотя бы кратковременно лежали бы на диске. Комплаенс важнее гибкости ELT. |
| Построение кэша профиля (источники 1, 7, 9) | BATCH | ETL | K8s CronJob | Кэш — готовый агрегат (долг + поверка + зона), а не сырая копия источников — хранить промежуточный сырой слой незачем. |
| События AI-виджета | STREAM, отложено до Этапа 3 | — (не ETL/ELT) | Redis Streams 〔предложение, отложено〕 | На Этапе 1 потребителя в реальном времени нет: квоты закрывает Quota Manager, диалоги пишутся напрямую в Session State Store (источник 6), аналитика идёт батчем в ClickHouse (источник 13) — всё уже существующими путями, без брокера. Redis Streams — задел на Этап 3 (proactive suggestions), не решение для Этапа 1. |
| Онлайн-инференс (источники 1, 4, 7, 9, 16) | ONLINE | — (не ETL/ELT) | GPU-инференс запроса, Redis, XML-RPC API Биллинга, REST API Диспетчерской | Синхронный lookup в рамках одного диалога, не пакетное перемещение данных — задержка ответа важнее throughput. |

**K8s CronJob vs Celery Beat — почему не унифицировано на одном инструменте.** Это не взаимозаменяемые
варианты одного и того же выбора, а инструменты для разной сложности задачи. Celery Beat — это ещё и
очередь задач: даёт per-task retry с backoff, fan-out на пул воркеров, цепочки шагов с изоляцией сбоя —
то, что нужно многошаговому конвейеру индексации. K8s CronJob — только расписание: запускает контейнер
целиком, без встроенной параллельности или retry на уровне подзадачи. Для одношаговых задач (выгрузка
БД обращений, материализация кэша профиля) это ровно достаточно и не создаёт новой зависимости от
кодовой базы ETL Worker, чья зона ответственности — база знаний, а не биллинговые/обращенческие данные.
Если бы стояла цель свести всё к одному инструменту, логичнее было бы расширить Celery Beat на всё (он
умеет и простые задачи), а не заменять его на CronJob там, где он не тянет многошаговый конвейер.

# 32. Консистентность данных и роль Feature Store

**Задача:** не допустить training-serving skew — расхождения между тем, что видит офлайн-оценка качества
при обучении, и тем, что видит Backend на инференсе.

**Решение:** материализованная таблица (кэш профиля, раздел 31) — единственный источник признаков; и
офлайн-оценка, и онлайн-Backend читают её одним и тем же кодом, а не двумя параллельными путями, которые
могли бы разойтись. Реализовано через семь правил:

1. Один код трансформации — офлайн-оценка и онлайн-чтение профиля берут данные из одной materialized view.
2. Версия модели эмбеддингов в payload вектора — запрос на инференсе эмбеддится той же моделью, что и индекс.
3. Point-in-time для Golden Set (набор эталонных вопросов с проверенными ответами) — Recall@3 (доля
   вопросов, для которых хотя бы один из трёх первых найденных фрагментов действительно релевантен)
   считается против состояния индекса на момент вопроса, не текущего.
4. TTL кэша профиля абонента — зафиксированный предел отставания от Биллинга.
5. Единая таксономия inquiry_type в Triage и в разметке Golden Set — прототип уже один раз ломался на
   этом рассинхроне (раздел 11), правило не даёт ему повториться.
6. Один PII-фильтр на путь обучения и путь инференса — не отдельная «облегчённая» версия для офлайн-корпуса.
7. Каталог источников (раздел 29) как Data Catalog — явные владельцы и происхождение каждого поля.

**Feature Store — что решено и почему.** Формальная платформа (Feast/Tecton) не строится — вместо неё
простой производный кэш (раздел 31). Причина: критерии применимости не выполняются — одна модельная
линия (RAG + один LLM-контур), один потребитель признаков (Backend), задержка закрывается обычным кэшем
без отдельной инфраструктуры. Роль против training-serving skew кэш выполняет и без платформы — правило 1
выше. Пересмотреть — если появится вторая независимая модель или команда, которой нужны те же признаки.

## 35.1. Что изменилось на диаграмме L3

Файл `dz6/C4_L3_LLM.html` — тот же контейнер LLM Gateway, что и в разделе 5.5 (draw.io-диаграмма,
встроенная в HTML через `data-mxgraph`). Изменения относительно исходной версии:

# 36. План тестирования RAG (`Приложения/План теста RAG.html`)

Отдельный документ, отвечающий на пункт ДЗ «как оценивается качество RAG (Faithfulness, Answer
Relevancy), каким инструментом (Ragas/DeepEval)».

## 36.1. Метрики

| Метрика | Что показывает | Тип | Стартовый порог |
|---|---|---|---|
| Faithfulness | Ответ подтверждён найденным контекстом, а не додуман моделью (галлюцинации) | reference-free | ≥ 0.85 |
| Answer Relevancy | Ответ отвечает на заданный вопрос, а не уходит от темы | reference-free | ≥ 0.80 |
| Context Precision | Доля релевантных чанков среди найденных top_k | reference-based | ≥ 0.70 |
| Context Recall | Не пропущен ли чанк, необходимый для полного ответа | reference-based | ≥ 0.80 |

Пороги помечены как стартовые: становятся обязательным критерием после первого полного прогона на Golden
Set, который даёт базовую линию (без них правило регрессии, раздел 36.3, было бы «деградация на 5% от
ничего» — нечисловое и неисполнимое замечание, устранено по итогам точечного разбора).

Приоритет при конфликте метрик: безопасность (ПДн, Guardrails) → Faithfulness → Context Recall → Answer
Relevancy → Context Precision.

## 36.2. Инструменты

- **Ragas** — офлайн-батч по Golden Set (ночной прогон, все четыре метрики) и сэмплирование
  продакшн-трафика (Faithfulness/Answer Relevancy без эталона, т.к. они reference-free).
- **DeepEval** — CI-гейт на каждый PR, pytest-нативный формат. Подвыборка (10–15 примеров) —
  **стратифицированная по типам обращений**, не случайная: при 10 типах таксономии случайная выборка
  могла бы не покрыть часть типов, и CI-гейт «молча» пропускал бы деградацию именно по ним.

## 36.3. Контуры оценки и регрессия

| Контур | Когда | Описание | Инструмент |
|---|---|---|---|
| Запуск тестов (PR) | Каждый PR, меняющий prompt/retrieval | Стратифицированная подвыборка, блокирует merge | DeepEval |
| Ночной батч | Ежедневно, K8s CronJob | Весь Golden Set, все 4 метрики, тренд в ClickHouse | Ragas |
| Продакшн-сэмплирование | Непрерывно | N% трафика, низкий score → очередь Annotator | Ragas |
| Регрессионный контроль | Каждый ночной прогон | Деградация любой ключевой метрики >5% к базовой линии — блокирующая регрессия | Ragas + DeepEval |

## 36.4. Судья (LLM-judge)

> **[ПОПРАВКА v4.5 — конкретные модели, ADR-007]** Ниже три сценария сформулированы как правило
> «судья из другого пула». При сборке ADR-007 выяснилось, что **правило невыполнимо в лоб**: во всём
> проекте названы только два управляемых провайдера на территории РФ, GigaChat Pro и YandexGPT, и оба
> отданы генерации (второй — резервом по подтверждению ADR-002, п. 1). Судья-YandexGPT совпал бы
> с отвечающей моделью в момент failover, причём гарантированно.
>
> **Зафиксировано в ADR-007:** прототип — судья Qwen2.5-7B-Instruct, та же локальная модель, что уже
> используется для smoke-тестов (новой сущности не вводится); MVP — судья **YandexGPT** против
> отвечающего GigaChat Pro. **Пока failover генерации на YandexGPT активен, оценка не выполняется:**
> ночной прогон пропускается, факт пропуска пишется в ClickHouse рядом с `quality_report`. Failover —
> временное деградированное состояние, и потерять один ночной прогон дешевле, чем получить завышенную
> оценку, неотличимую от честной. Третьего провайдера назначать не стали — его в проекте нет, а
> выдумать означало бы повторить ошибку раздела 26.4.

Три варианта, привязанные к триггерам ADR-002 (раздел 26), с устранением логического противоречия,
найденного точечным замечанием:

1. **SaaS отвечает абоненту** (Этап 1, дефолт) → судья из другого пула провайдеров (не тот же GigaChat
   Pro, что отвечает).
2. **Self-hosted отвечает, переход по триггеру объёма токенов или latency** → судья может быть управляемый
   API — внешний запрет на управляемые API тут не действует.
3. **Self-hosted отвечает, переход именно по триггеру запрета ИБ на внешние управляемые API** → судья
   тоже локальный (второй self-hosted-инстанс другой модели, например Llama 3.1 при основной Qwen2.5) —
   использовать внешний API как судью в этом случае противоречило бы самому триггеру перехода.

Дополнительные требования: версия судьи фиксируется (иначе оценки не сравнить между прогонами); сама
модель-судья периодически сверяется с ручной разметкой Annotator, чтобы деградация судьи не маскировалась
под стабильное качество продукта.

> **[РЕАЛИЗОВАНО v4.51 — код-шаг 10]** `app/quality/judge.py` (`AnswerJudge`). Судья читает

## 36.5. Эталонный набор (Golden Set)

Объём — 50–100 вопросов (реальные обращения абонентов + синтетические edge-кейсы), покрытие всех типов
таксономии (раздел 9) плюс пограничные случаи (пустая база знаний, низкая уверенность, неоднозначный тип,
вопрос вне тематики). Требования консистентности: тот же PII-фильтр, что и у продового трафика; та же
версия эмбеддингов, что в индексе Vector DB; версионирование набора (сравнение версий системы — только на
одинаковой версии набора). Пополняется ролью Annotator, в том числе диалогами с низким score из
продакшн-сэмплирования.

## 36.6. Тесты безопасности

Четыре сценария, напрямую проверяющие компоненты раздела 35: попытка prompt injection (Guardrails
блокирует, системный промпт не раскрывается); попытка получить чужие ПДн через ответ (sync-проверка
Guardrails обрывает поток); запрос с реальными ПДн в тексте вопроса (PII Sanitizer скрывает их до
LLM Provider, в логе только `pii_report`); провокация токсичного ответа (Guardrails возвращает safe
fallback).

Token Usage (расход в минуту) + отдельный виджет «Токены за месяц» (накопление за 30 дней против

— рост ≥200% за 5 мин или абсолютно ≥30% за 5 мин, было «резкий рост» без числа) · RAG Quality (тренд
Faithfulness/Answer Relevancy из ночного батча) · Fallback Rate (доля ответов в запасном пути без LLM).

## 39.1. Sizing self-hosted GPU (Qwen2.5-32B / Qwen2.5-72B)

Источники: презентации курса «Sizing» и «Оптимизация LLM» (папка `dz7`) + живой опрос калькулятора
`apxml.com/tools/vram-calculator` в браузере — характеристики GPU ниже взяты оттуда, не по памяти.

> **[ПОПРАВКА v4.5]** Допущение λ = 5 RPS оказалось консервативнее реальности примерно в 20 раз.
> Отчёт по мощностям (`Capacity_Report.html`, раздел 42) вывел нагрузку из числа абонентов:
> при 100 000 абонентов λ = 0,25 RPS, L = 0,75. Значение λ = 5 RPS соответствует примерно
> 2 млн абонентов — в 20 раз больше всей абонентской базы. Расчёт VRAM ниже остаётся верным
> для своей нагрузки, но **выбор GPU под тираж нужно пересчитать** под реальную конкурентность,
> где решающим становится время генерации при batch = 1, а не пропускная способность.

**Допущение по нагрузке** (реальная нагрузка проекта не определена, раздел 28.1) — λ = 5 RPS (пиковая),
W = 3 с (DoD раздела 18, полный ответ), отсюда по закону Литтла L = λ×W = 15 конкурентных запросов.
Контекст на запрос — 4096 токенов (system + top_k=3 чанка ×~800 ток. + история + запас на ответ).

VRAM = N_параметров × M_байт_на_параметр (FP16 = 2, INT4 = 0.5) + KV-cache (на L=15, с учётом GQA у
Qwen2.5: 8 KV-heads, head_dim 128) + 10% overhead:

| Модель | Квантование | Итого VRAM |
|---|---|---:|
| Qwen2.5-32B (32.5 млрд, по публичному config) | FP16 | ≈ 88 ГБ |
| Qwen2.5-32B | INT4 | ≈ 34 ГБ |
| Qwen2.5-72B (72.7 млрд) | FP16 | ≈ 181 ГБ |
| Qwen2.5-72B | INT4 | ≈ 61 ГБ |

Характеристики GPU (из apxml.com): A100 80GB — 2039 GB/s / 312 TFLOPS; A100 40GB — 1555 GB/s / 312
TFLOPS; L4 24GB — 300 GB/s / 121 TFLOPS; T4 16GB — 320 GB/s / 65 TFLOPS.

**Рекомендация: Qwen2.5-32B в INT4 на 1× A100 80GB.** Обоснование — инференс memory bound (лекция
«Оптимизация LLM»): скорость генерации ≈ bandwidth / размер_весов. На A100 это ≈125 ток/с (укладывается в
DoD), на T4/L4 — ≈19–20 ток/с (типовой ответ ~150 токенов займёт ~7.5 с, **нарушает** DoD `<3 сек`), из-за
чего T4 и L4 отклонены не по объёму VRAM (они технически вмещают модель на нескольких картах), а по
пропускной способности памяти. Qwen2.5-72B INT4 тоже проходит по VRAM (1–2× A100 80GB), но decode-скорость
(~56 ток/с) вплотную к границе DoD при batch=1 — раздел 28.2 прямо требует эмпирической проверки на
целевой GPU, а не расчёта «по аналогии».

# 40. Deployment View и закрытие находки F7 (v4.5)

## 40.1. Решение по F7 — окно обслуживания

Находка F7 (раздел 25.2) — конкуренция за GPU между офлайн-ETL и онлайн-ретривалом — была
**единственным открытым P0 проекта** начиная с версии 4.0. Решение принято при построении деплой-схемы.

**Выбран вариант «окно обслуживания»** — один GPU-пул, разведение по времени:

- Полный реиндекс базы знаний выполняется **только в окне 02:00–05:00** (`CronJob: etl-index`,
  расписание `0 2 * * *`), когда онлайн-трафик абонентов минимален.
- Жёсткая граница окна — `activeDeadlineSeconds = 10800`; `concurrencyPolicy: Forbid`.
- Если окно не закрылось, job прерывается принудительно. Курсоры и контрольные суммы сохранены в
  Sync State (источник 14) — работа продолжается в следующем окне. Индекс при этом не повреждается:
  переключение alias blue-green происходит только после полного успеха.
- Delta-индексация новых документов идёт днём, но малыми порциями с ограничением параллелизма батчей.
- Контроль — виджет Saturation дашборда (раздел 37), который группирует утилизацию GPU по
  `workload = etl-worker | llm-inference`: конкуренция видна на одном графике.

**Цена решения, принятая осознанно:** днём полный реиндекс невозможен, свежие документы попадают в
индекс с задержкой до следующего окна. **Условие пересмотра:** если delta-объём перестанет укладываться
в окно — переходить на два раздельных пула узлов (`gpu-online` / `gpu-batch`), что удваивает
GPU-строку CAPEX.

**Рассмотренные и отклонённые альтернативы:** два пула узлов (полная изоляция, но минимум 2 GPU —
для MVP не оправдано, пока нагрузка не измерена); приоритеты в одном пуле через PriorityClass с
preemption (вытесненный ETL теряет прогресс батча, а в момент вытеснения p99 всё равно проседает).

> **[ВАЖНО ДЛЯ СЛЕДУЮЩЕЙ LLM]** Детали вида `PriorityClass batch-gpu-low` / `nodeAffinity` ранее
> приходили в проект через **сфабрикованную ссылку на несуществующий ADR-003** (раздел 34.1) и были
> намеренно не использованы. Решение выше принято заново, как инженерный выбор из трёх вариантов, и
> не является восстановлением того текста. Механизм выбран другой — временнóе разведение, а не
> приоритеты планировщика.

## 41.2. РЕШЕНИЕ: Draft Validator — это не Guardrails

## 41.6. `C4_L3_LLM.html` не открывался в draw.io — две причины

Файл не распознавался как диаграмма. Причин оказалось две, вторая нашлась только после устранения
первой:

1. **UTF-8 BOM** (`EF BB BF`) в первых трёх байтах — единственный такой файл в проекте. draw.io ищет
   `<mxfile` / `<!--[if IE]>` с первого байта, BOM его сдвигал.
2. **Текстовое описание компонентов внутри того же файла.** Файл был на 100 строк против 12 у всех
   остальных: под диаграммой шли `<link>` и `<style>` с таблицей компонентов. draw.io парсит `.html`
   строгим XML-парсером, а `<link>` не закрыт и содержит сырые `&` в href — ошибка
   `Opening and ending tag mismatch: link line 12 and body`.

**Решение — разделение файла, а не починка тега.** Сделать `<link>` XML-валидным было бы лечением
симптома: **draw.io при сохранении перезаписывает файл своей обёрткой**, и описание компонентов
исчезло бы молча при первом же редактировании диаграммы.

- `C3/C4_L3_LLM.html` — только диаграмма, 12 строк, как остальные семь;
- `C3/C4_L3_LLM_Components.html` — таблица компонентов (PII Sanitizer, Guardrails, Quota Manager,
  LiteLLM Core; Billing Callback свёрнут в v4.50 — см. раздел 35.1).

**Правило на будущее:** файл диаграммы держать чистой обёрткой draw.io; пояснительный текст — только
отдельным файлом. Проверять первые три байта на BOM.

## 42.2. Вывод 1 — триггер №2 ADR-002 измеряет не ту величину (ADR исправлен)

Один абонент даёт около 6 300 токенов в месяц. Порог 50 млн достигается примерно при **7 900
абонентах** — то есть **уже на MVP одного города** (63 млн), не дожидаясь тиража.

При этом λ в тот же момент — 0,025 RPS. Триггер задумывался как экономический сигнал «SaaS стал дороже
собственного железа», но стоимость владения self-hosted-контуром определяется **пиковой
конкурентностью**, а не суммарным объёмом токенов: при такой λ выделенная GPU простаивала бы более
99% времени. Объём токенов велик не от нагрузки, а от длины RAG-контекста (~3 500 токенов на запрос
при трёх чанках по ~800) — это свойство архитектуры поиска, а не признак роста спроса.

**Внесено в ADR-002** (раздел «Поправка v4.5» файла `ADR/ADR-002-llm-hosting-strategy.md`):
порог 50 млн сохраняется как **сигнал к пересчёту стоимости владения**, но перестаёт быть основанием
для миграции сам по себе. Перевод выполняется только если «амортизация CAPEX self-hosted + его OPEX»
оказалась меньше OPEX управляемого API при измеренной конкурентности. В раздел «Подтверждение» ADR-002
добавлены пункты 5 и 6.

**Новое число вместо 50 млн намеренно не подставлено:** у проекта нет ни одной цены, корректный
экономический порог сейчас невычислим, а подстановка «по ощущению» повторила бы ошибку `adr_1.md` /
`adr_2.md`. Порог пересчитывается вместе со сметой (P0 №1).

Это ровно то действие, которое раздел 28.4 предписывал заранее: «при расхождении обновить сам триггер
в ADR-002, а не игнорировать расхождение».

## 42.3. Вывод 2 — sizing раздела 39.1 переразмерен примерно в 20 раз

Раздел 39.1 считал GPU-конфигурацию под ПРЕДПОЛОЖЕНИЕ λ = 5 RPS, L = 15 и получил Qwen2.5-32B в INT4
на 1× A100 80GB. Фактически при 100 000 абонентов (базовый сценарий) λ = 0,25 RPS, L = 0,75.

Значение λ = 5 RPS соответствует примерно **2 млн абонентов** — в 20 раз больше всей абонентской базы;
даже λ = 1 RPS требует около 400 000 абонентов. Само допущение было честно помечено в разделе 39.1 как
неподтверждённое — теперь известно, насколько оно консервативно.

Расчёт VRAM при этом не отменяется: он верен для той нагрузки, под которую делался. Но **выбор GPU под
тираж нужно пересчитать** под реальную конкурентность, где решающим становится время генерации при
batch = 1, а не пропускная способность. Поправка внесена в раздел 39.1 и в ADR-002.

## 42.4. Вывод 3 — размер GPU определяет ETL-реиндекс, а не трафик абонентов

Онлайн-контур тратит на запрос один эмбеддинг запроса и один реранжинг `top_k = 20`. При λ = 0,25 RPS
(тираж, базовый) это даёт загрузку карты порядка **1%**, на MVP — около 0,1%. Одна GPU покрывает
онлайн-контур с запасом в два порядка на всём диапазоне до тиража включительно.

Реальный потребитель GPU — пакетная переиндексация базы знаний. То есть **решение ADR-005 (окно
обслуживания 02:00–05:00) определяет размер GPU-пула, а нагрузка абонентов на него практически не
влияет**. Это усиливает ADR-005: условие пересмотра там сформулировано через длительность ночного job,
а не через рост трафика — и, как теперь видно, это единственно верная привязка.

## 42.5. Хранилища и поведение при кратном росте

| Компонент | MVP (10 тыс.) | Тираж (100 тыс.) | Поведение при ×10 |
|---|---|---|---|
| Qdrant — векторы | ≈ 195 МБ | ≈ 195 МБ | **Не меняется** — зависит только от базы знаний (20 000 чанков × 1024-d float32 × 2,5), не от числа абонентов |
| Loki — логи | ≈ 0,2 ГБ / 30 дней | ≈ 1,7 ГБ / 30 дней | Линейный рост; критична политика ротации, а не объём |
| ClickHouse — телеметрия | ≈ 0,1 ГБ/год | ≈ 1,0 ГБ/год | Линейный рост, объёмы малы |
| Postgres | единицы ГБ | десятки ГБ | Растёт с логом диалогов; **срок хранения не задан** — открытый пункт |
| Embedding / Reranker GPU | загрузка ~0,1% | загрузка ~1% | **Не меняется** — размер диктует ETL (ADR-005) |
| Backend, LLM Gateway | L = 0,08 | L = 0,75 | **Реплики не растут** — нужны для отказоустойчивости, не для пропускной способности |
| Расход токенов | 63 млн/мес | 630 млн/мес | **Единственное, что растёт болезненно** |

**Главный вывод про тираж:** при переходе 10 000 → 100 000 абонентов инфраструктура практически не

обращений к модели, а не стоимость железа. Именно поэтому исправление триггера (раздел 42.2) важнее
для бюджета, чем выбор конфигурации GPU.

Конкурентность L нигде не превышает 3,2 даже в самом тяжёлом сценарии тиража — асинхронная модель
обработки (раздел 28.1) закрывает задачу с большим запасом.

## 43.3. Новая страница 3 — потоки записи Этапа 2

Три горизонтальные дорожки, разделяющие путь данных наружу:

1. **Порождение и подтверждение — данные ещё внутри периметра.** Абонент → Agent Orchestrator
   (слоты, черновик) → Draft Validator (полнота обязательных слотов) → HITL Gate. Отдельная ветка:
   Document Generator → S3/MinIO → ссылка абоненту как вложение в диалоге.
2. **Запись во внешние системы — только через их API.** Billing Adapter → XML-RPC API Биллинга
   (Write + Idempotency-Key); Сервис работы с обращениями → API микросервиса обращений; аварийные
   заявки (`inquiry_type = emergency`) → REST API Диспетчерской системы.
3. **След внутри — аудит и телеметрия остаются у нас.** Audit Writer → Session State Store →
   ClickHouse. Отказ абонента пишется в аудит тоже, с пометкой, что write не выполнялся.

**HITL Gate выделен как единственный переход между дорожками 1 и 2** — ни одна стрелка записи
не может стартовать в обход него (правило 4.7). Три ноты на схеме: правило 4.7, ADR-003, stage-gating
(схема проектная, на MVP эти контейнеры не разворачиваются).

## 44.1. План тестирования всего проекта (`Test_Plan.html`)

Строка матрицы «План тестирования (весь проект)» имела статус «частично»: существовал только план
качества RAG (`Приложения/План теста RAG.html`), закрывающий метрики ответа и ничего больше.

Шестнадцать разделов, девять уровней проверки:

| Уровень | Доказывает | Гейт |
|---|---|---|
| L1 модульные | Ни один из девяти дефектов раздела 11 не вернулся | PR |
| L2 контрактные | API отвечает ровно по разделу 7: коды, схемы, заголовки, SSE, RFC 7807 | PR |
| L3 интеграционные | Фильтры реально применяются, поток не собирается целиком, состояние переживает рестарт | PR / ночь |
| L4 e2e | 14 сценариев по `C4_Sequence_Diagrams.drawio` — 8 для Этапа 1, 6 для Этапа 2 | ночь |
| S security | 8 тестов по STRIDE раздела 24.5 + требования 152-ФЗ | PR / ночь |
| P нагрузочные | 5 профилей, выведенных из `Capacity_Report.html` | пред-релиз |
| D данные и ETL | Delta-индексация, blue-green, tombstones, версия эмбеддингов | ночь |
| O наблюдаемость | Метрики дашборда реально эмитятся, 9 алертов срабатывают | PR |
| Q качество RAG | Ссылкой на `Приложения/План теста RAG.html` — **не дублируется** | PR / ночь |

**Решения, принятые в документе:**

- **Инструмент нагрузки — Locust, не k6.** Ключевая метрика DoD — TTFT, время до *первого* токена.
  Обычный HTTP-нагрузчик измерит полное время ответа и покажет «всё в порядке» при нарушенном TTFT.
  Нужен клиент, читающий SSE и засекающий первое событие; Locust на Python совпадает со стеком проекта.
- **Сегмент провайдера измеряется отдельно от нашего.** На MVP генерирует внешний API, его латентность мы
  не контролируем: если мерить только сквозной TTFT, ухудшение у провайдера будет выглядеть как регрессия
  нашего кода. Гейт ставится на «Backend + Gateway без провайдера», сегмент провайдера — наблюдаем.
- **Нагрузка не гоняется по платному API** — массовые прогоны на локальной модели (код-шаг 0.5), против
  реального провайдера только короткий калибровочный прогон. Иначе нагрузочное тестирование стало бы
  отдельной статьёй расхода токенов — при том, что расход токенов и так единственная болезненно растущая
  статья (раздел 42.5).
- **Архитектурный тест как способ защитить правило ADR-003.** «Только через API владельца» нельзя
  проверить функциональным тестом — дубль ответит одинаково и на корректный вызов, и на нарушение.
  Вводится статический тест по импортам: ни один модуль вне адаптеров не тянет драйвер чужой БД.
- **«PII filtering 100%» переформулировано в проверяемое:** ноль пропусков на фиксированном корпусе
  ≥ 200 запросов (шесть типов сущностей × минимум три формата написания каждый) плюс прод-инвариант
  `guardrails_blocked_total{reason="pii_leak"} == 0`. Абсолютное «100%» недоказуемо в общем виде.

**Что план закрыл.** Риски Spoofing и IDOR — единственные две угрозы STRIDE со статусом «не описано» в
разделе 24.5 — получили проверяемые тесты S1–S2. Расхождение Р3 (сценарии ошибок нигде не описаны)
закрыто частично: сценарии E5–E7 задают ожидаемое поведение при 429, 502, 504 и блокировке Guardrails.
Тест раздела 8.2 плана даёт ADR-005 ровно те два измерения, которых ему не хватает для Accepted —
длительность полного реиндекса и дневной delta-объём.

**Отличия структуры кода от раздела 12.3 — и почему.** Добавлен `etl/` (ETL Worker — отдельный контейнер
на L2, его код не может жить в `vector/`); добавлен `metrics/` (конвенция имён — контракт дашборда);
добавлен `agents/draft_validator.py` (по решению раздела 41.2 это не Guardrails); `quota.py` вынесен из
`llm_gateway.py` (порядок quota-first проще тестировать отдельным модулем); `application_router.py`
переименован в `inquiry_service.py` вслед за переименованием контейнера в разделе 5.4.

**Практические решения, которых в проекте не было:**

- **Корневые сертификаты НУЦ Минцифры** внесены в список доступов отдельной строкой: без них обращение к
  GigaChat падает на проверке TLS, и это выглядит как сетевая ошибка, а не как отсутствие сертификата.
  Отключать проверку сертификата вместо установки — недопустимо.
- **Источник 10 не генерируется даже синтетически.** Голос — биометрия по ст. 11 152-ФЗ, согласия нет.
  Синтетический файл создал бы в коде готовый путь обработки, который потом легко наполнить реальными
  данными без повторной проверки основания.
- **Локальный рантайм — Ollama:** даёт HTTP-API, который LiteLLM подключает как обычного провайдера,
  поэтому обёртка код-шага 0.5 получается тонкой, а переключение SaaS ↔ локальная модель остаётся
  правкой конфигурации (это и есть проверка центрального тезиса ADR-002).
- **Клиент XML-RPC берётся из стандартной библиотеки** — внешняя зависимость для Биллинга не нужна.
- **Версии пакетов намеренно не проставлены числами** — фиксируются в `uv.lock` при первой установке.
  Проставить их сейчас «по памяти» означало бы записать в проектный документ непроверенные числа
  (правило разделов 26.4 и 28.4).
- **LangGraph на шаге 2 не берётся:** ADR на миграцию не написан (раздел 26.5, п. 2), взять его сейчас
  значило бы принять архитектурное решение кодом в обход правила «сначала решение, потом код».

**Оценка:** 26–47 ч, критический путь `0 → 1 → 3 → 4 → 6 → 7 → 8 → 8.5 → 11`, при 4–6 ч в день — 7–10
рабочих дней. Шаги 2/3, 4/5 и 9/10 параллелятся. Риск сроков сосредоточен в шаге 0 (см. 44.3).

### Добавлено: шаг 8.5 — демо-стенд вместо личного кабинета

**Это был пробел, а не изменение объёма.** Диаграмма `C3/C4_L3_Widget.html` существует, карта покрытия
плана тестирования включает виджет, но ни один шаг плана разработки его не создавал; раздел 12.3
контекста фронтенд тоже не описывает. Доступа к реальному личному кабинету на прототипе не будет —
показывать систему было бы нечем.

Решение: одна страница, отдаваемая статикой самим сервисом (`web/index.html`, `app.js`, `style.css`),
имитирующая кабинет — переключатель абонента, его карточка из синтетического Биллинга, под ними виджет
диалога. Компоненты берутся с диаграммы виджета: лента сообщений, потребитель SSE, диалог подтверждения,
панель документа, кнопки предлагаемых действий, блок источников. Плюс служебная панель — сырые события
потока, `pii_report`, `trace_id`, счётчик токенов, — делающая наблюдаемым весь демонстрационный сценарий.

> **[ОТКЛОНЕНИЕ ПРОТОТИПА ОТ ЦЕЛЕВОЙ ТЕХНОЛОГИИ — зафиксировано осознанно]** На L2 виджет заявлен как
> React / TypeScript, встраиваемый в существующий кабинет, и это решение **не меняется**. На прототипе
> берётся простая страница без сборочного конвейера: React здесь не проверил бы ничего архитектурного,
> зато потребовал бы установки Node и второго процесса на демонстрации. Правило 4.1 не нарушено — новых
> контейнеров на L2 не вводится, меняется только реализация стенда.

**Зачем переключатель абонента.** Не оформление: это единственный способ показать привязку
`subscriber_id` к сессии и воспроизвести вручную сценарии S1 и S2 плана тестирования — войти одним
абонентом и попробовать подтвердить черновик другого. Без него две угрозы STRIDE, закрытые тестами,
нечем продемонстрировать на защите.

> **[ОБНОВЛЕНО v4.45 — раздел 78 журнала.]** Переключатель на двух зашитых абонентах заменён
> справочником с поиском по всем 200 из примера Биллинга (`scripts/build_subscriber_directory.py` →
> `web/subscribers.json`, читается стендом как статический файл). Довод тот же — сценарии S1/S2 и
> разные состояния абонента, — но двух карточек для них мало. Признак планового отключения в
> справочнике **вычисляется** поиском по графику (`app/outages`), а не вписан: прежний комментарий про
> «контрастную пару» устарел молча, когда демо-график пересобрали (раздел 77.1).

Оценка шага — 3–5 ч; параллелится с шагом 9. Итог по фазе 6 вырос с 23–42 до **26–47 ч**, критический
путь стал `0 → 1 → 3 → 4 → 6 → 7 → 8 → 8.5 → 11`.

## 75.1. Шесть путей ответа, и только один идёт к модели

Тема запроса решает, звать ли модель вообще. Определяется правилами до вызова:
узнавать её моделью значило бы платить за вызов на каждом запросе, включая те,
где она не нужна.

> **[ДОБАВЛЕНО v4.54, ПЕРЕПИСАНО v4.55]** Правила не всегда находят тему — маркеры узкие и
> составные намеренно (раздел 75, `TOPIC_MARKERS`/`TEMPLATE_PATTERNS`), и реальная формулировка
> абонента иногда мимо: «По моему адресу до скольки отключение?» без слова «вода» мимо `outage»,
> «нужно оформить новое подключение…» без слова «бланк» мимо `template` (живые находки, журнал
> разделы 90, 92). Модель на маршрутизацию **не** ставится первым гейтом — тот же довод, что выше, —
> но подключена **запасным** классификатором (`app/agents/topic_fallback.py`,
> `TopicFallbackClassifier`, `Triage.classify_async`): зовётся только когда правила не нашли тему.
>
> **v4.55: не генеративная модель, а k-NN по эмбеддингам.** Первая редакция (v4.54) звала
> локальную модель через Ollama — замер (журнал 91.1) показал разброс 0,4–11+ с: Ollama выгружает
> веса по простою, это нестабильность самого класса «вызов модели». Классификация — не генерация:
> заменена на косинусную близость к полусотне размеченных примеров (`EXAMPLES`) той же моделью
> эмбеддингов, что уже поднята и тёплая для поиска (`KnowledgeBase.embedder`, вторая копия весов
> не грузится) — **~22 мс** на вызов (ADR-014) вместо секунд, внешнего провайдера нет как класса.
> Порог 0.90 и разрыв 0.05 до второй темы — проверены на реальных случаях (журнал разделы 92, 93), не
> подобраны: 0.80 не прошёл проверку («спасибо за помощь» → 0.87 до `template`) той же природы,
> что заставила ADR-014 поднять `score_threshold` поиска. По корректности регрессии нет —
> классификатор либо находит тему, либо отдаёт `None`, и путь остаётся прежним. Раздел 93: разрыв
> 0.03 пропустил ложную классификацию («подключить» и «включат» — общий корень) — закрыто разрывом
> 0.05 и перефразировкой коллизионного примера, не только числом.
>
> **[ДОБАВЛЕНО v4.56]** Тем же приёмом закрыт и `InquiryType` (регистрационная ось,
> `app/agents/inquiry_type_fallback.py`, журнал раздел 96) — но только **семь типов из
> шестнадцати**, тех, что входят в `REGISTRABLE` (раздел 75.8). Остальные девять на прототипе не
> запускают действие, а разбор `fixtures/inquiries_voronezh.csv` показал, что их реальные тексты —
> споры, а не заявки: строить на них примеры значило бы учить модель путать одно с другим. Порог
> 0.85 / разрыв 0.03 замерены `scripts/measure_inquiry_type_fallback.py` на 63 настоящих текстах —
> ноль ложных срабатываний, охват 11% (большинство текстов — операторские пометки, не форма
> вопроса чата). `TriageResult` получил отдельное поле `type_matched_by` — тема и тип определяются
> независимо. Пункт 85 TODO.

| Тема | Путь | Почему без модели |
|---|---|---|
| `outage` | Точный поиск по графику плановых отключений по адресу абонента | График протухает за дни; адрес не несёт смысла для векторного поиска (ADR-013). Адрес берётся из Биллинга по ЛС (`Orchestrator._with_address`, v4.53), а не из запроса — присланный клиентом чужой адрес игнорируется (раздел 86 журнала) |
| `water_quality` | Утверждённая формулировка из реестра дословно | Текст обязан не меняться, а провайдер меняет версию модели без нас (ADR-012) |
| `tariff` | Точный поиск по таблице тарифов по дате | Соседние периоды различаются датами и парой цифр; неверный тариф — неверная сумма в ответе про деньги |
| `account` | Точное чтение Биллинга по лицевому счёту: задолженность, начисления за период, срок поверки, показания | Факт о счёте абонент проверит по квитанции; **только нейтральный запрос — спор «почему столько» уходит в базу знаний** (раздел 79.1) |
| `template` | Образец заявления из реестра (семь бланков по ПП РФ № 644, 776), заполненный из Биллинга по ЛС; недостающее ассистент **спрашивает по одному** (раздел 81); готовый бланк отдаётся ещё и ссылкой на лист для печати (v4.53, раздел 41.4) | Текст формы обязан не меняться и опираться на норматив; вопросы к абоненту фиксированные, модель не нужна; отличается от регистрации — ассистент только выдаёт бланк, никуда не пишет |
| `general` | Поиск по базе знаний, затем генерация | Исход по умолчанию |

Общее у первых пяти: **нужен поиск по ключу, а не по смыслу.** Это одно правило
в пяти применениях: база знаний отвечает на то, что объясняется; то, что
проверяется по факту, отвечается точным поиском.

Все пять подключены одним швом — протоколом `DirectResponder`: Backend знает
только, что у него есть цепочка прямых ответчиков, и ничего про воду, адреса,
тарифы, лицевые счета и бланки. Предметная логика живёт в самих ответчиках; на
диаграмме `C3/C4_L3_Backend.html` это **один узел** Response Router, а не пять
боксов (раздел 80.2).

Кроме шести путей ответа есть **путь записи**: обращение подаётся из диалога,
растянуто на несколько реплик и держит состояние. Раздел 75.8.

**[ДОПОЛНЕНО v4.45.]** В таблицу внесён `app/billing/source.py` — он читает
пример Биллинга (ФИО и лицевой счёт для слотов регистрации, счётчики и
начисления для ответов) и до сих пор в составе кода не значился. Метод
`accounts()` того же модуля отдаёт перечень всех счетов для справочника абонентов
стенда (раздел 78 журнала); в протокол `BillingSource` он не входит — настоящий
API Биллинга такого списка не отдаст.

**[ДОПОЛНЕНО v4.46, v4.48.]** Два новых прямых ответчика (раздел 79).
`app/billing/answer.py` отвечает по фактам лицевого счёта — задолженность,
начисления за период, срок поверки, показания; спор «почему столько» отсекается
и уходит в базу знаний. `app/documents/` держит семь образцов заявлений
(подключение, поверка, опломбировка, установка, снятие пломбы, справка,
обследование) со структурой по ПП РФ № 644 и 776: заполняет их из Биллинга по
лицевому счёту (ФИО, счёт, адрес, а для счётчика — назначение, номер, показание,
срок поверки, когда прибор один), недостающие поля спрашивает по одному
(раздел 81). Обе темы — `Topic.ACCOUNT` и `Topic.TEMPLATE` — пятое и шестое
значения оси.

**[ДОПОЛНЕНО v4.50.]** `app/gateway/usage.py` — `UsageStore` пишет по строке на
вызов шлюза в таблицу `usage_events`: `trace_id`, `subscriber_id`, `session_id`,
канал, модель, провайдер, токены, latency, исход (`ok` / `blocked` / `error`),
причина обрыва, факт срабатывания PII. ПДн не пишутся. Запись — best-effort
(исключения гасятся, поток абонента не рушится) и после сборки ответа. На
прототипе хранилище — Postgres (БД `telemetry`), на MVP — ClickHouse. Это
свёрнутый box «Billing Callback» с диаграммы `C4_L3_LLM` (журнал раздел 83).

**[ДОПОЛНЕНО v4.51 — код-шаг 10.]** `app/quality/judge.py` — судья качества
ответа (`AnswerJudge`, ADR-007 роль 4a): отдельная от отвечающей модель
оценивает готовый ответ по контексту двумя reference-free метриками раздела
36.1 (faithfulness, answer_relevancy). Вызов через тот же `litellm.Router`,
псевдоним `judge_provider` (прототип `local-test`, MVP `yandexgpt`). При
совпадении судьи с отвечающей моделью — `JudgeConflict`, прогон пропускается
(failover генерации, ADR-007). `app/quality/store.py` (`QualityStore`) пишет
итог прогона в таблицу `quality_reports` БД `telemetry`. Ночной прогон —
`scripts/run_quality_eval.py` по подмножеству `real` эталонного набора.
Судья вне пути абонента; на асинхронном выходе шлюза остаётся дешёвая
`check_groundedness` (`provisional`). Журнал раздел 84.

## 75.3. Поиск: что и как индексируется

Корпус — FAQ воронежского филиала, двадцать пар вопрос-ответ с публичного сайта.

**Единица поиска не совпадает с единицей контекста.** Индексируются порознь
вопрос и части ответа (предел части — 300 знаков, подобран перебором); в промпт
уходит пара целиком. Склейка «вопрос + ответ» одним вектором топила короткий
вопрос в длинном ответе: у `faq-11` вопрос 24 знака против 611.

Хранилище — в памяти, модель `multilingual-e5-small`, переранжирования нет
(ADR-014). Порог 0,872 выбран решением владельца по замеру.

**Ограничение названо прямо:** на эталонном наборе больше половины настоящих
вопросов получают отказ там, где ответ в корпусе есть. Двадцать пар — маленький
корпус, и потолок теперь в нём, а не в числах. Порог при этом есть свойство пары
«модель + индексация», а не константа проекта: меняется одно из двух — число
подлежит пересчёту.

## 75.8. Путь записи: обращение подаётся из диалога

Кроме шести путей ответа (раздел 75.1) есть путь **записи**. Он устроен иначе:
растянут на несколько реплик и держит состояние.

```text
1. «Хочу заказать поверку»  → ответ по базе знаний + черновик + две кнопки
2. «Подтверждаю»            → запись, номер обращения
   «Отменить»               → возврат к правке, отказ в аудит
```

**Подтверждение приходит обычной репликой** в `POST /v1/generate`, а не своим
адресом: правило 4.4 разрешает ровно два адреса, и диаграмма последовательностей
Этапа 2 описывает именно такой ход.

**Намерение — признак `intent`, а не текст реплики.** Слова «да», «хорошо»,
«ага» абонент говорит и в ответ на другое; прочитать их как подтверждение
значило бы выполнить запись, которой он не просил. Правило 4.7 требует **явного**
подтверждения, а вывод из свободного текста явным не бывает. Признак ставит
виджет по нажатию кнопки — там намерение однозначно по построению.

### Где что стоит

| Слой | Что делает |
|---|---|
| `app/backend/sessions.py` | Состояние между репликами: автомат, слоты, черновик, аудит |
| `app/backend/registration.py` | Предложить, принять решение абонента, выполнить |
| `app/adapters/inquiry_service.py` | Три гейта: подтверждение, привязка к сессии, идемпотентность |
| `app/inquiries/store.py` | Запись в таблицу вместо микросервиса владельца |

Шов проходит по адаптеру: он зовёт у клиента `create_inquiry(payload, key)`, и на
MVP клиентом станет обёртка над REST владельца. Гейты, автомат и всё, что выше,
не изменятся — то же построение, что у приёма графика отключений и чтения
Биллинга.

### Три решения, принятые здесь

**Слоты берутся из профиля, а не из формы.** Обязательных полей три — ФИО,
лицевой счёт, основание, — и все три известны: первые два в профиле Биллинга,
третье — сам вопрос абонента. Спрашивать у человека то, что система про него
знает, — худший вид формы.

**Перечень типов для регистрации закрытый и короткий:** поверка, опломбировка,
установка и снятие прибора учёта, справка, обследование, приём документов. Аварии
исключены — у них другой путь (ADR-009); вопросы «почему столько» исключены — на
них отвечает база знаний; `other` исключён — регистрировать нераспознанное значит
регистрировать неизвестно что.

**Идемпотентность живёт в базе.** `WriteAdapter` держит виденные ключи в памяти
процесса и честно оговаривает, что перезапуск их теряет; `UNIQUE` в таблице не
теряет. Повтор возвращает номер первой записи, а не создаёт вторую.

### Где здесь персональные данные

**В состоянии сессии** — слоты и черновик обращения, а с версии 4.48 ещё и
`template_fill`: ответы абонента на вопросы при заполнении бланка (свободный
текст — место установки счётчика, контактное лицо и телефон). Это первое место,
где прототип вообще хранит ПДн абонента: до сих пор вопрос уходил обезличенным и
нигде не оседал. Единственный механизм удаления — срок жизни
(`session_ttl_seconds`, 30 минут от последней реплики), он же ответ на
требование назвать срок хранения диалогов.

**В таблице обращений** — те же слоты, но там они и должны быть: это и есть
обращение. Срока хранения у неё нет, и на MVP его назначает владелец.

### Недоступность хранилища сессий — не `503`

ADR-008 отвечает `503` при отказе хранилища **лимитов**, и довод там денежный.
С сессиями иначе: потеря состояния не открывает дыру, а **закрывает путь** — без
состояния обращение никогда не окажется в ожидании подтверждения, и запись не
выполнится. Правило 4.7 остаётся выполненным по построению.

Поэтому отказ вырождается в «сессии нет»: вопрос без записи по-прежнему получает
ответ, а попытка подтвердить получает честное «черновик не найден».


## 75.7. История обработки обращений в векторную базу не кладётся

Вопрос возникает естественно: у водоканала есть переписка с абонентами —
настоящие вопросы и настоящие ответы операторов. Не проиндексировать ли её,
чтобы модель отвечала точнее? **Нет**, и на то три причины, каждая измерена на
самой выгрузке (136 обращений, `fixtures/inquiries_voronezh.csv`).

### Материала в ней почти нет

Медиана длины ответа оператора — **38 знаков**. Это не ответы, а пометки:
«Перерасчет по пени отобразится в квитанции за август 2026».

| Что | Из 136 |
|---|---:|
| Со ссылкой на норматив — то есть обобщаемое | **4** |
| С признаками конкретного случая (л/с, суммы, «по вашему обращению») | 11 |
| И то и другое в одном ответе | 3 |

Счёт грубый, по ключевым словам, но порядок величины он задаёт: обобщаемого
содержания там единицы записей, а не сотня.

### Ответ оператора — факт, а не объяснение

«В связи с передачей показаний выполнен перерасчет, сумма отразится в квитанции
за сентябрь» — правда **про один лицевой счёт**. Найдись этот фрагмент по чужому
вопросу, модель уверенно сообщит человеку о перерасчёте, которого не было.

Это тот же класс, что график отключений и тарифы, и правило для него уже
выведено дважды (ADR-012, ADR-013, обобщение раздела 57.5): **база знаний
отвечает на то, что объясняется; то, что проверяется по факту, отвечается точным
поиском.** Переписка по конкретному счёту — крайний случай проверяемого факта:
он верен ровно для одного человека.

### Персональные данные — отдельный запрет, а не довод о качестве

Индексировать обращение одного абонента, чтобы отвечать другому, — вопрос
152-ФЗ, а не точности.

И механически это не сработало бы даже при желании: обезличиватель стоит на пути
ответа и **искалечит найденный фрагмент**. Измерено в разделе 56.10: «передавала
показания ИПУ ХВ 142,858м3» превращалось в «⟨ФИО⟩», то есть уничтожалось само
число, ради которого вопрос задан.

### Куда обращения идут вместо этого

**В корпус для дообучения** (источник 3, раздел 30), батчем. Это другая работа:
дообучение учит модель языку и манере отвечать, RAG подставляет факты в промпт.
Смешение этих двух и есть ошибка, от которой предостерегает весь раздел.

**И как сигнал спроса — это ценнее индексации.** Измеренная проблема поиска не в
том, что мало фактов, а в том, что корпус мал: больше половины настоящих
вопросов получают отказ там, где ответ мог бы быть. Эталонный набор уже называет
пятнадцать вопросов, на которые в корпусе ответа нет — возврат средств, расчёт
водоотведения, отмена заявки, оплата госпошлины. Это готовый список тем, на
которые владелец пишет объяснения, и они идут в базу знаний обобщёнными, без
персональных данных и без ложной конкретности (пункт 68 TODO).

> Обращения превращаются в знание **руками владельца**, а не подстановкой чужой
> переписки в промпт.
