# Нагрузочный отчёт

Дата замера: 26 сентября 2026. Объект замера: Backend вместе с LLM Gateway в одном процессе (`app/main.py`), настоящие
Redis, Postgres и Qdrant из `docker-compose.yml`. Провайдер модели заменён заглушкой (см. раздел 2).

## 1. Краткая справка

Сколько запросов в секунду держит один процесс Backend и какая задержка на этом железе (AMD Ryzen 5 5500U, 6 ядер /
12 потоков, 15,3 ГБ ОЗУ, Windows 11):

| Путь ответа | Пропускная способность | Задержка при одном запросе (p50 / p95) | Ошибок |
|---|---|---|---|
| **Без модели** (тарифы, отключения, лицевой счёт, бланки, регламентные ответы) | **18 запросов/с** на одно ядро; 22–23 запроса/с при свободных 6 ядрах | 55 / 74 мс (одно ядро); 45 / 55 мс (6 ядер) | 0 |
| **С моделью** (поиск по базе знаний, обезличивание, проверка ответа на потоке; провайдер — заглушка) | **1,3 ответа/с** на одно ядро; 1,4–1,6 ответа/с при свободных 6 ядрах | до первого куска: 126 / 155 мс; до конца ответа (616 знаков): 788 / 885 мс (одно ядро) | 0 |

Что важно для оценки задержки абонента:
- К задержке пути с моделью добавляется время провайдера. По замеру от 24 сентября (19 вызовов YandexGPT) время до
  первого куска: медиана 0,78 с, P90 5,6 с (`AI_docs/Capacity_Report.html`). Суммарно медианное время до первого
  куска на этом железе — около 0,9 с (126 мс своей работы плюс 0,78 с провайдера; складываются два отдельных замера).
- Процесс занимает около 1,3 ГБ памяти.
- Пропускная способность не растёт с числом параллельных запросов: процесс насыщается уже на одном запросе, дальше
  запросы встают в очередь и задержка растёт пропорционально числу ожидающих. Ошибок и отказов нет: при 1–32
  параллельных запросах на 6 ядрах и при 1–8 на одном ядре.

Сопоставление с прогнозной нагрузкой (`AI_docs/Capacity_Report.html`, максимальный сценарий: пик 0,058 запроса/с на MVP
и 0,656 запроса/с на тираже, 30% запросов доходят до модели):

| Контур | Пик, запросов/с | Из них до модели | Ёмкость одной реплики (расчёт по замеру на одном ядре) | Запас |
|---|---|---|---|---|
| MVP, 8 000 абонентов, реплика 0,5 vCPU | 0,058 | 0,017 | 0,65 ответа/с с моделью, 9 без модели | в 38 раз (с моделью) |
| Тираж, 90 000 абонентов, реплика 1 vCPU | 0,656 | 0,20 | 1,3 ответа/с с моделью, 18 без модели | в 6,5 раза (с моделью) |

Ёмкость реплики с 0,5 vCPU получена делением измеренного значения для одного ядра пополам. Число реплик в проекте
(2 на MVP, 3 на тираже) выбрано ради отказоустойчивости (`AI_docs/ADR/ADR-500-resources-and-cost.md`), суммарная ёмкость
кратна числу реплик: реплики независимы, общее состояние лежит в Redis.

## 2. Как измерялось

**Стенд.**
- Машина: AMD Ryzen 5 5500U (6 ядер, 12 потоков), 15,3 ГБ ОЗУ, питание от сети. Клиент нагрузки работал на той же
  машине и делил с сервером процессор.
- Redis 7, Postgres 16, Qdrant — контейнеры из `docker-compose.yml` (Docker Desktop). Qdrant: коллекция `kb_faq`,
  51 фрагмент. Использовались отдельные база Redis №1 и отдельная база телеметрии `telemetry_load`, рабочие данные
  разработки не затрагивались.
- Backend — один процесс `uvicorn` на хосте (Python 3.12), эмбеддинги `multilingual-e5-small` на CPU, обезличивание
  Presidio + spaCy (`ru_core_news_md`).

**Что подменено или выключено** (`scripts/load_server.py`):
- Провайдер модели заменён заглушкой: поток из 22 кусков по четыре слова, всего 616 знаков, пауза перед первым куском
  нулевая. Задержка и лимиты настоящего провайдера в замер не входят: они чужие и заслонили бы собственную задержку.
- Лимиты запросов подняты до 1 000 000 в минуту: штатные (20 на абонента, 10 на сессию, 300 на сервис в минуту) защищают
  от злоупотреблений и дали бы `429` вместо замера пропускной способности.
- Судья качества на живом пути выключен (`QUALITY_SAMPLE_RATE=0`): он вызывает модель на каждом ответе.

**Всё остальное настоящее:** разбор вопроса, классификация, поиск в Qdrant, лимиты в Redis, состояние диалога в Redis,
обезличивание, охранители на потоке, запись событий использования в Postgres, метрики.

**Клиент** (`scripts/load_test.py`): замкнутый цикл, N параллельных «абонентов»; каждый шлёт следующий вопрос, получив
ответ на предыдущий. Ответ читается потоком SSE, как это делает виджет. Уровни N = 1, 2, 4, 8, 16, 32; окно замера 20 с
после прогрева 5 с (для пути с моделью при N = 16 и 32 — 60 с после прогрева 10 с, чтобы набрать выборку). Два вопроса:
- «без модели» — «Какие сейчас тарифы на холодную воду?» (ответчик тарифов);
- «с моделью» — «Почему начисляются пени?» (поиск по базе знаний, шлюз, заглушка провайдера).

**Две конфигурации сервера:**
- «6 ядер» — процесс не ограничен; библиотеки эмбеддингов используют все потоки процессора;
- «одно ядро» — `OMP_NUM_THREADS=1` и привязка процесса к одному логическому процессору. Это соответствует реплике с
  1 vCPU из расчёта ресурсов (ADR-500).

## 4. Где узкие места

Профилирование в процессе (`cProfile`, один поток, тот же код и стенд):

**Путь с моделью — 82% времени в проверке ответа на потоке.** На 10 ответах из 12,7 с процессорного времени 10,4 с
приходится на вызовы Presidio и spaCy из охранителей (`app/gateway/guardrails.py`, `StreamGuard`): охранитель
проверяет накопленный текст обезличивателем на каждом куске потока, 22 проверки на ответ (по одной на кусок) по ≈45 мс. Это следствие
принятого решения (нарушение должно оборвать поток до того, как абонент увидит его, ADR-100); стоимость растёт с длиной
ответа (по замеру от 24 сентября: 800 знаков — P95 ≈49 мс на проверку, 2 000 знаков — P95 ≈120 мс). Из-за этого путь с
моделью упирается в 1,3–1,6 ответа/с на процесс независимо от числа параллельных запросов.

**Путь без модели — 89% времени в классификации типа обращения.** На 40 запросах из 2,6 с процессорного времени 2,3 с
занимает запасной классификатор типа обращения (`Triage._type_async` → `InquiryTypeFallbackClassifier.classify`):
эмбеддинг вопроса (≈48 мс) и сравнение с размеченными примерами (≈10 мс) выполняются на каждом запросе, в том числе на
вопросе о тарифе, который затем получает прямой ответ. Лимиты в Redis занимают ≈6 мс на запрос. Исключение этого шага
для прямых ответов сократило бы процессорное время пути без модели примерно на 90% (оценка по профилю).

## 5. Границы замера

- Один процесс сервера, одна машина; клиент нагрузки и контейнеры Redis, Postgres, Qdrant делят с ним процессор.
- Провайдер модели — заглушка с ответом 616 знаков и нулевой задержкой; время настоящего провайдера добавляется
  сверху (раздел 1). Ответы длиннее увеличивают стоимость проверки на потоке.
- Окно замера 20–60 с на уровень, один прогон на конфигурацию; у пути с моделью на малых окнах набирается 28–40
  ответов, поэтому значения RPS для него округлены до 0,1; в разных прогонах они лежат в диапазоне 1,3–1,6.
- Сеть между клиентом и сервером — петля localhost; сетевые задержки кластера в замер не входят.
- Ёмкость реплик 0,5 vCPU в разделе 1 — расчёт (деление измеренной ёмкости одного ядра пополам), не отдельный замер.
- Прежнее значение «117 запросов/с, 8,5 мс CPU на запрос без модели» (ADR-500, `Capacity_Report.html`) не подтвердилось
  замером через HTTP на текущем коде и заменено числами этого отчёта: путь без модели со всем стеком стоит 47 мс CPU на запрос.
  Для пути с моделью прежняя оценка (0,9 с CPU на ответ в 800 знаков) согласуется с измеренными 0,65 с на ответ в
  616 знаков.

## 6. Как повторить

```bash
docker compose up -d postgres redis qdrant
docker exec vk-postgres psql -U vodokanal -d postgres -c "CREATE DATABASE telemetry_load"
python scripts/load_server.py --port 8100
python scripts/load_test.py --url http://127.0.0.1:8100 --server-pid <pid процесса сервера> --json golden_set/load_test.json
```

Конфигурация «одно ядро»: перед запуском сервера задать `OMP_NUM_THREADS=1` и привязать процесс к одному логическому
процессору (PowerShell: `(Get-Process -Id <pid>).ProcessorAffinity = 1`). Для `--server-pid` нужен пакет `psutil`.
