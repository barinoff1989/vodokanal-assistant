# 0. Что нового с версии 3.0 (читать в первую очередь)

С момента написания версии 3.0 контекста произошло следующее:

1. **Проведена верификация архитектуры** по методике «CTO Challenge» (Definition of Ready, матрица
   Verification/Validation, ATAM Utility Tree, STRIDE, sizing по закону Литтла) применительно к
   диаграммам C4 L2 (контейнеры) и C4 L3 (ETL Worker) и к тексту версии 3.0. Итоговый вердикт —
   **CONDITIONAL** («да, но»): архитектурная логика и дисциплина по стадийности сильные, но отсутствуют
   смета CAPEX/OPEX и расчёт производительности под заявленные NFR, а в диаграммах найдены конкретные
   технические дефекты. Полные результаты — раздел 24.

2. **Найдены и задокументированы конкретные дефекты диаграмм C4 L2 и L3** — незафиксированное соединение
   в draw.io-модели, тупиковый узел без пути доставки результата пользователю, конкуренция за GPU между
   офлайн-ETL и онлайн-обслуживанием запросов, рассинхронизация текста версии 3.0 с фактическим
   содержимым диаграммы L3. Полный список — раздел 25.

3. **Принято архитектурное решение по хостингу LLM — ADR-002** («Стратегия хостинга LLM: SaaS vs
   Self-hosted»). Статус — **Proposed** (направление решено, финальный Accepted — после утверждения
   сметы и sizing-расчёта). Решение: единый шлюз доступа к модели (LLM Gateway) с самого начала проекта;
   по умолчанию — управляемый API российского провайдера; переход на self-hosted-модель — по факту
   наступления одного из четырёх явных триггеров. Полный текст решения и таблица триггеров — раздел 26.

4. **В папке проекта существуют два альтернативных черновика того же решения** — файлы, которые в этом
   контексте называются условно «черновик ADR-001» и «черновик ADR-006» (оба посвящены той же дилемме
   SaaS vs Self-hosted). Структурно и по логике триггеров они совпадают с ADR-002, но содержат
   **недостоверные финансовые цифры** (конкретный бюджет CAPEX, срок в днях, стоимость GPU в долларах в
   месяц), которые не подтверждаются никаким документом этого проекта и, по всем признакам, заимствованы
   из постороннего иллюстративного примера, не относящегося к водоканалу. Подробности и что именно нельзя
   использовать как факт — раздел 26.4. Это важно: следующая LLM не должна принимать эти цифры за
   реальные данные проекта.

5. **Смета CAPEX/OPEX по-прежнему не существует.** Это главный открытый пункт: без неё ни архитектура
   Этапа 2, ни ADR-002 не могут перейти в статус Accepted. Актуальный список задач — раздел 27.

# 0.1. Что нового с версии 4.1 — спроектирована архитектура данных

После верификации и ADR-002 отдельным блоком работы спроектирована архитектура данных проекта: откуда
берутся данные, как они собираются (ETL/ELT, Stream/Batch), где хранятся и как обеспечивается
консистентность между обучением/оценкой и онлайн-инференсом. Кратко:

1. **Собран полный каталог из 16 источников данных** — от уже известных (БД Биллинга, БД личного
   кабинета) до найденных по ходу анализа (Диспетчерская, реестр договоров, CRM колл-центра, публичный
   сайт, служебные Sync State и Golden Set). Полный разбор — раздел 29.

2. **Уточнена связь Backend с Биллингом.** Реальный протокол Биллинга — не REST, как предполагала
   версия 3.0 (раздел 5.3), а **собственный внешний XML-RPC API** Биллинга. Backend читает через этот
   API на Этапе 1, Billing Adapter на Этапе 2 пишет через него же, добавляя HITL и Idempotency-Key.
   Отдельного контейнера-слоя доступа нашей разработки **не требуется** — API самой системы уже играет
   эту роль. Подробности и общее правило доступа к внешним системам — раздел 29.5.
   > **[ПОПРАВКА v4.5]** Промежуточная редакция v4.1–v4.4 утверждала «прямой SQL через сервис на Go
   > (приоритет) / XML-RPC (резерв)» и вводила из-за этого новый контейнер на L2. Это отменено.

3. **Спроектирован ETL/ELT-пайплайн** с явным разделением, где происходит очистка данных и где —
   генерация эмбеддингов, и с обоснованием, почему для одних участков выбран ELT (индексация базы
   знаний), а для других — ETL (корпус для дообучения, кэш профиля). Раздел 30.

4. **Выбраны хранилища по этапам**: Data Lake (S3/MinIO), Vector DB (уже существующий Qdrant), кэш
   профиля абонента в роли Feature Store (Postgres MV + Redis — **не** формальная платформа Feast/Tecton),
   курируемый корпус для дообучения, ClickHouse, событийная шина. Каждый выбор обоснован явно, включая
   разбор «почему не типовой стек Kafka → Spark → S3 → Pinecone». Раздел 31.

5. **Закрыт открытый вопрос оркестрации batch-задач**: не Airflow — выбран **K8s CronJob** для простых
   периодических задач без DAG-зависимостей (новые источники, материализация кэша), а уже существующий
   **Celery Beat** оставлен только для многошагового конвейера индексации документов, где нужны
   task-уровневые retry и fan-out, которых у голого CronJob нет. Раздел 30.

6. **Определён подход к консистентности данных** (защита от training-serving skew) без формального
   Feature Store: единая materialized view, которую читает и офлайн-оценка, и онлайн-Backend, плюс шесть
   дополнительных правил (версия модели эмбеддингов, point-in-time для Golden Set, TTL кэша, единая
   таксономия, единый PII-фильтр, каталог источников как источник истины). Раздел 32.

7. **Исправлена унаследованная неточность**: база знаний в версиях 3.0/4.0/4.1 называлась «Confluence /
   Jira» — это было наследием исходного шаблона архитектуры, не фактом проекта. Реальные источники базы
   знаний — файлы Word, реестр договоров и публичный сайт (см. раздел 5.1, поправка v4.1, и раздел 33.4).

8. **Созданы новые артефакты в папке `dz5`**: каталог источников, две отдельные диаграммы (обучение /
   онлайн-инференс) плюс общая обзорная диаграмма, документ по консистентности и итоговое текстовое
   описание архитектуры данных. Полный список файлов и что в каждом — раздел 33.

# 0.3. Что нового с версии 4.3 — Security Layer, план тестирования RAG и дашборд наблюдаемости (папка `dz6`)

Отдельным блоком работы выполнено ДЗ «Комплексное обеспечение качества»: на диаграмму LLM Gateway
добавлены компоненты защиты, спроектирован план тестирования RAG и дашборд наблюдаемости для Grafana.
Кратко:

1. **На диаграмму L3 LLM Gateway (`dz6/C4_L3_LLM.html`) добавлен Security Layer.** `PII Middleware`
   переименован в **PII Sanitizer** (та же технология — Presidio + кастомные распознаватели; список
   сущностей дополнен email). Добавлен новый компонент **Guardrails**, которого на диаграмме не было
   вообще: sync-проверка (PII в ответе, токсичность, policy — обрыв потока при нарушении, <50 мс) и
   async-оценка groundedness/faithfulness (не блокирует streaming, правило 4.3). Путь ответа изменён с
   `LiteLLM Core → Backend` на `LiteLLM Core → Guardrails → Backend`. Оба компонента остаются внутри
   существующего контейнера LLM Gateway (зона «наш код») — новых контейнеров на L2 не введено, правило
   4.1 не нарушено. Полный разбор — раздел 35.

2. **Попутно исправлена логическая ошибка в Quota Manager**: было «квоты по департаментам водоканала» —
   департаменты не являются пользователями чат-интерфейса (раздел 1), квотировать их бессмысленно;
   заменено на лимиты на абонента/сессию + глобальный лимит сервиса, добавлено обязательное «429 +
   Retry-After» (было пропущено). Billing Callback переформулирован («в ClickHouse», не «во внутренний
   биллинг» — не путать с legacy-системой Billing). Раздел 35.1.

3. **Спроектирован план тестирования RAG** (`Приложения/План теста RAG.html`): метрики Faithfulness (≥0.85) и
   Answer Relevancy (≥0.80) как reference-free ядро + Context Precision/Recall как reference-based;
   инструменты — Ragas (офлайн-батч по Golden Set + сэмплирование прод-трафика) и DeepEval (CI-гейт на
   PR, стратифицированная по типам обращений подвыборка); три контура оценки + правило регрессии (>5% —
   блокирующая); требования к судье, включая устранение противоречия «self-hosted по триггеру запрета ИБ,
   но судья — внешний управляемый API» (раздел 26) — для этого случая судья тоже локальный. Полный разбор
   — раздел 36.

4. **Спроектирован дашборд наблюдаемости** (`Приложения/Дашборды.html`): 5 Golden Signals (TTFT и
   полный ответ разнесены и привязаны к реальным цифрам DoD — раздел 18, вместо одного смешанного
   виджета с ничем не подтверждённым порогом; Traffic с разбивкой по `inquiry_type`; Saturation видит оба
   контура GPU — ETL Worker и онлайн-инференс, что делает видимой конкуренцию за GPU, находка F7 раздела
   25) + 9 AI-метрик (включая отдельный миссия-критичный виджет «Утечка ПДн в ответе», не смешанный с
   общим Guardrails Block Rate; накопленный расход токенов против триггера 50M ADR-002; прогноз
   месячного OPEX). Полная таблица алертов по формуле «метрика + условие + приоритет + доставка +
   ранабук». Полный разбор — раздел 37.

5. **Оба новых документа прошли по два раунда точечных замечаний** (не общее ревью «дай оценку всему
   документу», а конкретные пункты с вердиктом по каждому — CONFIRMED / частично устарело / не в фокусе).
   При проверке одного из замечаний числа DoD (TTFT < 500 мс, полный ответ < 3 сек, поиск P99 < 100 мс),

# 0.4. Что нового с версии 4.4 — sizing инференса и план сборки финальной сдачи (папка `dz7` → `AIproject`)

Отдельным блоком работы рассчитаны ресурсы под инференс LLM (self-hosted GPU и локальная машина
прототипа) и составлен план сборки всего пакета финальной сдачи проекта. Кратко:

1. **Проанализированы презентации курса** «Sizing» и «Оптимизация LLM» (папка `dz7`), плюс напрямую
   опрошен калькулятор `apxml.com/tools/vram-calculator` в браузере — характеристики GPU (bandwidth,
   TFLOPS) взяты из него, а не по памяти.

2. **Рассчитан VRAM/GPU для self-hosted-кандидатов** (Qwen2.5-32B и Qwen2.5-72B, раздел 8.1) в FP16 и
   INT4, с явно обозначенным **ПРЕДПОЛОЖЕНИЕМ** целевой нагрузки (λ = 5 RPS, конкурентность L = 15 по
   закону Литтла, раздел 28.1 — реальная нагрузка проекта по-прежнему не определена, раздел 27/28).
   Рекомендация: **Qwen2.5-32B в INT4 на 1× A100 80GB** — единственная из рассмотренных конфигураций,

# 46. Внешний провайдер прототипа — YandexGPT (v4.9–4.10)

Решение от 1 сентября 2026. **Меняется только прототип**; состав моделей MVP, зафиксированный
ADR-007, остаётся прежним.

## 46.1. Что решено

| Контур | Генерация | Второй backend шлюза | Судья качества |
|---|---|---|---|
| Прототип | **YandexGPT** | локальная Qwen2.5-7B | локальная Qwen2.5-7B |
| MVP в проде | GigaChat Pro | YandexGPT | YandexGPT |

## 46.2. Причина — техническая, не предпочтение

GigaChat требует корневых сертификатов НУЦ Минцифры. Их нет ни в поставке Python, ни в наборе
`certifi`, которым пользуются `httpx` и `requests`, и без установки в систему любой вызов падает на
проверке TLS. **На машине прототипа эти сертификаты получены не будут.**

Обходной путь — отключить проверку сертификата — отвергнут: по этому соединению идут персональные
данные абонента, а система строится под 152-ФЗ. Барьер, выстроенный правилом 4.2, нельзя обходить
на транспортном уровне.

Регуляторная часть решения не затрагивается: GigaChat и YandexGPT равнодопустимы по ADR-002 — оба
управляемые API на территории РФ. Меняется исполнитель роли, не принцип.

## 46.3. Цена решения

**Путь GigaChat не проверяется до MVP.** Его особенности — авторизация, формат ответа, поведение
потока — вскроются позже. Это принятый риск, и он же ровно тот сценарий, ради которого в ADR-002
выбран вариант с единым шлюзом: смена провайдера должна быть правкой конфигурации.

**Штатной поддержки Яндекса в LiteLLM нет.** Проверено на установленной версии 1.99.0: в списке из
152 провайдеров есть `gigachat`, но `yandex` отсутствует. Подключение идёт через OpenAI-совместимый
режим с явным адресом, и ответственность за совпадение формата ответов и потоковой отдачи ложится
на нас.

Побочный эффект скорее полезный: прототип проходит **более трудный** путь интеграции, а переход на
MVP означает смену на штатно поддерживаемого провайдера, то есть упрощение, а не усложнение.

## 48.3. ADR-008 — отказ хранилища лимитов

Вопрос числился пунктом 7 TODO и блокировал код-шаг 4.

| Контур | Поведение |
|---|---|
| Прототип и MVP | **Отказ в обслуживании**: `503` + `Retry-After`, абоненту — «сервис временно недоступен» |
| Тираж | Вырожденный режим: учёт лимитов в памяти процесса + алерт, по условию пересмотра |

**Почему именно так.** Отказ Redis вполне может быть *следствием* всплеска нагрузки, а не независимым
событием, — и тогда пропуск запросов снял бы защиту ровно в тот момент, когда она нужна. Расход токенов
при этом единственная статья, растущая болезненно (раздел 42.5).

**Условие перехода к вырожденному режиму** — оба сразу: реплик больше одной **и** измеренная за квартал
доля отказов значима. Второе важнее: если хранилище не падало ни разу, вырожденный режим — это код,
который никогда не исполнялся и потому не проверен.

### Код 503, а не 429 — пятое решение по спецификации

`429` означает «вы превысили лимит», то есть возлагает причину на абонента, который ни при чём. Виджет
реагирует на коды по-разному: на `429` тихо повторяет запрос, на `503` сообщает о недоступности.
Смешение превратило бы отказ инфраструктуры в невидимую в метриках «активность абонентов, упирающихся в
лимит».

Кода `503` в разделе 7.4 нет — это **пятое** решение, требующее внесения в спецификацию (пункт 5 TODO),
наряду с четырьмя, закодированными в схемах данных (раздел 47.3).

# 49. Код-шаг 4: шлюз к модели (v4.14)

**206 тестов**, линтер и типизация чисты. Живой сквозной вызов на настоящем YandexGPT проходит:
лимиты → обезличивание → модель → охранители → поток событий.

## 49.1. Что сделано

`app/gateway/quota.py` и `app/gateway/llm_gateway.py`. Порядок проверок — раздел 41.3, quota-first.
Отдельный тест проверяет, что **при исчерпанном лимите провайдер не вызывается вовсе**: иначе порядок
был бы соглашением, а не свойством кода.

Три обязательные проверки: контракт ответа с источниками и расходом токенов; `429` с временем повтора
при превышении (закрывает дефект раздела 35.1, где заголовок был пропущен); `503` при недоступности
хранилища по ADR-008 — сверх плана, без неё решение осталось бы текстом.

**Два решения по существу, принятых при реализации:**

- `Retry-After` возвращает **остаток окна**, а не постоянное значение из настроек. Сказать «через 30
  секунд», когда счётчик обнулится через две, — задержать абонента без нужды; когда через пятьдесят —
  обречь на второй отказ.
- **Отклонённые запросы тоже увеличивают счётчик.** Иначе абонент за лимитом получал бы неограниченные
  бесплатные попытки и продолжал нагружать шлюз.

## 49.2. Две ошибки, найденные проверками

**Дыра в распознавателе лицевого счёта.** Подсказка требовала «лицевой счёт» или «номер счёта», а модель
в ответе естественно пишет «задолженность **по счёту** 1234567890» — утечка проходила насквозь.
Обнаружено тестом на реалистичном тексте ответа, а не умозрительно. Подсказка расширена до слова «счёт»
в любой форме; ложных срабатываний не добавилось — рядом должно стоять девяти- или десятизначное число,
а суммы в рублях столько цифр не имеют.

**Идентификатор каталога Яндекса хранился в двух местах** — в `YANDEX_FOLDER_ID` и внутри
`YANDEX_MODEL_URI`. При правке каталога после диагностики поправили первое, второе осталось с
заглушкой; живой вызов упал с «не удалось разобрать имя модели». Имя модели теперь **собирается из
каталога**, второй источник убран.

Это третий случай одного и того же класса ошибки в проекте: два источника истины расходятся при первой
же правке. Первый — устаревшая схема в `dz5`, породившая ложное замечание ревьюера (раздел 43.2);
второй — самоподтверждающийся счёт «C3 готово 4 из 4» (раздел 41.1).

## 49.3. `config.yaml, не код` — на прототипе это пока не так

Раздел 5.5 описывает целевое устройство: смена провайдера должна быть правкой конфигурации. **Сейчас
это не выполняется.** Файл `litellm_config.yaml` разбирает только прокси LiteLLM, которого в прототипе
нет — шлюз обращается к `acompletion` напрямую, и конфигурация не читается ничем.

Вскрылось живым вызовом: псевдоним `yandexgpt` уходил провайдеру как имя модели.

Временное устройство: рабочий источник параметров — `LlmGateway._provider_params`, файл остаётся
описанием целевого. Значения в обоих местах берутся из `app/config.py`, чтобы расхождение не завелось в
третьем. Помечено в самом файле, в методе и поправкой к разделу 5.5.

**Что это значит для ADR-002.** Его «Подтверждение», пункт 1, требует шлюза с двумя провайдерами и
автоматическим переключением при сбое. Переключение **правкой одной переменной** работает уже сейчас
(`LLM_PROVIDER`), а вот автоматический fallback описан только в конфигурации, то есть пока не
исполняется. Внесено в TODO.

# 53. ADR-010: последний ненаписанный ADR (v4.18)

**Ненаписанных ADR в проекте не осталось.** Реестр раздела 26 содержит девять решений — с ADR-002 по
ADR-010, все в статусе Proposed с явно названным препятствием к Accepted.

## 53.1. Вопрос был поставлен иначе, чем в разделе 12.2

Раздел 12.2 называл желательным улучшением перевод конечного автомата на LangGraph с использованием
`interrupt_before` для подтверждения абонента. К моменту написания решения обстоятельства изменились.

**Дефект 11.9** — библиотека `transitions` настраивается строковыми ключами, и пробел в ключе не вызывал
ошибки: переход просто не находился. Прототип на этом ломался молча.

**Код-шаг 2 сделан без библиотеки вовсе** — таблица из семи состояний и десяти переходов на
перечислениях, с полным перебором в проверках.

То есть выбор стоял не «`transitions` или LangGraph», а «оставить работающую таблицу или взять
LangGraph», и решать нужно было по тому, чего таблица не умеет.

## 53.2. Решение и главный довод против LangGraph сейчас

Автомат остаётся таблицей. Переход — по одному из трёх триггеров: агенту нужно самому выбирать
инструмент; состояние диалога должно переживать перезапуск; появились параллельные ветви.

Довод, который перевесил: **`interrupt_before` завёл бы второй механизм подтверждения**. Правило 4.7

# 54. Метрики, интерфейс и закономерность живых проверок (v4.19)

**315 тестов.** Работа началась с вопроса «что можно проверить через интерфейс и какие ещё метрики
вывести» — и вскрыла больше, чем предполагала.

## 54.1. Метрика без записи — та же болезнь, что виджет без метрики

`http_requests_total` была **объявлена в коде и не записывалась ничем**. Виджет доли ошибок в дашборде
остался бы пустым — ровно тот дефект, который блок работы раздела 49 закрывал с другой стороны.

Подключена через промежуточный слой интерфейса. Путь берётся из **шаблона адреса**, а не фактического:
иначе каждый запрос с разными параметрами создавал бы свой временной ряд.

**Связь стала двусторонней.** К проверке «виджет ссылается на объявленную метрику» добавлена обратная —
«у каждой собираемой метрики есть виджет». Без обеих сторон половина расхождений остаётся невидимой.

## 54.2. Четыре метрики под то, что утверждалось без измерения

| Метрика | Что подтверждает |
|---|---|
| `quota_rejections_total{scope}` | Код `429` не попадает в долю ошибок — та считает пятисотые. Без разбивки упёршийся в лимит абонент и исчерпанный предел сервиса неразличимы, хотя это разные инциденты |
| `guardrails_check_seconds` | Раздел 35.1 задаёт бюджет **менее 50 мс**; до сих пор это было утверждением без замера. Проверка стоит на пути ответа и задерживает каждый его кусок |
| `pii_sanitize_seconds` | Обезличивание целиком входит во время до первого куска; при выходе за цель показывает, чей это вклад |
| `llm_provider_used_total{alias,model}` | Псевдоним против фактически ответившей модели. Расхождение и есть срабатывание запасного провайдера — требование ADR-002 измерять ежемесячно |

Виджеты для всех пяти внесены в спецификацию дашборда тем же блоком работы.

## 54.3. Что попало в интерфейс, а что осознанно нет

Вопрос «добавлены ли новые метрики в интерфейс» имеет разный ответ для разных метрик.

**Длительности остались на порту метрик.** Обезличивание и проверка охранителей — внутренние величины
сервера; настоящему виджету в кабинете абонента они не нужны, и протащить их в события потока значило
бы засорить контракт служебными подробностями. В панели стенда стоит ссылка на порт метрик с
объяснением, почему они там.

**Фактически ответившая модель добавлена.** Это законная часть контракта: поле `routing` есть в разделе
7.3 и предназначено ровно для этого; раньше в нём был только псевдоним. Событие завершения теперь несёт
то же, что ответ целиком, — иначе переключение на запасного провайдера было бы видно только в одном из
двух режимов. Панель помечает случай, когда ответил запасной.

## 54.4. Живая проверка снова нашла то, чего не видят тесты

**Битое тело запроса давало `500` с трассировкой вместо `400` по RFC 7807.** Клиент получал внутреннюю
ошибку там, где виноват его собственный запрос.

Нашлось случайно: команда проверки отправила русский текст в неверной кодировке. Проверки этого не
ловили — они шлют заведомо корректные тела.

**Это четвёртый случай одной закономерности**, и её стоит зафиксировать явно:

| Что нашла живая проверка | Чего не видел тест |
|---|---|
| Внутренний текст ошибки провайдера у абонента | Тесты подменяют провайдера |
| Восемь секунд до первого куска | Тесты не платят за ленивые загрузки |
| Псевдоним провайдера уходил как имя модели | Тесты подменяют функцию вызова |
| `500` вместо `400` на битом теле | Тесты шлют корректные тела |

> **[ДОПОЛНЕНО v4.20 — проверка на вопрос «а поправлено ли?»]** Все четыре дефекта были исправлены в
> коде, но сверка показала: **два из четырёх не защищены ничем**. Нейтральный текст ошибки провайдера —
> существующая проверка касалась отказа хранилища лимитов (`503`), а ошибки провайдера (`502` и `504`)
> оставались открытыми: похожие формулировки создали видимость покрытия. Прогрев — теста не было вовсе.
>
> Оба закрыты. У прогрева проверок две, и вторая важнее: **приложение действительно вызывает его при
> запуске**. Без неё метод мог остаться написанным и неподключённым — а исходная ошибка выглядела
> ровно так.
>
> Отдельно проверено, что тесты ловят возврат дефекта, а не проходят по случайности: внутренний текст
> ошибки вернули намеренно — проверка упала; восстановили — прошла. Тридцать секунд, снимающие вопрос,
> который иначе остаётся открытым.
>
> **Правило, которое стоит держать:** исправление без теста возвращается, а похожая формулировка
> соседней проверки создаёт видимость покрытия там, где его нет.

Общее у всех четырёх: **дефект живёт на стыке с внешним миром** — с человеком, с сетью, с чужой
библиотекой. Подмена, которая делает тест быстрым и независимым, ровно этот стык и убирает. Вывод не
«тесты плохи», а «набора тестов недостаточно»: каждый блок работы должен заканчиваться прогоном по
живому пути, иначе класс дефектов остаётся невидимым до защиты.

## 55.2. Расхождение оказалось в оси, а не в названиях

Канонический перечень раздела 9.3 построен **по теме** обращения. Реальный — **по заказываемой
услуге и документообороту**, и смешивает четыре вещи: деньги, заявку на работу, документы и операцию
над обращением («Отмена обращения» — вообще не тип, а действие над уже поданным).

Отсюда главное следствие: **предписание docstring `app/taxonomy.py` не сработало.** Оно требовало
при расхождении завести таблицу соответствия, не трогая канонический перечень, — и было написано в
расчёте на то, что реальный справочник окажется теми же понятиями под другими именами. Таблица
отображает 9 из 13 типов в пустоту; это не перевод между словарями, а потеря данных. Доля `other`
стала бы структурной нормой около 70%, а она заведена как **сигнал деградации классификатора**
(раздел 37.1).

Решение — ADR-011: две оси. `inquiry_type` — регистрационная, реальный справочник, нужна только на
пути записи Этапа 2. `topic` — тематическая, выводится из документов базы знаний, нужна для фильтра
поиска. Правило 4.8 переформулировано: не «одна таксономия на всё», а «у каждой оси один справочник
и одно назначение; значения разных осей никогда не сравниваются между собой».

Довод, снимающий возражение о возврате дефекта 11.1: прототип ломался на **двух словарях для одного
и того же**. Две оси для **разного** — не тот же дефект, при условии что тест сторожит их
несравнимость. Проект уже делал это различение в разделе 41.2, разводя `GuardrailAgent` и
`Guardrails`.

**Побочный результат:** шаг 5 (поиск) перестал зависеть от справочника обращений. На его пути
остался один внешний блокер — образцы документов базы знаний (пункт 3 `Data_Request.md`).

**Список полный** — отсутствие шести кодов не неполнота выгрузки.

**Аварии — отдельный источник (Диспетчерская), к обращениям не относятся.** Это **внешнее
подтверждение ADR-009**, до сих пор выведенного нами логически, и оно закрывает пункт 34: там стояло
«согласовать», а согласовывать нечего — установлен факт устройства систем. Ограничение
`app/adapters/inquiry_service.py`, отклоняющее регистрацию аварийных заявок, оказалось не нашей

**Исполнителя по обращениям не выводим.** Назначение №5 раздела 9.1 (выбор подразделения) снято с

## 55.4. Коды синтетические — и это помечено, а не умолчано

Реальные коды не переданы, только названия (пункт 2 `Data_Request.md` просил и то и другое). Ждать
их — значит держать заблокированными шаги 1, 5 и 9, поэтому коды назначены нами.

Тринадцать синтетических кодов перечислены в ADR-011. Из десяти канонических угаданы два — `debt` и
`meter_verification`; `recalculation` стал псевдонимом `accrual_recalculation`, потому что реальное

прототип оперировал русскими значениями, а эти коды жили только в наших документах.

месте, и колонка реального кода добавится туда же без правки чего-либо ещё.

## 55.6. Ответ о качестве воды не будет генерироваться (ADR-012)

Владелец задал требование: ответ про стандарт качества — определённая фраза, не должна меняться.
**Языковая модель такого дать не может по построению**, и дело не в настройке температуры: провайдер
меняет версию модели без нашего участия, а проект вдобавок **переключает провайдера автоматически** —
это реализовано и проверено живым прогоном (раздел 52.3). Формулировка, дословность которой зависит
от того, кто сегодня ответил, дословностью не является.

Решение: текст отдаётся из реестра регламентных ответов, без обращения к модели. Правило шире одного
случая — **текст, который обязан не меняться, не производится языковой моделью.**

Разбор проверок сделан явно, чтобы его не решала реализация: лимиты применяются (иначе появится путь
в обход них), обезличивание не нужно (наружу ничего не уходит), Guardrails не применяются (проверять
утверждённый норматив нашими правилами — ставить фильтр выше норматива, вплоть до блокировки).
Проверки не отменены, а сдвинуты ко входу: формулировка проходит их один раз при внесении в реестр.

Реестр живёт рядом с таксономией, а не в базе знаний: **база знаний обязана меняться, реестр обязан
не меняться**, и один механизм для двух противоположных требований — плохая опора.

`water_quality` остаётся кодом нашей оси как третья категория — маршрут к фиксированному ответу,
наравне с `emergency` как маршрутом в Диспетчерскую. Реализация — на код-шаге 6: до классификации
распознать тему нечем.

**Но колонки `text_request` и `answer_msg` первой пары обезличивание не прошли.** В них шаблонный
текст вида «Вопрос от ⟨ФИО⟩ (л/с ⟨номер⟩): подскажите порядок обращения», и ФИО с номером в нём —
**не те, что в обезличенных колонках**:

| Признак | Значение |
|---|---|
| Строк с ФИО в шаблонных текстах | **112 из 136** |
| Строк с номером лицевого счёта | **126 из 136**, различных номеров — **119** |
| Фамилия из обезличенного `fname` встречается в тексте | **0 из 136** |
| Номер в тексте совпадает с обезличенным `ls_refid` | **10 из 136** |
| Длина номеров в тексте | 6, 7, 9, 10 и 12 знаков — разнородная, в отличие от единообразного `ls_refid` |

Разнородность длин и верхний регистр части ФИО (характерный для выгрузок биллинга) говорят, что это
значения из настоящего источника, а не вторая партия подставных.

**Настоящие тексты (вторая пара колонок) вычищены почти полностью** — три остатка: ФИО в ответе
строки 26, адрес почты в запросе строки 56, телефон в ответе строки 87.

Это ровно тот класс дефекта, ради которого в проекте существует PII Sanitizer: обезличили поля,
пропустили текст. Файл не вносится в репозиторий, пока шаблонные колонки не очищены — тем более что
ценности они не несут (см. 56.2).

## 56.2. Одинаковые имена колонок скрывают два разных содержимого

Заголовок объявляет 12 колонок, но `text_request` и `answer_msg` встречаются **дважды каждая**, и
содержимое пар не совпадает ни в одной строке:

- **первая пара** — сгенерированный шаблон, одинаковый по форме для всех тем; ценности нет, а
  персональные данные есть;
- **вторая пара** — **настоящий текст абонента и настоящий ответ**. Ради них файл и запрашивался.

Ловушка на будущее: `csv.DictReader` при одинаковых именах молча оставляет **последнее** вхождение.
Здесь это случайно сохраняет нужные колонки и отбрасывает вредные, но полагаться на такое нельзя —
читать выгрузку следует по номерам колонок.

## 56.3. Типов шестнадцать, а не тринадцать

Сверх переданного ранее списка в выгрузке есть **«Другое»**, **«Повторная приемка узла учета воды в
эксплуатацию (без авто) »** и **«…(с авто)»**. Все тринадцать прежних присутствуют.

**У «(без авто) » хвостовой пробел.** Это дефект 11.1 — тот самый, из-за которого переписан
прототип, — **в живых данных реальной системы**. `_clean()` в `app/taxonomy.py` защищает, как теперь
видно, не от гипотетической ошибки.

**Пара «с авто» / «без авто» — по-видимому, ответ на вопрос о подтипах** (пункт 39): подтип выражен
суффиксом в названии, а не отдельным полем. Что означают сами суффиксы — неизвестно; тексты не
проясняют, и назначать по догадке нельзя.

## 56.4. «Другое» существует — и работает свалкой

Вывод раздела 55.5 («катch-all отсутствует, значит нужен гейт записи») **неверен**. Гейт не
заводится: он запрещал бы то, что принимающая система разрешает.

Но данные показывают другое, и оно важнее. Среди девяти обращений «Другого» — «акт сверки»,
«Направляю поверку счетчика», «Прошу опломбировать и принять на расчеты ПУ ХВС», «срыв пломбы»,
«неделю нет холодной воды». **У каждого есть свой тип в том же справочнике.**

Два следствия:

1. **`bname` нельзя брать как разметку истины** для эталонного набора. Пункт 14 (Golden Set)
   дорожает: требуется ручная переразметка, а не выгрузка «как есть».
2. Автоматическая классификация в «Другое» — не результат, а отложенная работа. Вместо гейта —
   порог на долю `other` и правило не засчитывать его как успех при оценке качества.

## 56.5. Аварии в обращениях встречаются — как вопрос, а не как заявка

«По адресу неделю нет холодной воды. Поясните причину» лежит в обращениях под типом «Другое».

ADR-009 это не отменяет: аварийная **заявка** идёт в Диспетчерскую, и типа `emergency` в справочнике
действительно нет. Но **вопрос про аварию абонент задаёт здесь**, и ассистент обязан на него
отвечать.

Это фактическое подтверждение правильности разделения осей из ADR-011: `emergency` обязан
существовать на оси `topic` (о чём спрашивают), не существуя на оси `inquiry_type` (во что
регистрируют). Одной осью такой случай не описывается вовсе.

## 56.6. Тексты вдвое короче, чем предполагал проект, и двух разных родов

Медиана длины настоящего текста — **38 символов**; 70 строк из 136 короче сорока. Разбивка по темам
показывает не разброс, а **расслоение**:

| Род | Темы | Медиана | Пример |
|---|---|---|---|
| Служебная пометка оператора | Повторная приемка, Обследование, Отмена обращения, Заказать установку / опломбировку | 6–23 симв. | «ХВ», «платно», «пу хвс», «ХВ полив» |
| Текст абонента | Пени, Возврат денежных средств, Начисления/Перерасчет, Задолженность, Направить документы | 107–246 симв. | связные предложения с обстоятельствами дела |

В одной колонке лежат два разных рода записей. Для обучения и оценки их надо разделять: половина
«эталона» иначе окажется операторской стенографией, на которой ни классификатор, ни поиск учить
нечему.

## 56.7. Запасной классификатор измерен — и не работает

Ключевые слова `KEYWORDS` были помечены в модуле как **[ПРЕДПОЛОЖЕНИЕ]**: подобраны по формулировкам
разделов 9 и 11.2, а не по реальным обращениям. Предположение проверено прогоном по настоящим
текстам:

| Исход | Строк |
|---|---|
| Ни одного кода → `other` | **73 из 136 (54%)** |
| Ровно один код | 52 |
| Два кода разом | 9 |
| Три кода разом | 2 |

Больше половины не распознаётся, а каждая шестая из распознанных неоднозначна. Перечень надо
**пересобирать по частотности реальных текстов**, как и предписывала пометка в модуле, — а не
дополнять на глаз.

Отдельно это довод в пользу того, что запасной режим не заменяет модель, а лишь удерживает сервис от
полного отказа: 54% `other` — не деградация качества, а его отсутствие.

## 56.8. Новое поле `type_docs`

В `Data_Request.md` (A5) не запрашивалось. Заполнено в 45 строках из 136, десять значений: «Акт
поверки» (8), «Чек об оплате» (6), «Паспорт» (5), «Платежные поручения» (3), «Акт УК», «Акт допуска
в эксплуатацию», «Акт обследования», «Выписка ЕГРН», «Прочие документы» и снова «Другое» (14 —
больше всех).

Это тип вложенного документа. Он относится к теме «Направить документы» и к генератору документов
(код-шаг 9), и его стоит внести в каталог данных: поле существует, используется и в проекте не
описано.

## 56.10. Обезличиватель проверен на настоящих текстах и оказался непригоден

Скрипт очистки (`scripts/sanitize_inquiries.py`) прогнал настоящие тексты через **наш собственный**
`app/gateway/pii_filter.py`. До сих пор он проверялся на придуманных примерах с очевидными
персональными данными.

**Три остатка, найденные разбором вручную (строки 26, 56, 87), фильтр нашёл** — телефон, почта и ФИО
подрядчика распознаны. На этом хорошие новости кончаются.

**Из 63 находок настоящими персональными данными являются пять.** Остальные 58 — ложные:

| Что найдено | Сколько | Как помечено |
|---|---|---|
| «РФ», «Российской Федерации» | 13 | АДРЕС |
| «ИПУ», «ХВ» — приборы учёта и холодная вода | 12 | АДРЕС |
| «Вами», «Ваше», «Вашей», «Вашему адресу» | 8 | ФИО и АДРЕС |
| «Пункту», «Сама», «Ещё», «Прилагаю», «Водой», «Контрагент» | 7 | ФИО и АДРЕС |
| «Эталон» — название подрядчика | 5 | ФИО |
| **«ХВ 142,858м3» — показания счётчика** | 1 | **ФИО** |

Что уходит провайдеру после обезличивания:

> «Согласно **Пункту** 84 Постановления Правительства **РФ** от 06.05.2011 № 354…»
> → «Согласно **⟨ФИО⟩** 84 Постановления Правительства **⟨АДРЕС⟩** от 06.05.2011 № 354…»

> «…передавала показания ИПУ **ХВ 142,858м3**, а в нашей программе внесены 143 м3…»
> → «…передавала показания ИПУ **⟨ФИО⟩**, а в нашей программе внесены 143 м3…»

Во втором случае **уничтожено само число, ради которого задан вопрос**. Модель получает текст, по
которому правильный ответ невозможен в принципе, — и по правилу 4.2 это происходит на пути каждого
запроса абонента.

**Порог не поможет:** у ложных находок та же оценка 0,85, что у настоящих. Разделить их числом
нельзя.

**Это пятый случай закономерности раздела 54.4 — и новая её разновидность.** Прежние четыре нашла
живая проверка: тесты подменяли провайдера, сеть, библиотеку. Здесь подменялись **данные**. Синтетика
для проверки обезличивателя содержит очевидные персональные данные и не содержит ни юридических
ссылок, ни отраслевых сокращений, ни местоимений с заглавной буквы — то есть ровно того, из чего
состоит настоящее обращение.

Вывод в ту же строку, что и прежние: **набора тестов недостаточно, если данные в нём придуманы теми
же, кто писал код.**

### Починено в тот же день

Добавлен отсев находок разбора языка — по форме и по словарю. Порог не годился: у ложных находок та
же оценка 0,85, что у настоящих.

| Правило отсева | Что снимает |
|---|---|
| Цифры внутри фрагмента | «ХВ 142,858м3» — показания счётчика |
| Знаки препинания внутри | «день!Объясните» — неверно найденные границы |
| Короткое сокращение заглавными | «РФ», «ИПУ», «ХВ», «ГВ», «УК» |
| Словарь местоимений и ролей | «Вами», «Ваше», «Контрагенту», «Пункту», «Сама» |
| Словарь месяцев и государства | «Август», «Российской Федерации» |

Отсев применяется **только** к находкам разбора языка. Собственные распознаватели считают
контрольные суммы и опираются на слова-подсказки — свидетельство сильнее, и трогать их нельзя:
СНИЛС, ИНН, счёт и телефон состоят из цифр и проверку формы не прошли бы. Это закреплено тестом.

**Результат на тех же 136 текстах: 63 находки в 34 строках → 16 находок в 13 строках.** Все три
остатка, найденные разбором вручную (строки 26, 56, 87), по-прежнему находятся; ФИО подрядчика
скрывается.

Из оставшихся шестнадцати настоящими данными являются пять; ещё три — телефоны организаций;
остальные восемь — избыточное скрытие («Эталон» — название подрядчика, «Воронеже», «Выписку»).
**Это допустимая цена и правильное направление ошибки:** скрыть лишнее название подрядчика —
косметическая потеря, скрыть показания счётчика — потеря смысла вопроса. Исчезли ровно те находки,
которые уничтожали смысл.

Проверено, что тесты ловят возврат дефекта, а не проходят по случайности: отсев отключён — два теста
упали, восстановлен — прошли. Дисциплина раздела 54.4, дополнение v4.20.

## 56.11. Запасной классификатор пересобран — и вскрыл потолок самих данных

Перечень ключевых слов подбирался по формулировкам разделов 9 и 11.2 и был
помечен в модуле как предположение. Замер: **54% настоящих текстов не
распознавались вовсе**.

**Почему — выяснилось при разборе, и это важнее самого перечня.** Слова брались
из названий типов, а оператор пишет не ими:

> **Только 28% текстов содержат хоть одно слово из названия собственного типа.
> У восьми типов из шестнадцати — ни один текст из девяти.**

«Обследование» во всех девяти случаях записано как **«снятие кп»** — слова
«обследование» нет нигде. «Справка» в этой системе означает справку для сделки
купли-продажи и пишется как **«сделка»**. А тексты под типом «Отмена обращения»
(«ПУ 1шт ГВ», «первичная», «Тестовая») к отмене отношения не имеют вовсе —
похоже, это **статус обращения, а не его тема**.

**Отсюда главный вывод: `bname` — не разметка текста.** Оператор классифицировал
случай, зная больше, чем написано: вложения, телефонный разговор, историю счёта.
Это дополняет находку 56.4 («Другое» — свалка) и делает её общей: дело не в
одном типе, а в том, что метка вообще не выводится из текста в двух случаях из
трёх.

### Что сделано

Перечень пересобран **по наблюдённому словарю, а не по названиям типов**. Там,
где наблюдений не хватило, слова не выдуманы, а тип оставлен без перечня:
пустой список честнее угаданного. Так остались `other` (исход по умолчанию) и
«Повторная приемка (с авто)» — одно наблюдение, и что означает «с авто»,
неизвестно (пункт 41).

Классификация переехала из скрипта в `app/taxonomy.py` (`classify_by_keywords`):
она понадобится на код-шаге 6, и логике не место в измерительном скрипте.
Возвращаются **все** подошедшие коды, а не первый: неоднозначность — свойство
текста, и прятать её выбором нельзя.

### Замер: `scripts/measure_classifier.py`

Слова собраны по этим же текстам, поэтому замер на них целиком показал бы
запоминание, а не качество. Выборка делится по каждому типу: две трети —
обучающая, треть — отложенная.

| Показатель | Обучающая | Отложенная |
|---|---|---|
| Охват (нашёлся хоть какой-то сигнал) | 74% | **75%** |
| Точность там, где сигнал есть | 75% | **65%** |
| Неоднозначных (два кода и больше) | 24% | 20% |

Было — охват 46%. Расхождение точности между частями (75% против 65%) и есть
мера подгонки под выборку; при девяти наблюдениях на тип иначе и быть не могло.

**Числа указывают направление, но метрикой качества не являются.** Настоящая
оценка появится на эталонном наборе (пункт 14), собранном ручной разметкой, — а
разбор выше показал, почему выгрузка «как есть» разметкой служить не может.

**И главное, что этот замер утверждает:** запасной режим не заменяет модель.
При потолке в 28% выводимых из текста меток он удерживает сервис от полного
отказа — не более, и обещать от него большего нельзя.

# 57. График отключений: источник, который не должен идти через базу знаний (v4.23)

Получен образец графика плановых отключений (`отключения.txt`, открытые данные, персональных данных
нет). В каталоге источников раздела 29 плановые отключения не значились вовсе. Решение — ADR-013.

## 57.1. Зачем он нужен: вопрос из выгрузки обращений

В `test44.csv` под типом «Другое» лежит: «По адресу неделю нет холодной воды. Поясните причину».
График отвечает на него прямо. Источник закрывает **реальный** сценарий, а не предполагаемый, — и
это первый случай в проекте, когда данные пришли под уже наблюдённый вопрос, а не под гипотезу.

## 57.2. Прототип живёт на открытых источниках — и это меняет критический путь

На прототипе — только открытые источники. Но «открытые» не значит «выдуманные»: настоящих источников
у прототипа **два**.

| Источник | Природа на прототипе |
|---|---|
| График отключений | Открытые данные, настоящие как есть |
| Обращения абонентов (`test44.csv`) | **Настоящие тексты**, замаскированы только персональные данные |
| Биллинг, личный кабинет | Синтетика |
| Документы базы знаний | Открытые источники — публичный сайт и FAQ |

Это меняет цену двух вещей. **Замер запасного классификатора (54% нераспознанных, раздел 56.7)
сделан на настоящем языке абонентов**, а не на выдуманных фразах, — то есть это оценка, а не
упражнение. И **остаток персональных данных в шаблонных колонках (пункт 40) — это данные реальных
людей**, а не вторая партия подставных: предположение раздела 56.1 подтвердилось.

**Следствие, выходящее за рамки графика:** база знаний прототипа собирается из открытых источников —
публичный сайт и FAQ (источник 11 каталога), — а не из документов Word. Пункт 3 `Data_Request.md`
уходит с критического пути кода-шага 5: строить поиск можно уже сейчас. Образцы закрытых документов
остаются нужны для MVP.

Во всех предыдущих версиях контекста шаг 5 числился заблокированным. Он не заблокирован.

## 57.3. Формат нестабилен — измерено, а не предположено

6 районов, 20 периодов, 180 строк улиц, **1827 уникальных адресов**, 152 написания улиц.

| Признак | Наблюдение |
|---|---|
| Тип улицы | префикс «ул.» — 108; **без типа вовсе** — 40; постфикс («Победы б-р, 2,4,6») — 18; **двойной тип** («ул. пер. Цимлянский», «ул. Ленинский пр.») — 13 |
| Одна улица разными именами | «О. Дундича» / «Олеко Дундича»; «Спор. Набережная» / «Спорт Набережная»; «Б. Победы» / «Победы б-р»; «Ленинский пр.» / «Ленинский пр-т» |
| Окончания строк | 106 «;», 40 «.», 34 — ничем |
| Мусор | 3 висячие запятые, 4 точки с запятой **внутри** списка домов, 3 пробела перед запятой |
| Даты | **года нет нигде**; 14 формулировок на 20 периодов; «по» и «до» вперемешку; составной период; **«с 28 июля по 10 июля»** — конец раньше начала |

**Ловушка, проверенная на себе:** улица **«Набережная»** носит название, совпадающее со словом-типом.
Первый проход разбора её уничтожил — нормализатор снял «набережная» как тип и получил пустое имя.
Правило: слово-тип снимается, только если после снятия остаётся непустое название. Это тот же класс
ошибки, что хвостовой пробел в таксономии, и найден он тем же способом — прогоном по настоящим
данным, а не рассуждением.

## 57.4. Данные внутренне противоречивы

**4 адреса числятся в двух районах сразу** (Димитрова 27 и 51а, Набережная 1а/1 — Железнодорожный и
Левобережный; Станкевича 45 — Ленинский и Центральный). **40 адресов попадают в два пересекающихся
периода** одного района.

На вопрос «когда у меня отключат» из одного файла следуют два разных ответа.

**Это свойство файла, а не данных.** Документ собран человеком по периодам, и один адрес попадает в
несколько списков; в БД, где запись заводится на адрес, такое противоречие не выражается. Значит
правило нужно только загрузчику прототипа, и принимаем его мы: **показывать все найденные интервалы,
не выбирая между ними**. Спрашивать владельца о противоречиях документа, который на MVP исчезнет, не
стоит.

## 57.5. Правило, обобщающее ADR-012 и ADR-013

> База знаний отвечает на то, что **объясняется**. То, что **проверяется по факту**, отвечается
> точным поиском, а не генерацией по найденному.

График — второй класс вопросов, обходящий генерацию, и причина **обратна** ADR-012: там текст обязан
не меняться, здесь обязан меняться постоянно. Общее — обоим нужен поиск по ключу, а не по смыслу.
Индексировать график в базу знаний нельзя по трём независимым причинам: он протухает, адрес не несёт
смысла для векторного поиска, а пересказ списка из шестидесяти домов — ровно то, в чём модель
ошибается убедительно.

Шов проходит по источнику: разбор — отдельный шаг приёма, при переходе файл → БД заменяется он один.

> **[ПЕРЕСМОТРЕНО в тот же день.]** Первая редакция советовала не читать чужую БД синхронно даже
> после получения доступа. Довод выводился из **файла** — источника без схемы. Уточнение владельца:
> в БД лежат **все адреса, атрибут отключения и время**, то есть время типизировано и разбирать на
> пути абонента нечего. И появляется довод *за* синхронное чтение: отключение может стать
> внеплановым, а ответ, отставший на часы, здесь не менее свежий, а неверный. Решение: читать
> онлайн, короткий кэш против задержки и всплесков, при недоступности БД — последнее известное
> состояние **с оговоркой о его времени**. Устаревание и недоступность различаются обязательно.

**Тестовая БД прототипа строится по форме будущей БД** (адрес · атрибут отключения · время), а не по
форме файла («период → список улиц»). Тогда разбор файла — одноразовый загрузчик, а хранилище и
запрос пишутся один раз. Обратный порядок означал бы переписывание всего, что стоит за хранилищем, —
цену расходящихся источников истины проект платил уже трижды.

**Побочная ценность:** «все адреса» — это адресный реестр. Нормализация адреса становится
сопоставлением с эталонным списком, а не разбором строки по словарю сокращений, и ловушка с улицей
«Набережная» на MVP не возникает вовсе.

## 57.6. Онлайн-доступ к БД на MVP — исключение из ADR-003, а не его отмена

ADR-003 запрещает прямой доступ к БД внешних систем. Заявленный на MVP доступ под запрет попадает.
Разбор по силам самого ADR-003: из четырёх применима одна (схема — не контракт); запись, ПДн и
множественность потребителей здесь не действуют. Поэтому — **явное исключение**, второе в проекте
после офлайн-выгрузки источников 3 и 10.

Смягчение, которое стоит запросить: доступ к **представлению**, а не к таблицам. Представление —
минимальный контракт, который владелец даёт дешевле, чем API.

## 57.7. Разбор написан и намеренно оставлен простым

`app/outages/parser.py`, 262 строки, 36 тестов. На настоящем файле — 6 районов, 1939 записей,
1821 уникальный адрес, 146 улиц.

Запись повторяет **форму будущей БД** (адрес · отключение · интервал), а не форму файла. Тест
сторожит состав полей: если запись снова станет «периодом со списком улиц», переход на онлайн-доступ
потребует переписать всё, что за ней.

**Ловушка с «Набережной» подтвердилась на практике.** Первый проход разбора снял «набережная» как
слово-тип и получил пустую строку — уничтожил улицу. Правило: последний оставшийся токен не снимается
никогда. Проверено, что тест ловит возврат: правило ослаблено — тест упал, восстановлено — прошёл.

Цена правила осознанна: «Спор. Набережная», «Спорт Набережная» и «Набережная» сводятся к одному
названию. Несогласованная нормализация хуже слияния — улица, не совпадающая сама с собой, не находится
вовсе; слияние же видно через сохранённое исходное написание и разводится районом.

**Отчёта о проблемах источника разбор не ведёт** — решено при упрощении. Две потери приняты: адреса
под перевёрнутым периодом (1 строка) и дубли адреса в разных периодах и районах (40 и 4). Оба — свойства
**файла**, а не данных: документ собран человеком по периодам, и в БД, где запись заводится на адрес,
ни того, ни другого не возникает. Разбирать противоречия источника, который на MVP исчезнет, дороже,
чем прожить с ними.

Не упрощена при этом нормализация: она не про терпимость к дефектам, а про то, найдётся ли адрес
вообще.

## 57.8. Путь ответа: адрес из профиля ЛК, модель не вызывается

Тема `outage` уводит вопрос на точный поиск. **Адрес берётся из профиля личного
кабинета**, а не из текста: ЛК его знает, а извлекать из формулировки — лишний
шаг, теряющий как раз нужные случаи («у нас третий день нет воды» адреса не
содержит вовсе).

В контракт добавлены два поля `RequestMetadata`: `topic` — вторая ось ADR-011,
до сих пор жившая только в коде, — и `address`. Спецификация API пересобралась
сама.

**Шлюз остался без предметной логики.** Он знает лишь, что у него может быть
«прямой ответчик» (`DirectResponder`), и ничего — про водоканал, адреса и
отключения; предметный ответчик внедряется снаружи. Иначе утверждение из
описания шлюза «здесь нет ничего про водоканал» перестало бы быть правдой при
первой же теме. Тем же механизмом на шаге 6 подключится реестр регламентных
ответов (ADR-012).

Разбор проверок на этом пути зафиксирован тестами, а не соглашением: **лимиты
проверяются** (иначе появился бы путь в обход них — ответ без модели ничего не
стоит нам, но обработка запроса стоит), обезличивание пропускается (наружу
ничего не уходит), охранители не применяются (они проверяют сочинённое моделью,
а здесь сочинять было некому).

**Пустой результат поиска — это ответ, а не молчание.** «Плановых отключений
нет» отдаём мы; промолчи ответчик, за него ответила бы модель, которой график
неизвестен, и выдумала бы срок. Молчание означает только «не мой случай»: чужая
тема или адрес, который не разобрался.

Оговорка о дате получения графика идёт **обоими путями** — и в ответе целиком, и
в потоке. Проект уже платил за односторонность: фактически ответившая модель
была видна только в ответе целиком, пока поле не добавили и в поток (54.3).

### Ошибка, пойманная сквозным прогоном

Сокращение «д.» означает и «дом», и «деревню». Первая редакция разбора адреса
отбрасывала «д. 2» как населённый пункт — адрес переставал разбираться целиком,
и ассистент **молча уходил отвечать моделью**. Нашлось не тестом, а прогоном
живого запроса через шлюз с провайдером, который падает при вызове.

Это шестой случай закономерности раздела 54.4: тест разбора адреса был бы
написан на том же наборе сокращений, из которого сделана ошибка.

## 58.1. Настройка времени повтора ни на что не влияла

`quota_retry_after_seconds` доходила из `app/config.py` через `app/main.py` до
`QuotaManager.store_retry_after` — и **там кончалась**. Заголовок `Retry-After` собирался
выскабливанием первого числа из русского текста пояснения.

На `429` это работало **случайно**: в пояснении стоит остаток окна. На `503` цифр в пояснении нет
вовсе, и заголовок всегда получал зашитую тридцатку — какое бы значение ни стояло в настройке.

Причина структурная: `ProblemDetail` объявлен с `extra="forbid"` и поля под секунды не имел, поэтому
величину было негде передать, кроме как прозой для человека. **Величина, которую передают прозой,
однажды перестаёт передаваться.**

Добавлено поле `retry_after` — не из RFC 7807, как и `trace_id`, и по той же причине. Выскабливание
удалено.

**Тест выглядел покрывающим и не был им.** Он подставлял синтетическое тело `detail="повторите через
17 с"`, которого шлюз на пути `503` никогда не производит. Новый тест кладёт в пояснение **другое**
число: если заголовок снова начнут собирать из текста, это станет видно. Второй тест ведёт величину
сквозь: от настройки до заголовка через недоступное хранилище.

Это ровно то, о чём предупреждает дополнение v4.20: *похожая формулировка соседней проверки создаёт
видимость покрытия там, где его нет.*

# 59. Модели поиска замерены: обе из ADR-007 не укладываются в бюджет (v4.25)

Шаг 5 начат с замера, а не с кода. ADR-007 фиксирует **BGE-M3** и кросс-энкодер
**BGE-reranker-v2-m3**, обе с пометкой «своя, GPU». Машина прототипа видеоускорителя не имеет, и
вопрос, что это значит для бюджета задержки, до сих пор не задавался: шаг 5 числился заблокированным
отсутствием базы знаний.

## 59.1. Числа

`scripts/measure_search_models.py`, медиана из трёх прогонов на кэшированных весах:

| Модель | Веса | Загрузка с диска | Запрос (синхронный путь) | Корпус, 64 фрагмента |
|---|---|---|---|---|
| BGE-M3 | 4,25 ГБ | 7,8 с | **210 мс** | 16,1 с (≈4/с) |
| BGE-reranker-v2-m3 | 2,14 ГБ | 5,4 с | **5 774 мс** на 20 кандидатов | — |
| multilingual-e5-small | **0,46 ГБ** | 8,7 с | **22 мс** | 1,3 с (≈48/с) |

Бюджет — `P99 поиска < 100 мс` (DoD, раздел 18). Эмбеддинг BGE-M3 превышает его **вдвое**,
переранжирование — **в 58 раз**. Маленькая модель укладывается с запасом: вдевятеро легче, в девять
раз быстрее.

**Две оговорки, без которых числа врут.** Первый прогон дал «загрузку» в 494 и 269 секунд — туда
попало скачивание весов; таблица снята со второго запуска. Память измерена приростом RSS и
показательной **не является**: 0,33 ГБ при 4,25 ГБ весов, а у кросс-энкодера ровно ноль. Обе оговорки
внесены в сам скрипт, чтобы следующий не принял восемь минут за время загрузки.

Это пятый случай, когда тяжёлая загрузка пряталась в первый вызов — после импорта LiteLLM, модели
обезличивателя, весов локальной модели и времени после перезапуска (пункт 35).

## 59.2. Почему переранжирование нельзя ни вынести наружу, ни сделать асинхронным

**Наружу** — ADR-007 это прямо запрещает, и причин две, из которых задержка вторая. Первая:
запрос абонента содержит ФИО, лицевой счёт и адрес, и по замыслу эмбеддится **внутри периметра, минуя
обезличиватель**, потому что не покидает контур. Вынос наружу означает сначала обезличить — ADR-007
разобрал ровно этот вариант и отклонил. Для кросс-энкодера хуже: он видит не только запрос, но и
найденные фрагменты.

**Асинхронно, параллельно генерации** — переранжирование по построению стоит **до** генерации: его
результат решает, что попадёт в промпт. Посчитанное после начала потока на ответ не влияет, а поток
необратим (правило 4.3).

Формально можно было бы подставить переранжированные источники в событие `metadata`, которое по
разделу 7.3 идёт после текста. Но тогда абоненту показываются **источники, на которых ответ не
построен**, — он пойдёт проверять по документу, которого модель не видела. Ложная атрибуция хуже
отсутствия переранжирования.

## 59.3. Решение — ADR-014, и главное в нём не про железо

На прототипе: **e5-small, переранжирования на пути абонента нет**, отсев берёт на себя порог 0,7. На
MVP ADR-007 остаётся как есть — ничего в нём не отменяется.

Главный пункт решения другой. Утверждение «на маленьком корпусе реранкер бесполезен» — **рассуждение,
а не число**, и за эту сессию проект семь раз получал от данных обратное тому, что казалось
очевидным. Поэтому судьба переранжирования отдана **офлайн-замеру расхождения**: прогнать эталонные
вопросы через векторный поиск и через кросс-энкодер вне пути абонента и посчитать, как часто тройка
расходится.

Совпадение почти всегда — переранжирование не нужно и на MVP, и ADR-007 подлежит пересмотру по
существу. Расхождение в заметной доле — оно нужно, и вопрос о видеоускорителе становится вопросом
качества, а не удобства. Стоимость замера ничтожна: сто вопросов — десять минут фоновой работы.

Так вопрос переводится из «нет железа» в «нет доказанной пользы». Это разные основания, и второе
применимо к MVP, а первое нет.

## 59.4. Цена, которую платим

**Прототип и MVP расходятся по модели эмбеддингов.** Всё, что будет измерено по качеству поиска на
прототипе, на MVP напрямую не переносится — это надо помнить при чтении любых цифр Recall@3 (пункт 14).

Ошибки векторного поиска на прототипе ничем не правятся: что нашлось, то и уходит в промпт.

И качество **ни одной из трёх моделей** на русскоязычной базе знаний водоканала не проверено. Замер
мерил скорость и вес; выводов о качестве из него не следует, и ADR-007 сам держит это открытым.

## 59.5. Обновление сведённого TODO (раздел 44.4)

ADR-014 в Accepted); проверка качества e5-small против BGE-M3 на русской базе знаний, когда корпус
появится.

**Не изменилось:** содержимое открытых источников — единственное, что сейчас блокирует и сам поиск, и

# 60. Один филиал, корпус найден (v4.26)

## 60.1. Прототип обслуживает Воронеж

Присланы четыре сайта Росводоканала — Сахалин, Архангельск, Краснодар, Воронеж. Решено: **прототип
обслуживает один филиал, воронежский.**

Это снимает размерность, которая иначе прошла бы через всё: шаблон сайтов общий, но телефоны, адреса
центров обслуживания и платёжная платформа у филиалов разные. При нескольких филиалах фильтру поиска
понадобилась бы ось «филиал» наравне с `topic`, а ответить абоненту из Архангельска краснодарским
телефоном — ошибка того же рода, что назвать чужую улицу в отключениях.

Заодно объяснилась странность выгрузки: «Краснодар Водоканал» и «г. Воронеже» в одних данных — это
разные филиалы, а не след маскирования.

## 60.2. Выгрузка приведена к одному филиалу

`scripts/sanitize_inquiries.py` дополнен приведением: любое упоминание филиала сводится к
`ООО "РВК-Воронеж"`, город в адресе — к «г. Воронеж». Результат: **17 упоминаний организации, 137
адресов, чужих филиалов ноль.**

Два решения по ходу:

**Название заменяется целиком, а не городом внутри.** «ООО "Краснодар Водоканал"» с подстановкой
города дало бы «ООО "Воронеж Водоканал"» — организации с таким именем не существует. Формы названий
у филиалов разные: краснодарская «⟨город⟩ Водоканал», остальные «РВК-⟨город⟩».

**Падеж не ломается.** «в г. Воронеже» — банковское отделение, город уже нужный; замена превратила бы
это в «в г. Воронеж».

**Найден пятый филиал, которого не было ни в одном списке** — «ООО "Оренбург Водоканал"». Первая
редакция перечисляла филиалы по именам и пропустила его. Шаблон переделан на «любое слово с
заглавной»: перечень филиалов не закрыт, и это доказано на месте. Тест сторожит именно оренбургский
случай.

## 60.3. Корпус базы знаний найден и подходит

Раздел «Абонентам» воронежского сайта — порядка 40–50 страниц, и среди них **FAQ из 20 пар
вопрос-ответ** (`/users/general_info/faq/`). Это лучший вид материала для поиска: вопрос уже
сформулирован так, как его задаёт абонент.

Содержание совпадает с реальными обращениями: справка об отсутствии задолженности («Справка»),
истёкший межповерочный интервал («Заказать поверку»), повышающий коэффициент
(«Начисления/Перерасчет»), недоставленная квитанция («Оплата»).

Тексты короткие — способы передачи показаний это список из шести пунктов по строке. Нарезка выйдет
простой.

**Страница отключений на сайте графика не содержит** — только подписку по улице и дому. Это
подтверждает ADR-013 с неожиданной стороны: сам сайт работает по схеме «адрес → отключения», ровно
как наш поиск.

## 60.4. Телефоны водоканала обезличиватель принимает за персональные данные

На краснодарском сайте опубликованы номера **8-903-411-86-76** и **217-03-33** — ровно те, что наш

# 61. Backend появился, шлюз вернулся к своим обязанностям (v4.27)

## 61.1. Почему это делалось именно сейчас

Оркестратора не было, и его работу подхватывал шлюз: ответчик отключений жил
внутри него, а демо-стенд обращался к шлюзу напрямую. Работало — но раздел 5.2
распределяет обязанности иначе, и связи раздела 5.3 подписаны недвусмысленно:
**Backend → Vector DB** «Поиск контекста», **Backend → LLM Gateway** «Промпт с
контекстом».

То есть искать должен Backend. Положить туда же поиск значило бы увеличить
отступление сразу после того, как разобрались, почему так делать нельзя.
Дешевле остановиться на третьем предметном пути, чем на шестом.

Порядок плана нарушен осознанно **в третий раз**: шаг 7 сделан раньше шага 6.
Причина внешняя, как и в прошлые два раза: поиск готов, а места для него нет.

## 61.2. Что переехало

`app/backend/orchestrator.py`. Три пути ответа, и только один идёт к модели:
`outage` — точный поиск по графику, `water_quality` — утверждённая формулировка
(ADR-012, ещё не реализована), всё остальное — поиск по базе знаний и генерация.

Из шлюза **удалены** `DirectAnswer`, `DirectResponder` и параметр `direct`.
Утверждение из его описания — «здесь нет ничего про водоканал» — снова стало
правдой. Два теста сторожат границу: шлюз не знает ни про прямые ответы, ни про
поиск, причём второй проверяет отсутствие упоминаний в исходнике.

Ответчик отключений переехал вместе с путём. В его описании записано, что
первая редакция жила в шлюзе и почему слой был не тот, — иначе через полгода
переезд выглядел бы беспричинным.

## 61.3. Лимиты проверяются один раз, но в разных местах

Это выглядит как недосмотр и им не является. Запрос, доходящий до модели,
проверяет шлюз (порядок quota-first, раздел 41.3). Запрос, отвечаемый напрямую,
до шлюза **не доходит** — его проверяет Backend.

Довод тот же, что в ADR-013: ответ без модели ничего не стоит нам, но обработка
запроса стоит, и путь в обход лимитов стал бы способом бесплатно давить сервис.
Backend при этом повторяет решения шлюза, а не заводит свои: `429` при
превышении, `503` при отказе хранилища — иначе абонент получал бы разные коды на
одну причину в зависимости от пути. Оба случая закреплены тестами.

## 61.4. Ожившая метрика

`vector_db_pending_queries` была объявлена под виджет дашборда и **не писалась
ничем** — та же болезнь, что разбирал раздел 54.1. Поиск дал ей источник:
глубина очереди и есть число запросов, находящихся в поиске прямо сейчас.

очередь навсегда непустой.

# 62. Шаг 6: классификация и правило, которого не хватало (v4.28)

## 62.1. План вскрыл недосмотр предыдущего шага

Проверки шага 6 читаются как список требований, и одно из них оказалось
невыполненным: **«Консультант не вызывает генерацию при пустом контексте»**.
Раздел 8.2 говорит то же с другой стороны — ниже порога контекст считается не
найденным, и включается запасной путь **без модели**.

Оркестратор же, написанный на шаге 7, при пустом поиске шёл к модели, и в его
описании было прямо сказано «модель отвечает без опоры». Это расходилось и с
планом, и с разделом 8.2, и заметил я это только читая план перед шагом 6.

**Почему это важнее, чем кажется.** Модель без контекста не молчит — она
отвечает связно, уверенно и на общих сведениях о водоснабжении, которых в
регламентах водоканала может не быть вовсе. Абонент получит правдоподобный
вымысел, и отличить его от настоящего ответа не сможет ни он, ни мы.

## 62.2. Тема определяется правилами, и это не упрощение

Тема решает, **звать ли модель вообще**: `outage` уходит на график,
`water_quality` — на утверждённую формулировку, оба минуют генерацию. Определять
её моделью значило бы звать модель, чтобы узнать, звать ли модель, — и платить
за это на каждом запросе, включая те, где она не нужна.

Правил хватает: тем три, две узнаются по прямым признакам. Признаки составные, а
не однословные: «вода» встречается в каждом втором обращении к водоканалу.

**Слово «авария» в признаки не входит,** хотя выглядит подходящим. В базе знаний
есть вопрос «Что делать, если прибор учета вышел из строя из-за аварии на
внутренних сетях» — это про счётчик, и по одному слову его увело бы на график
отключений, где ответа нет. Случай закреплён тестом.

**Замер на 136 настоящих обращениях: ровно один `outage`** — тот самый, что
находился вручную («По адресу неделю нет холодной воды»). Ложных срабатываний
ноль.

## 62.3. Тип обращения — пока только по ключевым словам

Тип нужен для регистрации (Этап 2) и для разбивки метрик. **На Этапе 1 ничего не
регистрируется**, поэтому единственный его потребитель — метрика, а лишний вызов
модели ради разбивки графика удвоил бы задержку и стоимость каждого ответа.

Охват запасного режима 75%, точность 65% там, где сигнал есть (раздел 56.11).
Для метрики достаточно, для регистрации нет — к Этапу 2 сюда добавится режим с
моделью, и место для него оставлено: классификатор принимает готовый тип извне.

## 62.4. Значение вне справочника не выходит ни по одному пути

Требование шага 6 сформулировано как условие готовности: «ни один путь возврата
типа обращения не выдаёт значения вне справочника». Обе оси проходят через
приведение — включая переданное снаружи, — и тест перебирает пустые строки,
бессмыслицу и посторонние вопросы.

Это же закрывает дефект 11.8: запасная ветка прототипа отдавала транслитерацию
`prochee` вместо кода, и фильтр поиска молча не находил ничего.

## 62.5. Осознанная дыра в правиле консультанта

Правило применяется, **только если поиск состоялся**. Пустой контекст —
свидетельство промаха поиска, а не его отсутствия: когда база знаний не
настроена, отказывать было бы не на что опереться, и ассистент молчал бы на
любой вопрос, ломая демо-стенд.

Дыра видна: `app/main.py` при отсутствии корпуса пишет предупреждение. **На MVP
так работать нельзя** — там пустая база знаний должна ронять запуск, а не
понижать качество молча. Записано в самом коде рядом с правилом.

## 62.6. Сквозной прогон

|---|---|---|
| «Как получить справку об отсутствии задолженности?» | поиск и генерация | вызвана |

# 63. Данные Биллинга: доступ сделан, связность разошлась (v4.29)

Владелец передал пример выгрузки — `data_example/`, четыре файла в UTF-8 с
разделителем `;`: счета физических лиц (200), профили личного кабинета (59),

**Реальных данных не будет вовсе.** На MVP они придут через API Биллинга, но на

то, на чём прототип живёт постоянно.

## 63.1. Отступление от ADR-003, записанное в самом ADR-003

Правило требует ходить в чужие системы только через их API. Здесь **нарушать
нечего**: интерфейса, через который следовало бы ходить, не существует, а данные
предоставил сам владелец. Отступление внесено отдельным разделом в ADR-003 и
ограничено прототипом.

**Шов проходит по источнику.** `app/billing/source.py` объявляет формы записей по
тому, что нужно ассистенту, а не по тому, что лежит в CSV: на MVP заменится
чтение, а вызовы и всё, что за ними, останутся. То же построение, что у приёма
графика отключений.

Запись правилу подчиняется полностью: на Этапе 1 Биллинг только читается, а
запись Этапа 2 идёт через XML-RPC API владельца и этих файлов не касается.

## 63.2. Деньги — `Decimal`, и это не педантизм

Суммы приходят с запятой («1250,00») и участвуют в ответах о задолженности.
`float` дал бы ошибку округления в копейках — а такую ошибку абонент замечает
первой, и доверия она стоит дороже любой другой.

## 63.3. Что показала проверка связности присланного примера

Проверка связности — прямое требование шага 0 плана («каждый лицевой счёт в
начислениях существует в списке счетов»). На присланном примере она выглядела
так (начисления с тех пор перегенерированы, см. 63.4):

| Что | Состояние |
|---|---|
| Профили ЛК → счета | **связны**, 59 из 59 |
| Счётчики → счета | **связны**, 180 из 180 |
| **Начисления → счета** | **не связывались: 0 из 30** — исправлено перегенерацией (63.4) |
| **Адреса → улицы графика отключений** | совпадало 1 из 12 — исправлено приведением адресов (63.5) |
| Город в адресах | «г. Тестовый» во всех 200 — заменён на «г. Воронеж» (63.5) |

## 63.4. Начисления перегенерированы, связность восстановлена

Владелец распорядился заменить присланный файл начислений, и генератор строит их
**из самих счетов ЛСФЛ** — связность выполняется по построению, а не проверяется
задним числом.

**Что задано владельцем:** услуги ХВ, ГВ, полив и раздельное водоотведение —
ХВО и ГВО; основания «по счётчику», «по нормативу», «перерасчёт»; несколько
строк за месяц у одного счёта; три последних периода; 90% счетов.

**Что выведено из соседних файлов, а не разыграно заново.** Выдумывать
независимо значило бы получить третий несвязный набор:

| Свойство | Откуда берётся |
|---|---|
| ГВ начисляется | только счетам со счётчиком ГВС — иначе плата за услугу без прибора учёта |
| Основание | по состоянию прибора: есть действующий — «по счётчику», нет или просрочен — «по нормативу» |
| ХВО и ГВО | один к одному со своей водой, **с тем же основанием**: пара «вода по счётчику, водоотведение по нормативу» в жизни не встречается |
| Полив | водоотведения не имеет — вода на полив в канализацию не попадает |
| Задолженность | разносится из долга счёта в ЛСФЛ, а не назначается независимо |

**Долг разносится помесячно, а не построчно.** Построчный обход давал месяц, где
холодная вода оплачена, а её водоотведение нет, — так не платят: абонент вносит
сумму по квитанции, а не по отдельным услугам. Свежие месяцы не оплачены
целиком, один оплачен частично и пропорционально по всем услугам, старые
оплачены полностью.

**У шести счетов из ста восьмидесяти долг больше, чем начислено за три месяца.**
Разносится столько, сколько помещается: часть задолженности старше окна, и
показывать её внутри окна значило бы выдумать начисления, которых в нём не было.
Тест проверяет неравенство, а не равенство, и говорит почему.

Итог: 1323 строки, 180 счетов из 200, периоды 2026-06 … 2026-08.

## 63.5. Адреса приведены к воронежским, город заменён

Оба оставшихся расхождения примера закрыты `scripts/normalize_addresses.py`.

**Улицы берутся из самого графика отключений**, а не из справочника и не
выдумываются: любой другой источник дал бы третий несвязный набор — ту же
болезнь, которой страдали присланные начисления. Названия подставляются в том
виде, в каком записаны в источнике («ул. Димитрова», а не «димитрова»), причём
из нескольких написаний берётся самое полное.

**Часть адресов попадает в график, часть — нет, и это намеренно.** Если бы
отключение находилось у каждого абонента, демонстрация показывала бы не работу
поиска, а его неспособность ответить «нет». Дом «не в графике» берётся заведомо
большим номером, а не случайным: случайный мог бы совпасть с отключаемым, и
тогда ответ «отключений нет» оказался бы неправдой.

Номер квартиры не трогается: он ни на что не влияет, и менять его — лишнее
движение в чужих данных.

**Результат на сквозном прогоне:** 200 счетов, **все 200 адресов разбираются**,
у **85 (42%) находятся отключения**. Проверено на настоящем поиске, а не на
совпадении строк:

    г. Воронеж, ул. Спор. Набережная, д. 4    Левобережный  28.07 — 10.08; 10.08 — 13.08
    г. Воронеж, ул. Путиловская, д. 2а        Советский     17.08 — 21.08
    г. Воронеж, ул. Г.Сибиряков, д. 85        Советский     03.08 — 06.08

Повторный прогон даёт побайтово тот же файл: адрес выводится из номера лицевого
счёта, а не из порядка строк.

## 63.6. Строгий `xfail` сработал дважды за день

Оба расхождения примера стояли тестами с пометкой `xfail(strict=True)`, и о
починке каждого сообщил сам тест — падением с обратным знаком, когда ожидаемая
ошибка исчезла.

Без строгости обе починки прошли бы незамеченными, а пометки остались бы
описывать то, чего больше нет. Приём стоит держать: **известное расхождение
лучше записывать красным тестом, чем комментарием**, — комментарий не заметит,
что его причина исчезла.

Красных пометок в проекте не осталось.

# 65. Эталонный набор собран, и он опроверг порог (v4.32)

Пункт 14 стоял открытым с версии 4.0 и блокировал ADR-006. Набор собран, замер
прогнан — и первое, что он показал, к качеству поиска отношения не имеет.

## 65.1. Из чего собран набор и почему не из перефразировок

Шестьдесят шесть вопросов, из них **шестьдесят три настоящих**. Пять
подмножеств, и они меряют разное:

| Подмножество | Сколько | Что меряет |
|---|---|---|
| `corpus` — вопрос корпуса дословно | 20 | Работает ли поиск вообще. **Мерой качества не является** |
| `real` — настоящий вопрос абонента, ответ в корпусе есть | 30 | **Единственное, что меряет качество** |
| `no_answer` — настоящий вопрос, ответа в корпусе нет | 12 | Порог |
| `outage` — настоящий вопрос про отключение | 1 | До поиска не доходит (ADR-013) |
| `control` — выдуманный посторонний вопрос | 3 | Порог |

**Тексты вопросов нигде не написаны руками.** `golden_set/labels.json` хранит
только номер строки выгрузки и ожидаемые фрагменты; текст подставляет
`scripts/build_golden_set.py`, падая, если источник сместился. Выдуманным
разрешено быть ровно трём посторонним вопросам, и они помечены источником
`invented`; тест сторожит, что выдуманный вопрос не окажется в подмножестве
`real`.

Это не аккуратность. Соблазн собрать эталонный набор перефразировками вопросов
корпуса огромен, а результат был бы отличный и пустой: замер измерил бы нашу
способность перефразировать. Проект этот урок уже оплатил — обезличиватель
проходил проверку на придуманных примерах и калечил настоящие тексты (раздел
56.10), и вывод был записан общим: **набора тестов недостаточно, если данные в
нём придуманы теми же, кто писал код.**

**Чего набор не является.** Соответствие «вопрос → фрагмент» проставлено нами и
владельцем данных не подтверждено. Вопросы настоящие, разметка наша — числа
показывают направление, а не качество, пока разметку не подтвердят. Отдельно:
`bname` выгрузки здесь **не используется вовсе** — размечается не тип обращения,
а то, какой фрагмент отвечает на вопрос.

## 65.2. Качество поиска: тройка почти всегда права, первое место — почти всегда нет

| Подмножество | hit@1 | hit@3 | MRR |
|---|---|---|---|
| `corpus` (санитарная) | 20 из 20 (100%) | 20 из 20 (100%) | 1,00 |
| `real` (качество) | **7 из 30 (23%)** | **26 из 30 (87%)** | 0,52 |

Санитарная проверка прошла: поиск работает, дословный вопрос корпуса находит
свой фрагмент первым во всех двадцати случаях.

**Recall@3 = 87%** — это и есть число, которого требовал пункт 14 и без
которого ADR-006 не мог быть принят. Низкий hit@1 при высоком hit@3 означает,
что в промпт правильный фрагмент попадает почти всегда, но первым идёт чужой:
`top_n = 3` здесь не запас, а несущая конструкция. Уменьшить его до единицы
значило бы потерять три четверти правильных ответов.

**Четыре промаха, и все четыре осмысленные:**

| Вопрос | Ждали | Место | Что вместо |
|---|---|---|---|
| «Прошу направить специалиста для ввода в эксплуатацию ИПУ холодной воды» | faq-13 «Как опломбировать прибор учёта» | 8 | faq-15, faq-16, faq-01 |

близость различает тему, а не наличие ответа, — а порог применяется так, будто
различает второе.

Показателен третий контрольный вопрос, выдуманный нарочно коварным: **«Как
поменять счётчик электроэнергии?» проходит порог с оценкой 0,853** и находит
faq-16 «Как установить новый счётчик». Абонент получил бы ответ водоканала на
вопрос энергосбыта.

**Это седьмой случай закономерности раздела 54.4 и второй, где подменялись
данные.** Первым был обезличиватель.

## 65.4. Что с этим делать — решение, а не настройка

Значение 0,80 **оставлено прежним намеренно**. Выбор между «абонент получил
ответ по чужому фрагменту» и «абонент получил отказ на вопрос, ответ на который
в корпусе есть» — не дело автора кода, и цена каждого варианта теперь известна
числом (пункт 62 TODO).

Три направления, и первое из них не про порог:

1. **Разделять должно не косинусное расстояние.** Оно меряет близость темы, а
   нужна пригодность фрагмента для ответа. Кросс-энкодер ADR-007 видит пару
   «вопрос — фрагмент» целиком и на этой задаче устроен лучше. **Пункт 50
   подорожал и одновременно стал важнее:** офлайн-замер должен теперь считать
   не только расхождение троек, но и то, разделяет ли оценка кросс-энкодера
   вопросы с ответом и без.
2. **Корпус из двадцати пар — часть причины.** На большинство настоящих
   вопросов он не отвечает не потому, что поиск плох, а потому что ответа в нём
   нет. С ростом корпуса доля таких вопросов упадёт, но свойство «близость темы
   ≠ наличие ответа» останется.
3. **Порог как единственная защита недостаточен в любом случае.** Правило «нет
   контекста — нет генерации» опирается на него целиком, и сейчас оно отсекает
   только вопросы не по теме.

**Ничего при этом не сломано:** ошибка не в том, что система делает не то, а в
том, что защита слабее, чем считалось. До сих пор это было неизвестно, потому
что никто не мерил.

## 66.1. Ответ на исходный вопрос ADR-014: тройки расходятся всегда

ADR-014 отдал судьбу переранжирования этому замеру, потому что утверждение «на

|---|---|---|---|

| `real` (настоящие вопросы) | **0 из 30 (0%)** | 0 из 30 | 7 из 30 (23%) |
| без ответа в корпусе | 0 из 15 | 0 из 15 | 3 из 15 (20%) |

На настоящих вопросах тройка **не совпала ни разу**. Рассуждение опровергнуто

Отдельно показателен `corpus`: на дословных вопросах первый фрагмент совпадает
всегда, а состав тройки — лишь в 30% случаев. То есть меры согласны, **что**
отвечает на вопрос, и не согласны, что похоже на него во вторую очередь.

## 66.2. Первое место втрое лучше, тройка — та же

| Мера | hit@1 | hit@3 | MRR |
|---|---|---|---|
| Косинус (e5-small) | 7 из 30 (23%) | 26 из 30 (87%) | 0,52 |
| Кросс-энкодер | **21 из 30 (70%)** | 26 из 30 (87%) | **0,79** |

Переранжирование **не находит ничего нового** — оно и не может, переставляя те
же двадцать фрагментов, — но кладёт нужный первым втрое чаще.

**Для прототипа это означает меньше, чем кажется.** В промпт уходит тройка, и
она содержит правильный фрагмент одинаково часто у обеих мер. Выигрыш
проявился бы, если бы `top_n` был равен единице, — а он равен трём именно
потому, что hit@1 у косинуса низок.

**Три исправления и три поломки, и это не случайность:**

| | Вопрос | Место | Стало первым |
|---|---|---|---|
| исправлено | «Откуда задолженность, если плачу по счётчику» | 4 → 1 | faq-02 (0,139) |
| исправлено | «Необходима поверка счетчика горячей воды на кухне» | 5 → 1 | faq-12 (0,045) |

отвечает», а порядок среди почти-нулей — шум.

Отсюда честное чтение: **три «поломки» — это места, где наша разметка натянута.**
faq-07 отвечает на вопрос «производятся ли начисления, если собственник не
зарегистрирован», а абонент спрашивает «почему огромные суммы, я не пользуюсь
водой». Тема та же, ответа нет. Кросс-энкодер это видит, а косинус — нет, и наша
метка ближе к косинусу, потому что размечали по теме. Это бьёт в обе стороны:
hit@3 = 87% у косинуса, возможно, тоже завышен, и пункт 63 (подтвердить разметку
у владельца) от этого замера только подорожал.

## 66.3. Главное: разделяет лучше, но не решает

Меры сравнивались **в точках равной цены**, с порогом, перебранным по всем
наблюдённым оценкам. Сравнивать по своим сеткам было нельзя: косинус живёт в
0,75…0,90, сигмоида кросс-энкодера — в 0,00…0,93, и разница вышла бы свойством
шага, а не свойством меры.

| Пропущено мимо (из 15) | Косинус сохраняет | Кросс-энкодер сохраняет |
|---|---|---|
| **0** | 4 из 30 | **10 из 30** |
| 1 | 5 из 30 | 11 из 30 |
| 2 | 11 из 30 | 12 из 30 |
| 3 | 12 из 30 | **19 из 30** |
| 5 | 16 из 30 | 20 из 30 |

Кросс-энкодер выигрывает в каждой точке — в полтора-два с половиной раза. При
нулевом пропуске: **10 ответов против 4**.

Разница видна и в самих оценках. Максимум среди вопросов **без** ответа: у
косинуса **0,876** при том, что вопросы с ответом лежат в 0,828…0,901 — то есть
почти весь их диапазон ниже этого максимума. У кросс-энкодера максимум среди
«без ответа» — **0,243**, а медиана вопросов с ответом 0,088 при максимуме 0,926.

**AUC при этом почти одинаков: 0,793 против 0,800.** Противоречия нет: AUC
усредняет по всей кривой, включая области, где пропускать мимо позволено
половину, — там косинус нагоняет. Работать же приходится на строгом конце, и там
кросс-энкодер лучше вдвое-втрое.

**Но проблема не решена, а смягчена.** Даже кросс-энкодер при нулевом пропуске
сохраняет 10 ответов из 30: две трети вопросов, на которые база знаний отвечает,
получили бы отказ. Смена меры не даёт бесплатного обеда — она передвигает цену,
а не отменяет её.

## 66.4. Что из этого следует для решений

**ADR-014 не меняется.** Пункт 2 — «переранжирования на пути абонента нет» —
подтверждён с запасом: 1049 мс на пару, 20,8 с на вопрос при бюджете поиска
100 мс. На процессоре это невозможно ни в каком виде.

**Пункт 4 «Подтверждения» ADR-014 выполнен:** офлайн-замер расхождения проведён,
результат записан. Препятствие к Accepted, названное самим ADR, снято — остаётся
общее для всех решений: смета (P0 №1).

**ADR-007 подтверждён, а не пересмотрен.** Онлайн-переранжирование на MVP имеет
смысл: тройки расходятся всегда, первое место улучшается втрое.

**У пункта 62 появился третий вариант — и он не для прототипа.** Отсекать не
косинусом, а оценкой кросс-энкодера: при нулевом пропуске это 10 сохранённых
ответов против 4. Синхронно на машине прототипа это невозможно; на MVP с
видеоускорителем — возможно, и там переранжирование и без того предусмотрено
ADR-007. То есть **отсев и переранжирование — одна и та же работа**, и делать её
дважды разными мерами не нужно.

**Чего замер не показывает.** Корпус — двадцать фрагментов, `top_k = 20`, то
есть кросс-энкодер видит его целиком. Сравнивались две меры близости, а не
конвейер с переранжированием против конвейера без него: на большом корпусе
полнота первой ступени ограничивала бы вторую. И доля «вопросов без ответа» —
15 из 45 — сама по себе свойство маленького корпуса, а не поведения абонентов.

## 67.3. ADR-012 реализован, и текст написан так, чтобы ничего не утверждать

`app/regulated.py` — реестр регламентных ответов. Путь работает: тема распознана,
ответ отдан дословно, модель не вызвана.

**Где живёт реестр — поправка к самому ADR.** ADR-012 писался до появления
оркестратора и помещал проверку реестра внутрь шлюза: тогда шлюз был
единственным местом, где собирался ответ. С появлением Backend (раздел 61) выбор
пути переехал туда, куда его относит раздел 5.2, а из шлюза удалено всё
предметное. Реестр встал в Backend через уже существующий `DirectResponder` —
тот же шов, которым подключён ответчик отключений. Класть его в шлюз значило бы
вернуть отступление, ради устранения которого Backend и появился.

**Содержание — главное решение этого блока.** Владелец просил «определённую фразу
про стандарт качества». Написать такую фразу самим значит **заявить от имени
водоканала, что вода соответствует нормативам**, — а это утверждение о
безопасности водоснабжения, и ровно от него ADR-012 предостерегает в своём же
тексте: «пересказ регламентной формулировки своими словами — не стилистическая
вольность, а изменение утверждённого утверждения о безопасности».

Поэтому текст **направляет, а не утверждает**: называет, кто ведёт контроль, где
опубликованы его результаты и куда обратиться за сведениями по адресу. Всё
проверяемо. Опубликованной формулировки о качестве на сайте филиала нет — это
проверено, а не предположено; есть раздел раскрытия информации по ПП РФ от
17.01.2013 № 6, и ссылка с номером постановления сверены с сайтом.

**Неутверждённость видна в данных, а не в оговорке.** У записи есть `approved`,
он `False`, и строгий режим загрузки реестра **роняет** её с отдельной ошибкой.
Прототип поднимается нестрого и пишет предупреждение — та же видимая дыра, что у
пустой базы знаний (раздел 62.5). Ошибка, а не пропуск записи: молча выключенный
регламентный ответ отправил бы вопрос на генерацию, то есть туда, откуда ADR-012
его и убирал.

Тест сторожит и содержание: в тексте не должно появиться «соответствует»,
«безопасн», «пригодна», «отвечает требованиям». Проверка грубая по построению —
она не разбирает смысл, а не даёт заявлению завестись при правке «чтобы звучало
лучше».

## 67.4. Живой прогон нашёл два дефекта, которых не видели тесты

Это **восьмой и девятый случаи закономерности раздела 54.4**, и первый из них
особенно показателен.

**Классификатор не узнавал собственную тему.** Вопросы «Какого качества у вас
питьевая вода?» и «Вода из крана пахнет хлоркой, это нормально?» получали тему
`general` и уходили к модели. Признаки в `TOPIC_MARKERS` были взяты **из названия
темы** («качество воды», «мутная вода»), а абонент так не пишет: «качества у вас
питьевая вода» не содержит этой пары подряд, а «пахнет хлоркой» не покрыто ничем.

Тот же дефект, что раздел 56.11 нашёл у ключевых слов классификатора типов —
**слова берутся из названий, а не из языка**, — и найден он снова не тестом:
тесты были написаны на тех же формулировках, из которых сделаны признаки.

Что при этом отвечала модель, стоит привести целиком, потому что это и есть
иллюстрация к ADR-012:

> «обычно информация о качестве воды предоставляется местными органами водного
> хозяйства или самим водоканалом… добавляется для disinfektion (дезинфекции)»

— по фрагментам faq-04 (нулевая квитанция) и faq-01 (повышающий коэффициент),
к качеству воды отношения не имеющим, с латиницей посреди русского слова.
Уверенный вымысел на вопрос, ради которого ADR-012 и написан.

**Починено парным правилом «вода + свойство»**, а не расширением списка
подстрок. Пара, а не одиночное слово: «запах» встречается и про канализацию,
а «питьевая вода» одна увела бы на регламентный ответ вопрос о тарифе на неё.
Замер на настоящих данных: **ноль ложных срабатываний** на 136 обращениях и 20
вопросах корпуса; тариф, перерасчёт, поверка и опломбировка не уводятся.

Признаки помечены как **предположение**, и вот почему: наблюдённого словаря для
этой темы не существует — в 136 настоящих обращениях вопросов о качестве воды
**ни одного**, в корпусе FAQ темы тоже нет. Ноль ложных срабатываний здесь —
отсутствие наблюдений, а не подтверждение. Пересобрать по частотности, когда
такие обращения появятся (пункт 64).

**Второй дефект — обезличиватель вырезает публичный адрес почты.** Ответ на

## 67.5. Зачем нужен доступ к GigaChat — ответ: на прототипе незачем

Пункт 8 так и был записан — «только к MVP», — но за вопросом стоит решение

# 69. Прогрев не выполнялся вовсе, и это нашёл замер, а не рассуждение (v4.36)

Второй из трёх дефектов, видных на экране. Пункт 35 требовал **замерить по
слагаемым, а не предполагать причину** — и замер дал не тот ответ, которого
ждали.

## 69.1. Что показал замер

`scripts/measure_first_request.py`, провайдер исключён, каждое слагаемое — в
отдельном процессе:

| Слагаемое | Время |
|---|---:|
| Импорт модулей | **37–47 с** |
| Сборка приложения | 8–9 с |
| Старт сервиса (прогрев) | 0,02 с |
| Первый запрос | 0,21 с |
| Второй и третий | 0,14 с |

**Первый запрос стоит 0,21 с.** Всё, что дорого, происходит **до** него.

## 69.2. Диагностическим оказался не самый большой столбец, а самый маленький

Замер прогонялся дважды: с прогревом и с выключенным прогревом. Столбец «старт
сервиса» дал **0,01 с в обоих случаях**.

Одинаковые числа там, где должна быть разница, и есть находка: **прогрев не
выполнялся ни в одном из прогонов, потому что вызывать было нечего.**

Интерфейс вызывает прогрев у того, кого ему внедрили:
`getattr(resolved, "warmup", None)`. Пока внедряли шлюз, всё работало. С
появлением Backend (раздел 61) внедрять стали **оркестратор**, у которого метода
не было: `getattr` молча вернул `None`.

То есть починка раздела 50.3 — вынос ленивых загрузок из первого запроса
абонента — **была отменена рефакторингом**, и никто этого не заметил.

## 69.3. Проверка была, и она не могла помочь

```
with TestClient(create_app(TrackingGateway())):
    pass
assert warmed == ["да"]
```

`TrackingGateway` — заглушка **с методом `warmup`**. Проверка доказывает, что
интерфейс вызывает прогрев у того, **у кого он есть**. Что настоящий объект
метод потерял, она увидеть не может по построению.

Раздел 54.4 предупреждал ровно об этом — «метод мог остаться написанным и
неподключённым», — и предупреждение сбылось на том самом месте, ради которого
писалось.

**Добавлена проверка, через которую проходит настоящий `Orchestrator`,** а
заглушкой подменён только шлюз: цепочка внедрения проверяется целиком. Обе новые
проверки падают при возврате дефекта — проверено снятием метода.

Правило, которое стоит держать рядом с правилом раздела 54.4:

> Проверка, подставляющая заглушку **на место проверяемого**, доказывает
> свойство заглушки. Подменять надо соседа, а не того, о ком утверждение.

## 69.4. Оговорка, без которой числа замера врут

Подставляя провайдера, замер заодно **отключает загрузку LiteLLM**: шлюз строит
маршрутизатор только когда вызов не подменён. А импорт LiteLLM — самое тяжёлое
из ленивого, 7,0 с по разделу 50.3.

Поэтому столбец «старт сервиса» показывает 0,02 с и **пользу прогрева не
измеряет**; он годится, чтобы поймать его отсутствие, и в этом качестве
сработал. Оговорка внесена в сам скрипт — как оговорки про скачивание весов в
замере моделей поиска.

## 69.5. Пункт 35 не закрыт, и это записано честно

Найденный дефект настоящий, но **21,6 с он объясняет не полностью**: первый
запрос и без прогрева занимал 0,21 с, а не двадцать секунд.

Вес лежит до запроса — импорт 37–47 с плюс сборка 8–9 с. При `uvicorn --reload`
перезапуск процесса идёт **при открытом сокете**, и запрос, пришедший в это
время, ждёт конца импорта, не получая ошибки. Это объяснило бы наблюдение
целиком.

**Но это гипотеза, а не замер**, и записана она как гипотеза. Проверяется прямым
прогоном стенда с секундомером до и после перезапуска — работа следующего блока.

# 70. Двадцать шесть секунд ждал не прогрев, а недоступный Redis (v4.37)

Продолжение раздела 69. Прогрев там был починен по-настоящему, но пункт 35
остался открытым честно: **21,6 с он не объяснял**. Живой прогон стенда
опроверг и вторую гипотезу — и нашёл причину.

## 70.1. Опровержение вышло из формы чисел, а не из их величины

Стенд поднят, четыре запроса подряд:

| Запрос | Время | Код |
|---|---:|---|
| На прогретом сервисе | 26,31 с | 503 |
| Повторный | 25,47 с | 503 |
| Сразу после трогания файла | 26,65 с | 503 |
| Следом за ним | 24,83 с | 503 |

**Все четыре одинаковы.** Значит дело не в первом запросе (второй такой же) и не
в `--reload` (до трогания файла столько же). Обе гипотезы отпали разом, и не
потому, что числа велики, а потому, что они **не различаются**.

И все четыре — `503`. Redis не поднят: Docker Desktop выключен.

## 70.2. Замер по слагаемым: решает не таймаут, а повторы

Клиент создавался без единой настройки времени. Разбор:

| Настройка | Время до отказа |
|---|---:|
| Как было: без таймаута, с повторами | **26,2 с** |
| Таймаут 0,5 с, повторы оставлены | 8,7 с |
| **Таймаут 0,5 с, повторы выключены** | **0,5 с** |

Попутно выяснилось, что `localhost` разрешается **сначала в `::1`**, и
подключение к нему висит. Напрашивалась замена адреса на `127.0.0.1` — и замер
показал, что она **не решает ничего**: 8,65 с. Догадка выглядела убедительно и
была неверна; решают повторы.

## 70.3. Почему повторы здесь неуместны в принципе

ADR-008 уже ответил на этот вопрос, просто ответ не был исполнен в коде.
Недоступное хранилище — это `503` + `Retry-After`: **повторяет клиент**, по
названному ему времени.

Повтор внутри запроса удлиняет ожидание абонента ровно во столько раз, сколько
попыток, и делает это невидимым: снаружи виден **один долгий запрос**, а не
четыре быстрых отказа. Ни в журнале, ни в метриках четырёх попыток не видно —
видно, что сервис «тормозит».

## 70.4. Что проверяет тест и почему не время

Проверка сторожит **настройку клиента**, а не длительность: время зависит от
машины и от того, поднят ли Redis, и порог сделал бы её хрупкой. Упущена же была
именно настройка, и упустить её снова можно тем же способом.

Проверено, что тест падает при снятии настройки.

## 70.5. Три вывода, которые стоит держать

**Одинаковые числа опровергают сильнее, чем большие.** Разница между гипотезами
искалась в величине, а нашлась в том, что величина не менялась.

**Найденный дефект не обязан быть искомым.** Прогрев (раздел 69) был сломан
по-настоящему, починен по-настоящему — и к 21,6 с отношения не имел. Соблазн
закрыть пункт первой же настоящей находкой был, и раздел 69.5 его удержал: там
записано, что пункт не закрыт и что осталось проверить.

**Отказ тоже имеет время.** Проект мерил задержку успешного ответа и не мерил
задержку отказа. Отказ через 26 секунд — не отказ, а зависание, и абоненту он
выглядит хуже ошибки.

# 71. Пункт 53: замер уточнил не только цену, но и сам довод (v4.38)

Третий из дефектов, видных на экране, — и единственный, где **замер изменил
обоснование**, а не только подтвердил его.

## 71.1. Формулировка пункта оказалась преувеличением

Пункт 53 звучал так: «телефоны в ответах краснодарские при воронежской
организации — демонстрация показывает организацию, которой нет».

Проверка, где эти номера стоят на самом деле:

| Что | Факт |
|---|---|
| Сколько строк выгрузки содержит чужие номера | **одна** (строка 87) |
| В каком поле | только `answer_msg` — ответ оператора |
| Попадают ли в эталонный набор | **нет**: там берётся `text_request` |
| Показываются ли абоненту | нет: абоненту отвечает корпус, а в нём кодов 861 ноль |

То есть **на демонстрации эти номера не видны нигде.** Довод, записанный в
пункте, не подтвердился.

## 71.2. Но нашёлся довод сильнее — и он про нас

В той же строке 87 стоит «в адрес ООО "РВК-Воронеж"». Это **наша подстановка**:
`sanitize_inquiries.py` сводит все филиалы к воронежскому (раздел 60.2).

Значит сочетание «воронежская организация, краснодарские телефоны» **создано
нашей нормализацией**, а не пришло из жизни. Оставить его — оставить след
собственной правки, который следующий читатель примет за свойство данных.

Это меняет и правило, под которое подводится решение. Не «привести данные к
правдоподобию» — настоящих данных проект не переписывает, — а **«не оставлять за
собой полуприведённых данных»**: если нормализация тронула запись, она обязана
оставить её согласованной.

## 71.3. Перечень явный, а не правило

Напрашивалось правило «любой номер не из воронежского списка заменить». Оно
однажды переписало бы **личный номер абонента** — а его надо скрывать, а не
подменять справочным, и разница между этими действиями существенная.

Поэтому в скрипте перечислены ровно три наблюдавшихся номера. Всё остальное
по-прежнему идёт в обезличиватель и попадает в его отчёт. Тест сторожит именно
это: личный номер `to_branch` не трогает.

## 71.4. Цена названа, а не замаскирована

В исходном тексте три номера отвечают за разное: информационно-справочная служба
(два номера) и автоматизированный приём показаний. Воронежских соответствий этим
службам мы **не знаем** — в корпусе известно назначение только у контакт-центра.

Поэтому все три сводятся к нему, и **различение служб теряется**. Подобрать
соответствие по догадке было бы хуже: это тот же класс ошибки, что назначить

# 72. Пункт 65: минута подъёма — цена решения, а не дефект (v4.39)

Последний пункт группы «до демонстрации». Разбор начался с подозрения, что

## 72.1. Замер частей: сумма больше целого

Каждая часть — в **отдельном свежем процессе**, иначе вторая измерялась бы на
уже загруженном стеке первой:

| Часть | Свежий процесс |
|---|---:|
| Обезличиватель: presidio и русская модель spaCy | 24,9 с |
| База знаний: модель эмбеддингов и индексация | 54,0 с |
| Импорт `app.api` | 1,1 с |
| **`app.main` целиком** | **45,3 с** |

**Сумма частей (79 с) больше целого (45 с).** Это и есть главный вывод замера:
`torch` и `transformers` нужны обеим моделям и грузятся **один раз на двоих**.
Отсюда следует то, чего по отдельным числам не видно: убрать одну из двух
моделей сэкономит куда меньше, чем стоит она сама.

**И это не дефект.** Ленивые загрузки вынесены из первого запроса абонента в
старт решением раздела 50.3 — минута при подъёме и есть та цена, которую там
согласились платить, чтобы её не платил первый абонент.

## 72.2. Ловушка замера, в которую я попал

Первая попытка разложить подъём по слагаемым дала 9,8 с вместо сорока с лишним,
и числа не сходились с замером импортов.

Причина: в пробе стояло `import app.main`, а в этом модуле `app = create()`
выполняется **на уровне модуля**. То есть весь подъём произошёл в строке
импорта, которую проба не замеряла, а последующие вызовы `_build_*` попадали на
уже готовое и показывали нули.

Это третий случай той же ловушки в проекте — после «загрузки», в которую попало
скачивание весов (раздел 59.1), и первого замера локальной модели. Общее:
**дорогая работа происходит раньше, чем её начинают мерить.**

## 72.4. Вторая правка: сервис ходил в интернет при каждом старте

Нашлась не рассуждением, а тем, что в журнале живого подъёма появились строки
`HTTP Request: HEAD https://huggingface.co/...`. Библиотека проверяла при каждом
запуске, не обновилась ли модель эмбеддингов.

| Режим | База знаний | Итого |
|---|---:|---:|
| С обращением к `huggingface.co` | 19,1 с | 46,2 с |
| Только из кэша | **5,3 с** | **31,5 с** |

Четырнадцать секунд из сорока шести. **Но главное не скорость.** На MVP сервис
живёт в закрытой сети, где `huggingface.co` недоступен вовсе, и обращение к нему
обернулось бы там ожиданием сетевых таймаутов при каждом подъёме.

Отдельный довод против самой проверки обновлений: **менять модель эмбеддингов
молча нельзя.** Смена модели означает переиндексацию корпуса (ADR-006), и
автоматическое подтягивание новой версии — это тихая смена того, на чём
построены все измерения качества поиска.

Сделано настройкой **на уровне вызова**, а не переменной окружения: переменная
подействовала бы на весь процесс, включая скрипты, которым скачивание как раз
нужно.

**Пустой кэш объясняет себя.** Отказ из-за отсутствия весов неотличим от сетевой
ошибки, поэтому сообщение называет и команду скачивания, и способ разрешить
сеть. Без подсказки причину искали бы не там.
