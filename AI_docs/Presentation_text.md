## 2. Зачем создан AI-помощник

- Абонент теряет время там, где мог бы получить ответ сразу
- Не знает, какое обращение выбрать — десятки типов обращений, не всегда понятно, какой подходит под конкретную ситуацию.
- Ошибается при заполнении — обращение с недостающими данными возвращается на доработку или обрабатывается дольше.
- Не понимает, что дальше — после отправки обращения не ясно, чего ждать и когда, отсюда повторные обращения по тому же вопросу.
- Звонит в колл-центр — каждый типовой вопрос без самостоятельного ответа — лишняя нагрузка на операторов и очередь для всех.

## 3. Цели проекта

- Что должно измениться для абонента и для водоканала
- Сократить время поиска ответа на вопрос
- Снизить долю обращений, оформленных с ошибками
- Снизить число повторных обращений по одному вопросу
- Улучшить качество взаимодействия абонента с личным кабинетом
- Снизить нагрузку на операторов колл-центра за счёт самообслуживания

## 4. Архитектура · контекст (C1): с кем взаимодействует помощник

- Блоки: Абонент водоканала; Платформа ЛК (вход, профиль абонента); AI-помощник абонента водоканала (отвечает на вопросы, помогает с документами и заявками); LLM Provider (GigaChat / YandexGPT — генерация ответа); База знаний (регламенты, инструкции, FAQ); Биллинг (лицевые счета, начисления, показания); Обращения абонентов (регистрация заявок); Диспетчерская (аварийные заявки).
- Связи: вход по SSO; вопрос → ответ; генерация ответа; регистрация заявок — Этап 2, в разработке (пунктир).

## 5. Архитектура · контейнеры (C2): из каких частей состоит решение

- Абонент → AI-виджет в ЛК → API Gateway / Backend (классификация, поиск, сборка ответа).
- Backend → LLM Gateway (обезличивание, лимиты, проверка ответа) → LLM Provider (GigaChat / YandexGPT).
- Backend → Поиск по базе знаний (векторная база + эмбеддинги; переранжирование выключено) ← Индексация документов ← База знаний (регламенты, инструкции, FAQ).
- Backend → Сессии · лимиты · телеметрия.
- Backend → Биллинг и Диспетчерская: чтение (Этап 1).
- Backend → Агент операций записи (заявки, показания, документы — после подтверждения абонента), Этап 2 → Биллинг, Диспетчерская, Обращения абонентов: запись после подтверждения (Этап 2).
- Легенда: работает сейчас (Этап 1); в разработке (Этап 2).

## 6. Архитектура · поток данных: как данные становятся ответом абоненту

- Подготовка — заранее, по расписанию: Документы водоканала (инструкции, договоры, FAQ) → Обработка и очистка (разбор, разбиение, эмбеддинги; отсев дублей — MVP) → База знаний (векторный поиск). Биллинг · Диспетчерская (только через их API) → Профиль абонента (MVP · пересчёт по расписанию) → Кэш профиля (MVP · готовый агрегат).
- Ответ абоненту — сразу, в момент вопроса: ① вопрос → Backend (собирает контекст ответа; лимиты запросов и история диалога) ② читает базу знаний и кэш профиля, свежие данные из Биллинга и Диспетчерской → ③ контекст → PII Filter (заменяет ПДн метками) → ④ без ПДн → Модель формирует ответ (внешний провайдер, получает только текст без ПДн) → ⑤ ответ модели → Проверка ответа (ПДн, тон, обоснованность) → ⑥ проверено → ⑦ ответ абоненту.
- Закрытая сеть водоканала — ПДн остаются внутри; вне периметра — только модель.
- Что важно: наружу, к провайдеру модели, выходит один поток — после PII Filter; с чужими системами (серые блоки) работаем только через их API; запись в чужие системы (Этап 2) — только после подтверждения абонента.

## 7. Архитектура · деплоймент: где и на чём развёрнута система на MVP

- Kubernetes-кластер — общий с личным кабинетом, закрытый контур водоканала. Абонент → Ingress.
- namespace platform: Ingress Controller (nginx); Secrets (Kubernetes Secret из GitLab CI); cert-manager (TLS-сертификаты).
- namespace ai-app: ai-widget (React / TS); backend (Python / FastAPI); llm-gateway (Python / LiteLLM); Этап 2: агент записи, billing-adapter, inquiry-service, doc-generator (после stage-gating).
- namespace inference — CPU, без GPU (GPU-узел — по решению владельца): embedding-inference (e5-small, CPU); reranker-inference (выключен; только при GPU-узле); CronJob etl-index (Kubernetes CronJob, 02:00–05:00); CronJob quality-judge (ночной прогон судьи качества).
- namespace ai-data (PVC на NVMe): qdrant (векторный поиск); postgres (сессии, состояние, телеметрия); redis (лимиты, кэш).
- namespace observability: Prometheus (метрики, запасной источник); Grafana владельца (дашборды как код); Loki (логи, сбор уточняется); Zabbix владельца (алерты не настроены).
- Вне кластера: LLM Provider (GigaChat Pro / YandexGPT, управляемый API, РФ); Своя модель (тираж): Qwen2.5-32B, vLLM, GPU по триггеру — нагрузка / ИБ; Системы водоканала (Биллинг · Диспетчерская · обращения · личный кабинет): чтение / запись после подтверждения.

## 11. Что дальше: Этап 1 — фундамент. Операции от имени абонента — следующий шаг

- Сейчас · Этап 1: консультации и справки по данным абонента; помощь в подготовке обращений; без изменения данных абонента и без отправки заявок; несколько задач в одной реплике — ответ на каждую.
