# ADR-022: Язык и фреймворк Backend / API Gateway — Python, Go, Node.js

## Статус

**Accepted.** Решение принято на этапе прототипирования; отдельного детального ADR в `AI_docs/ADR/`
под него не заводилось — оно жило одной строкой в сводной таблице стека ([ADR-017](ADR-017-tech-stack-by-stage.md)).
Здесь зафиксировано впервые как самостоятельное сравнение — для передачи проекта.

## Контекст

Команда проекта полиглотная: Go Middle, Python Middle, Node.js Upper — то есть все три языка ниже были
реальными, а не гипотетическими вариантами, на любом из них в команде есть практика. Диаграмма C2 на
раннем этапе прямо допускала выбор для контейнера Backend / API Gateway: «Go Middle или Python FastAPI».

Ключевое архитектурное ограничение, которое сужает пространство решения — правило 4.1 контекста проекта
(«L2 — источник истины»): вся RAG-логика (эмбеддинг запроса, поиск, сборка промпта) обязана жить
**внутри** контейнера Backend, не выноситься в отдельный сервис. Это делает выбор языка не вопросом
личных предпочтений или чистой производительности, а вопросом того, на каком языке нужный для RAG
инструментарий существует нативно.

## Сравнение

| Критерий | Python / FastAPI | Go | Node.js |
|---|---|---|---|
| Экосистема RAG/AI (эмбеддинги, PII-обезличивание, LLM-SDK) | Родная — LiteLLM, sentence-transformers, Presidio и подобные написаны на Python или имеют полноценные Python-биндинги | Зрелых библиотек для эмбеддингов и PII-обезличивания практически нет — пришлось бы переписывать их или вызывать Python-подпроцесс | Тоньше, чем у Python: SDK для LLM-провайдеров есть, но инструментов PII-обезличивания и локального инференса эмбеддингов уровня Presidio/sentence-transformers — нет |
| Совместимость с правилом 4.1 (RAG внутри одного контейнера Backend) | Прямая — нужный тулинг уже на этом языке, второй процесс не нужен | Нарушается или требует второго языка/процесса внутри контейнера — то есть фактически то же нарушение правила, которое оно запрещает | Та же проблема, что у Go, тулинга для RAG ещё меньше |
| Производительность и конкурентность | Достаточно для нагрузки проекта — она I/O-bound (сетевые вызовы к LLM Gateway, Vector DB, Биллингу), не CPU-bound | Объективно сильнее всего (goroutines), но выигрыш не используется — узкое место системы не здесь (см. «Решение») | Сопоставимо с Python — тоже событийный цикл, тоже рассчитан на I/O-bound нагрузку |
| Contract-first / OpenAPI | FastAPI генерирует OpenAPI-схему из кода — совпадает с принятым в проекте принципом «Contract First» | Нужна отдельная библиотека и дисциплина, не встроено так же нативно | Нужна отдельная библиотека (например, NestJS + swagger), не так нативно, как в FastAPI |
| Практика команды | Python Middle в составе | Go Middle в составе — практика тоже есть | Роль уже занята: Node.js/React отведён под AI-виджет (фронтенд), не под серверную RAG-логику |
| Итог | **Выбран** | Отклонён | Отклонён |

## Решение

**Backend / API Gateway — Python / FastAPI**, на прототипе и далее (контур не меняет этот выбор, только
инфраструктуру вокруг него — см. [ADR-017](ADR-017-tech-stack-by-stage.md)).

Главный довод — не скорость исполнения и не личные предпочтения, а архитектурное ограничение правила 4.1:
RAG-логика обязана жить в одном контейнере с оркестрацией запроса. Python — единственный из трёх языков,
где нужный для RAG инструментарий (эмбеддинги, PII-обезличивание, работа с LLM через единый шлюз)
существует нативно и зрело. Выбор Go или Node.js означал бы либо переизобретать этот инструментарий на
другом языке, либо держать внутри контейнера Backend второй процесс/язык только ради RAG-части — то есть
по факту два языка в одном контейнере вместо одного, а это и есть то самое нарушение, которое правило 4.1
явно запрещает.

**Go отклонён**, несмотря на объективное преимущество в производительности и конкурентности: этот выигрыш
не используется, потому что узкое место системы — сетевая задержка вызова внешнего LLM-провайдера (сотни
миллисекунд — секунды), а не накладные расходы веб-фреймворка (единицы миллисекунд). Выигрывать там, где
не находится узкое место, ценой полного пересобирания RAG-инструментария — плохой размен.

**Node.js отклонён** по двум причинам сразу: та же нехватка зрелого RAG/PII-инструментария, что и у Go, и
то, что эта роль в команде уже занята — Node.js/React отведён под AI-виджет (фронтенд-часть, см.
[ADR-017](ADR-017-tech-stack-by-stage.md)), а не под серверную RAG-логику. Использование одного языка для
фронтенда и бэкенда не решает проблему: ограничение — в инструментарии для RAG, а не в незнании команды
JavaScript.

**Отдельно:** LLM Gateway и ETL Worker на других языках даже не сравнивались — они с самого начала
Python-only, потому что весь нужный тулинг (LiteLLM, sentence-transformers) существует только в этой
экосистеме; альтернатив там по факту не было. Сравнение в этом документе — только про контейнер Backend /
API Gateway, где выбор действительно стоял между тремя языками.
