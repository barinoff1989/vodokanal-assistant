# ТЗ-002: Разработка AI-виджета в Личном кабинете абонента водоканала

## 0. Статус и основание

**Draft** — черновик для согласования с владельцем продукта, не утверждённый документ. Составлен на
основании принятых архитектурных решений: `контекст_4.md` (правила 4.3, 4.4, 4.7; раздел 7 — API-контракт;
раздел 18 — DoD Этапа 1), диаграммы компонентов [`C4_L3_Widget.drawio`](../C3/C4_L3_Widget.html) и пакета
[ТЗ-001](TZ-001-mvp-implementation.md) (реализация MVP целиком). Числа сроков — не даны там, где источник
проекта их не содержит (см. §9) — это не оценка «на глаз», а честное отсутствие данных до решения
открытого вопроса §6.

## 1. Назначение и бизнес-цели

AI-виджет — единственная точка контакта абонента с AI-помощником: элемент интерфейса, встраиваемый в уже
существующий Личный кабинет, а не отдельное приложение. Конечный пользователь виджета — **только
абонент**; у операторов колл-центра и внутренних сотрудников своего чат-интерфейса нет.

Бизнес-цели, которые виджет обязан обеспечивать на уровне UI/UX (те же цели проекта, в проекции на
интерфейс):

- абонент получает ответ на вопрос без обращения к оператору — экономия времени поиска;
- абонент понимает, какое обращение выбрать и как его заполнить — снижение доли неверно оформленных
  обращений;
- абонент видит, что делать после отправки (`suggested_actions`) — снижение повторных обращений;
- диалог ощущается как живой ответ, а не задержка загрузки страницы — поток печатается по мере
  генерации (правило 4.3).

## 2. Пользователь и сценарии использования

**Единственный пользователь — абонент**, уже аутентифицированный в Личном кабинете (виджет не имеет
собственного экрана входа — использует SSO-сессию ЛК, §7).

Сценарии Этапа 1 (объём этого ТЗ, см. §8):
1. Абонент задаёт вопрос → видит потоковый ответ с источниками, оценкой уверенности и рекомендуемыми
   следующими действиями.
2. Абонент выбирает готовое действие из `suggested_actions` → отправляется новый запрос с учётом выбора.
3. Ответа нет или уверенность низкая → абонент видит понятный fallback-текст, а не пустой экран или
   техническую ошибку.

Сценарии функционального Этапа 2 (архитектурно заложены в компонент виджета, но не активируются, пока
Этап 2 не пройдёт stage-gate — см. [ADR-016](ADR-016-scope-and-limitations.md)):
4. Абонент запрашивает операцию записи (заявка, показания, документ) → видит черновик и подтверждает или
   отклоняет его (HITL, правило 4.7) → при подтверждении видит готовый документ/результат.

## 3. Место виджета в архитектуре

| | |
|---|---|
| Контейнер | AI-виджет в ЛК |
| Технология (целевая) | React / TypeScript |
| Точка встраивания | Существующий Личный кабинет абонента (Платформа ЛК — внешняя система, не часть этого ТЗ) |
| С кем общается напрямую | API Gateway / Backend — `POST /v1/generate`, SSE-поток |
| С кем НЕ общается напрямую | LLM Provider, Vector DB, Биллинг — всё через Backend; виджет не хранит и не обрабатывает бизнес-логику, только отображает и собирает подтверждения |

Виджет не вводит новых контейнеров на уровне C2 — контракт с Backend уже зафиксирован (раздел 7
контекста, [ТЗ-001](TZ-001-mvp-implementation.md) §6).

## 4. Функциональные требования к виджету

Состав — четыре компонента, зафиксированные на [`C4_L3_Widget`](../C3/C4_L3_Widget.html). Ниже —
требования к каждому в терминах бизнес-функционала, не реализации.

### 4.1. Widget Shell / Session Context

| № | Требование |
|---|---|
| В1 | Виджет монтируется в существующую страницу ЛК, не открывает отдельный маршрут/окно |
| В2 | Получает `subscriber_id`, `session_id`, `channel` (`lk_web` \| `lk_mobile`) из SSO-сессии ЛК — не запрашивает у абонента повторный вход |
| В3 | Эти метаданные обязательны в каждом запросе к Backend — без них аудит и квоты (раздел 7.2 контекста) не работают |

### 4.2. Transport (канал обмена с Backend)

| № | Требование |
|---|---|
| В4 | Запрос — `POST /v1/generate` с `stream:true` |
| В5 | Ответ читается как поток SSE: `token` (печатать по мере поступления), `metadata` (источники, оценка уверенности, кнопки действий), `done` (поток завершён), `error` |
| В6 | Ошибки — понятное сообщение абоненту на основе `type/title/detail` (RFC 7807), не техническая заглушка |
| В7 | При ответе 429 (превышена квота) — повтор с учётом заголовка `Retry-After`, не мгновенный повтор и не бесконечный retry |

### 4.3. Chat View (лента диалога)

| № | Требование |
|---|---|
| В8 | Ответ печатается по мере поступления токенов (правило 4.3) — абонент видит, что система отвечает, а не ждёт готовый текст |
| В9 | Индикатор набора (typing indicator) во время ожидания первого токена |
| В10 | История диалога видна абоненту в пределах сессии |
| В11 | По завершении ответа показываются: источники, `confidence_score`, disclaimer (обязательное условие DoD Этапа 1, §10) |
| В12 | Кнопки `suggested_actions` — абонент может продолжить диалог выбором готового действия, не только свободным текстом |
| В13 | Панель готового бланка (`document_url`) — когда путь ответа выдаёт документ на печать |
| В14 | Черновик ввода абонента хранится только в памяти интерфейса — не кэшируется и не сохраняется локально (персональные данные абонента не должны оседать в браузере) |

### 4.4. Блок Этапа 2 (архитектурно заложен, не включается на MVP Этапа 1)

| № | Требование | Когда активируется |
|---|---|---|
| В15 | Confirmation Dialog — черновик операции + явные кнопки «подтвердить» / «отклонить» (HITL-гейт, правило 4.7) | Только с функциональным Этапом 2 |
| В16 | Document Panel — готовый документ/результат после подтверждения | Только с функциональным Этапом 2 |
| В17 | Slot Form — сбор недостающих обязательных полей, когда они не закрыты профилем Биллинга | Только с функциональным Этапом 2 |

**Важно для планирования разработки:** эти три состояния стоит проектировать в интерфейсе виджета уже на
MVP (чтобы не переделывать компонент при включении Этапа 2), но их видимость и активность в проде — под
функциональным флагом, синхронным со stage-gate Этапа 2 ([ADR-016](ADR-016-scope-and-limitations.md)).

## 5. Нефункциональные требования

| № | Требование | Источник |
|---|---|---|
| НФ1 | TTFT (время до первого токена) < 500 мс | контекст §18, DoD Этапа 1 |
| НФ2 | Полный ответ < 3 сек | контекст §18, DoD Этапа 1 |
| НФ3 | Поток обязан доходить до виджета целиком — без буферизации всего ответа на промежуточном слое | правило 4.3 |
| НФ4 | Персональные данные абонента не кэшируются в браузере (черновик ввода, история) | В14 |
| НФ5 | Понятная деградация при ошибке backend/LLM — сообщение по схеме RFC 7807, не пустой экран | В6, контекст §18 |

**Оговорка источника.** Цифры НФ1–НФ2 в самом контексте помечены как не подкреплённые расчётом
производительности под конкретную инфраструктуру MVP — открытый пункт, закрывается НФ1 из
[ТЗ-001](TZ-001-mvp-implementation.md) §4.

## 6. Открытый вопрос, критичный для начала разработки: способ встраивания

**Не выбран** ни один из трёх вариантов — раздел 16 контекста фиксирует это явно как открытый вопрос:

| Вариант | Что затрагивает |
|---|---|
| Widget (React-компонент внутри существующего фронтенда ЛК) | Общий бандл, общий DOM — минимум изоляции, максимум интеграции с существующим стилем и SSO |
| iframe | Полная изоляция стилей и рантайма ценой сложности передачи SSO-сессии и document-высоты; собственный CSP |
| Micro-frontend (Module Federation и т.п.) | Независимый деплой виджета от релизного цикла ЛК, но требует согласования со стеком/версией существующего фронтенда ЛК |

**Это решение блокирует старт разработки виджета**, а не деталь реализации: от него зависят изоляция
стилей, способ передачи SSO-сессии (В2), политика CSP и то, на каком фронтенд-стеке фактически пишется
ЛК (не задокументирован в этом проекте — внешняя система). Решение принимает владелец продукта совместно
с командой, отвечающей за Личный кабинет, до начала работ по этому ТЗ.

## 7. Интеграция с Платформой ЛК

Платформа ЛК — внешняя система по отношению к этому проекту (диаграмма `C4_L3_Widget`). Обязанности на
стороне ЛК, не входящие в разработку виджета, но блокирующие её:

- предоставить SSO-сессию, из которой виджет получает `subscriber_id`, `session_id`;
- определить и согласовать точку встраивания (см. §6);
- подтвердить `channel` — `lk_web` и/или `lk_mobile`, если мобильная версия ЛК тоже получает виджет на
  MVP.

## 8. Границы объёма — что явно НЕ входит в это ТЗ

- Реализация Backend, LLM Gateway, поиска по базе знаний — отдельный объём, описан в
  [ТЗ-001](TZ-001-mvp-implementation.md); виджет — только клиент их API.
- Активация экранов Этапа 2 (В15–В17) в проде — отдельный stage-gate, не решается разработкой виджета.
- Изменения на стороне Платформы ЛК (её фронтенд-стек, релизный процесс) — ответственность владельца ЛК,
  не этого проекта.
- Мобильное нативное приложение — если у ЛК есть отдельное мобильное приложение (не мобильная веб-версия),
  вопрос его охвата не поднят ни в одном источнике проекта и требует отдельного уточнения у бизнеса.

## 9. Состав работ и сроки

**Оценка не дана намеренно.** Ни один источник проекта (`ADR-021`, журнал разработки) не содержит оценку
трудозатрат именно на виджет отдельно от Backend — фронтенд ЛК не входил в объём прототипа (демо-стенд
на статике заменял его, раздел 8.5 журнала, зафиксировано как осознанный пробел, не готовая оценка).
Трудозатраты виджета обязаны быть переоценены отдельно **после** решения открытого вопроса §6 — варианты
различаются по сложности реализации на порядок (React-компонент в существующем бандле — недели;
micro-frontend с независимым деплоем — совсем другой объём инфраструктурной работы на стороне ЛК).

## 10. Критерии приёмки виджета (Definition of Done)

Адаптация функциональных и нефункциональных критериев DoD Этапа 1 (контекст §18) применительно к виджету:

1. Абонент получает потоковый ответ, который печатается по мере генерации (В8).
2. Ответ сопровождается источниками, `confidence_score`, disclaimer (В11).
3. Есть понятный экран/сообщение при пустом результате поиска и при низкой уверенности модели.
4. Кнопки `suggested_actions` кликабельны и инициируют новый запрос с учётом выбора (В12).
5. Ошибки любого типа (429, 5xx, обрыв потока) показывают абоненту понятный текст, не техническую
   заглушку и не пустой экран (В6, НФ5).
6. TTFT и полный ответ уложены в бюджет §5 на реальной production-инфраструктуре, не на стенде.
7. Черновик ввода и история диалога не сохраняются в локальном хранилище браузера между сессиями (В14,
   НФ4).
8. Экраны Этапа 2 (В15–В17) реализованы в компоненте, но скрыты/неактивны до прохождения stage-gate
   Этапа 2.
