# ТЗ-001: Реализация MVP — AI-помощник абонента водоканала

## 0. Статус и основание

**Draft** — черновик для согласования с владельцем продукта, не утверждённый документ. Составлен на
основании принятых архитектурных решений (`AI_docs/ADR/ADR-002…015`) и сводного пакета для сдачи
(`AI_docs/Сдача/ADR-016…021`). Числа стоимости и сроков — прогнозная модель, не смета (см. раздел 9).

Это ТЗ описывает **переход контура развёртывания** «прототип» → «MVP» при неизменной функциональности
«Этап 1» (см. §1). Реализация функционального «Этап 2» (агент, операции записи) в объём этого ТЗ не
входит — см. §5.

## 1. Назначение и бизнес-цели

AI-помощник встроен в существующий Личный кабинет абонента водоканала. Конечный пользователь — **только
абонент**; операторы колл-центра и внутренние сотрудники пользователями чат-интерфейса не являются.

Абонент часто не знает: какое обращение выбрать, как его заполнить, какие документы нужны, что делать
после отправки. Бизнес-цели MVP:

- сократить время поиска ответа;
- снизить долю неверно оформленных обращений;
- снизить количество повторных обращений;
- улучшить пользовательский опыт в личном кабинете.

MVP — первая версия, доступная **реальным абонентам** в production-контуре (не демо-стенду и не команде
разработки), в границах функциональности «Этап 1»: консультация и поиск информации, без операций записи.

## 2. Что уже сдано на прототипе (базовая точка)

Работающий путь: вопрос абонента → классификация темы → один из шести путей ответа. Пять путей отвечают
без модели (график плановых отключений, регламентная формулировка о качестве воды, таблица тарифов,
факты лицевого счёта, выдача бланка заявления); шестой — поиск по базе знаний и генерация через LLM
Gateway. На данных без синтетики, со сквозным тестовым покрытием.

Полный список сдано/отложено — [ADR-016](ADR-016-scope-and-limitations.md). Это ТЗ строится поверх
него: MVP не меняет функциональный состав, меняет контур — с одной машины разработки на
production-инфраструктуру с реальными абонентами и реальными интеграциями вместо демо-стенда.

## 3. Функциональные требования к MVP

| № | Требование | Источник |
|---|---|---|
| Ф1 | Все шесть путей ответа (§2) работают в production-контуре на реальном трафике абонентов | ADR-016 |
| Ф2 | Поиск по базе знаний — через Qdrant (не in-memory корпус прототипа) | ADR-006, ADR-017 |
| Ф3 | Переранжирование топ-20 → топ-3 кандидатов — кросс-энкодер BGE-M3/BGE-reranker-v2-m3 на GPU (на прототипе выключено по бюджету задержки на CPU) | ADR-014, ADR-018 |
| Ф4 | Генерация ответа — GigaChat Pro как основной провайдер, YandexGPT — резерв с автопереключением | ADR-018 |
| Ф5 | Каждый ответ возвращает источники, `confidence_score`, `suggested_actions`, disclaimer | контекст, §3 |
| Ф6 | Факты лицевого счёта (задолженность, начисления, показания, поверка) — из реальной интеграции с Биллингом, не из слепка Postgres прототипа | ADR-016, §"Границы" |
| Ф7 | Регистрация обращения — целевой путь через внешний микросервис обращений (на прототипе — временная запись напрямую в таблицу) | ADR-016 |
| Ф8 | Идентификация абонента — через настоящую SSO-сессию Платформы ЛК (на прототипе — метаданные демо-стенда) | ADR-019, §"Не входит в объём" |
| Ф9 | Запасной классификатор типа обращения расширен минимум до покрытия, согласованного с владельцем продукта (сейчас 7 из 16 типов) | ADR-018, ADR-021 |

**Явно вне объёма MVP:** операции записи (заявки, показания, документы, изменения данных абонента) —
функциональный Этап 2, отдельный stage-gate (§5).

## 4. Нефункциональные требования

| № | Требование | Источник |
|---|---|---|
| НФ1 | Расчёт NFR (TTFT, P99) под конкретную GPU-конфигурацию MVP — до запуска, не после | ADR-021, "Блокирует защиту бюджета" |
| НФ2 | Бюджет задержки поиска (эмбеддинг + переранжирование) — в рамках, подтверждённых на GPU-конфигурации MVP (на CPU прототипа переранжирование превышает бюджет в 2–58 раз) | ADR-014 |
| НФ3 | Лимиты запросов — fail-closed: недоступность хранилища квот (Redis) отклоняет запросы (503 + `Retry-After`), не пропускает их без учёта | ADR-019, ADR-008 |
| НФ4 | Kubernetes на своём железе, отказ узла не должен останавливать сервис | ADR-004, ADR-017 |
| НФ5 | Персональные данные не покидают периметр РФ (152-ФЗ) — соблюдается выбором провайдера (GigaChat/YandexGPT, управляемые API на территории РФ) | ADR-019 |
| НФ6 | PII-фильтрация текста неизвестного происхождения (вопрос абонента, ответ модели) — до отправки в LLM Provider | ADR-019, контекст §4.2 |

## 5. Границы объёма — что явно НЕ входит в MVP

- **Функциональный Этап 2** (агент, операции записи) — отдельный набор работ, начинается только после
  выполнения одновременно всех четырёх условий: стабильные метрики качества Этапа 1, подтверждённый
  бизнес-эффект, согласование ИБ, готовность интеграций. Календарной даты у перехода нет
  ([ADR-021](ADR-021-roadmap-and-migration.md)).
- **Контур «тираж»** (90 000 абонентов, собственная GPU-инфраструктура для генерации) — включается по
  триггеру (рост нагрузки, требование ИБ, деградация SLA провайдера), не по объёму MVP.
- Официальная смета CAPEX/OPEX — по этому ТЗ подготавливается (§8, задача "смета"), но не утверждена
  заранее его написанием.

## 6. Архитектура и технологический стек MVP

Целевой стек по слоям — таблица с альтернативами в [ADR-017](ADR-017-tech-stack-by-stage.md). Сводно
для MVP:

| Слой | Компонент MVP | Было на прототипе |
|---|---|---|
| Оркестрация | Kubernetes на своём железе | `docker compose`, один хост |
| Векторный поиск | Qdrant, self-hosted | Корпус в памяти процесса |
| Телеметрия | ClickHouse | Postgres |
| Переранжирование | BGE-reranker-v2-m3 на GPU | Выключено (не тянет CPU-бюджет) |
| Секреты | Vault Agent Injector в Kubernetes | `.env` / Vault dev-mode |
| Генерация | GigaChat Pro + резерв YandexGPT | YandexGPT (GigaChat недоступен без корневых сертификатов НУЦ на машине прототипа) |

Диаграмма развёртывания — [`C4_Deployment.html`](../C4_Deployment.html) (рабочая, полная) и
[`C4_Deployment_presentation.svg`](../C4_Deployment_presentation.svg) (презентационная версия).

## 7. Безопасность

Полная сводка — [ADR-019](ADR-019-security-by-stage.md). Обязательные для MVP пункты:

- Vault Agent Injector вместо переменных окружения, заданных вручную — единый источник истины, отзыв
  доступа без пересборки образа.
- Наименьшие привилегии доступа к внешним системам — только через их собственные API (XML-RPC у
  Биллинга, REST у Диспетчерской), без прямого доступа к чужой БД.
- Проверка TLS не отключается ни при каких обстоятельствах (по каналу идут ПДн).
- SSO-интеграция с Платформой ЛК — заменяет метаданные демо-стенда (Ф8 выше).

## 8. Состав работ и оценка (переход прототип → MVP)

Источник — [ADR-021](ADR-021-roadmap-and-migration.md), раздел «Переход прототип → MVP». Приведено без
изменений по существу, только как чек-лист ТЗ:

| Блок | Оценка разработки | Вне контроля команды |
|---|---:|---|
| P0: смета CAPEX/OPEX, расчёт NFR, подтверждение допущений о нагрузке | 1,5–2 недели | Цены поставщика, статистика ЛК и колл-центра |
| Согласования с владельцами систем (коды типов обращений, текст о качестве воды, бланки, сигнатуры внешних API) | 1–2 дня на пункт | Скорость ответа водоканала |
| Качество поиска и классификации (Golden Set, e5-small/BGE-M3, устранение ложных срабатываний) | 2–3 недели | Корпус для 9 оставшихся типов `InquiryType` |
| Реальные интеграции (Биллинг, SSO ЛК, микросервис обращений) | входит в объём Ф6–Ф8 выше | Сигнатуры и готовность внешних API |
| Документация и согласование ИБ | 1–1,5 недели | Согласование службы ИБ водоканала |
| **Итого разработка** | **≈9–13 недель (≈2–3 месяца)** | Календарный срок может быть больше — три блока зависят от внешних сторон |

## 9. Ресурсы и стоимость MVP (прогнозная модель)

Полный расчёт — [ADR-020](ADR-020-resources-and-cost.md). Ключевые цифры для ТЗ:

- Инфраструктура: Kubernetes-кластер + GPU-пул под эмбеддинги/переранжирование (сам GPU-сервер отдельной
  строкой сметы не оценён).
- Токены генерации при 8 000 абонентах: ≈150 ₽/мес (базовый сценарий 10% визитов через AI-чат) до
  ≈1 700 ₽/мес (максимальное вовлечение 50%) — на порядки меньше стоимости инфраструктуры.
- **Официальная смета CAPEX/OPEX не утверждена владельцем — открытый пункт P0 №1 проекта.** Числа выше
  требуют защиты перед финальным утверждением.

## 10. Критерии приёмки MVP (Definition of Done)

MVP считается принятым, когда одновременно выполнено:

1. Все шесть путей ответа (§3, Ф1) работают в production-контуре на реальном трафике абонентов, не на
   демо-стенде.
2. Реальные интеграции подключены (Ф6–Ф8) — Биллинг, SSO ЛК, микросервис обращений; временные замены
   прототипа (прямая запись в Postgres, метаданные демо-стенда) выведены из эксплуатации.
3. NFR (TTFT, P99) измерены на целевой GPU-конфигурации и подтверждены в рамках бюджета (НФ1, НФ2).
4. Смета CAPEX/OPEX утверждена владельцем продукта (закрывает P0 №1).
5. Чек-лист безопасности §7 закрыт, включая согласование с ИБ перечня триггеров self-hosted-перехода.
6. Диаграммы C1–C3 и `C4_Deployment.html` синхронизированы с фактическим состоянием (условие приёмки
   ADR-016 переносится на состояние MVP).

## 11. Риски и зависимости

Оба ключевых блока работы (§8, §5) содержат этапы вне контроля команды разработки: сроки ответа
водоканала (согласования, статистика нагрузки, сигнатуры внешних API), сроки поставщика (цены на
коммерческое предложение, лид-тайм оборудования), сроки службы ИБ (согласование архитектуры
безопасности). Календарный срок раздела 8 — нижняя граница при условии, что эти блокеры не задерживают
начало соответствующей работы.
