# ADR-019: Безопасность по этапам

## Статус

**Accepted** как сводка: что закрыто по безопасности сейчас и что добавляется на следующих
контурах, без полной истории обсуждения — для неё раздел «Источники» ниже. Реализация — в коде
(`app/gateway/pii_filter.py`, `app/gateway/quota.py`).

## Закрыто сейчас (Этап 1)

**Персональные данные не покидают периметр.** Правило 4.2: весь текст неизвестного происхождения —
вопрос абонента и ответ модели — проходит `PII Sanitizer` (Presidio + собственные распознаватели: ФИО,
СНИЛС, ИНН, номер лицевого счёта, телефон, email) **до** отправки в LLM Provider. Собственный корпус
базы знаний проверяется один раз при сборке, не на каждом ответе — обезличиватель предназначен для
чужого текста, а не для документов, которые собрала сама команда.

**ПДн абонента не покидают РФ.** 152-ФЗ соблюдается выбором провайдера: и YandexGPT (прототип), и
GigaChat (MVP) — управляемые API на территории РФ. Зарубежные провайдеры исключены архитектурно,
а не настройкой — заменить провайдера на зарубежный означало бы нарушить закон, не только архитектуру.

**Проверка TLS не отключается никогда.** GigaChat требует корневых сертификатов НУЦ Минцифры; там, где
их нет (машина прототипа), проект переключается на другого провайдера, а не отключает проверку
сертификата — по соединению идут персональные данные абонента, отключение проверки было бы дырой, а не
компромиссом.

**Лимиты — fail-closed.** Если хранилище квот (Redis) недоступно, сервис отказывает запросам (503 +
`Retry-After`), а не пропускает их без учёта — иначе лимит перестаёт быть лимитом именно в момент сбоя,
когда защита нужнее всего. Состояние диалога — отдельный случай: его недоступность закрывает
только путь записи («сессии нет»), не весь сервис, — эта асимметрия сознательная.

**Секреты не в открытом виде на диске разработки.** Ключ YandexGPT — вне `.env` по умолчанию (`.env`
не попадает в git), опционально через Vault в dev-режиме на локальной машине. Честно зафиксировано:
dev-режим Vault сам по себе не безопаснее `.env` — это репетиция интеграции для целевой схемы, не
самостоятельная защита секрета на прототипе.

**Наименьшие привилегии доступа к внешним системам.** Ни к одной внешней системе (Биллинг, Диспетчерская,
микросервис обращений) у проекта нет прямого доступа к БД — только через их собственные API (XML-RPC у
Биллинга, REST у Диспетчерской). Схема чужой БД — не контракт проекта.

## Что добавляется с функциональным Этапом 2 (операции записи, любой контур)

**HITL для всех операций записи (правило 4.7).** Заявки, показания, документы, изменения данных
абонента — только после явного подтверждения абонента (не текст реплики, отдельное действие в
интерфейсе). Обязательны: состояние ожидания подтверждения, идемпотентность (повтор с тем же ключом не
создаёт дубль), аудит-лог (кто/что/когда/ключ/результат), возможность отказа абонента — отказ тоже
пишется в аудит, с пометкой, что операция не выполнялась.

**Привязка сессии к абоненту на каждом write-шаге.** Защита от подмены (Spoofing/IDOR): каждый шаг
записи повторно проверяет, что `subscriber_id` действительно принадлежит текущей сессии, а не подставлен
в запросе. **Открытый пункт (P1)** — на целевой архитектуре Этапа 2 эта проверка спроектирована, но не
реализована: обращение на прототипе сейчас пишется по упрощённому пути (ADR-016), где этот риск ниже,
но при переходе на целевой путь Этапа 2 проверка обязательна до включения записи в проде.

## Что добавляется в контуре MVP (инфраструктура, независимо от функционального этапа)

**Секреты через Vault Agent Injector.** На целевой инфраструктуре (Kubernetes) секреты внедряются в
под через sidecar-инжектор, а не читаются из переменных окружения, заданных вручную — единый источник
истины, отзыв доступа без пересборки образа.

## Что добавляется в контуре тиража

**Данные не покидают периметр вообще, а не только территорию РФ.** Self-hosted-модель (Qwen2.5-32B)
разворачивается «в контуре» — внутри закрытой сети водоканала, на собственном GPU node pool. Это
включается по триггеру (запрет ИБ на внешние API или рост нагрузки), а не по расписанию — до триггера
данные продолжают идти через управляемый API на территории РФ, что уже соответствует 152-ФЗ.

**Изоляция GPU между офлайн-ETL и онлайн-обслуживанием.** Открытый вопрос F7 (не решён): инференс
эмбеддингов/реранжинга общий для индексации базы знаний и для ответов абонентам в реальном времени —
без изоляции (приоритетные очереди либо отдельный пул) массовая переиндексация может увеличить
задержку ответа абоненту. Решение спроектировано, реализация — на момент появления второй нагрузки.

## Не входит в объём Этапа 1 (открытые пункты для приёмки)

- Проверка `subscriber_id` ↔ `session_id` на write-шагах Этапа 2 — спроектирована, не реализована.
- Согласование перечня триггеров self-hosted-перехода с ИБ — не проведено.
- SSO-интеграция с Платформой ЛК — на прототипе `subscriber_id` берётся из метаданных запроса
  (демо-стенд), не из настоящей SSO-сессии; `Auth & Session Middleware` — целевой компонент Этапа 2.
- Изоляция GPU между ETL и онлайн-инференсом (находка F7) — открыта.

## Источники

Полная история решений по каждому пункту — правила, рассмотренные альтернативы, драйверы выбора — в
рабочем архиве разработки, вне пакета сдачи. Реализация — `app/gateway/pii_filter.py`,
`app/gateway/quota.py`, `app/secrets_vault.py`.
