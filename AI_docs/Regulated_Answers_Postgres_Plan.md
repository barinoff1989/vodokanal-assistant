# План: реестр регламентных ответов в Postgres + две новые темы

## Статус

**Отложено по времени, не по контуру.** Реализация — на прототипе (локальная машина, уже поднятый
`docker-compose` Postgres), не перенесена на MVP: миграция реестра из кода в БД не требует
production-инфраструктуры, весь план выше рассчитан на то же окружение, где сейчас работает
`PROTOTYPE_REGISTRY`. Черновики текстов подготовлены, план миграции записан, код не менялся.
Возобновление — по отдельному указанию.

## Зачем переносить из кода в Postgres

Сейчас реестр — константа `PROTOTYPE_REGISTRY` в [`app/regulated.py`](../app/regulated.py): правка текста
(например, когда владелец наконец утвердит формулировку о качестве воды) требует правки кода и деплоя.
В Postgres правку сможет сделать не разработчик — SQL-строка вместо pull request, а `approved`/`owner`/
`effective_from` получают историю изменений в БД, а не в `git blame`.

Это не меняет ADR-012 по существу: текст по-прежнему не производится языковой моделью, по-прежнему
проверяется один раз при внесении, а не на каждом ответе. Меняется только **где хранится**, не
**как работает**.

## Два новых черновика — готовы, не утверждены

Составлены по той же дисциплине, что `WATER_QUALITY` в `app/regulated.py`: текст **направляет, а не
утверждает**, конкретные цифры (ставки, номера, которые нельзя подтвердить) не изобретаются.

### Тема `penalty` — пени за просрочку платежа

```python
RegulatedAnswer(
    topic=Topic.PENALTY,  # новое значение оси Topic — сейчас его нет, см. «Что меняется в коде» ниже
    template=(
        "Пени за несвоевременную и (или) неполную оплату жилищно-коммунальных услуг "
        "начисляются в соответствии с частью 14 статьи 155 Жилищного кодекса РФ. "
        "Точный размер пени по вашему лицевому счёту зависит от суммы задолженности "
        "и периода просрочки — уточнить его можно в личном кабинете или в контакт-центре "
        "{phone}."
    ),
    source=(
        "Правовая основа — ч. 14 ст. 155 Жилищного кодекса РФ; та же ссылка уже "
        "использована и сверена в scripts/generate_kb_docs.py (OBSERVED_REFS['penalty']). "
        "Наша формулировка (черновик), владельцем не утверждена."
    ),
    owner="не назначен",
    effective_from=None,
    approved=False,
)
```

**Почему без конкретной ставки.** Формула пени (доля ключевой ставки ЦБ РФ, зависящая от срока
просрочки) в проекте не была сверена с достоверным источником — приводить её означало бы тот же риск,
от которого ADR-012 уже предостерегает для тарифов: «неверный тариф — это неверная сумма в ответе про
деньги, и абонент проверит её по квитанции». Текст направляет к проверке суммы, не вычисляет её.

### Тема `emergency` — авария на сетях

```python
RegulatedAnswer(
    topic=Topic.EMERGENCY,  # новое значение оси Topic
    template=(
        "При аварии на сетях водоснабжения или водоотведения (порыв, прорыв, "
        "подтопление, полное отсутствие воды по всему дому) обращайтесь в "
        "аварийно-диспетчерскую службу по телефону {phone}."
    ),
    source="Наша формулировка (черновик), владельцем не утверждена.",
    owner="не назначен",
    effective_from=None,
    approved=False,
)
```

**Блокер, найденный при подготовке, не выдуманный.** `{phone}` в `RegulatedAnswer.render()` сейчас —
единственная подстановка, и она жёстко привязана к `settings.contact_center_phone`
([`app/config.py:172`](../app/config.py:172)) — другого номера в настройках нет. У аварийно-диспетчерской
службы почти наверняка другой номер и, вероятно, круглосуточный режим работы, которого у общего
контакт-центра может не быть. Подставить сюда номер контакт-центра — не «то же самое с оговоркой», а
неверный номер в момент реальной аварии. **Тема не готова к `approved=True` не только по формулировке,
но и по механизму подстановки** — см. пункт 3 в разделе «Что меняется в коде» ниже.

## Схема Postgres

Новая база, по образцу уже существующих ([`app/config.py:383-394`](../app/config.py:383)) — `billing_db`,
`lk_db`, `inquiries_db` (слепки внешних систем) и `telemetry_db` (не слепок, наше собственное хранилище).
Реестр регламентных ответов — тоже «наше», не слепок чужой системы, поэтому по аналогии с `telemetry_db`:

```sql
CREATE TABLE regulated_answers (
    topic           TEXT PRIMARY KEY,          -- значение Topic enum, не производный ключ
    template        TEXT NOT NULL,
    source          TEXT NOT NULL,
    owner           TEXT NOT NULL,
    effective_from  DATE,
    approved        BOOLEAN NOT NULL DEFAULT FALSE,
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

`updated_at` — новое поле, которого нет в `RegulatedAnswer` сейчас: в коде историю правок даёт `git log`,
в БД без отдельного поля её не будет вовсе.

## Что меняется в коде (когда решение — реализовывать)

1. **`app/taxonomy.py`** — добавить `Topic.PENALTY` и `Topic.EMERGENCY`. Мелкая правка, но не нулевая:
   `Topic` явно проверяется на непересечение с `InquiryType` (докстринг `Topic`, «дефект 11.1»), и
   `EMERGENCY` уже существует как значение **другой** оси (`InquiryType.EMERGENCY`) — нужно явно
   зафиксировать, что это разные оси с одинаковым по смыслу, но раздельно объявленным кодом, как уже
   сделано для `water_quality` (см. ADR-012, раздел «Связь с таксономией»).
2. **`app/config.py`** — новая пара `regulated_db: str = "regulated_answers"` + свойство `regulated_dsn`
   по образцу `telemetry_dsn`/`inquiries_dsn` (строка 396-420). Отдельно — новое поле настроек под номер
   аварийно-диспетчерской службы (например, `emergency_phone`), раз он не совпадает с
   `contact_center_phone`.
3. **`app/regulated.py`** — `RegulatedResponder` перестаёт принимать `registry: tuple[RegulatedAnswer, ...]`
   как константу по умолчанию, читает записи из `regulated_answers` один раз при старте (тем же
   приёмом, что `build_knowledge_base()` читает корпус — не на каждый запрос). `RegulatedAnswer.render()`
   меняется с одной фиксированной подстановки `{phone}` на словарь подстановок либо на явное поле под
   аварийный номер — без этого тема `emergency` не может стать `approved=True` корректно.
4. **`docker-compose.yml` / `docker/postgres/init/`** — новая миграция `0X_regulated_answers.sql`
   (схема + `INSERT` трёх записей: существующая `water_quality`, плюс `penalty` и `emergency` из этого
   документа, все три с `approved=false`), плюс создание базы `regulated_answers` в
   `00_create_databases.sql` по образцу остальных.
5. **`app/main.py`** — `_build_regulated()` получает DSN вместо константы; `strict=False` на прототипе
   остаётся (ADR-012 это уже требует — неутверждённые записи не должны ронять прототип).

## Тесты

`tests/unit/test_regulated.py` сейчас строит `RegulatedResponder` прямо на `PROTOTYPE_REGISTRY` в памяти
— это сохраняется как модульный уровень (конструктор по-прежнему принимает готовый список записей, DSN
нужен только на пути загрузки при старте). Дополнительно нужен уровень интеграции — по образцу
`tests/unit/test_qdrant_store.py`, где Postgres поднимается реальным контейнером
(`docker compose up -d postgres`), а не мокается: проверить сам путь «строка в БД → запись в реестре →
ответ абоненту слово в слово», включая случай `approved=false` → `UnapprovedAnswerError` при `strict=True`.
