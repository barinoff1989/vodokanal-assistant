# ADR-100: Область и ограничения сдаваемого прототипа

## Статус

**Accepted.** Описывает то, что уже реализовано и работает, а не решение к принятию.

## Контекст — две независимые оси стадийности

В проекте используются **два разных деления**, и их легко перепутать:

1. **Функциональный этап** — что умеет система: **Этап 1** (RAG-ассистент, консультации, без записи
   данных) → **Этап 2** (агент, операции записи — заявки, показания, документы, всё через
   подтверждение абонента). Переход не связан с масштабом или инфраструктурой — это про возможности.
2. **Контур развёртывания** — где и для скольких пользователей система работает: **прототип**
   (локальная машина, приёмка) → **MVP** (production Kubernetes, реальные абоненты) → **тираж**
   (масштаб на порядок больше, включая собственную GPU-инфраструктуру по триггеру).

Оси независимы: `C4_Deployment.html` прямо показывает состояние «MVP в проде (Этап 1)» — то есть
production-инфраструктура, разворачивающая только функциональность Этапа 1 (RAG), без агентных
компонентов. Этап 2 может быть добавлен поверх уже существующего MVP-контура, а не требует нового
контура сам по себе. Документы этого пакета используют обе оси там, где это уместно, и не смешивают
их: контур — для ресурсов/стоимости/стека (ADR-200, ADR-500), функциональный этап — для состава
возможностей и безопасности записи (этот документ, ADR-400).

**Сдаётся сейчас: контур «прототип», функциональность «Этап 1».**

## Что сдано

Работающий путь: вопрос абонента → классификация темы (`Triage`) → один из шести путей ответа. Пять
путей отвечают **без модели**: график плановых отключений, регламентная формулировка о качестве воды,
таблица тарифов, факты лицевого счёта (задолженность, начисления, показания, поверка), выдача бланка
заявления (семь образцов по ПП РФ №644/776, поля из Биллинга). Шестой путь — поиск по базе знаний и
генерация через LLM Gateway на реальном YandexGPT.

Данные — настоящие, не синтетика: FAQ филиала (20 пар), график плановых отключений (1939 записей; на демо-стенде даты сдвинуты на 47 дней, улицы и дома настоящие),
выгрузка обращений (136 текстов, ПДн замаскированы), пример Биллинга и личного кабинета (200 счетов,
203 счётчика, 1323 начисления), таблица тарифов (19 периодов). Исключение — документы Word в базе знаний (5 договоров и 2 регламента): они синтетические, помечены свойством файла
`СИНТЕТИКА`, настоящих документов на прототипе нет. Демо-стенд — три файла статикой
(`web/index.html`, `app.js`, `style.css`), не целевой React/TS — стенд для приёмки, не продукт.

## Что явно отложено на функциональный Этап 2

Диаграммы C1–C3 (`AI_docs/C1/`, `AI_docs/C3/`) помечают отложенные узлы штрихом и подписью «Этап 2».
Состав:

| Узел (C2/C3) | Роль | Почему не сейчас |
|---|---|---|
| Agent Orchestrator | FSM обращения, tool-calling, HITL-гейты, аудит операций | Запись данных требует подтверждённого сценария подтверждения — стоимость ошибки выше, чем у консультации |
| Billing Adapter | Запись показаний/операций в Биллинг через XML-RPC | Write-доступ к чужой legacy-системе — отдельная интеграция, не нужна для консультационного сценария |
| Document Generator (целевой) | Рендер PDF, S3/MinIO | На прототипе путь `template` уже работает без Orchestrator — HTML-лист на печать вместо PDF/S3 (ниже) |
| Сервис работы с обращениями (целевой протокол) | Регистрация через внешний микросервис обращений | На прототипе обращение регистрируется в собственной таблице Postgres напрямую (`app/backend/registration.py`) — не тот же путь, что целевой Этап 2, а временная замена до готовности внешнего микросервиса |
| Диспетчерская — запись аварийной заявки | Передача заявки после HITL | На прототипе только чтение графика отключений для ответа; запись — заглушка |

Важная оговорка по регистрации обращений: **на прототипе она уже работает**, но не тем путём, что
описан для Этапа 2 на диаграммах (через `Agent Orchestrator` → `Сервис работы с обращениями`). Это
сознательная временная реализация — обращение пишется напрямую в таблицу, минуя Orchestrator, — а не
пробел. Целевой путь остаётся тем, что на диаграмме, и потребует переключения при готовности внешнего
микросервиса обращений (пункт дорожной карты, ADR-600).

## Что отложено на контур «тираж»

Собственная GPU-инфраструктура для генерации (`gpu-llm` в `C4_Deployment.html`, помечен «Этап 3
(тираж)» — обозначение узла, не третий функциональный этап) — сейчас там нет развёрнутых узлов, только
целевая архитектура. Она вступает в строй по одному из триггеров (рост нагрузки сверх
экономичного порога внешнего API, требование ИБ об отказе от внешних вызовов, или падение SLA внешнего
провайдера) — не по календарной дате.

## Целевые компоненты, у которых на прототипе — упрощённая замена (ось «контур»)

| Целевой компонент (MVP) | Замена на прототипе | Причина |
|---|---|---|
| Qdrant (Vector DB) | Корпус в памяти процесса **по умолчанию** — Qdrant подключается опционально одной переменной окружения (`VECTOR_STORE=qdrant`), модель эмбеддингов та же, реализация проверена | Прототип: 20 пар FAQ — память достаточна по умолчанию, но переход на Qdrant больше не требует разработки |
| BGE-M3 + BGE-reranker-v2-m3 (GPU) | `multilingual-e5-small` на CPU, без переранжирования | На CPU-машине без ускорителя эти модели превышают бюджет задержки в 3–70 раз (замер 24 сентября 2026: BGE-M3 — 300 мс на запрос, реранкер — 7,2 с на 20 кандидатах при бюджете 100 мс; на GPU не измерялись) |
| Сервис шаблонов заявлений (`template-service`, MVP; шаблоны из хранилища или с файлового сервера, ADR-200) | Семь образцов в коде (`app/documents/templates.py`), помечены как ориентировочные | Настоящих утверждённых бланков владельца нет; формат и место хранения формы неизвестны — ответ владельца (ADR-600) |
| Kubernetes на своём железе (ADR-200, «Почему Kubernetes») | `docker compose` на одной машине | Единственный разработчик, один хост — оркестрация избыточна до появления второй среды |

## Несколько задач в одной реплике: ограничение исправлено на прототипе

Первая версия прототипа обрабатывала одну задачу на реплику: тема ответа — первая сработавшая по правилам, тип — первый найденный, остальное
терялось без предупреждения, а модель могла написать, что выполнила действие («Передал показания 1234. Проверил наличие долга — его нет»),
которого в этом пути нет. Теперь реплика разбирается детектором намерений на задачи, каждая получает ответ или прямое «не выполняю»,
а фразы о невыполненном действии блокируются и в промпте, и в охранителях (реализация, результат прогонов, тесты и оговорки — ADR-200,
раздел «Оркестрация агента», подраздел «Как реализовано: несколько задач в одной реплике»). **Остаётся условие перехода:** если доля реплик
с двумя и более задачами по разметке людьми превысит 5%, агент переводится на LangGraph (ADR-200, ADR-600); измерение — при анализе живых
обращений и затем ежемесячно. Что не доделано (регистрация нескольких обращений, условия кроме долга, путь `generate`) — ADR-600, блок
«Несколько задач в одной реплике».

## Границы, не входящие в объём сдачи

- Смета CAPEX/OPEX официально не утверждена (см. ADR-500 — есть прогнозная модель, не смета).
- Golden Set для оценки качества генерации — не размечен на объёме, достаточном для A/B.
- Утверждение владельцем текста о качестве воды — открыто (регламентный ответ используется как есть,
  с пометкой «требует утверждения»).
- Согласование с ИБ по перечню триггеров self-hosted-перехода не проведено.
