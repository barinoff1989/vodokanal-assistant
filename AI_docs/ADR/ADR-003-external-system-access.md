# ADR-003: Доступ к внешним системам — только через их API, никогда напрямую в их БД

> **Оговорка о нумерации.** Реальные ADR этого проекта — ADR-002, ADR-003, ADR-004, ADR-005, ADR-006.
> Номера «ADR-001», «ADR-003», «ADR-005», «ADR-006», встречающиеся внутри файлов `dz4/adr_1.md`,
> `dz4/adr_2.md` и в одном из внешних ревью, — **фабрикации**, заимствованные из постороннего примера
> (разделы 26.4 и 34.1 контекста). Совпадение номеров случайно, содержание не имеет отношения к этим ADR.

## Статус

**Proposed.** Правило уже фактически действует: оно применено в разделах 5.3 и 29.5 контекста, отражено
на диаграммах C4 L2 и на всех C3 Этапа 2, и дважды служило основанием отклонить внешние замечания
(раздел 41.9). Этот документ переводит его из «сложившейся практики» в зафиксированное решение.
Перевод в Accepted — после закрытия исключения, описанного в разделе «Открытое исключение» ниже.

## Контекст и постановка проблемы

Система интегрируется с пятью внешними системами водоканала, каждая — со своей БД и своим владельцем:
Биллинг (legacy), Платформа ЛК, микросервис обращений, Диспетчерская система, файловое хранилище базы
знаний. Все пять находятся внутри закрытой сети водоканала: доступа снаружи нет ни на разработке, ни на
демонстрации (раздел 39, `Build_Plan.html`, код-шаг 0).

Вопрос: **как именно наши контейнеры обращаются к этим системам** — читают их базы данных напрямую или
ходят через программные интерфейсы, которые эти системы предоставляют.

Вопрос не абстрактный. Промежуточная редакция раздела 29.5 (версии 4.1–4.4) утверждала, что протокол
Биллинга — «прямой SQL через сервис на Go (приоритет), XML-RPC (резерв)», и вводила из-за этого
отдельный контейнер «Слой доступа к Биллингу» как anti-corruption layer. Уточнение показало, что у
Биллинга есть собственный внешний XML-RPC API, и отдельный слой нашей разработки не нужен. Это уже
привело к одной переделке L2 и одной несостоявшейся переделке C3 Backend — цена отсутствия
зафиксированного правила.

## Драйверы решения (силы, действующие на решение)

| Сила | Требование | В чём конфликт |
|---|---|---|
| Владение схемой | Схема БД принадлежит системе-владельцу и меняется без предупреждения нас | Прямой SQL делает нашу систему зависимой от внутреннего устройства чужой — любая миграция у соседа ломает нас молча, без ошибки компиляции и без уведомления |
| Контракт | API — это обязательство владельца перед потребителями; схема БД обязательством не является | Читая БД, мы получаем данные, но не получаем контракта: гарантий совместимости нет ни формальных, ни моральных |
| Целостность данных | Инварианты (валидация, каскады, бизнес-правила) живут в коде системы-владельца, а не в её таблицах | Прямая запись в чужую БД обходит эти инварианты и может оставить данные владельца в состоянии, которого его собственный код не допускает |
| Стадийность | Backend читает Биллинг на Этапе 1, Billing Adapter пишет на Этапе 2 (разделы 5.3, 5.4) | Два потребителя одной системы должны говорить с ней одинаково, иначе рано или поздно разойдутся (та же логика единого источника правды, что в разделе 32) |
| 152-ФЗ и аудит | Обращения к ПДн абонента должны быть контролируемы и логируемы | API системы-владельца даёт точку контроля доступа и аудита на её стороне; прямой SQL обходит и то, и другое |
| Закрытая сеть | Реальных систем нет ни на разработке, ни на демо (раздел 39) | Тестировать можно только против синтетики; чем уже и формальнее интерфейс, тем дешевле его достоверно заглушить |

## Рассмотренные варианты

### Вариант A — Прямой SQL в базы данных внешних систем

Наши контейнеры подключаются к БД Биллинга, БД обращений и прочим напрямую и читают/пишут таблицы.

**Pros**
- Максимально быстрый старт: не нужно ждать, пока владелец опишет или доработает API.
- Нет ограничений чужого API — доступны любые поля и любые выборки, включая те, которых в API нет.
- Меньше сетевых звеньев на пути запроса, потенциально ниже задержка.

**Cons**
- Схема БД не является контрактом: миграция на стороне владельца ломает нас без предупреждения, и
  поломка обнаружится в проде, а не при сборке.
- Обход инвариантов владельца при записи — риск оставить чужие данные в недопустимом состоянии.
- Обход контроля доступа и аудита на стороне системы-владельца, что плохо совместимо с требованиями
  к обработке ПДн абонента.
- Скрытая связанность: наш релизный цикл оказывается привязан к чужому, хотя формально мы независимы.

### Вариант B — Свой anti-corruption слой поверх чужих БД

Отдельный наш контейнер инкапсулирует прямой SQL, а остальные компоненты ходят в него по внутреннему
HTTP.

**Pros**
- Знание о чужой схеме сосредоточено в одном месте — при миграции у владельца правится один контейнер.
- Остальная система работает с чистым внутренним интерфейсом.

**Cons**
- Не устраняет корневую проблему, а переносит её: мы по-прежнему зависим от чужой схемы, просто
  в одном файле вместо нескольких.
- Инварианты владельца всё так же обходятся при записи.
- Дополнительный контейнер, который надо разрабатывать, разворачивать и сопровождать, — при том что
  система-владелец, как выяснилось для Биллинга, **уже предоставляет** ровно такой слой в виде своего API.
- Именно этот вариант был записан в разделе 29.5 версий 4.1–4.4 и отменён как избыточный.

### Вариант C — Только через API систем-владельцев (ВЫБРАНО)

Каждое обращение к внешней системе идёт через интерфейс, который эта система предоставляет и
поддерживает. В её БД мы не ходим ни на чтение, ни на запись.

**Pros**
- Мы зависим от контракта, а не от внутреннего устройства соседа; совместимость — обязательство владельца.
- Инварианты, контроль доступа и аудит на стороне владельца работают штатно.
- Не требуется собственный слой-посредник там, где владелец уже предоставил API (случай Биллинга).
- Заглушить API синтетикой для разработки и демо проще и достовернее, чем воспроизводить чужую схему БД.
- Одно правило на все пять систем — не нужно решать заново для каждой интеграции.

**Cons**
- Мы ограничены тем, что API отдаёт: если нужного поля или выборки нет, требуется договариваться
  с владельцем, а не написать свой запрос.
- Дополнительное сетевое звено и накладные расходы сериализации против прямого запроса к БД.
- Для пакетных выгрузок больших объёмов API может оказаться неудобным или медленным — см. открытое
  исключение ниже.

## Решение (Decision Outcome)

Выбран **Вариант C**. Правило формулируется так:

> **В чужую систему обращаемся только через её API. Ни на чтение, ни на запись мы не идём напрямую
> в базу данных, которой владеет другая система.**

Применение по системам:

| Внешняя система | Кто из наших обращается | Через что | Этап |
|---|---|---|---|
| Биллинг | API Gateway / Backend (read) | внешний XML-RPC API Биллинга | 1 |
| Биллинг | Billing Adapter (write) | тот же внешний XML-RPC API + Idempotency-Key | 2 |
| Микросервис обращений | Сервис работы с обращениями | API микросервиса обращений | 2 |
| Диспетчерская система | Backend (read справочно) | REST API | 1 |
| Диспетчерская система | Сервис работы с обращениями (write) | REST API | 2 |
| Платформа ЛК | Backend | SSO / HTTPS | 1 |
| База знаний | ETL Worker | файловый доступ, только чтение | 1 |

Следствия для архитектуры, уже отражённые в диаграммах:
- Отдельный контейнер «Слой доступа к Биллингу» **не вводится** — API самой системы выполняет эту роль.
- У Billing Adapter **нет** собственного SQL-клиента к БД Биллинга.
- У Сервиса работы с обращениями **нет** прямого доступа к БД обращений.
- Backend (Этап 1) и Billing Adapter (Этап 2) идут в Биллинг по одному и тому же протоколу независимо
  друг от друга; общий код-посредник между ними не вводится.

Правило распространяется и в обратную сторону: чужие системы не читают наши БД. Если подрядчикам нужны
обращения, они получают их из микросервиса обращений, а не из нашего Session State Store.

## Открытое исключение — корпус для дообучения

Раздел 30 описывает батч-сбор корпуса для дообучения из источников 3 (БД обращений абонентов),
6 (лог диалогов) и 10 (CRM колл-центра) через K8s CronJob + PII Filter. Источник 6 — наш собственный
Session State Store, к нему правило не относится. **Источники 3 и 10 принадлежат чужим системам**, и
способ их выгрузки в разделе 30 не уточнён.

Если выгрузка задумана как прямое чтение чужих БД — она **нарушает это решение** и должна быть
переведена на один из вариантов: пакетный метод API системы-владельца; выгрузка, которую владелец
делает сам и кладёт в согласованное место; либо чтение реплики, предоставленной владельцем явно и
под его ответственность.

До закрытия этого вопроса ADR остаётся в статусе Proposed. Это единственное, что мешает Accepted.

## Последствия (Consequences)

**Хорошо, потому что:**
- Снимает целый класс будущих споров: вопрос «как ходим в эту систему» решён один раз для всех пяти.
- Уже окупилось дважды — правило позволило отклонить два внешних замечания, которые развели бы
  диаграммы с каноном (раздел 41.9), причём одно из них предлагало Shared Database с подрядчиками.
- Делает синтетику для закрытой сети (код-шаг 0) достовернее: заглушается формальный интерфейс,
  а не воспроизводится чужая схема БД.
- Сохраняет контроль доступа и аудит на стороне владельцев ПДн — аргумент, который понадобится
  при согласовании с ИБ.

**Плохо, потому что:**
- Мы становимся зависимы от полноты чужих API. Если в XML-RPC API Биллинга не окажется нужного метода,
  быстрого обходного пути по этому решению нет — только переговоры с владельцем.
- Пакетные сценарии (корпус для дообучения) через API могут оказаться медленнее и дороже, чем прямая
  выгрузка; это прямая цена решения, а не недосмотр.
- XML-RPC как протокол Биллинга нам не нравится и не выбирался нами — он навязан legacy-системой.
  Решение фиксирует, что мы принимаем это ограничение, а не обходим его через SQL.

## Подтверждение (Confirmation)

Решение считается реализованным, когда выполнены все условия:

1. Ни в одном модуле кода нет строки подключения к БД, принадлежащей внешней системе. Проверяется
   поиском по конфигурации и коду на этапе ревью — отдельный пункт чек-листа.
2. Закрыт вопрос выгрузки источников 3 и 10 для корпуса дообучения (раздел «Открытое исключение»),
   и выбранный способ описан в разделе 30 контекста.
3. Для каждой из пяти внешних систем в каталоге источников (раздел 29) явно указан протокол доступа
   и подтверждено, что это интерфейс системы-владельца, а не её БД.
4. Синтетические заглушки (код-шаг 0) реализуют именно интерфейсы систем, а не копии их схем БД.
