# ADR-400: Безопасность по этапам

## Статус

**Accepted** как сводка: что закрыто по безопасности сейчас и что добавляется на следующих
контурах. Сравнения вариантов по слоям безопасности — в конце документа. Реализация — в коде
(`app/gateway/pii_filter.py`, `app/gateway/quota.py`).

## Закрыто сейчас (Этап 1)

**Персональные данные не покидают периметр.** Весь текст неизвестного происхождения —
вопрос абонента и ответ модели — проходит `PII Sanitizer` (Presidio + собственные распознаватели: ФИО,
СНИЛС, ИНН, номер лицевого счёта, телефон, email) **до** отправки в LLM Provider. Собственный корпус
базы знаний проверяется один раз при сборке, не на каждом ответе — обезличиватель предназначен для
чужого текста, а не для документов, которые собрала сама команда.

**ПДн абонента не покидают РФ.** 152-ФЗ соблюдается выбором провайдера: и YandexGPT (прототип), и
GigaChat (MVP) — управляемые API на территории РФ. Зарубежные провайдеры исключены архитектурно,
а не настройкой — заменить провайдера на зарубежный означало бы нарушить закон, не только архитектуру.

**Проверка TLS не отключается никогда.** GigaChat требует корневых сертификатов НУЦ Минцифры; там, где
их нет (машина прототипа), проект переключается на другого провайдера, а не отключает проверку
сертификата — по соединению идут персональные данные абонента, отключение проверки было бы дырой, а не
компромиссом.

**Ответ модели проверяется до показа абоненту (Guardrails).** Модель отвечает уверенно и связно, но может выдать то,
чего абонент видеть не должен: персональные данные из контекста, недопустимый тон, внутренние инструкции
ассистента. Синхронная проверка (бюджет менее 50 мс на кусок потока; **на длинных ответах бюджет не выдерживается**, замер ниже)
смотрит накопленный текст и при нарушении обрывает поток, отдавая вместо ответа безопасную заглушку; причина блокировки пишется отдельным полем, а утечка ПДн
выводится на дашборде отдельно от общего счётчика. Отдельная причина `unperformed_action` блокирует ответ, где модель пишет, что выполнила
операцию («Передал показания…», «Проверил долг…»): абонент видит текст о том, что действие не выполнено, а не нейтральную заглушку
(правило начала предложения с глаголом первого лица; перечень глаголов собран вручную, на живых ответах не проверялся). Обоснованность ответа считается асинхронно, после выдачи, и не
блокирует её. Реализация — `app/gateway/guardrails.py`; выбор регулярных выражений для проверок на потоке — в
разделе «Сравнение вариантов по слоям безопасности».

**Лимиты — fail-closed.** Если хранилище квот (Redis) недоступно, сервис отказывает запросам (проверено остановкой Redis: запрос без потока —
HTTP 503 с `Retry-After: 30`; потоковый — HTTP 200 и событие `error` со статусом 503), а не пропускает их без учёта — иначе лимит перестаёт быть лимитом именно в момент сбоя,
когда защита нужнее всего. Состояние диалога — отдельный случай: его недоступность закрывает
только путь записи («сессии нет»), не весь сервис, — эта асимметрия сознательная.

**Секреты не в открытом виде на диске разработки.** Ключ YandexGPT задаётся только переменной
окружения оболочки — файла на диске с секретом нет вообще (приложение `.env` не читает), опционально
через Vault в dev-режиме на локальной машине. Честно зафиксировано: dev-режим Vault сам по себе не
безопаснее обычной переменной окружения и целевой схеме MVP не соответствует (там GitLab CI variables, ниже) — это необязательный локальный вариант, не
самостоятельная защита секрета на прототипе.

**Наименьшие привилегии доступа к внешним системам.** Ни к одной внешней системе (Биллинг, Диспетчерская,
микросервис обращений) у проекта нет прямого доступа к БД — только через их собственные API (XML-RPC у
Биллинга, REST у Диспетчерской). Схема чужой БД — не контракт проекта.

## Что добавляется с функциональным Этапом 2 (операции записи, любой контур)

**HITL для всех операций записи.** Заявки, показания, документы, изменения данных
абонента — только после явного подтверждения абонента (не текст реплики, отдельное действие в
интерфейсе). Обязательны: состояние ожидания подтверждения, идемпотентность (повтор с тем же ключом не
создаёт дубль), аудит-лог (кто/что/когда/ключ/результат), возможность отказа абонента — отказ тоже
пишется в аудит, с пометкой, что операция не выполнялась.

**Привязка сессии к абоненту на каждом write-шаге.** Защита от подмены (Spoofing/IDOR): каждый шаг
записи повторно проверяет, что `subscriber_id` действительно принадлежит текущей сессии, а не подставлен
в запросе. **Открытый пункт (P1)** — на целевой архитектуре Этапа 2 эта проверка спроектирована, но не
реализована: обращение на прототипе сейчас пишется по упрощённому пути (ADR-100), где этот риск ниже,
но при переходе на целевой путь Этапа 2 проверка обязательна до включения записи в проде.

## Что добавляется в контуре MVP (инфраструктура, независимо от функционального этапа)

**Проверка работоспособности Guardrails на живых данных.** Проверки на потоке подобраны без живых ответов модели:
неизвестно, как часто они срабатывают зря (ложные блокировки) и что пропускают (тон, ПДн в необычной форме). На
MVP до включения в работу проверка запускается на ограниченном объёме живых вопросов: размечаются нарушения,
измеряются ложные срабатывания и пропуски, шаблоны правятся. Оценка работ — ADR-600.

**Трафик внутри кластера не шифруется.** Backend ходит в Qdrant по gRPC (порт 6334) или REST (порт 6333) **без TLS и без ключа API**: в compose и в клиенте их нет. Защита — закрытый контур и сетевые правила кластера (NetworkPolicy; правила доступа именно к Qdrant
в документах не описаны). Нужен ли TLS между подами и ключ Qdrant, решает ИБ; в оценки работ не включено. Так же устроены связи с Postgres и Redis (проверить).

**Секреты: GitLab CI/CD variables, деплой через pipeline.** Принято 24 сентября 2026: целевой механизм секретов — **GitLab CI/CD variables, деплой через pipeline** (в реальном контуре уже используется GitLab; документально не подтверждено, настройки GitLab и кластера не проверялись). Ранее в ADR был выбран Vault Agent Injector (sidecar); выбор отменён как не обоснованный:
сравнение с альтернативами не проводилось, а механизм не учитывал, что у владельца уже есть GitLab. Сравнение вариантов — ADR-200, «Секреты в проде: GitLab CI variables и альтернативы».

**Как устроено.**
- Секреты хранятся как CI/CD variables проекта или группы: **masked** (значение скрыто в логах job) и **protected** (доступны только pipeline защищённых веток и тегов); по возможности с областью по окружению
  (доступность этой возможности зависит от версии и редакции GitLab — проверить).
- Job деплоя создаёт или обновляет **Kubernetes Secret** в namespace `ai-app` из переменных, значения в лог не выводятся. Поды получают значения через `secretKeyRef` или `envFrom`:
  приложение читает переменные окружения, как на прототипе, **изменений кода нет**.
- Секреты не попадают в образ, в Git и в манифесты репозитория.
- Состав: токены и ключи LLM-провайдера, учётные данные Биллинга, `X-Internal-Token`, пароли Postgres и Redis, ключи S3.

**Что этот механизм не даёт (ограничения, а не упущения).**
- Значения переменных видны ролям проекта GitLab с правом их читать (по документации GitLab — Maintainer и выше; проверить). **Аудита чтения нет**; журнал изменений зависит от редакции GitLab.
- Kubernetes Secret лежит в etcd в кодировке base64; шифрование etcd — настройка кластера, в кластере владельца **неизвестна**. Доступ к секрету — RBAC namespace.
- Замена секрета: изменить переменную, повторить deploy и **перезапустить поды** (переменные окружения фиксируются при старте). Перечитывания без перезапуска нет.
- Маскирование в логах — по документации GitLab только для значений определённого формата и не защищает от вывода значения в изменённом виде (например, по частям): в скриптах job секреты не печатаются.
- Динамических секретов и коротких аренд нет. Для статичных ключей внешних провайдеров это не требуется.

**Когда пересмотреть (перейти на Vault или другое хранилище).** ИБ требует аудит чтения секретов, динамические секреты или замену без перезапуска; у владельца появляется своё хранилище секретов; число секретов
и окружений растёт до того, что ручная работа с переменными GitLab становится неуправляемой. Путь без переделки приложения: pipeline или Kubernetes Secret получают значения из хранилища,
а поды по-прежнему читают переменные окружения (GitLab CI умеет получать секреты из Vault в job — по документации, не проверялось).

**Работы.** Заведение переменных по окружениям, job деплоя с созданием Kubernetes Secret без вывода в лог, подключение в поды, регламент замены секрета, проверка, что значения не попадают в лог pipeline, образ и
манифесты: **2–3 чел-дн** (оценка автора, в итог сметы не добавлено — строка «Секреты и конфигурация» матрицы). Согласование с ИБ и владельцем кластера (шифрование etcd, права на namespace, кто имеет роль Maintainer) — календарный срок, а не чел-дн; вопросы владельцу перечислены в ADR-200, «Почему Kubernetes».

## Что добавляется в контуре тиража

**Данные не покидают периметр вообще, а не только территорию РФ.** Если будет принято решение о собственной модели (Qwen2.5-32B), она
разворачивается «в контуре» — внутри закрытой сети водоканала, на собственном GPU node pool. Решение не принято и принимается только после замеров и оценки реальной
работы на MVP; поводы вынести вопрос — запрет ИБ на внешние API или рост нагрузки. До решения данные идут через управляемый API на территории РФ, что уже соответствует 152-ФЗ.

**Изоляция GPU между офлайн-ETL и онлайн-обслуживанием.** Открытый вопрос (не решён): инференс
эмбеддингов/реранжинга общий для индексации базы знаний и для ответов абонентам в реальном времени —
без изоляции (приоритетные очереди либо отдельный пул) массовая переиндексация может увеличить
задержку ответа абоненту. Решение спроектировано, реализация — на момент появления второй нагрузки.

## Не входит в объём Этапа 1 (открытые пункты для приёмки)

- Проверка `subscriber_id` ↔ `session_id` на write-шагах Этапа 2 — спроектирована, не реализована.
- Согласование критериев решения о собственной модели с ИБ — не проведено.
- SSO-интеграция с Платформой ЛК — на прототипе `subscriber_id` берётся из метаданных запроса
  (демо-стенд), не из настоящей SSO-сессии; `Auth & Session Middleware` — целевой компонент Этапа 2.
- Изоляция GPU между ETL и онлайн-инференсом — открыта.
- Время синхронной проверки Guardrails растёт с длиной ответа и на ответах около 2 000 знаков не укладывается в 50 мс (замер в разделе «Время синхронной проверки»).

## Сравнение вариантов по слоям безопасности

Как и в ADR-200, сравнение сделано по документации проектов и требованиям проекта; замеров, кроме указанных в
ADR-300 и в подразделе «Время синхронной проверки», нет. Строка «Итог» — решение проекта.

### Почему Presidio и собственные распознаватели

Требования: находить ФИО, СНИЛС, ИНН, лицевой счёт, телефон и электронную почту в русском тексте; работать внутри
закрытого контура; отдавать в журнал только типы найденного, без значений.

| Критерий | Presidio + собственные распознаватели (выбрано) | Только регулярные выражения | Специализированный русский NER (например, Natasha) | Внешний сервис обезличивания |
|---|---|---|---|---|
| ФИО (нужен разбор языка) | Presidio с русской моделью spaCy | Нет | Да | Да |
| СНИЛС и ИНН с проверкой контрольных сумм, лицевой счёт | Собственные распознаватели (без контрольных сумм любые одиннадцать цифр выглядели бы как СНИЛС) | Да, если написать контрольные суммы | Не из коробки | Зависит от сервиса |
| Данные остаются в закрытом контуре | Да | Да | Да | Нет: запрещено правилом «ПДн не покидают периметр» |
| Итог | **Выбран** | Отклонён: не находит ФИО | Не выбран: по документации находит имена и адреса, СНИЛС, ИНН, лицевой счёт, телефон и почту всё равно писать самим (не проверялась); Presidio даёт общий каркас и разрешение перекрытий | Отклонён: 152-ФЗ, периметр |

Замер базового набора Presidio показал, почему одного его мало: лицевой счёт определялся как телефон, одна почта
получала три метки сразу. Поэтому распознаватели разделены на две группы: собственные (СНИЛС, ИНН, лицевой счёт,
телефон — чистые функции, работают мгновенно) и Presidio (ФИО, почта — нужен разбор языка).

### Почему проверки ответа — регулярные выражения на потоке

Требование: синхронная проверка стоит на пути ответа и задерживает каждый кусок потока, её бюджет — менее 50 мс;
при нарушении поток обрывается.

| Критерий | Регулярные выражения (выбрано) | ML-классификатор токсичности | Проверка LLM-судьёй | Внешний сервис модерации |
|---|---|---|---|---|
| Укладывается в 50 мс на кусок | На ответах до ≈800 знаков — на границе (P95 ≈ 49 мс); на ≈2 000 знаков — нет (P95 ≈ 120 мс), см. замер ниже | Не измерялось; на CPU есть риск | Нет: секунды (у YandexGPT время до первого куска — 0,3–21 с, 19 вызовов) | Нет: сетевая задержка |
| Что проверяет | ПДн в ответе, недопустимые формулировки, разглашение промпта | Тон точнее | Обоснованность ответа | — |
| Данные остаются в контуре | Да | Да | Зависит от судьи | Нет |
| Итог | **Выбраны для синхронной проверки** | Не выбран: бюджет и вес модели | **Выбран для асинхронной оценки обоснованности**: не блокирует выдачу | Отклонён: периметр |

Слабое место решения: тон и тонкие случаи регулярными выражениями ловятся плохо; обоснованность оценивает отдельный
судья после выдачи (ADR-300, раздел 5).

### Время синхронной проверки

Проверка на каждом куске потока прогоняет **весь накопленный текст** через обезличиватель (Presidio, разбор языка
spaCy, `app/gateway/guardrails.py`), а не только новый кусок. Поэтому время растёт с длиной ответа. Замер 24 сентября
2026 на машине прототипа (CPU, без параллельной нагрузки), ответ подаётся кусками, время одной проверки:

| Длина ответа | Кусок | Медиана | P95 | Максимум | Суммарная задержка потока |
|---|---|---:|---:|---:|---:|
| 798 знаков | ≈30 знаков (27 проверок) | 28,7 мс | 49,3 мс | 59,1 мс | 0,83 с |
| 798 знаков | ≈100 знаков (8 проверок) | 44,9 мс | 48,2 мс | 57,6 мс | 0,30 с |
| 1 995 знаков | ≈30 знаков (67 проверок) | 69,3 мс | 119,0 мс | 171,2 мс | 4,5 с |
| 1 995 знаков | ≈100 знаков (20 проверок) | 62,3 мс | 122,1 мс | 127,9 мс | 1,4 с |

Вывод: бюджет 50 мс на кусок держится только на коротких ответах (реальные ответы YandexGPT на прототипе — порядка
80–110 токенов, то есть до ≈500–700 знаков, 19 вызовов); на ответах около 2 000 знаков проверка вдвое-втрое дороже
бюджета. Замер на синтетическом тексте без ПДн (типичный для справочных ответов), одна машина. Инициализация
обезличивателя занимает около 36 с (один раз при старте). Проверять нужно только новый кусок с небольшим перекрытием, а
не весь текст заново — это изменение кода, оно не сделано (ADR-600, «Проверка Guardrails»).

### Как выбран способ доступа к внешним системам

Требование: прямого чтения чужих БД нет; доступ только через интерфейс, который предоставил владелец.

| Система | Способ | Альтернативы | Итог |
|---|---|---|---|
| Биллинг | XML-RPC API Биллинга | Прямой SQL (запрещён), реплика или выгрузка владельца | **XML-RPC** — единственный доступный у Биллинга интерфейс |
| Диспетчерская | REST API | Прямой SQL (запрещён), выгрузка владельца | **REST** — интерфейс владельца |
| Микросервис обращений | HTTP API владельца | Прямая запись в таблицу (на прототипе, временно) | **API владельца**; сигнатуры пока не получены |
| Платформа личного кабинета | SSO | Идентификатор в метаданных запроса (только на стенде) | Протокол SSO **не выбран**: интеграция не начата |

Для источников, у которых нет пакетного метода API (история обращений, расшифровки колл-центра), допустимы три
варианта: пакетный метод API, выгрузка, которую владелец делает сам, чтение реплики под его ответственность.
Выбор не сделан (см. заметку «Как выгружаются история обращений и расшифровки колл-центра» на странице 1 схемы потоков данных, `Data_Flow_Diagrams.html`).

### Модель разбора языка для обезличивания: что будет сравниваться

ФИО находит Presidio с русской моделью spaCy `ru_core_news_md`. На прототипе проверка сделана на 136 настоящих
обращениях: отсев ложных находок разбора языка снимает 58 находок из 63; **полнота** (сколько настоящих ФИО и адресов
пропущено) на живых данных не измерялась. Для 152-ФЗ пропуск опаснее ложной находки, поэтому на MVP полнота
обезличивания проверяется на размеченных живых обращениях.

| Кандидат | Что известно | Замер в проекте | Статус |
|---|---|---|---|
| spaCy `ru_core_news_md` | Средняя русская модель, работает на CPU | Ложные находки измерены, полнота нет | **Прототип** |
| spaCy `ru_core_news_sm` / `_lg` | Меньшая и большая модели того же семейства | Не измерялись | Кандидат для сравнения |
| Natasha (русский NER) | Специализированная библиотека для русских имён и адресов | Не измерялась | Кандидат для сравнения и для адресов |
| Собственные распознаватели (СНИЛС, ИНН, лицевой счёт, телефон, почта) | Правила и контрольные суммы | Проверены на 136 обращениях | Остаются |

Сравнение: разметка ПДн в живых обращениях, полнота и точность по видам (ФИО, адрес, телефон, лицевой счёт, почта),
время на запрос в бюджете шлюза; правка распознавателей и выбор модели (ADR-600, «Полнота обезличивания на живых
данных»).
