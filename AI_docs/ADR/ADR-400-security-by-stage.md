# ADR-400: Безопасность по этапам

## Статус

**Accepted** как сводка: что закрыто по безопасности сейчас и что добавляется на следующих
контурах, без полной истории обсуждения — для неё раздел «Источники» ниже. Реализация — в коде
(`app/gateway/pii_filter.py`, `app/gateway/quota.py`).

## Закрыто сейчас (Этап 1)

**Персональные данные не покидают периметр.** Весь текст неизвестного происхождения —
вопрос абонента и ответ модели — проходит `PII Sanitizer` (Presidio + собственные распознаватели: ФИО,
СНИЛС, ИНН, номер лицевого счёта, телефон, email) **до** отправки в LLM Provider. Собственный корпус
базы знаний проверяется один раз при сборке, не на каждом ответе — обезличиватель предназначен для
чужого текста, а не для документов, которые собрала сама команда.

**ПДн абонента не покидают РФ.** 152-ФЗ соблюдается выбором провайдера: и YandexGPT (прототип), и
GigaChat (MVP) — управляемые API на территории РФ. Зарубежные провайдеры исключены архитектурно,
а не настройкой — заменить провайдера на зарубежный означало бы нарушить закон, не только архитектуру.

**Проверка TLS не отключается никогда.** GigaChat требует корневых сертификатов НУЦ Минцифры; там, где
их нет (машина прототипа), проект переключается на другого провайдера, а не отключает проверку
сертификата — по соединению идут персональные данные абонента, отключение проверки было бы дырой, а не
компромиссом.

**Лимиты — fail-closed.** Если хранилище квот (Redis) недоступно, сервис отказывает запросам (503 +
`Retry-After`), а не пропускает их без учёта — иначе лимит перестаёт быть лимитом именно в момент сбоя,
когда защита нужнее всего. Состояние диалога — отдельный случай: его недоступность закрывает
только путь записи («сессии нет»), не весь сервис, — эта асимметрия сознательная.

**Секреты не в открытом виде на диске разработки.** Ключ YandexGPT задаётся только переменной
окружения оболочки — файла на диске с секретом нет вообще (приложение `.env` не читает), опционально
через Vault в dev-режиме на локальной машине. Честно зафиксировано: dev-режим Vault сам по себе не
безопаснее обычной переменной окружения — это репетиция интеграции для целевой схемы, не
самостоятельная защита секрета на прототипе.

**Наименьшие привилегии доступа к внешним системам.** Ни к одной внешней системе (Биллинг, Диспетчерская,
микросервис обращений) у проекта нет прямого доступа к БД — только через их собственные API (XML-RPC у
Биллинга, REST у Диспетчерской). Схема чужой БД — не контракт проекта.

## Что добавляется с функциональным Этапом 2 (операции записи, любой контур)

**HITL для всех операций записи.** Заявки, показания, документы, изменения данных
абонента — только после явного подтверждения абонента (не текст реплики, отдельное действие в
интерфейсе). Обязательны: состояние ожидания подтверждения, идемпотентность (повтор с тем же ключом не
создаёт дубль), аудит-лог (кто/что/когда/ключ/результат), возможность отказа абонента — отказ тоже
пишется в аудит, с пометкой, что операция не выполнялась.

**Привязка сессии к абоненту на каждом write-шаге.** Защита от подмены (Spoofing/IDOR): каждый шаг
записи повторно проверяет, что `subscriber_id` действительно принадлежит текущей сессии, а не подставлен
в запросе. **Открытый пункт (P1)** — на целевой архитектуре Этапа 2 эта проверка спроектирована, но не
реализована: обращение на прототипе сейчас пишется по упрощённому пути (ADR-100), где этот риск ниже,
но при переходе на целевой путь Этапа 2 проверка обязательна до включения записи в проде.

## Что добавляется в контуре MVP (инфраструктура, независимо от функционального этапа)

**Секреты через Vault Agent Injector.** На целевой инфраструктуре (Kubernetes) секреты внедряются в
под через sidecar-инжектор, а не читаются из переменных окружения, заданных вручную — единый источник
истины, отзыв доступа без пересборки образа.

## Что добавляется в контуре тиража

**Данные не покидают периметр вообще, а не только территорию РФ.** Self-hosted-модель (Qwen2.5-32B)
разворачивается «в контуре» — внутри закрытой сети водоканала, на собственном GPU node pool. Это
включается по триггеру (запрет ИБ на внешние API или рост нагрузки), а не по расписанию — до триггера
данные продолжают идти через управляемый API на территории РФ, что уже соответствует 152-ФЗ.

**Изоляция GPU между офлайн-ETL и онлайн-обслуживанием.** Открытый вопрос (не решён): инференс
эмбеддингов/реранжинга общий для индексации базы знаний и для ответов абонентам в реальном времени —
без изоляции (приоритетные очереди либо отдельный пул) массовая переиндексация может увеличить
задержку ответа абоненту. Решение спроектировано, реализация — на момент появления второй нагрузки.

## Не входит в объём Этапа 1 (открытые пункты для приёмки)

- Проверка `subscriber_id` ↔ `session_id` на write-шагах Этапа 2 — спроектирована, не реализована.
- Согласование перечня триггеров self-hosted-перехода с ИБ — не проведено.
- SSO-интеграция с Платформой ЛК — на прототипе `subscriber_id` берётся из метаданных запроса
  (демо-стенд), не из настоящей SSO-сессии; `Auth & Session Middleware` — целевой компонент Этапа 2.
- Изоляция GPU между ETL и онлайн-инференсом — открыта.

## Сравнение вариантов по слоям безопасности

Как и в ADR-200, сравнение сделано по документации проектов и требованиям проекта; замеров, кроме указанных в
ADR-300, нет. Строка «Итог» — решение проекта.

### Почему Presidio и собственные распознаватели

Требования: находить ФИО, СНИЛС, ИНН, лицевой счёт, телефон и электронную почту в русском тексте; работать внутри
закрытого контура; отдавать в журнал только типы найденного, без значений.

| Критерий | Presidio + собственные распознаватели (выбрано) | Только регулярные выражения | Специализированный русский NER (например, Natasha) | Внешний сервис обезличивания |
|---|---|---|---|---|
| ФИО (нужен разбор языка) | Presidio с русской моделью spaCy | Нет | Да | Да |
| СНИЛС и ИНН с проверкой контрольных сумм, лицевой счёт | Собственные распознаватели (без контрольных сумм любые одиннадцать цифр выглядели бы как СНИЛС) | Да, если написать контрольные суммы | Не из коробки | Зависит от сервиса |
| Данные остаются в закрытом контуре | Да | Да | Да | Нет: запрещено правилом «ПДн не покидают периметр» |
| Итог | **Выбран** | Отклонён: не находит ФИО | Не выбран: закрывает ФИО, остальное всё равно писать самим; Presidio даёт общий каркас и разрешение перекрытий | Отклонён: 152-ФЗ, периметр |

Замер базового набора Presidio показал, почему одного его мало: лицевой счёт определялся как телефон, одна почта
получала три метки сразу. Поэтому распознаватели разделены на две группы: собственные (СНИЛС, ИНН, лицевой счёт,
телефон — чистые функции, работают мгновенно) и Presidio (ФИО, почта — нужен разбор языка).

### Почему проверки ответа — регулярные выражения на потоке

Требование: синхронная проверка стоит на пути ответа и задерживает каждый кусок потока, её бюджет — менее 50 мс;
при нарушении поток обрывается.

| Критерий | Регулярные выражения (выбрано) | ML-классификатор токсичности | Проверка LLM-судьёй | Внешний сервис модерации |
|---|---|---|---|---|
| Укладывается в 50 мс на кусок | Да | Зависит от модели; на CPU есть риск | Нет: секунды | Нет: сетевая задержка |
| Что проверяет | ПДн в ответе, недопустимые формулировки, разглашение промпта | Тон точнее | Обоснованность ответа | — |
| Данные остаются в контуре | Да | Да | Зависит от судьи | Нет |
| Итог | **Выбраны для синхронной проверки** | Не выбран: бюджет и вес модели | **Выбран для асинхронной оценки обоснованности**: не блокирует выдачу | Отклонён: периметр |

Слабое место решения: тон и тонкие случаи регулярными выражениями ловятся плохо; обоснованность оценивает отдельный
судья после выдачи (ADR-300, раздел 5).

### Как выбран способ доступа к внешним системам

Требование: прямого чтения чужих БД нет; доступ только через интерфейс, который предоставил владелец.

| Система | Способ | Альтернативы | Итог |
|---|---|---|---|
| Биллинг | XML-RPC API Биллинга | Прямой SQL (запрещён), реплика или выгрузка владельца | **XML-RPC** — единственный доступный у Биллинга интерфейс |
| Диспетчерская | REST API | Прямой SQL (запрещён), выгрузка владельца | **REST** — интерфейс владельца |
| Микросервис обращений | HTTP API владельца | Прямая запись в таблицу (на прототипе, временно) | **API владельца**; сигнатуры пока не получены |
| Платформа личного кабинета | SSO | Идентификатор в метаданных запроса (только на стенде) | Протокол SSO **не выбран**: интеграция не начата |

Для источников, у которых нет пакетного метода API (история обращений, расшифровки колл-центра), допустимы три
варианта: пакетный метод API, выгрузка, которую владелец делает сам, чтение реплики под его ответственность.
Выбор не сделан (см. заметку «Как выгружаются история обращений и расшифровки колл-центра» на странице 1 схемы потоков данных, `Data_Flow_Diagrams.html`).
