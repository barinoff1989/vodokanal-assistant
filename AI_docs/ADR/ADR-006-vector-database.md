# ADR-006: Векторная база данных — Qdrant (self-hosted)

> **Оговорка о нумерации.** См. ADR-003. Номер «ADR-006» носит файл `dz4/adr_2.md`, посвящённый хостингу
> LLM, — это черновик того же вопроса, что и ADR-002, содержащий недостоверные финансовые цифры
> (раздел 26.4 контекста). К настоящему ADR он отношения не имеет. Там же встречается ссылка на
> «ADR-002: выбор Vector DB» — такого документа не существовало; реальный выбор Vector DB фиксируется
> здесь, впервые.

## Статус

**Proposed.** Qdrant используется в проекте с самого начала (раздел 8.2) и уже определяет параметры
индексации, схему payload, деплой-схему и C3 ETL Worker. Как решение с рассмотренными альтернативами
нигде зафиксирован не был. Перевод в Accepted — после первого замера Recall@3 на Golden Set (см.
«Подтверждение»), поскольку целевые 90% — пока декларация, а не измеренный факт.

## Контекст и постановка проблемы

Этап 1 — RAG-ассистент: ответ строится по фрагментам базы знаний, найденным семантическим поиском.
Нужно хранилище векторов, которое обеспечивает:

- **Поиск по косинусной близости** с `top_k=20` и последующим реранжингом до `top_n=3` (раздел 5.5,
  C3 Backend).
- **Фильтрацию по метаданным одновременно с поиском** — по `inquiry_type` в первую очередь (правило 4.8),
  а также `department`, `effective_date`, `source_title`. Это не постфильтрация выдачи: фильтр должен
  участвовать в поиске, иначе при десяти типах обращений релевантные фрагменты нужного типа могут просто
  не попасть в `top_k`.
- **Целевой показатель**: P99 поиска < 100 мс, Recall@3 > 90% (раздел 18, DoD).
- **Переиндексацию без простоя поиска** — blue-green переключение alias (раздел 5.5, C3 ETL Worker).
- **Удаление по источнику** — tombstones по `source_id` при удалении документа из базы знаний.
- **Версионирование модели эмбеддингов в payload** — правило 2 раздела 32: запрос на инференсе должен
  эмбеддиться той же моделью, что и индекс.

**Жёсткое ограничение.** Векторы строятся из документов базы знаний и из связанных с ПДн обращений.
Управляемый зарубежный SaaS исключён по той же причине, по которой в ADR-002 отклонён зарубежный
LLM-провайдер: это трансграничная передача данных без правового основания по 152-ФЗ. Вопрос
допустимости, а не цены. Плюс закрытая сеть водоканала (раздел 39) — внешние сервисы недоступны
физически.

Масштаб — небольшой: база знаний это тысяча документов, а не петабайты (раздел 31).

## Драйверы решения (силы, действующие на решение)

| Сила | Требование | В чём конфликт |
|---|---|---|
| Регуляторный (152-ФЗ) | Векторы, производные от ПДн, не покидают периметр РФ | Любой зарубежный управляемый сервис исключён как класс — та же логика, что в ADR-002 |
| Закрытая сеть | Всё работает внутри контура водоканала (раздел 39) | Внешние сервисы недоступны и на разработке, и на демо |
| Фильтрация при поиске | Фильтр по `inquiry_type` обязан участвовать в поиске, а не применяться к готовой выдаче | Хранилище без встроенной фильтрации по payload ломает таксономию как механизм (правило 4.8) |
| Задержка | P99 поиска < 100 мс (раздел 18) | Число не подкреплено расчётом (P0 №2, раздел 27) — выбор обязан оставлять запас, а не идти впритык |
| Масштаб | Тысяча документов, не петабайты | Тяжёлое распределённое решение — избыточная эксплуатационная нагрузка на команду без выделенного инженера |
| Переиндексация без простоя | Полный реиндекс не должен останавливать поиск | Нужен механизм атомарного переключения на новую коллекцию |
| Ресурс поддержки | Выделенного инженера по ML-инфраструктуре нет (ADR-002) | Чем сложнее кластер, тем выше постоянные затраты команды |

## Рассмотренные варианты

### Вариант A — pgvector (расширение PostgreSQL)

Векторы хранятся в уже имеющемся PostgreSQL, поиск — расширением pgvector.

**Pros**
- Не добавляет нового хранилища: PostgreSQL в проекте уже есть (Session State Store, Sync State,
  materialized view профиля) — одним StatefulSet меньше в эксплуатации.
- Фильтрация по метаданным — обычный SQL WHERE, никаких специальных механизмов.
- Транзакционность и знакомые команде инструменты резервного копирования.
- Достаточен для MVP-масштаба; прямо назван альтернативой для MVP в разделе 8.2.

**Cons**
- Индексация ANN уступает специализированным решениям по управляемости: тонкая настройка HNSW и
  контроль качества/скорости беднее.
- Совмещение векторной нагрузки с транзакционной в одном экземпляре создаёт конкуренцию за ресурсы
  ровно там, где живёт состояние сессий абонентов.
- Механизма переключения alias для реиндексации без простоя нет — его пришлось бы строить самим
  на таблицах и представлениях.
- При росте базы знаний упирается раньше остальных.

### Вариант B — Milvus

Специализированная распределённая векторная СУБД, self-hosted.

**Pros**
- Богатые возможности индексации, зрелость на больших объёмах.
- Горизонтальное масштабирование заложено в архитектуру.
- Также упомянут как MVP-альтернатива в разделе 8.2.

**Cons**
- Существенно более тяжёлая эксплуатация: несколько взаимозависимых компонентов вместо одного сервиса.
- Возможности масштабирования избыточны для тысячи документов — платим сложностью за то, что не нужно.
- Наибольшая эксплуатационная нагрузка из трёх при отсутствии выделенного инженера.

### Вариант C — Qdrant, self-hosted (ВЫБРАНО)

Специализированная векторная СУБД, разворачивается одним StatefulSet внутри кластера.

**Pros**
- **Фильтрация по payload выполняется вместе с векторным поиском**, а не после него — прямое попадание
  в требование по `inquiry_type` (правило 4.8), самое важное функциональное требование этого выбора.
- Payload-индексы по `inquiry_type`, `effective_date`, `department`, `source_title` (раздел 8.2).
- Настраиваемый HNSW с понятными параметрами (`m=16`, `ef=128`, раздел 8.2).
- Штатный механизм алиасов коллекций — blue-green переключение при реиндексации без простоя поиска
  (раздел 5.5) реализуется без самописи.
- Одна служба в эксплуатации: один StatefulSet с PVC на NVMe, без распределённого контура.
- gRPC-клиент, уже заложенный в связи L2 (Backend → Vector DB, ETL Worker → Vector DB).
- Разворачивается внутри закрытой сети — регуляторное ограничение выполняется по построению.

**Cons**
- Отдельное хранилище со своим жизненным циклом, резервным копированием и обновлениями — против
  варианта A, где ничего нового не добавляется.
- Ещё одна технология, которую команде нужно знать.
- Специализированное решение: если проект пойдёт в сторону сложных гибридных запросов с богатой
  реляционной логикой, часть работы придётся делать на стороне Backend.

## Решение (Decision Outcome)

Выбран **Вариант C — Qdrant, self-hosted**, внутри кластера Kubernetes (ADR-004), StatefulSet с
постоянным томом на локальных NVMe.

**Зафиксированные параметры:**

| Параметр | Значение | Источник |
|---|---|---|
| Индекс | HNSW, `m = 16`, `ef = 128` | раздел 8.2 |
| Метрика | косинусная близость | раздел 8.2 |
| Поиск | `top_k = 20` → реранжинг → `top_n = 3` | раздел 5.5, C3 Backend |
| Порог | `score_threshold = 0.7`, ниже — fallback без LLM | раздел 8.2 |
| Payload-индексы | `inquiry_type`, `effective_date`, `department`, `source_title` | раздел 8.2 |
| Обязательно в payload | версия модели эмбеддингов | правило 2, раздел 32 |
| Реиндексация | новая коллекция → переключение alias (blue-green) | раздел 5.5 |
| Удаление | tombstones по `source_id` | раздел 5.5 |

**Отдельно зафиксировано, что исключено и почему.** Управляемые зарубежные векторные сервисы (Pinecone
и аналоги) не рассматривались как вариант вовсе — не из-за цены или качества, а по недопустимости:
векторы производны от связанных с ПДн обращений, и их размещение за периметром РФ означало бы
трансграничную передачу без правового основания. Это то же основание, по которому в ADR-002 исключён
зарубежный LLM-провайдер. Формулировка «не из экономии, а по той же регуляторной причине» уже
зафиксирована в разделе 31 контекста.

**Условие пересмотра:** если появится потребность в сложных гибридных запросах, где реляционная часть
существенно богаче фильтрации по нескольким полям, либо если объём вырастет на порядки против тысячи
документов — вернуться к сравнению с Milvus. Обратный переход к pgvector имеет смысл только при
сокращении масштаба задачи.

## Последствия (Consequences)

**Хорошо, потому что:**
- Требование фильтрации по `inquiry_type` внутри поиска закрыто штатно — таксономия работает как
  механизм, а не как пометка в метаданных.
- Реиндексация без простоя реализуется алиасами коллекций, без самописных схем переключения.
- Регуляторное ограничение выполняется по построению, а не доработкой постфактум.
- Эксплуатационная нагрузка — одна служба, что соразмерно команде без выделенного инженера.

**Плохо, потому что:**
- В эксплуатации появляется ещё одно stateful-хранилище со своим резервным копированием и обновлениями
  (в деплой-схеме — StatefulSet с PVC, бэкапы CronJob → S3/MinIO).
- Целевые P99 < 100 мс и Recall@3 > 90% этим решением **не гарантированы**: они по-прежнему не
  подкреплены расчётом (P0 №2, раздел 27) и зависят не только от хранилища, но и от чанкинга,
  модели эмбеддингов и реранкера.
- Выбор сделан до появления Golden Set — то есть без возможности сравнить варианты на реальных данных.
  Это осознанное следствие того, что хранилище нужно раньше, чем набор для оценки.

## Подтверждение (Confirmation)

Решение считается реализованным, когда выполнены все условия:

1. Qdrant развёрнут StatefulSet с PVC на NVMe; параметры индекса соответствуют таблице выше.
2. Payload-индексы созданы по всем четырём полям; проверено, что фильтр по `inquiry_type` применяется
   **внутри** поиска — тест на фикстуре из нескольких типов обращений (код-шаг 5 `Build_Plan.html`,
   он же закрывает дефект раздела 11.6).
3. Blue-green переключение alias проверено на полном реиндексе: поиск доступен всё время переключения.
4. Recall@3 измерен на Golden Set (раздел 36.5) и сопоставлен с целевыми 90% — без этого числа ADR
   не переводится в Accepted.
5. P99 поиска измерен под нагрузкой и сопоставлен с целевыми 100 мс; расхождение — повод пересмотреть
   либо параметры HNSW, либо сам целевой показатель (P0 №2, раздел 27).
6. В payload каждого вектора присутствует версия модели эмбеддингов, и онлайн-путь проверяет
   её совпадение с моделью, которой эмбеддится запрос (правило 2, раздел 32).
7. **Задано поведение при несовпадении версий** — проверка без последствия бесполезна.
   При mismatch система **не выдаёт ответ по такому контексту**: запрос уходит в fallback
   без LLM (раздел 8.2), поднимается алерт приоритета «миссия-критичный» (та же категория,
   что утечка ПДн, раздел 37.3), и в `quality_report` пишется причина. Обоснование: рассогласование
   версий даёт молча неверный retrieval — ответ выглядит нормальным, но построен по нерелевантным
   фрагментам, и обнаружить это по метрикам качества можно только постфактум. Штатный путь
   устранения — полная переиндексация в окне обслуживания (ADR-005), а не подмена модели запроса.
