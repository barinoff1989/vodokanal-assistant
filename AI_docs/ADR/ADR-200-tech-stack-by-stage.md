# ADR-200: Технологический стек по контурам развёртывания

## Статус

**Accepted** как сводка: вывод и таблица «выбор против альтернатив» по каждому слою стека. Подробные сравнения
вариантов — в разделах «Почему Python, а не Go или Node.js», «Почему FastAPI…», «Почему uvicorn», «Как устроен
шлюз к модели» и «Сравнение вариантов по слоям» (хранилища, виджет, протокол потока, кэш профиля, индексация,
наблюдаемость, документы Этапа 2).

## Как читать таблицу

Колонка «Контур» показывает, где компонент реально разворачивается: **прототип** — уже работает,
**MVP** — целевая production-инфраструктура (разворачивается после stage-gating, ADR-100), **тираж** —
масштаб на порядок больше. Это ось развёртывания, а не функциональный этап (Этап 1/Этап 2 — про
возможности системы, см. ADR-100) — строка про FSM-оркестрацию ниже единственная, где важна именно
функция, а не контур, это отмечено отдельно.

### Почему Python, а не Go или Node.js — Backend / API Gateway

Команда полиглотная (Go Middle, Python Middle, Node.js Upper) — все три языка были реальными вариантами,
не гипотетическими. Решающее ограничение — архитектурное: RAG-логика
(эмбеддинг запроса, поиск, сборка промпта) обязана жить **внутри** контейнера Backend, не выноситься в
отдельный сервис.

| Критерий | Python / FastAPI | Go | Node.js |
|---|---|---|---|
| Экосистема RAG/AI (эмбеддинги, PII-обезличивание, LLM-SDK) | Родная — LiteLLM, sentence-transformers, Presidio написаны на Python или имеют полноценные Python-биндинги | Зрелых библиотек почти нет — пришлось бы переписывать их или звать Python-подпроцесс | Тоньше, чем у Python: SDK для LLM-провайдеров есть, но нет инструментов PII-обезличивания и локального инференса эмбеддингов уровня Presidio/sentence-transformers |
| Совместимость с ограничением «RAG внутри одного контейнера» | Прямая — тулинг уже на этом языке | Нарушается или требует второго языка/процесса внутри контейнера | Та же проблема, что у Go |
| Производительность и конкурентность | Достаточно — нагрузка I/O-bound (вызовы LLM Gateway, Vector DB, Биллинга) | Объективно сильнее всего (goroutines), но выигрыш не используется — узкое место не здесь (см. ниже) | Сопоставимо с Python — тоже событийный цикл, тоже под I/O-bound |
| Contract-first / OpenAPI | FastAPI генерирует OpenAPI-схему из кода — совпадает с принципом проекта | Нужна отдельная библиотека и дисциплина | Нужна отдельная библиотека (например, NestJS + swagger) |
| Итог | **Выбран** | Отклонён | Отклонён |

**Go отклонён**, несмотря на объективное преимущество в конкурентности: этот выигрыш не используется,
потому что узкое место системы — сетевая задержка вызова внешнего LLM-провайдера (сотни миллисекунд —
секунды), а не накладные расходы веб-фреймворка (единицы миллисекунд). Замер 24 сентября 2026: время до первого куска у YandexGPT — медиана 0,78 с,
P90 5,6 с (19 вызовов); простой запрос `/v1/healthz` к Backend в docker — медиана 5,9 мс, P95 8,0 мс (200 запросов, включая запуск curl и
пересылку порта — это верхняя оценка накладных расходов). **Node.js отклонён** по той же
причине, что и Go — нехватка зрелого RAG/PII-инструментария; использование одного языка для фронтенда и
бэкенда не решает эту проблему, ограничение именно в инструментарии, а не в знании команды JavaScript.

LLM Gateway и ETL Worker на других языках даже не сравнивались — они с самого начала Python-only, потому
что весь нужный тулинг (LiteLLM, sentence-transformers) существует только в этой экосистеме.

### Почему FastAPI, а не другой Python-фреймворк

Выбор языка оставляет вопрос фреймворка. Сравнение сделано по документации фреймворков и по требованиям
проекта; замер скорости не проводился и не нужен — узкое место системы задержка внешней модели (см. выше),
а не накладные расходы фреймворка.

Требования, которые следуют из самого проекта:

1. **Асинхронность и потоковая выдача.** Ответ абонента идёт потоком, а сервис ждёт внешние системы
   (модель, Qdrant, Redis, Биллинг).
2. **Схемы и валидация на pydantic.** Модели проекта (`app/models.py`) уже написаны на pydantic; второй
   слой описаний рядом с ними — источник расхождений.
3. **OpenAPI из тех же моделей.** Спецификация `API_Spec.yaml` собирается из кода
   (`scripts/build_openapi.py`), а не пишется руками.
4. **Тесты без сети.** Тестовый клиент фреймворка (`fastapi.testclient`) гоняет контрактные тесты без
   запуска сервера.
5. **Небольшой вес.** Проекту нужен API, а не ORM, админка и шаблоны.

| Критерий | FastAPI | Flask | Django REST Framework | Litestar |
|---|---|---|---|---|
| Асинхронность и потоковый ответ | Родные (ASGI), потоковый ответ из коробки | По умолчанию синхронный (WSGI); async-обработчики возможны, но параллельные ожидания и потоковая выдача сложнее | По умолчанию синхронный, поддержка async ограничена | Родные (ASGI) |
| Схемы и валидация на pydantic | Встроены, тот же pydantic, что в моделях проекта | Отдельные библиотеки (marshmallow и т. п.) — дублируют модели | Собственные сериализаторы — дублируют модели | Поддерживает pydantic и msgspec |
| OpenAPI из кода | Из коробки | Через расширения | Через дополнение | Из коробки |
| Вес и лишние части | Лёгкий: только то, что нужно API | Лёгкий | Тяжёлый: ORM, админка, настройки Django, которые проекту не нужны | Лёгкий |
| Сообщество и зрелость | Самое широкое среди async-фреймворков Python | Самое широкое в целом | Широкое | Моложе, сообщество заметно меньше |
| Итог | **Выбран** | Отклонён | Отклонён | Отклонён |

**Flask отклонён**: всё, что FastAPI даёт из коробки (схемы, валидация, OpenAPI, async), пришлось бы
собирать из расширений. **Django REST Framework отклонён**: тянет за собой части Django, которые проекту не
нужны, и ведёт второй слой описаний рядом с моделями. **Litestar** близок по возможностям и не отвергнут по
качеству: выигрыша для проекта он не даёт (FastAPI уже закрывает все требования), а сообщество у него
меньше, что важнее для поддержки командой. Голый **Starlette** отдельно не рассматривался: FastAPI построен
на нём, а схемы, валидацию и OpenAPI пришлось бы дописывать самим.

Решение обратимо частично: модели pydantic и логика переживают смену фреймворка, переписываются только
маршруты (`app/api.py`).

### Почему uvicorn

FastAPI сам по себе сеть не слушает — ему нужен ASGI-сервер, который принимает HTTP-соединения и вызывает
код приложения. Требования: асинхронная работа и потоковая отдача; запуск в контейнере одной командой с
режимом перезагрузки на время разработки; минимум лишних зависимостей; масштабирование на MVP репликами
подов Kubernetes, а не менеджером процессов внутри контейнера.

| Критерий | uvicorn | Hypercorn | Daphne | Granian | gunicorn |
|---|---|---|---|---|---|
| Работает с ASGI и потоковой отдачей | Да | Да | Да | Да | Сам — нет (синхронный, WSGI); работает только как надстройка над воркерами uvicorn |
| Место в экосистеме FastAPI | Сервер по умолчанию в документации FastAPI | Поддерживается, встречается реже | Создан для Django Channels | Новее, сообщество меньше | Менеджер процессов, а не замена серверу |
| Чем отличается | Минимум настроек, режим `--reload` для разработки | Поддержка HTTP/2 и HTTP/3 — проекту не нужна: внешний трафик и TLS закрывает Ingress (nginx) | Ориентирован на Django | Ядро на Rust, быстрее — выигрыш не используется, узкое место в задержке внешней модели | Следит за процессами и перезапускает упавшие; в Kubernetes это делает сам оркестратор |
| Итог | **Выбран** | Отклонён | Отклонён | Отклонён | Не нужен на MVP; может добавиться, если появится причина держать несколько процессов в одном контейнере |

Как запускается: на прототипе — `python -m uvicorn app.main:app` с режимом перезагрузки и подключёнными
каталогами (только для разработки); на MVP — без `--reload` и без подключённых каталогов, число процессов
задаётся репликами подов. Если нагрузка потребует несколько процессов в одном поде, у uvicorn для этого есть
параметр `--workers`; замера под такую нагрузку в проекте нет.

### Почему Kubernetes, а не другая оркестрация

Роль: платформа, на которой на MVP работают приложение, хранилища, модели на GPU, задания по расписанию и наблюдаемость (20 компонентов,
24 пода в расчёте ADR-500). Прототип работает на `docker compose` на одной машине; для MVP платформа **выбрана предварительно и
владельцем инфраструктуры не согласована**. Известно и решено со слов заказчика проекта (24 сентября 2026, документально не подтверждено): личный кабинет водоканала уже работает на
Kubernetes; наш контур **размещается в том же кластере**; **эксплуатирует тот же отдел**; **GPU-узлов в кластере нет**. Не известно: дистрибутив и
версия, квоты и правила размещения, классы хранилищ и быстрые диски, есть ли в кластере Vault и своя наблюдаемость (Prometheus, Grafana, Loki), сетевые правила.

**Требования проекта, из которых следует выбор**

1. **Отказоустойчивость.** Потеря одного сервера не останавливает ответы: не менее двух реплик Backend и шлюза, запас на потерю одного узла (ADR-500, «Расчётный sizing»).
2. **Обновление без остановки** и возврат на предыдущую версию при сбое.
3. **Закрытый контур.** Кластер внутри сети водоканала, без управляемых облачных сервисов (ADR-400, C4_Deployment): требование владельца, мной не перепроверялось.
4. **Разные типы узлов.** Пул без ускорителей и пул данных с быстрыми дисками; GPU-узел под эмбеддинги и реранкер в кластере отсутствует (см. «GPU» ниже), позже
   понадобился бы узел под собственную модель (ADR-500).
5. **Задания по расписанию** с ограничением по времени: ночная индексация в окне 02:00–05:00, ночной прогон судьи качества.
6. **Секреты без переменных окружения.** Vault Agent Injector (ADR-400) внедряет секрет в под через sidecar — механизм, рассчитанный на Kubernetes.
7. **Хранилища с состоянием** (Qdrant, Postgres, Redis, MinIO) на постоянных томах и связка Prometheus, Grafana, Loki, Alertmanager (ADR-200).

**Что нагрузка не требует.** Расчётная нагрузка невелика: одновременно обрабатывается не более 0,17 запроса на MVP и 2 на тираже (`Capacity_Report.html`),
а запросы всех 24 подов — 11,2 vCPU и 23,6 ГиБ (лист «Sizing»). Это помещается на один сервер. Kubernetes выбирается **не ради пропускной способности,
а ради требований 1–7**; если бы требований 1–2 не было, хватило бы `docker compose` на одном сервере.

| Критерий | `docker compose` на одном сервере (прототип) | `docker compose` на нескольких хостах без оркестратора | Docker Swarm | Nomad (HashiCorp) | Kubernetes на своём железе (выбрано предварительно) |
|---|---|---|---|---|---|
| Переживает отказ сервера | Нет | Нет: сервисы не переезжают сами | Да (по документации) | Да (по документации) | Да (по документации) |
| Обновление без остановки | Нет | Нет | Есть скользящее обновление (по документации) | Есть (по документации) | Есть (по документации) |
| Пулы узлов и планирование GPU | Один сервер | Вручную | Ограниченно: ресурсы описываются вручную (по документации) | Плагины устройств, GPU поддерживаются (по документации) | Плагин устройств и метки узлов — штатный путь для GPU (по документации) |
| Задания по расписанию с лимитом времени | Внешний cron | Внешний cron | Нет отдельного объекта, нужен внешний планировщик (по документации) | Периодические и пакетные задания есть (по документации) | `CronJob` |
| Секреты через Vault | Vault Agent на хосте | То же | Через Vault Agent вручную | Встроенная интеграция с Vault (по документации) | Vault Agent Injector (выбран в ADR-400) |
| Наблюдаемость | Отдельно | Отдельно | Отдельно | Отдельно | Готовые связки и метрики кластера (по документации) |
| Сложность эксплуатации | Минимальная | Высокая: всё вручную | Ниже, чем у Kubernetes | Ниже, чем у Kubernetes | **Высокая**: отдельная эксплуатационная компетенция |
| Экосистема и кадры | — | — | Развитие замедлено (по общим сведениям, не проверялось) | Меньше, чем у Kubernetes; условия лицензии HashiCorp изменились в 2023 (по общим сведениям, для РФ не проверено) | Самая широкая |
| Итог | Только прототип | Отклонён | Не выбран: слабее по GPU и заданиям, меньше сообщество | **Реальная альтернатива**, если эксплуатационной команды нет: проще Kubernetes; в проекте не рассматривалась подробно | **Предварительно выбран** |

Сравнение сделано по документации проектов и требованиям проекта; **ни один из вариантов, кроме `docker compose`, в проекте не разворачивался**.

**Цена решения**

- **Накладные расходы кластера.** Системные поды Kubernetes (планировщик, сеть, DNS, метрики) занимают порядка 1 vCPU и 2 ГиБ на узел — допущение, не замер.
  На шести узлах MVP это ≈6 vCPU и ≈12 ГиБ против 11,2 vCPU и 23,6 ГиБ приложения, то есть более половины полезной нагрузки.
- **Управляющая часть кластера.** Для отказоустойчивости нужны три узла с `etcd`. В расчёте узлов (ADR-500) отдельные узлы под неё не заложены:
  принято, что она размещена на трёх узлах общего пула (допущение); при отдельных узлах их станет на три больше. Так как контур размещается **в
  кластере владельца**, управляющая часть и системные поды общие, число заказываемых узлов меньше расчёта (расчёт для отдельного кластера — верхняя
  оценка), а вопрос переходит в договорённость: квоты, отдельное пространство имён, тома, сетевые правила.
- **Эксплуатация.** Кластер эксплуатирует отдел владельца, который уже ведёт личный кабинет: отдельной команды и обучения под Kubernetes не нужно, это
  снимает главный риск решения. Остаются: правила размещения (квоты, пространство имён, сеть), порядок обновлений и заявок, нагрузка на отдел; GPU
  им эксплуатировать пока не приходилось.
- **GPU.** В кластере GPU-узлов нет, и это меняет план моделей. **Решение о GPU-узле принимается владельцем только после проверки на реальных данных** (решение заказчика проекта, 24 сентября 2026); порядок и критерий — ADR-600, «GPU-узел в кластере владельца — решение после проверки на реальных данных». До этого решения план — вариант 1; вариант 2 остаётся открытым. Аренда GPU на месяц берётся, только если не подойдёт «CPU + Яндекс» (ADR-600); покупка — по итогам аренды:
  1. **Без GPU (базовый расчёт).** Эмбеддинги `multilingual-e5-small` на CPU (36–37 мс на запрос, замер), реранкер выключен, индексация считает
     эмбеддинги на CPU. Ограничение: BGE-M3 (300 мс) и реранкер (7,2 с на 20 кандидатов) в бюджет 100 мс на CPU не укладываются; допустимы только
     модели, укладывающиеся в бюджет на CPU (e5-base и e5-large не измерялись).
  2. **С GPU-узлом.** Покупка сервера с видеокартой и подключение к общему кластеру: драйверы, плагин устройств, метки и запреты размещения, квоты,
     согласование с отделом. Цена и сроки не оценены; работа — 3–5 чел-дн по оценке автора (ADR-600, вне итога). Тогда возможны BGE-M3 и реранкер.
- **Подготовка платформы.** Работа на разворачивание кластера, Ingress, сертификатов и хранилищ заложена в матрицу как оценка автора (10–15 чел-дн, строка
  «Оркестрация контейнеров»); разбивки под неё нет.

**Дистрибутив и версию задаёт кластер владельца** — какой именно, неизвестно; выбирать его нам не нужно, но манифесты и требования (Ingress,
классы хранилищ, `CronJob`, Vault) должны с ним совпасть. Требования по отечественному программному обеспечению неизвестны.

**План Б почти неактуален:** платформа у владельца уже есть и общая. Возвращаться к Nomad или `docker compose` имеет смысл, только если владелец
откажет в размещении в своём кластере.

**Когда пересмотреть.** До начала работ MVP: владелец ответил на вопросы о квотах, сети, Vault и наблюдаемости или отказал в размещении; решил вопрос
о GPU-узле. После MVP: стоимость эксплуатации оказалась выше ожидаемой либо нагрузка на отдел владельца недопустима.

**Что здесь не подтверждено.** Все возможности платформ описаны по документации; накладные расходы на узел — допущение; то, что кабинет работает на
Kubernetes, что мы размещаемся в его кластере и что GPU там нет, известно со слов и документом не подтверждено; дистрибутив, квоты, Vault и
наблюдаемость кластера неизвестны (секреты: в ADR-400 выбран Vault Agent Injector, но используется ли Vault в кластере владельца, неизвестно —
возможно, придётся использовать их механизм); отечественные ограничения на программное обеспечение неизвестны.

### Оркестрация агента: собственная таблица переходов, LangGraph — по триггеру

Роль: конечный автомат обращения на пути записи (Этап 2): подтверждение абонента, идемпотентность, аудит, отказ абонента.
Главное требование — **запись возможна ровно из одного состояния «ожидает подтверждения»**, и механизм подтверждения один.

**Что есть.** Собственная таблица переходов на перечислениях (`app/fsm.py`, 200 строк): 7 состояний, 10 переходов, 7 событий;
тесты (`tests/unit/test_fsm.py`, 251 строка) перебирают **все** остальные состояния и проверяют, что из них запись невозможна.
Внешних зависимостей у модуля нет. LangGraph рассматривался как кандидат с самого начала проекта, но ни разу не подключался и не
пробовался; сравнение ниже сделано по документации и по требованиям проекта, кроме замеров, отмеченных отдельно.

Другие движки (например, движки надёжного исполнения вроде Temporal) не рассматривались и не сравнивались.

**Триггеры перехода на LangGraph — точные условия.** Переход выполняется, когда наступает **одно из четырёх событий** ниже. Три первых —
свойства утверждённого сценария Этапа 2, которые можно показать документом; четвёртое — измеренная доля реплик абонентов. Ощущение сложности
не является событием. Решение о переходе
принимает владелец архитектуры проекта (тот, кто утверждает ADR); ответ и доказательство записываются в журнал ниже.

| № | Что должно случиться | Как установить (доказательство) | Порог | Что триггером **не** считается |
|---|---|---|---|---|
| 1 | В сценарии **следующий шаг после вызова инструмента выбирает модель**, а не таблица: модель получает результат инструмента и сама решает, вызывать ли другой инструмент и какой (function-calling) | Описание сценария: диаграмма шагов с развилкой «решает модель» и не менее чем двумя инструментами на выбор (Биллинг, обращения, Диспетчерская) | Развилка есть. Дополнительное условие запуска такого сценария: тест function-calling у выбранного провайдера на ≥30 размеченных запросах — верный инструмент и аргументы не менее чем в 90% случаев, неверных вызовов не более 5% (пороги — предложение автора, не расчёт; если тест не пройден, агентный сценарий не запускается, а упрощается до фиксированного) | Модель только формулирует текст ответа; выбор ветки по правилам (тип обращения, признак нажатой кнопки); фиксированная последовательность вопросов |
| 2 | В сценарии есть шаг, который **ждёт внешнее событие дольше срока жизни сессии** (сейчас 30 минут, `session_ttl_seconds = 1800`), и после ожидания диалог должен продолжиться **с того же шага и с тем же состоянием** | Требование в описании сценария: максимальное время ожидания шага (ответ микросервиса обращений, оператора, абонента) или явное требование «продолжить после закрытия вкладки или перезапуска» | Ожидание дольше 30 минут либо требование возобновления с шага | Перезапуск пода в пределах сессии — состояние хранит Redis (на MVP с сохранением); ожидание подтверждения абонентом в пределах 30 минут |
| 3 | В сценарии **два и более шага выполняются одновременно, у каждого свои повторы, таймауты и правило при ошибке, а результаты сливаются** в одно решение | Описание сценария: ветви, правило слияния и что делать, если одна ветвь упала | Не менее двух ветвей с разными правилами повтора или ошибки | Параллельные чтения для одного ответа без общего решения (Биллинг и график отключений через `asyncio.gather`) |
| 4 | **Доля реплик абонентов, в которых две и более задачи сразу, превысила 5%** (решение владельца архитектуры) | Разметка выборки реплик (правила и способ подсчёта ниже) | Доля > 5% по точечной оценке | Одна задача с уточнениями; несколько частей одного вопроса про одно и то же |

**Триггер 4 — как считать долю.** Задача — отдельный запрос из разных путей ответа или типов обращений (например, «долг» и «поверка»;
«отключение» и «тариф»; «заказать поверку» и «справку»). Реплика с двумя и более такими задачами считается многозадачной, в том числе с
условием («если долга нет, закажите поверку»). Считается **доля многозадачных реплик от всех содержательных реплик выборки** (приветствия и
реплики без вопроса не входят). Размечают двое, спорные случаи решает третий; каждая размеченная реплика получает число задач.

| Что | Как |
|---|---|
| Первое измерение | На выгрузке живых обращений (ADR-600, анализ типов на живых данных, не менее 1 500 текстов): при доле 5% погрешность около ±1,1 п.п. (95%, расчёт по формуле, не замер) |
| Повторные измерения | После запуска чата — раз в месяц по выборке не менее 400 реплик (±2,1 п.п.) либо по метрике детектора намерений, когда он появится |
| Решение | Точечная оценка выше 5% — триггер сработал, запись в журнал. Если выгрузка обращений (регистр по телефону и почте) и чат дают разные доли, решение принимается по каждому измерению отдельно и фиксируется |

Оговорки. Регистр обращений — письменные тексты, они длиннее и чаще многозадачны, чем реплики чата; поэтому первое измерение ориентировочное, а
измерение по чату после запуска обязательно. Ключевые слова дают верхнюю оценку: 31 из 136 настоящих обращений (23%) подходят под несколько
типов сразу, но пересечение слов не означает несколько задач; детектор намерений на тех же текстах находит их в 0,7% (ниже). LangGraph сам реплику на задачи не разбирает: разбор (детектор намерений) нужен в
любом случае, граф даёт цикл по очереди задач и условные ветви. Потеря части ответа и ложное «сделал» исправлены в таблице независимо от
перехода (см. «Как реализовано» ниже); доработка после прототипа — отдельный блок ADR-600.

**Как реализовано: несколько задач в одной реплике** (прототип, 24 сентября 2026; код — `app/agents/intents.py`, `app/backend/orchestrator.py`,
`app/gateway/guardrails.py`). Решено тремя частями в текущей таблице, без LangGraph.

1. **Детектор намерений** (`split_intents`) — правила, без модели. Реплика режется по жёстким границам (конец предложения, `;`, «а также»,
   «потом») и по мягким («и», запятая, «, а»); разрез принимается, только если каждая сторона несёт свою задачу: узнаётся тема ответа,
   тип обращения или операция, которую помощник не выполняет. Тип обращения считается отдельной задачей, только если фрагмент — просьба
   или вопрос либо просьба прозвучала раньше в том же предложении («Хочу заказать поверку и справку»). Реплики длиннее 300 знаков не
   разбираются: это письма, а не вопросы чата. Факты счёта различаются (`долг`, `поверка`, `показания`, `начисления`): ответчик счёта
   отвечает на один факт за раз, поэтому «долг и поверка» — две задачи. Условная часть («Если нет — закажите поверку») привязывается к
   предыдущей; проверяется единственное условие, которое можно проверить по Биллингу, — наличие долга.
2. **Ответ по каждой части** (`Orchestrator._stream_parts`): часть идёт тем же путём, что и отдельная реплика (ответчики, затем база знаний,
   затем модель), ответ выводится по очереди под заголовком «1. …», «2. …». Что не сделано, говорится прямо: операция без выполнения
   («передача показаний», «оплата», «изменение данных») — отказ с телефоном контакт-центра и фразой «я ничего не передавал»; условие не
   выполнено — «условие не выполнено, часть не выполняю»; условие не проверяется — «проверить не могу». Регистрация предлагается по
   **первой** подходящей части (в состоянии диалога один черновик), об остальных абонент предупреждён. Вопрос «Как передать показания?» —
   вопрос о порядке, а не просьба, и идёт в базу знаний. Метрика `assistant_multi_intent_total{tasks}` считает такие реплики.
3. **Запрет фраз о выполненном действии** — два рубежа. Первый: к запросу, идущему к модели, добавляется правило «ты только консультируешь,
   никогда не пиши, что выполнил операцию» (`NO_ACTIONS_RULE`). Второй: синхронная проверка ответа (`unperformed_action`) блокирует
   предложение, начинающееся с глагола первого лица в форме выполненного или выполняемого действия («Передал…», «Проверил…»,
   «Оформляю…»), и подставляет текст «Я не выполняю операции… это можно сделать в личном кабинете», а не нейтральную заглушку: абоненту
   важно узнать, что действие не выполнено. Третье лицо («Специалист проверил»), обращение к абоненту («Если вы передали»), приказ и
   инфинитив не блокируются.

находила несколько задач в 14% текстов, но это были ложные срабатывания: длинные письма («Прошу вернуть переплату. Реквизиты прикрепляю»)
несут одну просьбу, а признак типа есть в каждой фразе. После ограничения длины, требования «просьба или вопрос» и исключения прошедшего
времени («оплатил») детектор находит две задачи в **1 из 136 текстов (0,7%)**. Оба числа — срабатывание детектора, не доля
многозадачных обращений: порог подбирался на этих же текстах, а полнота не измерена. Важно: 23% текстов, где ключевые слова подходят под
несколько типов сразу, — это пересечение слов, а не несколько задач; ожидание, что доля превысит 5%, по этим данным не подтверждается. Решение по триггеру 4 принимается по разметке людьми (правила выше).

**Что не сделано и что не подтверждено.**
- Разбор идёт только на пути абонента (`stream`); `generate` для служебных вызовов остался прежним.
- Регистрация предлагается по одной задаче; несколько черновиков в состоянии диалога не хранятся.
- Из условий проверяется только наличие долга; остальные («если скоро», «если дорого») не выполняются, и об этом сказано.
- Предел 300 знаков, перечни глаголов и операций выбраны автором и подобраны на 136 обращениях регистра, не на репликах чата. Точность и полнота
  детектора на размеченных репликах чата не измерены.
- Охранитель ловит только начало предложения с глаголом первого лица; «Уже всё передано» или фраза в середине предложения не ловится.
  Частота ложных блокировок на живых ответах неизвестна (ADR-600, блок Guardrails).
- Ответчик бланка ведёт диалог по шагам в состоянии сессии: если бланк запрашивают сразу в двух частях, второй перезапишет первый.
- Каждая часть, идущая к модели, считается в лимитах шлюза отдельным запросом; части отвечаются последовательно, задержка складывается.

**Сигналы — не триггеры.** Они не ведут к автоматическому переходу, а вызывают пересмотр решения владельцем архитектуры: автомат вырос
заметно выше 15–20 состояний и ветвление разошлось по коду (порог — ориентир автора); нужно воспроизводить шаги диалога для разбора инцидента.

**Когда проверяется — четыре момента, по календарю проверка не проводится.**

1. **При постановке сценария или блока Этапа 2 в разработку, до проектирования.** Владелец отвечает «да» или «нет» по каждому из трёх
   триггеров по описанию сценария и записывает ответ с доказательством в журнал.
2. **При изменении сценария** (добавлен шаг, изменено ожидание или ветвление): ответ даётся заново.
3. **При пересмотре архитектуры по метрикам Этапа 1** — условие перехода к Этапу 2 (ADR-600).
4. **После каждого измерения доли многозадачных реплик** (триггер 4): первое — при анализе живых обращений, дальше — ежемесячно после запуска чата.

**Что должно произойти после ответа «да».**

1. Запись в журнал: дата, сценарий, номер триггера, доказательство.
2. Решение владельца: переходить или упростить сценарий так, чтобы триггер не наступал. Для триггера 1 предварительно проведён тест
   function-calling; если он не пройден, сценарий не запускается на агенте.
3. **До написания кода сценария** выполняется миграция (ADR-600, «Переход агента на LangGraph — по триггеру»): граф с тем же составом переходов.
4. Миграция считается выполненной, когда одновременно верно: тесты, перебирающие все состояния, проходят на графе; из любого состояния,
   кроме подтверждения, запись невозможна; при включённой библиотеке нет исходящих соединений на внешние адреса (проверка сетевым
   наблюдением, для 152-ФЗ); ИБ согласовала зависимость.
5. Только после этого сценарий реализуется на графе. Если триггер обнаружен, когда сценарий уже написан на таблице, миграция
   становится критическим путём — это риск позднего обнаружения, потому проверка стоит до проектирования.

**Журнал проверки триггеров.**

| Дата | Сценарий Этапа 2 или измерение | Триггер 1 | Триггер 2 | Триггер 3 | Триггер 4 (доля > 5%) | Доказательство | Решение |
|---|---|---|---|---|---|---|---|
| — | Ни один сценарий Этапа 2 не поставлен в разработку, доля многозадачных реплик не измерена | — | — | — | — | — | Остаётся собственная таблица |

**В каком случае LangGraph нужен — подробно.** LangGraph — библиотека для сценариев, где путь по шагам не задан заранее, а состояние
надо хранить между шагами. На пути записи Этапа 2 проекта сейчас всё наоборот: сценарий фиксирован (черновик → подтверждение →
запись), состояние живёт в рамках одной сессии (30 минут), и вся сложность — в одном правиле подтверждения, которое таблица
закрывает лучше. Поэтому решение принимается по признакам ниже, а не по дате; проверяется при планировании каждого блока Этапа 2.

| Ситуация в проекте | Нужен ли LangGraph | Почему |
|---|---|---|
| Абонент заполняет заявку **фиксированными вопросами** (сейчас так: сбор без модели), подтверждает, запись | **Нет** | Путь известен заранее; таблица переходов с 7 состояниями справляется |
| Одно подтверждение, одна запись, отказ абонента пишется в аудит | **Нет** | Это и есть таблица: запись из одного состояния, перебор всех остальных в тестах |
| Модель сама решает, что делать дальше: в одной реплике абонента «передайте показания и проверьте долг» → агент выбирает инструменты (показания, задолженность, регистрация обращения, аварийная заявка) и может вызвать несколько подряд | **Да — триггер 1** | Нужен цикл «модель → выбор инструмента → результат → модель», ограничение числа шагов, обработка неверного вызова инструмента. Без библиотеки это пишется вручную, и результат — собственный, менее проверенный LangGraph. Решение зависит от качества function-calling у провайдеров РФ: оценка (≈1 неделя) стоит в плане перехода к тиражу и не проведена |
| Шаг **ждёт внешнее событие** дольше сессии: ответ микросервиса обращений, подтверждение оператором, срок в часы или сутки; за это время под перезапускается или сессия истекла | **Да — триггер 2** | Нужно вернуться на тот же шаг с тем же состоянием (контрольные точки). Для простого сохранения диалога после перезапуска достаточно Redis с сохранением, который уже заложен на MVP |
| Несколько шагов идут **одновременно и сходятся**: запрос к Биллингу, Диспетчерской и графику отключений, каждый со своими повторами и ошибками, результат объединяется | **Только если ветви имеют своё состояние**; простые параллельные запросы делаются средствами языка без библиотеки | Параллельные вызовы без общего состояния решает `asyncio.gather`; LangGraph нужен, когда у каждой ветви свои повторы, ошибки и правила слияния (триггер 3) |
| Автомат разросся: заметно больше 15–20 состояний, ветвление размазано по коду, переходы трудно показать аудитору | **Сигнал, не триггер** | Ориентир автора, не расчёт: граф даёт визуализацию и единое описание переходов; таблица при таком размере читается хуже |
| Нужно **воспроизвести шаги** прошедшего диалога для разбора инцидента или аудита | **Сигнал, не триггер** | Контрольные точки хранят историю шагов; аудит-лог проекта уже пишет кто, что, когда и ключ идемпотентности |
| Нужен человек в цикле для **записи** (HITL) | **Нет** | Подтверждение записи уже есть в таблице; `interrupt_before` создал бы второй механизм подтверждения |

**Что нужно сделать до решения.** 1) Для агентного сценария провести тест function-calling у GigaChat Pro и YandexGPT (порог — в
триггере 1). В плане ADR-600 оценка function-calling (≈1 неделя) стоит в таблице перехода к тиражу, а для триггера 1 она нужна раньше —
перед запуском агентного сценария Этапа 2: несоответствие момента не устранено, перенос строки решает владелец плана. 2) Для каждого
сценария Этапа 2 ответить на три вопроса триггеров и записать ответ в журнал. 3) Проверить, что библиотека не отправляет
телеметрию за периметр: в составе LangGraph идёт `langsmith` (трассировка во внешний сервис), по документации она включается
настройкой, но в проекте это не проверялось, а для 152-ФЗ это условие миграции.

**Чего стоит переход.** Дополнительные работы — в ADR-600 («Переход агента на LangGraph — по триггеру», от 7 до 24 чел-дн в зависимости от того, какие триггеры сработали, оценка автора) и в
матрице (строка «Переход агента на LangGraph (по триггеру)»; в итог сметы не входит).

**Что переход не отменяет.** Таблица переходов остаётся формулировкой правила подтверждения, меняется только исполнитель;
тесты, перебирающие все состояния, сохраняются; второй механизм подтверждения не заводится.

**Что здесь не подтверждено.** Довод «усложнение ради возможностей, которые пока не нужны» проверить нечем, пока нет агентного
сценария. Возможности LangGraph описаны по документации и в проекте не пробовались. Вес зависимости замерен и невелик: аргументом
против перехода он не является (в прежней редакции решения он назывался «тяжёлым» без замера). Триггер 1 в плане Этапа 2 (ADR-600)
может наступить уже при выборе сценария; оценка перехода (7–24 чел-дн по триггерам) заложена в ADR-600 отдельно и в итог не входит.

### Как устроен шлюз к модели

Шлюз — модуль Python внутри контейнера Backend (`app/gateway/`). Порядок работы: проверка лимитов (Redis) →
обезличивание (Presidio, русская модель spaCy и собственные распознаватели — ADR-400) → вызов модели через
LiteLLM → проверка ответа на потоке → запись события использования (Postgres)
и метрики.

**LiteLLM подключён библиотекой (`Router`) внутри процесса, а не отдельным прокси-сервером.** Прокси — второй
процесс со своим портом, конфигурацией и жизненным циклом; на прототипе с 15 ГБ памяти ему тесно, а библиотека
принимает тот же список моделей, цепочки запасных провайдеров, число повторов и таймаут из
`litellm_config.yaml`. Формат файла совместим с прокси, поэтому вынос шлюза в отдельный контейнер на MVP — смена
способа запуска, а не переписывание кода. Провайдер выбирается переменной окружения `LLM_PROVIDER`
(`local-test`, `yandexgpt`, `gigachat`); YandexGPT вызывается через OpenAI-совместимый адрес.

**Почему Python и LiteLLM, а не собственный код.** Весь нужный инструментарий (LiteLLM, Presidio,
sentence-transformers) существует в Python — том же языке, что у Backend. Свой клиент на каждого провайдера
означал бы дублирование ради контроля, который LiteLLM уже даёт: единый интерфейс, повторы, переключение на запасного провайдера при сбое (circuit breaker библиотека тоже умеет, в проекте не настроен).
Переключение на запасного проверено на живом трафике: в таблице `usage_events` шесть вызовов ушли на локальную модель, когда ключ YandexGPT был пуст.

### Протокол потока ответа: SSE

Требование: ответ абонента идёт потоком (ADR-100). Данные идут в одну сторону — от сервера к виджету.

| Критерий | SSE (поток событий по HTTP) | WebSocket | Периодический опрос (long polling) |
|---|---|---|---|
| Направление | Сервер → клиент — как нужно | Двустороннее — не нужно | Клиент опрашивает сервер |
| Прохождение через Ingress и прокси | Обычный HTTP | Требует поддержки смены протокола | Обычный HTTP |
| Задержка первого куска | Сразу | Сразу | До интервала опроса |
| Сложность | Текстовый формат, легко читать и тестировать | Выше: состояние соединения, переподключение | Ниже, но лишняя нагрузка запросами |
| Итог | **Выбран** | Отклонён | Отклонён |

Особенность: встроенный в браузер `EventSource` умеет только GET-запросы, а вопрос абонента отправляется POST-ом.
Поэтому виджет читает поток через `fetch` и разбирает события сам; на стороне сервера события формируются на
`StreamingResponse` (Starlette), а не отдельной библиотекой.

### Почему PostgreSQL и Redis

Требования к базе данных: транзакции и точная арифметика; общая база для нескольких сервисов; JSON; материализованные
представления (кэш профиля на MVP); зрелый драйвер для Python.

| Критерий | PostgreSQL | MySQL / MariaDB | SQLite |
|---|---|---|---|
| Материализованные представления | Есть | Нет встроенных | Нет |
| Несколько сервисов и реплик работают с одной базой | Да | Да | Нет: один файл, одна запись за раз |
| JSON и сложные типы | JSONB | JSON, возможности скромнее | Ограниченно |
| Драйвер и инструменты в стеке проекта | psycopg 3 | Есть | Встроен |
| Итог | **Выбран** | Отклонён: нечего добавить, материализованных представлений нет | Отклонён: не подходит для нескольких сервисов |

Требования к хранилищу счётчиков и состоянию диалога: атомарный счётчик с окном времени; общее состояние для
нескольких реплик; быстрый доступ; отказ хранилища не должен пропускать запросы без учёта (ADR-400).

| Критерий | Redis | Memcached | PostgreSQL (таблица счётчиков) | Счётчики в памяти процесса |
|---|---|---|---|---|
| Атомарный счётчик с временем жизни | `INCR` + `EXPIRE` | `incr` и время жизни есть | Строка и блокировки; окно с истечением пишется вручную | Есть, но только в одном процессе |
| Общее состояние для нескольких реплик | Да | Да | Да | Нет |
| Структуры данных для сессии (хеши, списки) | Есть | Только ключ-значение | Есть | — |
| Сохранение при перезапуске | Настраивается | Нет | Да | Нет: лимиты обнуляются |
| Итог | **Выбран** | Отклонён: нет структур для сессии | Отклонён не по нагрузке: при пике до 0,66 вопроса в секунду на тираже в максимуме прогноза (ADR-500) Postgres справился бы; счётчик с окном пришлось бы писать вручную, а Redis уже нужен для сессий | Отклонён: теряет лимиты (fail-open) |

### Почему Qdrant, а не другая векторная база

Требования: фильтр по типу обращения одновременно с векторным поиском; переиндексация без остановки поиска; один
сервис в эксплуатации; работа в закрытом контуре.

**Какой объём заложен.** База знаний MVP — **несколько тысяч документов** (решение по проекту: 3 000–5 000). Документ
режется на части (до 300 знаков), каждая индексируется своим вектором. Сколько частей на документ — **допущение**:
10–20 (на реальных документах не измерялось). Отсюда **30 000–100 000 векторов**. Размерность целевой модели BGE-M3 —
1 024 числа по 4 байта: 123–410 МБ одних векторов, без индекса и payload. Замер на 100 000 таких векторов с индексом по типу: 477 МБ на диске, ОЗУ 527 МиБ (718 МиБ при загрузке). На прототипе для сравнения — 190 фрагментов
размерности 384 (20 пар FAQ и примеры классификатора). Замер по вариантам ниже сделан только для Qdrant (см. после таблицы);
pgvector, Milvus и OpenSearch не измерялись, их сравнение — по документации.

| Критерий | Qdrant | pgvector | Milvus | OpenSearch (векторный поиск) |
|---|---|---|---|---|
| Фильтр по payload вместе с поиском | Встроен, есть индексы по полям | Через SQL `WHERE`. На 30–100 тыс. векторов размерности 1 024 точный перебор читает сотни мегабайт на запрос (по оценке, не замер) — нужен приближённый индекс; фильтр вместе с ним в документации описан как источник неполной выдачи при выборочном фильтре (в новых версиях расширения смягчено) | Есть | Есть |
| Эксплуатация | Один сервис | Расширение к Postgres, отдельного сервиса нет | Набор компонентов, тяжелее | Кластер на JVM, тяжелее |
| Переключение индекса без остановки | Алиасы коллекций | Решается вручную | Алиасы | Алиасы индексов |
| Итог | **Выбран** | Не отклонён по качеству: рабочая альтернатива на нашем объёме, требует настройки индекса и проверки фильтра; не выбран из-за алиасов и разделения нагрузки | Не выбран: набор компонентов тяжелее без выигрыша на нашем объёме (по документации) | Не выбран: универсальный движок, векторный поиск — надстройка (по документации) |

**Замер Qdrant на верхней границе объёма.** 100 000 случайных векторов размерности 1 024, payload `inquiry_type` с индексом
(8 значений), Qdrant в docker на рабочей машине, запрос из Python по HTTP, топ-20, 300 запросов подряд: без фильтра
**P50 27,5 мс, P99 64,9 мс**; с фильтром по типу (1/8 точек) **P50 14,3 мс, P99 36,8 мс**. Оба значения укладываются в
бюджет поиска 100 мс. Оговорки: векторы случайные, а не эмбеддинги документов; одна машина, запросы не параллельные; в
конце загрузки около 2 000 векторов остались вне индекса (перебираются напрямую); задержка эмбеддера сюда не входит.

**Что это меняет и что нет.** Довод «pgvector не справляется с фильтрацией» в первой редакции раздела не был основан на
замере и убран. Qdrant выбран по другим причинам: переиндексация без остановки поиска через алиасы коллекций (уже
реализована: коллекции `kb_faq__v<время>`), отдельный сервис под векторную нагрузку, проверенное на прототипе подключение
(`VECTOR_STORE=qdrant`). Сравнение pgvector на том же объёме — замер, которого нет; при желании убрать отдельный сервис его
нужно сделать на выгрузке владельца.

Два частных решения:

- **Клиент по HTTP, а не gRPC.** Задержка HTTP-вызова — единицы миллисекунд при бюджете поиска 100 мс; gRPC добавил
  бы зависимость без выигрыша.
- **Переиндексация blue-green, а не на месте.** Обновление на месте оставляет интервалы с неполным индексом. Новая
  коллекция собирается рядом, алиас переключается атомарно; цена — двойное хранение на время сборки. Удалённые
  документы уходят при полной пересборке.

### Телеметрия: почему Postgres, а не ClickHouse

Требование: нарезка событий (токены, стоимость, исход вызова) по абоненту, типу, модели, не мешая основной базе.
**Решение: телеметрия остаётся в Postgres на всех этапах** (отдельная база `telemetry`, таблицы `usage_events` и
`quality_reports`) **с хранением подробных событий 12 месяцев и сводной таблицей по периодам**. ClickHouse из целевой схемы убран:
объём этого не требует, при условии хранения не дольше года.

**Объём — по числу абонентов.** Одно событие — один вызов модели (`usage_events`, `app/gateway/usage.py`). Спрос — минимальный и
максимальный сценарии `Capacity_Report.html` (не все абоненты приходят в чат; до модели доходит 30–70% вопросов).

| Контур | Вопросов в месяц | До модели в месяц | Событий в год |
|---|---:|---:|---:|
| MVP, 8 000 абонентов | 1 680–42 000 | 504–29 400 | 6 048–352 800 |
| Тираж, 90 000 абонентов | 18 900–472 500 | 5 670–330 750 | 68 040–3 969 000 |

**Замеры в Postgres** (docker на рабочей машине, настройки по умолчанию, синтетические данные с равномерным распределением; схема
`usage_events` с тремя индексами; агрегат — число вызовов, сумма токенов и P95 времени по месяцу × типу × модели):

| Строк в таблице | Размер | Агрегат по всей таблице | За 30 суток: расход по абонентам | Соответствует |
|---:|---:|---:|---:|---|
| 2 млн | 589 МБ (308 байт на строку) | 1,5 с | 0,35 с | ≈6 месяцам на тираже, максимум |
| 12 млн | 3 492 МБ (305 байт на строку) | **39 с** | **5,8 с** (за 31 сутки, 87 583 абонента) | ≈3 годам на тираже, максимум |

Время растёт быстрее числа строк (×26 при ×6 строк): таблица перестаёт помещаться в кэш. Для 4 млн строк (≈1 год на тираже, максимум)
по этим двум точкам получается ≈5 с — это интерполяция, не замер.

| Критерий | PostgreSQL (отдельная база `telemetry`) | ClickHouse | TimescaleDB | OpenSearch |
|---|---|---|---|---|
| Хватает ли на объёме проекта | **Да на MVP и в минимуме тиража; на тираже в максимуме — при хранении событий до 12 месяцев (≈4 млн строк). Агрегат по всей таблице на 12 млн строк — 39 с (замер)** | Хватает с огромным запасом | Хватает | Хватает |
| Сколько систем в стеке | Уже есть | Ещё одна СУБД со своей эксплуатацией и резервным копированием | Расширение существующей | Ещё одна система |
| Мешает ли основной базе | Нет: отдельная база; до 0,13 записи в секунду в среднем на тираже, максимум | Нет | Нет | Нет |
| Итог | **Выбран для прототипа, MVP и тиража** (с ограничением по сроку хранения) | Отклонён: вторая СУБД ради объёма, которого нет | Не нужен на этом объёме | Не нужен: тяжелее без выигрыша |

**Ограничение решения и когда вернуться к вопросу.** Довод «агрегаты за секунды» верен только до нескольких миллионов строк. Поэтому
принято: подробные события хранятся 12 месяцев (≈4 млн строк на тираже в максимуме), более старые сворачиваются в сводную
таблицу по дням, отчёты по всей истории строятся по ней, а не по событиям; таблица делится на секции по месяцам. Сводная таблица и
секционирование не реализованы и не измерялись. Если потребуется аналитика по подробным событиям дольше года либо агрегаты по
всей таблице станут дольше 10 с, ClickHouse рассматривается заново (порог 10 с — предложение, не расчёт). Переезд — смена DSN и
диалекта запросов записи, а не бизнес-логики (ADR-100), поэтому откладывать безопасно. Замер сделан на синтетических данных и не
заменяет проверку на реальных событиях после запуска.

### Кэш профиля абонента: где хранить и с чем сравнивали

Требования: профиль абонента читается при каждом вопросе; не нагружать Биллинг и Диспетчерскую на каждый вопрос;
одно определение признаков для офлайн-оценки и онлайна; профиль — общий для нескольких реплик Backend.

**Как сейчас (прототип).** Ни Postgres, ни Redis для профиля не используются. Пример данных (`ЛКК.csv`, `ЛСФЛ.csv`,
`счетчики.csv`, `начисления.csv`) читается при старте в словари в памяти процесса (`app/billing/source.py`); запрос
абонента ничего не разбирает. Redis на прототипе хранит только квоты и состояние диалога (раздел «Почему PostgreSQL и Redis»
выше).

| Критерий | Слепок в памяти процесса (прототип) | Материализованное представление в Postgres (план MVP) | Postgres + Redis поверх | Feature Store (Feast, Tecton) | Чтение из Биллинга на каждый вопрос |
|---|---|---|---|---|---|
| Общее состояние для нескольких реплик Backend | Нет: у каждой реплики своя копия и свой возраст данных | Да | Да | Да | Да |
| Задержка чтения | Наносекунды | Запрос по индексу, порядка миллисекунд (оценка, не замер) | Запрос к Redis, порядка миллисекунд (оценка, не замер) | Зависит от онлайн-хранилища | Сетевой вызов внешней системы на каждый вопрос |
| Что добавляет в стек | Ничего | Ничего: Postgres уже есть | Слой инвалидации кэша, второй источник данных | Отдельная платформа | — |
| Нагрузка на чужие системы | Разовая загрузка при старте | Пересчёт по расписанию | Пересчёт по расписанию | Пересчёт по расписанию | На каждый вопрос |
| Одно определение признаков для офлайн и онлайн | Да, но данные — статичный пример | Да — одна таблица | Да | Да | Нет |
| Итог | **Прототип** | **Выбран для MVP** | Не берётся: выигрыш замером не показан; вернётся, только если замер ниже не уложится в бюджет | Отклонён: избыточен для одной таблицы | Отклонён: нагрузка и задержка |

**Решение: Redis для профиля не используется.** Профиль читается из материализованного представления Postgres по
индексу. Redis остаётся в стеке только для квот и состояния диалога. Слой Redis поверх представления добавил бы второй
источник данных и сброс устаревшего без доказанного выигрыша на объёме 8 000 абонентов.

**Что не подтверждено и проверяется на MVP.** Задержка чтения профиля из Postgres пока оценка, не замер. В плане MVP
заложен замер (ADR-600, «Замер чтения профиля из Postgres»): чтение по индексу под целевой нагрузкой 8 000 абонентов
должно укладываться в бюджет задержки Backend. Если не укладывается — Redis поверх представления возвращается в план как
отдельное решение. Сравнение с Feature Store и чтением из Биллинга сделано по требованиям и документации, не по
пробному внедрению.

Цена решения: данные в кэше отстают на период пересчёта. Свежие факты (например, баланс) запрашиваются у Биллинга
через API в момент вопроса.

### Почему индексация — задание по расписанию, а не Airflow

Требования: редкое, некритичное по задержке обновление базы знаний; ночное окно с жёсткой границей; изоляция от
обслуживания абонентов.

| Критерий | Планировщик по расписанию (K8s CronJob; Celery Beat по схеме развёртывания) | Apache Airflow | Cron внутри контейнера Backend |
|---|---|---|---|
| Состав | Примитив Kubernetes, в схеме развёртывания предусмотрен и для резервного копирования (кластера пока нет) | Отдельная платформа: планировщик, веб-сервер, база метаданных | Нет отдельного процесса |
| Подходит для одного периодического задания | Да | Избыточен | Да |
| Изоляция от обслуживания абонентов | Отдельный под с окном и ограничением времени | Отдельные воркеры | Нет: индексация конкурирует с ответами за процессор |
| Итог | **Выбран** | Отклонён: платформа ради одного задания | Отклонён: нет изоляции |

Планировщик для профиля абонента (CronJob) выбран по тому же доводу.

### Индексация базы знаний: что реализовано и какой объём

**Реализовано (прототип).** Python-скрипт `scripts/reindex_kb.py` вызывает `app/kb/build.py`: разбор документов Word
библиотекой `python-docx` (`app/kb/documents.py`, фрагмент = раздел с путём заголовков, таблицы разворачиваются в строки) и
пар FAQ из `kb/faq_voronezh.json` → нарезка частей до 300 знаков → проверка на ПДн обезличивателем (Presidio; найденные
ПДн — ошибка сборки) → эмбеддинги `multilingual-e5-small` (sentence-transformers, CPU) → запись в новую коллекцию Qdrant
и атомарное переключение алиаса (blue-green). Запуск — сервис `reindex` в `docker compose`, одноразовый при подъёме стека.
Очереди задач и планировщика в коде нет (Celery в зависимостях проекта отсутствует): «Celery Beat» — название на схеме
развёртывания, а не реализованная технология. На MVP выбран планировщик по расписанию (Kubernetes CronJob), Celery Beat
рассматривался бы, только если понадобится очередь задач; решение не принято.

**Что в базе сейчас.** 27 источников: 20 пар FAQ и 7 документов Word (5 договоров и 2 регламента) → 51 фрагмент → 190
частей (векторов). Документы Word **синтетические** (свойство файла `СИНТЕТИКА`, собраны `scripts/generate_kb_docs.py`):
настоящих регламентов на прототипе нет.

**Какой объём планируется.** MVP — несколько тысяч документов (3 000–5 000), 30 000–100 000 частей (допущение о числе
частей на документ, 10–20, не измерялось). Реального источника документов и их формата (Word, PDF, сканы) владелец не
назвал: это открытый вопрос, от него зависит разбор.

**Хватит ли ночного окна 02:00–05:00 (3 часа).** Расчёт по замеру скорости эмбеддингов на CPU (64 фрагмента,
`scripts/measure_search_models.py`, 24 сентября 2026):

| Модель | Время на часть | 30 000 частей | 100 000 частей |
|---|---:|---:|---:|
| `multilingual-e5-small`, CPU | ≈27 мс | ≈14 мин | ≈46 мин |
| BGE-M3, CPU | ≈320–345 мс | ≈2,7–2,9 ч | ≈8,9–9,6 ч |
| BGE-M3, GPU | не измерялось | — | — |

Вывод: на CPU BGE-M3 в 3-часовое окно не укладывается уже на нижней границе объёма; для полного ночного реиндекса
нужен GPU, но скорость на GPU **не измерялась**, поэтому «окно хватит» — допущение. Замер скорости индексации на GPU и
решение между полным и инкрементальным (только изменённые документы) реиндексом входят в тест моделей эмбеддингов
(ADR-600). Время на разбор документов и проверку ПДн (spaCy) в расчёт не входит и не измерялось.

## Общий принцип выбора на прототипе

Везде, где прототип использует не целевой компонент, а упрощённую замену (Qdrant→память,
Kubernetes→docker compose), причина одна и та же: **объём прототипа не оправдывает
эксплуатационную стоимость целевого инструмента**, а миграция — это смена конфигурации/DSN, не
переписывание бизнес-логики (см. ADR-100, таблицу «Целевые компоненты — упрощённая замена»).
