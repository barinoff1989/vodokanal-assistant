# ADR-300: Выбор моделей — классификация, эмбеддинги, генерация

## Статус

**Accepted** как сводка трёх независимых решений: вывод и таблица альтернатив по каждой роли
(классификация, эмбеддинги, генерация). Замеры, на которые ссылаются таблицы, — в `golden_set/` и в скриптах `scripts/measure_*.py`.

## Контекст

В системе не одна модель, а несколько, с разными ролями и разными требованиями. Их часто путают —
ниже они разведены явно, по функции, а не по этапу.

## 1. Классификация (тема обращения + тип обращения)

**Модель НЕ используется как основной путь.** Классификация — правила (ключевые слова по теме,
частичные совпадения по типу), написанные по реальным примерам обращений. Модель подключается только
как запасной путь, когда правила ничего не нашли — эмбеддинг-классификатор (k-NN, косинусная близость
к размеченным примерам), не генеративная модель.

| Вариант | Выбор | Почему |
|---|---|---|
| Правила (ключевые слова) — основной путь | ✅ Выбрано | Дёшево, прозрачно, воспроизводимо; на реальных данных покрывает большую часть вопросов без модели вообще |
| LLM-классификатор (отдельный вызов генеративной модели на каждый запрос) | Отклонено | Стоимость и задержка на каждый запрос ради задачи, которую решают правила; отдельная модель классификации не заведена нигде в проекте |
| k-NN по эмбеддингам (запасной путь) | ✅ Выбрано, только как fallback | Переиспользует уже загрученный эмбеддер поиска (`multilingual-e5-small`) — вторая копия весов не грузится; порог и разрыв близости подобраны замером на реальных текстах, не назначены |

Запасной классификатор типа обращения (`inquiry_type`) сейчас покрывает **7 из 16 регистрируемых
типов** — только те, что по факту оказались заявками на регистрацию, а не спорами (найдено разбором
реальной выгрузки обращений); расширение на оставшиеся девять — пункт дорожной карты (ADR-600).

Все типы обращений и темы вопросов со словами, проработкой и этапом сведены в таблицу
`AI_docs/Inquiry_Types.xlsx` (правила по ключевым словам находятся в ней и в коде: `app/taxonomy.py`,
`app/agents/triage.py`).

**Какой эмбеддер у запасного классификатора.** Отдельной модели для классификации нет: k-NN использует эмбеддер поиска.
На прототипе это `multilingual-e5-small`. На MVP — тот же эмбеддер, что выберут для поиска (предварительно BGE-M3,
раздел 2); пороги k-NN подбираются заново, потому что они получены замером на e5-small и на другую модель не
переносятся. Окончательная модель выбирается после анализа на живых обращениях (следующий подраздел).

### Решение для MVP: анализ всех типов на живых обращениях

Таблица построена на 136 настоящих обращениях — по девять на тип, у одного типа одно; слова подбирались на
двух третях этих же текстов, поэтому её цифры завышены (на отложенной трети охват 75%, точность 65%).
Метка типа в выгрузке поставлена оператором, знавшим больше, чем написано в тексте. Поэтому **до выбора
моделей для MVP** принято решение провести анализ всех 16 типов и 6 тем на живых обращениях (не менее 100
на тип), **после этого заново собрать таблицу** типов и тем и **заново выбрать модели** — эмбеддингов и запасного
классификатора — для MVP и для тиража. Оценка работы — ADR-600.

## 2. Эмбеддинги (поиск по базе знаний)

| Модель | Контур | Размер весов | Задержка запроса | Причина |
|---|---|---:|---:|---|
| `multilingual-e5-small` | Прототип (выбрано) | 0,46 ГБ | 22 мс | Укладывается в бюджет P99 < 100 мс с девятикратным запасом на CPU без ускорителя (замерено) |
| **BGE-M3** | MVP (целевое) | 4,25 ГБ | 210 мс на CPU | Многоязычная, качественнее на русском по репутации модели — но **не проверена на Golden Set проекта**; на CPU превышает бюджет вдвое, нужен GPU |
| GigaChat Embeddings (внешний API) | Только офлайн-индексация | — | сетевая | Онлайн запрещён явно: эмбеддинг запроса минует PII-обезличиватель (обезличивание закрывает только путь генерации) — отправка сырого текста запроса внешнему сервису обошла бы этот барьер |

**Важное ограничение, а не деталь:** смена модели эмбеддингов — самое дорогое решение для отмены в
проекте. Версия модели обязана храниться в payload каждого вектора, и смена означает полную
переиндексацию базы знаний. Решение принимается один раз на этап, не «по ходу».

**Выбор предварительный.** e5-small выбран по замеру задержки на CPU, BGE-M3 для MVP — по репутации модели;
качество двух моделей на эталонном наборе не сравнивалось. Сравнение моделей проводилось в этом разделе
(задержка и размер — замер `scripts/measure_search_models.py`), замер поиска на прототипе — в
`golden_set/measurement.json` (e5-small: на вопросах корпуса 20 из 20, на живых формулировках 12 из 30 на
первом месте и 23 из 30 в первой тройке). Окончательный выбор для MVP и тиража — после анализа на живых
обращениях (раздел 1, ADR-600). Запасной классификатор использует тот же эмбеддер: при смене модели его пороги
подбираются заново.

### Почему BGE-M3 — кандидат для MVP и что будет сравниваться

BGE-M3 назван целевой моделью MVP по двум причинам. Первая — свойства модели: многоязычная, работает с длинными
текстами, в открытых сравнениях эмбеддинг-моделей показывает высокое качество на русском. Вторая — практическая: она
входит в семейство, для которого уже есть инструментарий (sentence-transformers) и вторая модель тех же авторов —
реранкер `BGE-reranker-v2-m3` (раздел 3), поэтому GPU-сервис эмбеддингов и реранкера можно строить одним образом.
**Проверки на собственных данных не было**: измерены только задержка и размер (`scripts/measure_search_models.py`), а
качество поиска — только у e5-small (`golden_set/measurement.json`). Поэтому выбор — предварительный.

| Кандидат | Что известно | Замер в проекте | Статус |
|---|---|---|---|
| `multilingual-e5-small` | Малая многоязычная модель, работает на CPU | Задержка 22 мс, 0,46 ГБ; качество поиска измерено | **Прототип** |
| `multilingual-e5-base` / `-large` | То же семейство, что у прототипа, больше по размеру | Не измерялись | Кандидат для сравнения |
| **BGE-M3** | Многоязычная, длинные тексты, общий каркас с реранкером | Задержка 210 мс на CPU, 4,25 ГБ; качество не измерено | **Целевой выбор MVP, предварительный** |
| Модели, дообученные на русском (например, `deepvk/USER-bge-m3`, `ai-forever/ru-en-RoSBERTa`) | Ориентированы на русский язык | Не измерялись | Кандидат для сравнения |
| GigaChat Embeddings (внешний API) | Управляемый сервис | — | Только офлайн-индексация: онлайн запрещён (минует обезличивание) |

На MVP после анализа на живых обращениях кандидаты сравниваются на размеченном наборе по качеству поиска и
классификации (ADR-600, блок «Качество поиска и классификации»). Модель выбирается один раз на этап: смена — полная
переиндексация.

## 3. Переранжирование (уточнение топ-3 из топ-20 кандидатов)

| Вариант | Контур | Причина |
|---|---|---|
| Без переранжирования, топ-3 сразу из косинуса | Прототип (по умолчанию) | Кросс-энкодер `BGE-reranker-v2-m3` на CPU — 5,8–25 с на 20 кандидатах при бюджете поиска 100 мс: превышение на два порядка, неработоспособно, не «неоптимально» (замерено дважды) |
| `BGE-reranker-v2-m3` (кросс-энкодер) | Реализовано и проверено, выключено по умолчанию (`app/kb/reranker.py`, `RERANKER_ENABLED`); MVP (целевое, нужен GPU для синхронного пути) | Штатная роль — переранжирование по паре «запрос ↔ документ»; меняет порядок, не оценку — калиброванного порога для оценки кросс-энкодера в проекте нет. Офлайн-применение для отбора дублей в ETL остаётся открытым вопросом (не решён) |

## 4. Генерация ответа абоненту

| Модель | Контур | Хостинг | Причина |
|---|---|---|---|
| **YandexGPT Pro** | Прототип (выбрано) | Управляемый API, РФ | GigaChat технически недоступен на машине прототипа — требует корневых сертификатов НУЦ Минцифры, которых там нет; отключать проверку TLS недопустимо (по каналу идут ПДн) |
| **GigaChat Pro** | MVP (целевое) | Управляемый API, РФ | Ранее выбран как основной по совокупности; YandexGPT остаётся резервом с автопереключением |
| Зарубежные провайдеры (OpenAI, Anthropic и т.п.) | Отклонено на всех этапах | — | 152-ФЗ: ПДн абонента не может покидать периметр РФ без отдельного правового основания, которого у проекта нет |
| **Qwen2.5-32B, INT4** (self-hosted, vLLM, 1× A100 80GB) | Тираж (по триггеру) | Свой GPU-контур | Вступает в строй только по триггеру (рост нагрузки / требование ИБ об отказе от внешних API / деградация SLA провайдера) — не по дате |

**Выбор провайдера для MVP предварительный.** GigaChat Pro как основной и YandexGPT как резерв выбраны по совокупности
свойств; на живых данных оба не сравнивались (GigaChat на машине прототипа недоступен — нужны корневые сертификаты
НУЦ Минцифры). Поэтому на MVP, на ограниченном объёме живых вопросов (порядка 100–200), проверяются **оба**
провайдера — и YandexGPT, и GigaChat: все ответы идут через PII Filter и Guardrails, сравниваются качество (судья и
ручная проверка выборки), время до первого куска и полного ответа (цели — 0,5 с и 3 с), доля блокировок Guardrails,
отказы и сбои, стоимость токенов. **После этого принимается решение о выборе основного и запасного провайдера** и
настраиваются цепочки переключения при сбое. До решения строка «MVP» в таблице выше — рабочее предположение.
Оценка работ — ADR-600.

### Сравнение семейства self-hosted-модели тиража (роль на будущее)

| Семейство | Лицензия | Плюсы | Минусы |
|---|---|---|---|
| **Qwen2.5 (выбрано)** | Apache 2.0 | Сильный русский язык среди открытых моделей; одно семейство 7B (уже используется для тестов) → 32B (тираж) без переделки; зрелая экосистема (vLLM, официальные INT4-веса) | Происхождение весов — репутационный вопрос для регулируемой организации, не обсуждался |
| Llama 3.1/3.3 | Кастомная лицензия Meta, не полностью открытая | Крупное сообщество | Разрыв размеров 8B/70B — нет варианта под одну карту A100, как у Qwen; русский язык слабее сопоставимых по размеру |
| Открытые веса GigaChat | Требует проверки условий | Та же модель, что на MVP через API — единое поведение MVP/тираж | Менее зрелые инструменты на момент выбора, задержка публикации нужного размера |

**Явно не измерено проектом:** выбор Qwen сделан по репутации модели, не по прогону на собственном
Golden Set — как и выбор BGE-M3/e5-small по качеству на русском. Закрывается тем же приёмом, что и
порог поиска на прототипе: прогон эталонного набора через кандидатов.

## 5. Судья качества ответа (LLM-judge, не отвечает абоненту)

| Модель | Контур | Причина |
|---|---|---|
| Qwen2.5-7B-Instruct, локальная (Ollama) | Прототип | Уже используется как тестовая модель — новая не заводится ради судьи; качество оценки на прототипе некритично, важна работоспособность конвейера |
| YandexGPT | MVP | Другой провайдер, чем отвечающий GigaChat Pro — независимость оценки обеспечена конструктивно, не договорённостью |

Правило, общее для всех этапов: **судья не может совпадать с отвечающей моделью.** При совпадении
(например, во время failover генерации) оценка не выполняется, а факт пропуска фиксируется — так
дешевле, чем получить завышенную оценку, неотличимую от честной.
