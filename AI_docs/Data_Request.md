# Запрос данных для разработки AI-помощника абонента

**Назначение документа.** Перечень того, что нужно получить от владельцев систем, чтобы начать
разработку прототипа. Всё остальное генерируется нами синтетически.

**Главное, что стоит понять сразу.** Нам **не нужны реальные данные абонентов**. Нужна **структура**:
перечень полей, их типы и по несколько обезличенных строк-образцов, чтобы синтетический генератор
воспроизводил форму настоящих данных. Прототип работает на локальных базах, наполненных выдуманными
записями; доступа к боевым системам не запрашивается и не предполагается.

**Почему структура важнее содержимого.** Генератор синтетики — первый шаг разработки, от него зависят
поиск, адаптеры и все проверки. Пока структура неизвестна, он строится на гипотезе, и при расхождении
переделывать придётся и генератор, и слепки баз, и часть тестов.

## Часть A — что нужно получить от владельцев систем

Для каждого пункта: **перечень полей** (имя, тип, обязательность, пример значения) и **10–30
обезличенных строк** в CSV с разделителем `;`, кодировка UTF-8.

### A1. Биллинг — лицевые счета (источник 1)

Ожидаемый состав, уточнить по факту:

| Поле | Зачем нужно |
|---|---|
| Номер лицевого счёта | Ключевая сущность: по ней идёт вся привязка |
| ФИО владельца | Проверка обезличивания — это персональные данные |
| Адрес | То же |
| Тип абонента (физическое / юридическое лицо) | Влияет на маршрутизацию обращения |
| Статус договора | Часть ответов зависит от него |
| Текущий баланс, задолженность | Тип обращения «задолженность» |
| Дата открытия счёта | — |

**Формат образца:** `billing_accounts_sample.csv`, 20–30 строк с подменёнными ФИО и адресами.

### A2. Биллинг — начисления (источник 1)

| Поле | Зачем нужно |
|---|---|
| Номер лицевого счёта | Связь с A1 |
| Расчётный период | Тип обращения «перерасчёт», «сверка расчётов» |
| Начислено, оплачено, задолженность | — |
| Вид услуги | Водоснабжение / водоотведение и т. д. |

### A4. Личный кабинет — профиль абонента (источник 4)

| Поле | Зачем нужно |
|---|---|
| Идентификатор пользователя кабинета | Он же станет идентификатором абонента в запросах |
| Связь с лицевым счётом | Один ко многим или один к одному — это влияет на логику |

### A5. База данных обращений (источник 3) — самый важный пункт

Это единственный источник, где есть **реальные формулировки абонентов**. От него зависит и качество
классификации, и эталонный набор для оценки.

| Поле | Зачем нужно |
|---|---|
| Номер обращения | — |
| Дата создания, дата закрытия | — |
| **Тип обращения (код и название так, как ведётся в системе)** | См. вопрос ниже — критично |
| Подтип, если есть | — |
| Статус и перечень возможных статусов | Переходы статусов нужны для сценария Этапа 2 |
| Подразделение-исполнитель | Маршрутизация |
| Канал поступления | Кабинет, колл-центр, очно |
| **Текст обращения** | Главное: по нему настраивается классификация и собирается эталонный набор |
| Результат / резолюция | — |

**Формат образца:** `inquiries_sample.csv`, **50–100 строк**, покрывающих как можно больше типов
обращений. Тексты обезличить: ФИО, адреса, номера счетов и телефоны заменить на выдуманные, сохранив
формулировки самих обращений — именно они представляют ценность.

> **Ключевой вопрос, ответ на который влияет на объём работ.** Справочник типов обращений в вашей

> тарифа, прочее), или там своя номенклатура? Если своя — нужен полный справочник кодов и названий:
> понадобится таблица соответствия, и это отдельная работа, которая сейчас не запланирована.

| Статус | — |

### A7. Реестр договоров (источник 8)

Нужен **перечень файлов**, не сами файлы целиком:

- имя файла и соглашение об именовании;

- версия и дата вступления в силу, если ведутся;

### A8. База знаний — образцы документов (источники 2, 5, 12)

**По 2–3 файла каждого вида, в исходном формате (`.docx`), со всей структурой заголовков:**

- регламент (например, порядок перерасчёта);
- инструкция по работе с биллингом;
- инструкция по общению с абонентом;
- типовая форма заявления;
- устав или оферта — один документ для примера.

Содержимое может быть любым реальным нечувствительным — это внутренние регламенты, не персональные
данные. Важна именно **структура документа**: как оформлены заголовки, таблицы, приложения. От неё
напрямую зависит нарезка текста на фрагменты, а от неё — качество поиска.

Дополнительно: **общее количество документов** в хранилище и их суммарный объём — нужны для расчёта
размера индекса и длительности переиндексации.

Ссылка на раздел сайта либо выгрузка вопросов и ответов. Данные публичные, ограничений нет.

Не данные, но нужно на шаге адаптеров:

| Система | Что нужно |

| Микросервис обращений | Описание API регистрации обращения: метод, обязательные поля, формат ответа, правила формирования номера обращения |

## Часть C — что не запрашивается принципиально

| Не запрашиваем | Причина |
|---|---|
| Доступ к боевым системам, учётные записи, подключение к сети | Системы внутри закрытого контура. На этом проекте доступа не будет ни на разработке, ни на демонстрации — это зафиксированное ограничение, а не недоработка |
| Реальные записи абонентов в любом объёме | Нужна структура, а не содержимое. Реальные данные создали бы обязанность обеспечивать их защиту на машине разработчика |
| **Расшифровки звонков колл-центра** | Голос относится к биометрическим персональным данным и требует письменного согласия абонента. Согласия нет, поэтому источник не используется вовсе — ни в реальном, ни в синтетическом виде, чтобы в коде не появился готовый путь обработки |

## Что произойдёт, если данные не придут

Разработка не останавливается: шаги подготовки локальной модели, справочника типов, конечного автомата
и слоя защиты персональных данных от этих данных не зависят и выполняются первыми. Но генератор
синтетики строится на гипотезе о структуре, и при последующем расхождении переделывать придётся сам
генератор, слепки баз и часть проверок — оценка этого шага вырастет примерно втрое.

Приоритет запроса, если получить всё сразу не выйдет:

1. **A5** — обращения с текстами и справочник типов: без них не построить ни классификацию, ни эталонный набор;
2. **A8** — образцы документов базы знаний: от их структуры зависит качество поиска;
3. **A1–A3** — структура Биллинга;
4. **A10** — описания интерфейсов, нужны позже, к шагу адаптеров;
5. остальное.
