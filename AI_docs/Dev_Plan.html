План разработки

Двенадцать шагов от пустого репозитория до работающего MVP: что пишется, какое ПО ставится, какие модели и доступы нужны, какими стартовыми данными наполняется система и как проверяется закрытие каждого шага. В конце — структура проекта и план запуска.

0. Как устроен план

Фаза 6 плана сборки. Диаграммы (фаза 1) и решения ADR (фаза 2) уже зафиксированы — код пишется под них, а не параллельно с ними.

ПринципПочему именно так
Порядок шагов — от независимого к зависимомуТаксономия и схемы данных нужны всем; адаптеры Этапа 2 — никому. Обратный порядок заставил бы переписывать основание
Шаг не закрыт, пока не прошла его проверкаПрототип уже один раз потребовал полного переписывания, потому что решения менялись после написания кода
Всё на синтетикеБиллинг, ЛК, БД обращений, БД ЛКК и файловое хранилище — внутри закрытой сети. Ни на разработке, ни на демонстрации доступа к ним не будет
Генерация ответов — внешняя модельПо ADR-002 на MVP генерирует управляемый API на территории РФ. Локальная модель нужна только для офлайн-проверок без трат на платный API
Ничего «по аналогии»Версии, размеры и сигнатуры, не подтверждённые документом проекта, помечены как ДОПУЩЕНИЕ и подлежат сверке
Два блокера, которые нужно снять до начала кодирования. Первый: CSV-примеры структуры реальных систем ещё не получены — без них шаг 0 строится на гипотезе о схеме, и при получении примеров генератор придётся переделывать. Второй: спецификация API не доведена — семь остаточных проблем раздела 7.6 контекста (в том числе servers: localhost как production и отсутствие схемы SSE-события error) делают шаг 8 работой по неточному контракту. Оба не останавливают шаги 0–7, но должны быть закрыты до шагов 8 и 9.

Зарубежные провайдеры исключены не по цене, а по допустимости. Абонент — физическое лицо, и передача его персональных данных за периметр РФ без правового основания нарушает 152-ФЗ. Поэтому в конфигурации шлюза не должно появиться ни одного зарубежного провайдера общего назначения — даже как временного варианта «пока не дали доступ к GigaChat». Если доступ задерживается, работа идёт на локальной тестовой модели, а не на зарубежном API.

Почему судья и отвечающая модель — разные. Модель, оценивающая собственный ответ, систематически завышает оценку. Правило «судья из другого пула» прослеживается во всех трёх состояниях: на MVP отвечает GigaChat Pro, судит YandexGPT; при переключении генерации на YandexGPT оценка на эту ночь пропускается, а факт пропуска фиксируется — потерять один прогон дешевле, чем получить завышенную оценку, неотличимую от честной; при полном переходе на собственные модели судьёй становится второй локальный экземпляр другой модели.

Требования к генератору, которые нельзя пропустить. Первое: покрытие всех десяти типов таксономии в достаточном объёме — иначе стратифицированная подвыборка для проверки на каждом изменении не наберётся, и просадка по отдельному типу останется незамеченной. Второе: выход генератора обязан пройти через тот же фильтр персональных данных, что и рабочий трафик — не потому, что в синтетике есть настоящие данные, а потому что генератор может случайно воспроизвести валидный СНИЛС или существующий номер телефона. Третье: фиксированное зерно случайности, иначе данные меняются между прогонами и метрики качества становятся несравнимыми.

2 — конечный автомат готово Таблица переходов, правило 4.7 закреплено запретом: запись возможна ровно из состояния ожидания подтверждения
3 — слой защиты готово Обезличивание с контрольными суммами и подсказками, охранители на потоке. Четыре сценария безопасности плана тестирования проходят
4 — шлюз к модели готово Лимиты, порядок quota-first, ошибки RFC 7807. Живой сквозной вызов на настоящем YandexGPT проходит
5–11 — поиск, агенты, API, стенд, наблюдаемость не начаты Шаг 5 упирается в тот же блокер, что и шаг 0: индексировать нечего, пока нет образцов документов базы знаний
Порядок нарушен осознанно. Шаги 1–4 сделаны раньше шага 0, хотя план ставил его первым. Причина — внешняя: примеры структуры систем не получены, и генератор синтетики строился бы на гипотезе. Шаги 1–4 от этих данных не зависят, поэтому работа шла по ним; шаг 5 первым упрётся в отсутствие базы знаний.

Каждый шаг закрывается своей проверкой. Переход к следующему без закрытия предыдущего запрещён: именно так прототип однажды пришлось переписывать целиком.

  • Попытка подтвердить черновик, созданный другим абонентом, отклоняется — сценарии S1 и S2 воспроизводимы вручную на демонстрации
  • Готовый документ появляется в ленте вложением или ссылкой, отдельно от черновика в диалоге подтверждения
  • В служебной панели видны отчёт о персональных данных без самих значений и сквозной идентификатор трассировки
Готово, когда: все девять пунктов демонстрационного сценария раздела 8 проходятся на этой странице без обращения к консоли.

Один сценарий этого шага не имеет ожидаемого результата. Что происходит, если обращение зарегистрировано, а аварийная заявка не ушла — компенсация при частичном отказе двух путей записи не спроектирована. Пока решения нет, сценарий с аварийным обращением не может быть покрыт тестом. Решить до начала шага.

7. План запуска

Порядок команд от чистой машины до отвечающего сервиса. Каждая строка — цель в Makefile, чтобы запуск не зависел от того, что человек помнит наизусть.

7.1. Первый запуск

git clone <репозиторий> && cd vodokanal-assistant uv sync установка зависимостей из блокировки версий cp .env.example .env затем заполнить учётные данные провайдера make infra поднять Qdrant, Postgres, Redis, MinIO make seed сгенерировать синтетику и наполнить хранилища make models скачать веса эмбеддингов, реранкера, локальной модели make index проиндексировать синтетическую базу знаний make run запустить сервис make smoke проверить, что всё поднялось

7.3. Режимы работы

РежимПровайдер генерацииКогда используется
Офлайнлокальная модельРазработка, отладка промптов, нагрузочные прогоны, проверки Security Layer — без расхода платных токенов
Боевойвнешний управляемый APIДемонстрация, калибровка задержек, ночная оценка качества
ПереключениеПравка одной строки конфигурации шлюза. Код не меняется — это и есть проверка того, что абстракция шлюза работает так, как обещано в решении о хостинге
Что в запуске проверяет архитектурное решение, а не работоспособность. Возможность переключить провайдера строкой конфигурации — не удобство разработчика, а подтверждение центрального тезиса решения о хостинге модели: переход на собственную модель должен быть правкой конфигурации, а не переработкой системы. Если для переключения потребуется трогать код, решение не выполнено, и это нужно фиксировать как расхождение, а не обходить.
