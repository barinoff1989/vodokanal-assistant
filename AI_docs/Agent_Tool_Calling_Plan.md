# План: агент с выбором инструмента на прототипе (LangGraph, запись)

## Статус

**Отложено.** Зафиксировано по итогам обсуждения — реализация не начата, приоритет и срок начала не
назначены. Документ существует, чтобы решение и оценка не потерялись до момента, когда работа
возобновится. Смежные записи: [ADR-010](ADR/ADR-010-fsm-implementation.md) (триггер 1 — «агенту нужно
самому выбирать инструмент»), [ADR-007](ADR/ADR-007-mvp-model-composition.md) (открытый вопрос «модель
агента Этапа 2»), `TODO.md` пункт 79.

## Что строим

Агент, который сам решает, какой write-инструмент вызвать (function-calling / tool-calling), вместо
жёсткой последовательности вызовов, которая сейчас зашита в коде ([`app/backend/registration.py:158-235`](app/backend/registration.py:158)).
Это функциональный Этап 2 (операции записи), не Этап 1 — **чтение остаётся без изменений**: пять прямых
ответчиков и RAG-генерация ничего не выбирают, работают как сейчас.

Реализация — на [LangGraph](ADR/ADR-010-fsm-implementation.md) (`StateGraph` вместо таблицы переходов
`app/fsm.py`), `interrupt_before` как **единственный** механизм подтверждения абонента (правило 4.7) —
заменяет текущую проверку `ALLOWED_FROM_AWAITING_CONFIRMATION`, не дополняет её (жёсткое условие
ADR-010: два параллельных механизма подтверждения не заводятся ни при каких условиях).

## Набор инструментов — три, не четыре

[ADR-007](ADR/ADR-007-mvp-model-composition.md) называет четыре кандидата (`register_inquiry`,
`submit_meter_reading`, `generate_document`, `create_incident`). На прототипе реально нужны три —
`create_incident` (запись в Диспетчерскую) из объёма исключена: авария не требует записи в этом плане.

| Инструмент | Состояние на прототипе |
|---|---|
| `register_inquiry` | Есть — `Registrar.register()`, пишет в локальную таблицу Postgres (`inquiries_db`), не в настоящий внешний сервис обращений |
| `generate_document` | Есть — `TemplateResponder`, HTML-лист на печать, не настоящий PDF/S3 |
| `submit_meter_reading` | **Нужно построить** — см. ниже. Не блокер, но три отдельных шага, не один `INSERT` |
| ~~`create_incident`~~ | Исключён из объёма — запись в Диспетчерскую не нужна для этого плана |

### Почему `submit_meter_reading` — не «уже почти готово»

База под него зарезервирована (`billing_db: str = "billing_stub"`, [`app/config.py:388`](app/config.py:388);
контейнер `vk-postgres` её создаёт), но:

- В `docker/postgres/init/` есть схемы `inquiries`, `usage_events`, `quality_reports`,
  `quality_assessments` — схемы биллинга **нет**. База создана пустой.
- Реальный источник данных биллинга на прототипе — CSV-файлы, не Postgres:
  [`app/billing/source.py:179`](app/billing/source.py:179), `billing_data_path = "data_example"`, читаются
  в память при старте, только на чтение (`BillingSource.meters()` и т.п.).

Синтетические данные достаточны как источник правды (решение принято в диалоге — реальный Биллинг на
прототипе недоступен и не нужен для проверки самого агента), но нужны три подготовительных шага, а не
один:

1. Спроектировать схему `billing_stub` (счётчики, показания, начисления).
2. Перенести туда те же синтетические данные, что сейчас в CSV — иначе после записи чтение
   (`BillingSource.meters()`) продолжит показывать старое значение из файла, и демонстрация станет
   несвязной.
3. Переключить `BillingSource` читать из Postgres вместо CSV (или держать запись и чтение по одному
   источнику правды).

**Оценка: 2–3 дня**, отдельно от работы над самим агентом.

## Что не измерено — и должно быть измерено первым

[ADR-007](ADR/ADR-007-mvp-model-composition.md#открытый-вопрос--модель-агента-этапа-2) держит статус
Proposed именно по этой причине: надёжность function-calling у GigaChat Pro и YandexGPT на write-
инструментах проекта **не измерена**. Дословно:

> Открытые модели класса 7B часто ненадёжны в function-calling; 14–32B приемлемы.

Единственная локальная модель на этой машине — Qwen2.5-7B (Ollama, CPU) — ровно класс, названный
рискованным. Внешний провайдер (YandexGPT, уже используется на прототипе для генерации) не зависит от
локального железа, но его function-calling тоже не проверялся — открытый вопрос, не факт ни в одну, ни в
другую сторону.

## Поэтапный план и оценка

### Стадия 0 — обязательный замер, идёт первым

Оценить надёжность function-calling YandexGPT на трёх реальных сценариях записи (`register_inquiry`,
`generate_document`, `submit_meter_reading`) плюс контрольный сценарий без записи (агент не должен
вызывать инструмент, когда вопрос не требует действия). Показатели — по методологии, уже применённой в
проекте (ADR-014, ADR-018): доля кривого JSON, доля неверного выбора инструмента при нескольких похожих.

**Оценка: 3–5 дней.** Решение по итогам: если результат плохой (частый кривой JSON, путаница между
похожими инструментами) — стадии 1–2 требуют либо строгого JSON-режима, либо второго прохода-валидатора
поверх модели, и общая оценка ниже вырастает.

### Стадия 1 — граф и инструменты (после успешной стадии 0)

| Работа | Оценка |
|---|---|
| Схема `billing_stub` + перенос данных + переключение `BillingSource` | 2–3 дня |
| JSON-схемы трёх инструментов + валидация аргументов против `Slots`/таксономии | 3–4 дня |
| `StateGraph` с роутингом по выбору модели вместо таблицы `app/fsm.py` | 3–4 дня |
| `interrupt_before` как единственный механизм подтверждения (замена, не дополнение) | 2–3 дня |

### Стадия 2 — обязательна из-за новой поверхности атаки

Модель, свободно выбирающая write-инструмент, — новая поверхность атаки, поэтому то, что раньше было
опциональным улучшением, здесь становится условием.

| Работа | Оценка |
|---|---|
| Привязка `subscriber_id` к сессии на каждом write-шаге (сейчас спроектирована, не реализована — открытый P1, [ADR-019](Сдача/ADR-019-security-by-stage.md)) | 3–5 дней |
| Проверка на подмену выбора инструмента (STRIDE, тот же приём, что уже применялся в проекте) | 3–5 дней |
| Golden Set для оценки «выбрала ли модель правильный инструмент» — размечать с нуля, набора нет | 3–5 дней |

### Итог

**3–4 недели** чистой разработки после успешной стадии 0. **5–6 недель**, если function-calling окажется
ненадёжным и потребует обходных механизмов.

## Работоспособность на локальной машине

- **Через YandexGPT** (внешний, уже используется) — локальные ресурсы почти не растут: сам `LangGraph`
  лёгкий (~1–2 МБ пакетов без транзитивных зависимостей, проверено `pip download --no-deps`, ни одной
  ML-библиотеки среди зависимостей). Риск — не ресурсный, а качество function-calling, которое и
  закрывает стадия 0.
- **Через локальную Qwen2.5-7B** — не рекомендуется для проверки: класс модели сам ADR-007 называет
  ненадёжным для этой задачи; CPU-инференс уже проваливал бюджеты на заметно более лёгкой задаче
  (реранкинг — превышение в 2–58×, ADR-014); reason-act цикл агента — несколько последовательных
  вызовов модели на один ответ абонента вместо одного, то есть кратно дольше ожидание.

## С чего начинать, когда работа возобновится

Стадия 0 — замер function-calling YandexGPT на трёх сценариях записи. Самый дешёвый способ узнать, стоит
ли продолжать, и единственный пункт плана, не зависящий от решения по `billing_stub`.
