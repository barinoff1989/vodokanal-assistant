01 Definition of Ready

Обязательный минимум перед тратой бюджета (методика CTO Challenge). Два из четырёх пунктов — стоп-факторы.

Пункт DoRСтатусКомментарий
Проблема понятна (бизнес-цели) ✓ Есть §1–2 контекста: цели и боли абонента сформулированы, роль AI-помощника внятная.
Решение визуализировано (C4 Context + Container) ⚠ Частично Container (L2) и один Component (L3 ETL) есть. Файла L1 Context среди переданных артефактов нет — проверить, что он существует отдельно.

Риски названы (таблица + Mitigation Plan) ✓ Есть §13: 10 рисков с митигацией. Не хватает risk-владельцев/сроков и пунктов Spoofing/IDOR (см. §05).

02 Верификация vs Валидация

Инженерный вопрос «соблюдены ли NFR?» и бизнесовый «решает ли это задачу?» — оба пока без расчётной опоры.

Нет Sizing Calculator под заявленные NFRDoD §18

TTFT < 500 мс, P99 поиска < 100 мс, Recall@3 > 90% — это цели, но нет расчёта по Little's Law (L = λ × W) под целевой RPS, нет разбивки латентности LLM-генерации (T_total = T_prefill + N_tokens × T_per_token) для выбранного GPU/модели (Qwen2.5-32B/72B или GigaChat). Без этого сами цифры NFR — декларация, а не архитектурное решение.

Валидация бизнес-эффекта не квантифицирована§2

Цели («сократить время поиска ответа», «снизить повторные обращения») сформулированы качественно, но не привязаны к числам — нет базовой линии и целевого % снижения, на которые можно сослаться при защите бюджета.

03 Находки по диаграмме C4 L2 (контейнеры)

C4_L2_mul_ag_1.html — «целевой ландшафт + Inference-сервисы».

Незафиксированная связь Backend → Billing Adapteredge e_backend_billingadapter

У ребра «Данные абонента (read)» задан source="backend", но атрибут target отсутствует — в draw.io это висящая стрелка, геометрически расположенная у Billing Adapter, но не привязанная к нему как к узлу. На реальной защите это ровно тот случай, когда просят «покажи пальцем на диаграмме, где именно срабатывает связь» — и её там формально нет.

Document Generator — тупиковый узелedge e_orch_docgen

Есть ребро Orchestrator → DocGen («Заполнение/рендер документа»), но нет исходящего ребра от DocGen к Widget/Backend/абоненту. Не показано, как готовый документ доходит до абонента.

Один диапазон нумерации на два разных потокаedges 1–7c

Прямой RAG-путь Этапа 1 (Backend→VectorDB=«1», Backend→LLMGateway=«2», LLMGateway→Provider=«3») и агентный путь Этапа 2 (Backend→Orchestrator=«4», Orchestrator→Backend=«5», …=«7c») пронумерованы одной сквозной серией на одной статичной диаграмме. Читается как единый 7-шаговый вызов, хотя по правилам проекта (§16–17) Этап 2 не должен внедряться до готовности Этапа 1 — это два разных, стадийно разнесённых потока. Стоит разнести на два вида (L2 Этап 1 / L2 Этап 2) либо использовать раздельные серии нумерации.

Session State Store не виден для Этапа 1container sessionstore

Хранилище состояния FSM/аудит-лога связано только с Agent Orchestrator. Но session_id обязателен в metadata API-контракта (§7.1) уже в чистом RAG-режиме Этапа 1, где Orchestrator не участвует. Неясно, где в Этапе 1 живёт сессия/аудит/квоты — нужно либо провести ребро Backend↔SessionStore, либо явно описать отдельный, более лёгкий механизм для Этапа 1.

Нет визуального разделения «сейчас» / «целевое»whole diagram

Кроме пометки «[НОВЫЙ]» на Reranker Inference, контейнеры Этапа 1 и Этапа 2 не различаются ни цветом, ни swim-лейном — при первом взгляде не видно, что часть контейнеров ещё не построена.

04 Находки по диаграмме C4 L3 (ETL Worker)

C4_L3_ETL_RAG_1.html — «финальная, целевая модель».

Конкуренция за GPU между batch-ETL и онлайн-retrievalEmbedding/Reranker Inference

Одни и те же сервисы Embedding Inference [GPU] и Reranker Inference [GPU] обслуживают и офлайн ETL-пайплайн (шаги 5, 7 на L3), и онлайн-путь Backend-ретривала (эмбеддинг запроса, реранжинг top_k=20→top_n=3 на L2). Ни в одном артефакте нет изоляции GPU, приоритетных очередей или admission control между batch- и интерактивным трафиком. Ночной полный реиндекс базы знаний может насытить GPU и сорвать целевые P99<100мс / TTFT<500мс именно в момент, когда абоненты продолжают пользоваться ботом. Это ровно тот тип вопроса («что будет с латентностью при батч-джобе»), который на защите задают первым.

Диаграмма опережает контекст-документ§5.5, §11–12 vs L3

Пайплайн на диаграмме — Ingest Pipeline (ридер + 3-уровневый классификатор) → Text Splitter → Quality & Dedup Filter (MinHash/SimHash) → офлайн Reranker Client → Embedding Client → Vector DB Client (tombstones + blue-green alias-реиндекс) — заметно богаче, чем описание в контексте (Document Reader → Text Splitter → Metadata Enricher → Embedding Client → Vector DB Client, без dedup, без офлайн-реранкера, без alias-стратегии реиндекса). Диаграмма помечена как целевая — вероятно, она новее, но markdown-источник истины не обновлён. Это тот же класс риска, что и «если не записано — значит, не было».

Кросс-энкодер для дедупликации — нетиповое применениеreranker node, шаг 4–5

BGE-reranker-v2-m3 обучен на паре запрос↔документ, а используется для отбора «представительного чанка» из кластера дублей (скоринг «чанк ↔ заголовок раздела»). Это добавляет второй GPU-инференс на каждый прогон ETL для задачи, которую вероятно закрыл бы уже посчитанный quality_score или центроидное сходство — дешевле и без второй GPU-зависимости. Стоит зафиксировать это решение как ADR с explicit trade-off (точность vs. стоимость/латентность индексации).

Хорошие практики, не описанные в контекстеSync State, alias-реиндекс

Курсоры/чек-суммы источников и blue-green переключение alias при реиндексе — зрелые решения, отсутствующие в context_3.md. Стоит перенести их в письменную спецификацию, а не оставлять только на диаграмме.

05 STRIDE: то, чего не хватает в реестре рисков

PII/Tampering закрыт LLM Gateway хорошо. Spoofing и IDOR по цепочке Backend → Billing Adapter / Application Router — нет.

УгрозаВопрос челленджераТекущее покрытие
Spoofing Доверяет ли Backend/Orchestrator полю subscriber_id из сессии ЛК без повторной проверки на каждом write-шаге? Не описано
IDOR Может ли Billing Adapter / Application Router выполнить операцию над данными не того абонента, если subscriber_id подменён на уровне запроса? Не описано
Tampering (PII) Уходят ли сырые ПДн в LLM Provider? Закрыто — LLM Gateway, §4.2
DoS Что произойдёт при резком всплеске запросов от одного абонента? Quota Manager (slowapi + Redis), 429 + Retry-After

Что уже сделано правильно

  • Stage-gating зафиксирован явно: Этап 2 не стартует до метрик Этапа 1 (§16–17) — редкая для первой итерации дисциплина.
  • HITL + идемпотентность + аудит-лог требуются consistently на всех write-путях (Billing, Application Router, документы).
  • PII-барьер архитектурно закреплён на границе LLM Gateway, а не «когда-нибудь потом».
  • Известные дефекты прототипа (таксономия, regex, синтаксис) уже самостоятельно найдены и приоритизированы в §11–12.
  • RFC 7807, URI-версионирование и минимальный API-контракт — хорошая гигиена уровня контракта с первой ревизии.

06 Приоритизированный план действий

  • P0 Смета CAPEX/OPEXДаже грубый Sizing Calculator (K8s, GPU-инференс, managed DB, лицензии/токены LLM) — без него бюджет не защищается по определению DoR.
  • P0 Расчёт производительности под целевые NFRLittle's Law + разбивка LLM-латентности для выбранного железа/модели — обосновать TTFT<500мс и P99<100мс цифрами, не декларацией.
  • P0 Исправить связи на L2Привязать ребро Backend→Billing Adapter к целевому узлу; продлить путь DocGen → доставка абоненту.
  • P0 План изоляции GPU между ETL и онлайн-retrievalПриоритетные очереди, отдельный пул или окно обслуживания для полного реиндекса — иначе ночной ETL рискует SLA живых пользователей.
  • P1 Оформить 3–5 ADRПлатформа оркестрации, триггер миграции transitions→LangGraph, триггер self-host LLM, trade-off офлайн-реранкера для дедупликации.
  • P1 Sequence-диаграмма для двух критических сценариевStage-1 streaming RAG и Stage-2 confirm/write-флоу — отдельные Mermaid/PlantUML артефакты, не только текст в §6.
  • P1 Синхронизировать §5.5/§11 с L3-диаграммойДобавить Dedup Filter, офлайн Reranker, Sync State, blue-green реиндекс в письменную спецификацию.
  • P1 Добавить Spoofing/IDOR в реестр рисковЯвно описать проверку subscriber_id на каждом write-шаге Billing Adapter / Application Router.
  • P1 Разнести нумерацию/виды L2-диаграммыОтдельные виды или серии нумерации для потока Этапа 1 и целевого потока Этапа 2.
  • P2 Подтвердить наличие L1 Context-диаграммыКак отдельный файл рядом с L2/L3, а не только упоминание в тексте.
  • P2 Визуально пометить контейнеры по этапамЦвет/swim-лейн «Этап 1» vs «Этап 2 (целевое)» на L2, а не только тег «[НОВЫЙ]».
⤷ Дополнение · Trade-off Analysis

07 Дилемма: SaaS (GPT-класс) vs Self-hosted (Llama 3)

По методике слайда «Trade-offs» из урока 9 (LLM Model Strategy) и статье a16z «Navigating the High Cost of AI Compute». Разобрано по пяти критериям и по этапам дорожной карты проекта (§17 контекста).

Важная поправка к формулировке дилеммы152-ФЗ

GPT-5 как SaaS-вариант в этом проекте — вероятно, юридически недоступен: субъект — абонент российского водоканала, ПДн (ФИО, лицевой счёт, адрес) при обращении к OpenAI (США) означают трансграничную передачу ПДн без надёжной правовой основы по 152-ФЗ. Это ровно причина, по которой context.md §5.1/§8.1 уже выбрал в качестве SaaS-провайдера GigaChat Pro / YandexGPT, а не GPT-4/5. Ниже сравнение сохраняет общую логику «SaaS vs Self-hosted» из задания, но как SaaS-кандидат рассматривается класс «управляемый API отечественного провайдера», а не конкретно GPT-5.

КритерийSaaS (GigaChat Pro / YandexGPT-класс)Self-hosted (Qwen2.5-32B/72B, резерв Llama 3.1)
Стоимость OPEX = цена за токен, без CAPEX. a16z: розничная цена SaaS обычно включает наценку над «сырой» стоимостью компьютинга (для GPT-3-класса инференса — сырая цена ≈$0.0002–0.0014 за 1000 токенов против розничных ≈$0.002) — часть этой наценки при самохостинге теоретически можно забрать себе, но взамен появляется фиксированный CAPEX на GPU и его простой в непиковые часы. Компании до $50M ARR по данным a16z успешно оставались на управляемых API, не переходя на self-host. CAPEX на GPU-сервер + постоянный OPEX инфраструктуры вне зависимости от факта использования. Окупается только при стабильно высоком объёме — в этом проекте порог уже зафиксирован в §8.1: >50M токенов/мес. a16z предупреждает: цена A100 on-demand различается почти в 4× между провайдерами — считать CAPEX по одной цифре из прайс-листа нельзя.
Приватность данных Данные абонента покидают периметр компании (идут во внешний API). Требует PII-фильтрации до отправки (LLM Gateway, правило §4.2) — это единственный компенсирующий контроль. Данные не покидают периметр — снимает необходимость доверять внешнему провайдеру и упрощает аргументацию перед ИБ/152-ФЗ. Именно этот критерий в §8.1 назван первым триггером перехода на self-host («запрет ИБ на внешние API»).
Качество ответов Топовые SaaS-модели обычно сильнее на сложных рассуждениях и меньше требуют prompt-инженерии — быстрее выйти на приемлемый Recall@3>90% (DoD §18) без A/B-цикла. Open-weight модели среднего размера (32–72B) обычно уступают топовым SaaS в сложных кейсах (лекция: «Llama-70b уступает GPT-4 в сложных рассуждениях»). Для узкой предметной области (регламенты водоканала) разрыв можно частично закрыть RAG + Golden Set +, при необходимости, LoRA-дообучением (§8.1) — но это дополнительный этап работы, а не выигрыш «из коробки».
Latency Сетевой хоп до внешнего API добавляет задержку и зависит от провайдера; TTFT<500мс (DoD) достижим, но не полностью в руках команды — при инцидентах у провайдера единственная защита — fallback/circuit breaker в LLM Gateway. При грамотном sizing латентность полностью контролируется командой — единственный способ добиться триггера «latency<200мс» из §8.1. Но это требует расчёта по Little's Law и LLM-latency формуле (T_total=T_prefill+N_tokens×T_per_token) под конкретную GPU — без него можно получить обратный эффект (см. §02 находки этого отчёта).
Сложность поддержки Низкая: нет GPU-парка, нет ответственности за аптайм модели, апгрейды версий — на стороне провайдера. Основная нагрузка — на LLM Gateway (квоты, PII, ретраи). Высокая: нужен GPU node affinity, мониторинг модели, план обновления весов, бэкапы/DR для инференс-сервиса, обученная DevOps-экспертиза. a16z: софт-оптимизации (квантование, pruning, mixed precision) дают до 10× выигрыша в рантайме, но это отдельная инженерная работа, которую придётся делать самим или заказывать.

Триггеры перехода уже зафиксированы в context.md §8.1 — таблица привязывает их к конкретным этапам вместо общего «когда-нибудь».

ADR-002
Стратегия хостинга LLM: поэтапный переход SaaS → Self-hosted
PROPOSED (DRAFT)

Context

Объём обращений на старте неизвестен, CAPEX на GPU не заложен в смету (её пока нет вовсе, см. §01), а требования ИБ/152-ФЗ ограничивают выбор SaaS-провайдера рынком РФ.

Alternatives Considered

  • Только SaaS весь проект — просто, но не закрывает будущие триггеры (объём, latency, дообучение).
  • Только self-hosted с Этапа 1 — CAPEX и DevOps-нагрузка до подтверждения спроса, риск сорвать 53-дневный/аналогичный дедлайн MVP.
  • Гибрид через LLM Gateway с миграцией по триггерам §8.1 — выбрано.
DecisionLLM Gateway (LiteLLM) — единая точка абстракции с Этапа 1. По умолчанию — SaaS (GigaChat Pro/YandexGPT). Переход на self-hosted (Qwen2.5-32B/72B) — поэтапно, по мере фактического срабатывания триггеров §8.1, без изменения кода приложений (только config.yaml).

Consequences

  • Нулевой CAPEX GPU на старте, быстрый time-to-market Этапа 1.
  • A/B SaaS vs self-hosted на Golden Set — без переписывания Backend/Orchestrator.
  • Если триггер (например, запрет ИБ) сработает резко, а не постепенно — нужен «разогретый» staging self-hosted контур заранее, иначе миграция сорвёт SLA.
  • GPU-инференс (embedding/reranker) уже self-hosted с Этапа 1 (см. §04) — часть DevOps-сложности self-host уже присутствует независимо от выбора LLM-провайдера.
